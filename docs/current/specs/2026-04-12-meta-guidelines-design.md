# 設計仕様書: AI駆動開発ガイドライン

- **Status**: Accepted
- **Date**: 2026-04-12

## 概要

システム開発全般に適用できる AI駆動開発ガイドライン（普遍的原則）を策定し、それを GitHub Copilot の `copilot-instructions.md` および Skills として実践するためのプロジェクト。

対象とする「システム」には、純粋なプログラムコードで動くものだけでなく、AIエージェントによる情報収集・分析・意思決定を含むワークフロー型システムも含む。

### 対象者

自分自身が AIエージェントと協働開発する際の個人的な指針として使用する。

### 方針

- 原則はツール非依存の普遍的なもの。実践は GitHub Copilot 中心
- 小さく始めて、実践を通じて育てる（リビングドキュメント）
- 拡張性・保守性を重視した構造設計

## アーキテクチャ: レイヤード方式

原則（なぜ）・実行指示（どう振る舞うか）・スキル（どうやるか）を3層に分離する。

```
principles.md（なぜ・何を）
    ↓ 人間が翻訳・反映
copilot-instructions.md（どう振る舞うか）
    ↓ 具体的な手順はskillsに委譲
skills/（どうやるか）
```

### 各レイヤーの役割

| レイヤー | ファイル | 主な読者 | 役割 |
|----------|----------|----------|------|
| Layer 1 | `docs/principles.md` | 人間 | ツール非依存の AI駆動開発ガイドライン原則集。判断の拠り所、「なぜ」の記録 |
| Layer 2 | `.github/copilot-instructions.md` | AIエージェント | Layer 1 の原則を Copilot 向けに翻訳した行動指示 |
| Layer 3 | `skills/` | AIエージェント | 特定のワークフローを実装するスキル群 |

### レイヤー間の関係

- AIエージェントが自動的に読むのは Layer 2（copilot-instructions.md）と Layer 3（skills）
- Layer 1（principles.md）は主に人間のためのドキュメント。必要に応じてエージェントに参照させることも可能
- 各レイヤーは独立して編集・拡張可能

## Layer 1: AI駆動開発ガイドライン原則集

### 前文

これらの原則は一律に適用する絶対ルールではない。タスクのリスク・複雑さ・可逆性に応じて、適用の強度を調整する。低リスクで可逆なタスクには高い自律性を与え、高リスクで不可逆なタスクには厳密に原則を適用する。

### 原則一覧

#### 原則1: 意思決定の追跡可能性（Traceability of Decisions）

> 「なぜそうしたか」を記録する。変更や改善の判断には過去の文脈が必要になる。

- 設計判断とその理由を記録に残す
- 「何を作ったか」だけでなく「なぜその方法を選んだか」を残す
- **適用**: 常に適用。記録の深さはタスクの重要度に応じて自然に変わる（コミットメッセージから設計文書まで）

#### 原則2: 関心の分離（Separation of Concerns）

> AIエージェントを「万能な1人」ではなく「責務を持った専門家」として設計する。

- 1つの指示・スキルに複数の責務を混ぜない
- エージェント間・エージェントとプログラム間のインターフェースは構造化データで定義する
- **適用**: 常に適用。タスクの規模によらず、責務の分離は設計の基本原則

#### 原則3: コンテキストの明示的管理（Explicit Context Management）

> エージェントが「何を知っているか」を前提に頼らず、明示的に制御する。

- 各タスクの開始時に必要な前提情報を注入する
- エージェントが取得した情報の信頼性を検証する手段を持つ
- **適用**: 常に適用。注入するコンテキストの量はタスクの複雑さに応じて自然に変わる

#### 原則4: 重要局面での人間の関与（Human Oversight at Critical Points）

> 重要な判断や不可逆な操作の前には、人間の確認またはシミュレーションを挟む。

- 書き込み・デプロイ・削除など不可逆操作の前にチェックポイントを設ける
- 設計上の重要な分岐点（アプローチの選択など）でも人間の判断を仰ぐ
- エージェントが行き詰まった場合のフォールバック（撤退条件）を定義する
- **適用**: タスクのリスク・複雑さ・可逆性に応じて適用強度を調整する。定型的で低リスクなタスクにはチェックポイント不要。高リスク・不可逆なタスクには承認必須

#### 原則5: 漸進的な検証（Incremental Verification）

> 作業は小さく区切り、各ステップで正しさを確認してから次に進む。

- AIエージェントに大きなタスクを一度に任せず、検証可能な小さな単位に分割する
- 各ステップの出力を確認してから次のステップに進む
- 問題が起きた場合の影響範囲を限定できる
- **適用**: タスクのリスク・複雑さに応じて適用強度を調整する。単純で低リスクなタスクは一括実行して構わない。複雑・高リスクなタスクは段階的に進める

## Layer 2: copilot-instructions.md

2つのカテゴリに分類したセクション構成を採用する。

### カテゴリ構成

**カテゴリ1: システム設定** — エージェントの基本動作に関する操作的なルール
- 言語設定（日本語使用）
- responding-to-user スキルの必須呼び出し
- 今後追加される基本動作設定もここに配置

**カテゴリ2: AI駆動開発ガイドライン** — 5原則に1対1で対応する行動指示
- **意思決定の記録**: 設計判断の理由をコミットメッセージまたはコメントに残す。複数の選択肢を比較検討して選んだ場合は decision-log スキルでADRを作成する
- **タスク構造**: 1タスク1責務。エージェント間のデータ受け渡しには構造化データを使用。スキルの出力は明確なフォーマットに従う
- **コンテキスト管理**: タスク開始時に前提情報を確認。外部情報使用時はソースの信頼性を明示
- **不可逆操作**: 不可逆操作前にユーザー確認（リスクに応じて判断）。実行不能時は状況報告して撤退
- **検証**: 複雑なタスクは小ステップに分割し各ステップで確認（低リスクなら一括実行可）。変更後は既存動作への影響を確認

## Layer 3: Skills

### Skill 1: decision-log（意思決定ログ）

- **対応原則**: 原則1（意思決定の追跡可能性）
- **役割**: 重要な設計判断が行われた際に、判断内容・理由・代替案を構造化して記録する

#### ADRフォーマット

Nygard式 + Considered Alternatives セクション:

```markdown
# ADR-NNNN: タイトル

- **Status**: Proposed | Accepted | Deprecated | Superseded by ADR-XXXX
- **Date**: YYYY-MM-DD

## Context
（この判断に至った背景・状況）

## Considered Alternatives
（検討した他の選択肢と、それぞれの簡潔な評価）

## Decision
（何を決めたか、なぜこの選択肢を選んだか）

## Consequences
（この判断の結果起きること。良い影響・悪い影響の両方）
```

#### ファイル命名規則

連番 + スラグ: `NNNN-slug.md`
- 例: `0001-adopt-layered-guidelines.md`
- 連番はインデックスの最大番号+1を自動採番

#### インデックスファイル

`docs/decisions/README.md` にテーブル形式で一覧を管理:

```markdown
# Architecture Decision Records

| # | タイトル | ステータス | 日付 |
|---|---------|-----------|------|
| [0001](0001-adopt-layered-guidelines.md) | レイヤード方式のガイドライン構成を採用 | Accepted | 2026-04-12 |
```

ADR作成・ステータス変更時にインデックスも必ず更新する。

#### 作成トリガー

1. **設計・アーキテクチャの決定時** — 例: 「レイヤード方式を採用する」「マイクロサービスではなくモノリスで始める」
2. **プロセス・ワークフローの決定時** — 例: 「情報収集タスクと分析タスクを別のエージェントセッションに分ける」
3. **スコープ・優先度の決定時** — 例: 「MVPでは通知機能を含めない」「セキュリティ強化を機能追加より優先する」
4. **方針・ルールの決定時** — 例: 「外部APIから取得した情報は必ずキャッシュに保存してから利用する」
5. **既存の判断の変更時** — 例: 旧ADRを Superseded に更新 + 新ADR作成

**判断基準**: 「迷って選んだもの」はすべてADR候補。迷わなかったもの（自明な選択）はADR不要。

#### 更新トリガー

- 判断の撤回・差し替え時: Status を Deprecated / Superseded に変更し理由を追記
- 重大な結果（Consequence）が判明したとき: Consequences セクションに追記

#### 漏れ防止

- copilot-instructions.md に指示: 「複数の選択肢を比較検討して一つを選んだ場合、decision-log スキルでADRを作成すること」
- 設計スキル完了時に「この判断をADRとして記録しますか？」とユーザーに確認する

### Skill 2: pre-action-review（操作前レビュー）

- **対応原則**: 原則4（重要局面での人間の関与）+ 原則5（漸進的な検証）
- **役割**: 不可逆操作や重要な変更の前に、実行内容のサマリーをユーザーに提示し確認を得る

#### 動作

- 操作前に「何をしようとしているか」「影響範囲」「リスク評価」を提示
- リスクレベルに応じて動作を変える:
  - 低リスク（可逆操作、定型作業） → ログのみ
  - 中リスク（複数ファイルの変更、外部サービスへの読み取りアクセス） → サマリー表示
  - 高リスク（データ削除、デプロイ、外部サービスへの書き込み、不可逆な設定変更） → 承認必須
- タスクが行き詰まった場合のフォールバック: 状況報告 + 撤退

## 運用モデル

### このリポジトリの位置づけ

「ガイドライン本体（正本）」兼「テンプレート」として機能する。

- `docs/principles.md` が原則の正本として常にここで管理される
- 新プロジェクト開始時に Layer 2（copilot-instructions.md）と Layer 3（skills）をコピーして使用
- プロジェクト固有の指示は、コピー先で追記する

### 成長サイクル

1. **実践で発見** — 新しいプロジェクトで「こういうルールがあればよかった」と気づく
2. **原則に追加** — `docs/principles.md` に新しい原則を追記
3. **指示に翻訳** — `copilot-instructions.md` に対応する行動指示を追加
4. **必要ならスキル化** — 自動化する価値があればスキルを作成
5. **ADRに記録** — 「なぜこの原則を追加したか」を記録
