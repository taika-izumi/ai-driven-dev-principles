# 設計: 記録の強化（サブプロジェクトA）

- **Date**: 2026-04-25
- **Status**: Draft
- **Scope**: サブプロジェクトA — ADRゲート + セッション継続ハンドオフ
- **関連サブプロジェクト**: サブプロジェクトB（機能ブロック駆動の設計＋仕様書分割）は別 spec で扱う

## 1. 背景・問題

本リポジトリの3層レイヤード方式（principles → copilot-instructions → skills）を実プロジェクトに適用したところ、以下の不満が観察された:

1. **意思決定時にADRが作成されない**
   - brainstorming で 2-3 案から1案を選択しても、ADR が残らない
   - writing-plans の方式選定や、実装中の方針変更でも同様
2. **セッションを跨ぐ作業継続が難しい**
   - 「ここまで」「続きは別セッションで」と伝えても、進捗ファイルが自動で出力・更新されない
   - 結果、ユーザーが手動で「進捗ファイルを出力してほしい」と依頼する必要がある

## 2. 目的

- 意思決定の場面を **継続的に検出** し、ADR ドラフトを即時作成する仕組みを導入する
- セッション間で作業を継続するための **ハンドオフ記録** を、マイルストーン到達時とセッション終了時に自動更新する
- これらを実現するために、**作業の起点となるスキル** を新設し、横断的な関心（handoff、ADR検出、不可逆操作レビュー）を一元化する

## 3. 既存原則との対応（原則は変更しない）

| 既存原則 | 本サブプロジェクトの実装 |
|---------|--------------------------|
| 1. 追跡可能性 | ADRゲート、handoffファイル |
| 2. 関心の分離 | start-work（オーケストレーション層）の独立 |
| 3. コンテキスト管理 | handoff によるセッション間コンテキスト引継ぎ |
| 4. 人間の関与 | ADR承認、handoff「続きから?」確認 |
| 5. 漸進的検証 | マイルストーン単位の handoff 更新 |

新しい関心事は導入されないため、`docs/principles.md` は変更しない。実装は Layer 2（copilot-instructions.md）と Layer 3（skills/）に限定される。

### 設計上の重要な特徴

- **フローを1本に固定しない**: superpowers の各スキル（brainstorming, systematic-debugging, executing-plans 等）は独立した発動条件を持ち、フロー逸脱（後戻り、分岐、ループ）が常態。`start-work` は順序を強制しない代わりに、**ユーザーの意図に応じた次手をナビゲート** し、**横断関心を強制適用** する
- **継続的ADR検出**: ADRゲートはフェーズ境界だけでなく、スキル実行中の任意のタイミングで発火する。これは copilot-instructions.md の常時ルールで担保する
- **superpowers 依存の緩和**: 各フェーズは抽象的な「能力」として定義し、superpowers 不在時はインライン簡易フローへフォールバック

## 5. 新規スキル: `start-work`

### 5.1 役割

「AIエージェントを活用した作業のフローを定義し、フロー通りに動かすための起点スキル」。superpowers のフレームワークで実行可能なすべての作業（新規開発、改修、デバッグ、レビュー、調査、ガイドライン拡張など）の入り口として機能する。

### 5.2 発動条件

- 新しい作業を開始する時、必ず最初に呼ばれる
- copilot-instructions.md の常時ルールにより遵守が要求される

### 5.3 フロー

```
┌──────────────────────────────────────────────────────┐
│ Phase 0: セッション継続チェック                      │
│   - 現在ブランチを取得                               │
│   - docs/handoff/<branch>.md があれば session-handoff│
│     スキルの read を呼んで内容を要約提示             │
│   - 「前回の続きから始めますか?」をユーザー確認      │
│     - Yes → 該当ワークフローの再開ポイントへ         │
│     - No → Phase 1 へ                                │
└──────────────────────────────────────────────────────┘
                         │
┌──────────────────────────────────────────────────────┐
│ Phase 1: 状況診断（state assessment）                │
│   - リポジトリ状態を確認（ブランチ、未コミット変更等）│
│   - ユーザーから作業意図をヒアリング                 │
│   - handoff 不在なら新規作成                         │
└──────────────────────────────────────────────────────┘
                         │
┌──────────────────────────────────────────────────────┐
│ Phase 2: 次手のナビゲーション（ループ）              │
│   作業意図に応じた推奨スキルを提示:                  │
│     - 新規開発・機能追加・改修 → brainstorming       │
│     - バグ修正・デバッグ → systematic-debugging      │
│     - 既存planの実装 → executing-plans               │
│     - コードレビュー対応 → receiving-code-review     │
│     - コードレビュー依頼 → requesting-code-review    │
│     - 調査・分析 → ad-hoc                            │
│     - ガイドライン拡張 → extend-guidelines           │
│   ユーザーまたはAIが選択 → そのスキルへ delegate     │
└──────────────────────────────────────────────────────┘
                         │
                         ▼ (任意のスキルを実行)
┌──────────────────────────────────────────────────────┐
│ 横断的ラッパー（全スキル実行の前後で適用）           │
│   Pre:  必要なら pre-action-review                   │
│   Post: 項目を1つずつ消し込み、結果を消化記録へ書く  │
│     1. ADR候補検出 → 必要なら decision-log           │
│     2. session-handoff:update（マイルストーン到達時）│
│     3. worklog-record（同上。ゲート棄却も記録）      │
│     4. 次手のナビゲーションへ戻る（Phase 2 ループ）  │
└──────────────────────────────────────────────────────┘
                         │
                         ▼ (ユーザーが「ここまで」を明示)
┌──────────────────────────────────────────────────────┐
│ セッション終了処理                                   │
│   - worklog-record を呼ぶ（切替直前の最終機会）      │
│   - session-handoff:finalize を呼ぶ                  │
│   - 次セッションのアクションを必ず埋める             │
└──────────────────────────────────────────────────────┘
```

### 5.3.1 Post ラッパーの消し込み規律（ADR-0057）

Post ラッパーの各項目は**1つずつ明示的に消し込む**。消し込みの結果のうち、判定結果が成果物として残らない2項目（1. ADR候補検出 / 3. worklog-record）を、ハンドオフの「Post ラッパー消化記録」へマイルストーンごとに1行で残す。項目2（session-handoff update）は行が存在すること自体が証跡であり、項目4（次手へ復帰）は記録対象外とする。

`session-handoff` update の完了は `worklog-record` の免除にはならない。両者は別項目であり、前者を実施したことをもって後者を済ませたと判断してはならない（実運用で観測された失敗モード。Issue-0037）。

`worklog-record` は記録ゲート（ADR-0044）で棄却された場合も、棄却した旨を消化記録へ書く。棄却を明示しない限り、**未発火とゲート棄却は外形的に区別できない**（どちらも中央ストアに行が増えない）ためである。

セッション終了処理でも `session-handoff` finalize の前に `worklog-record` を呼ぶ。節目でなくてもセッションが切り替われば delta を保持する文脈が失われるため、切り替え直前が記録の最終機会になる（ADR-0058）。

Post ラッパーに完全に入らなかった場合は消化記録の行そのものが書かれず、即時には検出できない。これは `retrospective` の Phase 3 で `git log` と突合して事後に回収する（ADR-0057）。

Post ラッパー項目1で据え置き ADR を Accepted へ昇格させるときは、`decision-log` の「承認の昇格」手順に含まれる粒度点検が先に走る（ADR-0059 / ADR-0060）。点検の規範は `decision-log` 側に一本化されており、Post ラッパー側およびセッション終了処理には重複して記述しない。

### 5.4 依存検出パターン

スキル冒頭で以下を実施:

1. superpowers プラグインの有無を確認
2. 必要なスキル（brainstorming, writing-plans, executing-plans, systematic-debugging 等）の存在確認
3. 不足があればユーザーに報告し、インライン簡易フローへフォールバックすることを通知
4. フェーズ→スキルのマッピング表を内部で構築

### 5.5 ADR候補検出基準

各スキル実行後、または重要な分岐に遭遇した時点で、次のいずれかに該当するか自己評価する:

- 複数の選択肢を比較して1つを選んだ
- 当初の方針を変更した
- スコープ・優先度を判断した
- アーキテクチャや構造に影響する決定をした

該当すれば自動で `decision-log` スキルを呼ぶ。

### 5.6 インラインフォールバック

superpowers が無い環境でも最低限動作するよう、各フェーズに簡易ガイダンスを内包する:

- 要件明確化: 1問ずつヒアリング、目的・制約・成功基準を確認
- 計画: タスクを箇条書きで列挙、依存関係を明示
- 実装: TDDサイクル、小さく区切る、各ステップで検証
- デバッグ: 仮説立案 → 検証 → 修正 → 再検証

## 6. 新規スキル: `session-handoff`

### 6.1 役割

セッション間の作業引き継ぎファイルを「読む」「作成する」「更新する」「確定する」専門スキル。

### 6.2 ファイル配置

```
docs/handoff/<branch-name>.md
```

- ブランチ名のスラッシュは `_` に置換（例: `feature/auth-flow` → `feature_auth-flow.md`）
- main/master ブランチでも作成可能
- git管理対象（コミットして履歴を残す）

### 6.3 ハンドオフファイルのフォーマット

```markdown
# Handoff: <作業タイトル>

- **Branch**: <branch-name>
- **Last Updated**: YYYY-MM-DD HH:MM (Asia/Tokyo)
- **Status**: in_progress | paused | completed
- **Current Phase**: <作業タイプ>/<現在のスキル or 段階>

## 作業の目的・背景

（このブランチで何を達成しようとしているかの要約。1-3段落）

## 関連ドキュメント

- Spec: `docs/current/specs/...`
- Plan: `docs/working/plans/...`
- 関連ADR: ADR-NNNN, ADR-NNNN

## 完了済みタスク

- [x] タスクA（YYYY-MM-DD 完了）

## 進行中のタスク

- [ ] **現在の作業**: タスクC
  - 状態: <どこまでやったか>
  - 残り: <次に何をすべきか>

## 未着手のタスク

- [ ] タスクD

## 既知のブロッカー・懸念

（なし、または箇条書き）

## Post ラッパー消化記録

マイルストーンごとに Post ラッパーの消し込み結果を1行残す（ADR-0057）。
形式: `- <日付> <マイルストーン>: ADR=<番号 or なし（理由）> / worklog=<エントリ id or 棄却（理由）>`
行が存在すること自体が `session-handoff` update の証跡であるため、update の項目は書かない。

- YYYY-MM-DD <マイルストーン名>: ADR=NNNN / worklog=`<project>-YYYY-MM-DD-NN`
- YYYY-MM-DD <マイルストーン名>: ADR=なし（<理由>） / worklog=棄却（delta なし）

## 次セッション開始時のアクション

1. 最初に確認すべきファイル: ...
2. 最初に実行すべきコマンド/スキル: ...
3. 留意点: ...

## 重要な意思決定の履歴

- ADR-NNNN: <タイトル>（YYYY-MM-DD）
```

### 6.4 操作

| 操作 | 呼ばれるタイミング | 動作 |
|------|------------------|------|
| `read` | start-work の Phase 0 | 現在ブランチの handoff を読み込み、要約をユーザーに提示。あわせて消化記録欄が空白のマイルストーンがないか検査する（ADR-0057） |
| `create` | start-work の Phase 1（handoff 不在時） | 目的・背景・関連docを最低限記入して新規作成 |
| `update` | 各スキル完了後・マイルストーン到達時 | 完了/進行中/未着手セクションを更新、Last Updated を更新。あわせて「Post ラッパー消化記録」へ当該マイルストーンの1行を追記する（ADR-0057） |
| `finalize` | セッション終了時 | 「次セッション開始時のアクション」を必ず埋め、Status 確定後コミット。確定済みの過去セッション分の消化記録行は削除してよい（履歴は git に残る。ADR-0057） |

### 6.5 完了済みハンドオフの扱い

PR マージなどで作業完了した handoff は、`Status: completed` のまま残す。`docs/handoff/archive/` への移動は将来検討（初版では実装しない）。

## 7. 既存スキル拡張: `decision-log`

### 7.1 「いつ使うか」セクションの全面改訂

旧内容（5項目の場面分類）を **「検出トリガー一覧」** に置き換える:

```markdown
## いつ使うか — 検出トリガー一覧

以下のいずれかを **検出した瞬間に**、現在実行中のスキル・タスクに
関わらずこのスキルを呼び出すこと。「スキルの途中だから後で」は禁止。

### 強トリガー（必ず呼ぶ）
1. 複数案からの選択 — 2つ以上の選択肢を比較し1つを選んだとき
2. 方針の変更 — 当初決めた方針・設計を覆したとき
3. アーキテクチャに影響する決定 — 層構成、モジュール境界、
   依存関係に関する判断
4. スコープ・優先度の判断
5. ガイドライン・ルールの追加・変更

### 弱トリガー（自己評価して必要なら呼ぶ）
- 命名規則の決定
- ライブラリ・ツールの選定
- フォーマット・スタイルの決定

### 呼ぶ必要がない場面
- 自明な選択（迷いがなかったもの）
- 既存ADRに従っただけの判断
- 一時的な実装の詳細
```

### 7.2 ADR作成手順への追記

既存手順の前に「検出を報告」ステップを追加し、ドラフト→承認フローを明示化:

```markdown
### 0. 検出を報告
ユーザーに「意思決定を検出しました。ADRを作成します」と通知。

### 1-3. （既存通り）採番・ファイル作成・インデックス更新

### 4. ドラフトを Status: Proposed として作成し、ユーザーに提示
- 承認 → Status を Accepted に
- 修正依頼 → 該当箇所を修正
- 却下 → ファイルを削除（インデックスからも除去）

### 5. ユーザー応答に応じて確定処理
- 承認: Status 更新 → コミット
- 却下: ファイル削除
```

### 7.3 description フィールドの強化

```yaml
description: "重要な意思決定をADR（Architecture Decision Record）として
記録・管理する。設計判断、プロセス決定、スコープ決定、方針決定を構造化して
記録する。意思決定を検出した瞬間に呼ぶこと。実行中の他スキルの完了を
待ってはならない。"
```

### 7.4 粒度の判定と追記時の点検（ADR-0059 / ADR-0060）

ADR の粒度は「後から探しに来るときの問い」1つを単位とする。1つの ADR は将来その決定を探しに来る人が立てる問い1つに答えるものとし、問いが2つ以上に割れるなら分割する。**文章量は粒度の基準にしない**（LoopForAlpha の実測で、肥大 ADR 5,545文字に対し分割後4本の合計が 13,918文字へ増え、かつ正常な ADR に 7,558文字が存在したため、閾値では見逃しと誤検出が同時に起きる）。

判定は3箇所へ配置する:

| 契機 | 配置先 | 内容 |
|------|--------|------|
| 起票時 | ADR ファイル作成手順の blockquote | 起票する決定が2つ以上の問いに割れないか |
| 追記時 | 「Proposed の ADR へ決定を追記するとき」節 | タイトルが追記する決定にも答えているかを突合し、ずれていれば AI 側から分割を提案する |
| 昇格前 | 「承認の昇格」手順の第1ステップ | タイトルが本文の全決定に答えているかを突合する |

追記時の点検を一次経路、昇格前の点検を受け皿とする。追記時に検出すると分割の影響面が最小で済むため（LoopForAlpha では起草直後10ファイル対 昇格時24ファイル）。いずれも**独立した消し込み項目としては設けない**（追記操作および既存の昇格ステップに内包させ、Post ラッパーの項目数を増やさない）。

規範の置き場所は `decision-log` に一本化し、昇格を促す側（`start-work` の Post ラッパー項目1、セッション終了処理）は手順を参照するに留める。

## 12. 検証方法

実装後、以下のシナリオで動作確認する:

1. **新規開発フロー**: start-work → brainstorming（途中で2-3案比較を含むシナリオ）→ ADR が中断作成されることを確認
2. **セッション継続**: 一度作業を中断 → handoff 確認 → 別セッション相当で start-work → 「続きから?」が表示されることを確認
3. **superpowers 不在環境**: 該当スキル無効化状態で start-work → インラインフォールバックが動作することを確認
4. **デバッグフロー**: start-work → systematic-debugging が選択肢に出ること、brainstorming を強制されないことを確認
