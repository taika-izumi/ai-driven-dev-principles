# サブプロジェクトB「機能ブロック駆動の設計＋仕様書分割」設計仕様

- **作成日**: 2026-05-01
- **対象**: 本リポジトリ `taika-izumi/ai-driven-dev-principles`
- **ステータス**: Draft（ユーザーレビュー待ち）

## このドキュメントの読み方

本仕様は `docs/specs/<topic>/` 配下にディレクトリ分割で配置する初の事例である。
本仕様自体が「機能ブロック駆動の仕様書分割」のドッグフーディングを兼ねている。

- 本ファイル `00-overview.md`: サブプロジェクトBの全体像、機能ブロック一覧、ブロック間の関係
- `01-skill-feature-block-design.md`: 機能ブロックB1「`feature-block-design` スキル本体」の詳細
- `02-principle-extension.md`: 機能ブロックB2「原則2の拡張」の詳細
- `03-instructions-update.md`: 機能ブロックB3「`copilot-instructions.md` への追記」の詳細
- `04-template-and-docs-sync.md`: 機能ブロックB4「テンプレート同期と周辺ドキュメント更新」の詳細

## 背景・動機

サブプロジェクトA「記録の強化」が完了し、`start-work` / `session-handoff` / 強化版 `decision-log` という横断関心の基盤が整った。
次に対処すべきは、AIエージェントを活用した開発で繰り返し顕在化している以下の課題である。

### 解消したい課題

1. **大規模仕様書の肥大化**: 中規模以上のシステムでも1ファイルに全仕様を詰め込んでしまう。AI も人間も全体把握のために全文を読まされる。
2. **概要→詳細の流れの欠如**: 「概要・機能一覧・主要処理フロー」がなく、いきなり詳細から始まる仕様書になりがち。
3. **大きな泥団子化・スパゲッティ化**: システムが疎結合な機能ブロックに分割されず、複数機能への依存を抱えた一枚岩になる。
4. **差分仕様書化**: システム改修時に変更差分のみを別ファイルとして追記してしまい、「現時点のシステム全容を1つで説明するドキュメント」が消失する。

### この設計のゴール

AIエージェントが、ソフトウェア工学の知見（高凝集・疎結合、単一責任など）を**確実に・機械的に・繰り返し**適用してシステムを設計・開発できる仕組みを、本リポジトリの AI駆動開発ガイドライン側に組み込む。

## 主要な処理フロー（運用視点）

新スキル導入後の標準ワークフロー（中規模以上のシステム開発時）:

```
1. ユーザー指示
   ↓
2. start-work（横断関心ゲートウェイ）
   ↓
3. brainstorming（要件・全体方針の合意）
   ↓
4. feature-block-design  ← 本サブプロジェクトで新設
   ├─ 4-1. 適用要否判定（しきい値: 主要機能 ≥ 2 or 想定モジュール ≥ 3）
   │   └─ 該当しなければ writing-plans へ直行
   ├─ 4-2. 既存仕様書チェック（新規モード or 修正モード）
   ├─ 4-3. 機能ブロック抽出（ユーザー承認、ADR候補）
   ├─ 4-4. 00-overview.md の作成/更新（スナップショット）
   ├─ 4-5. 各ブロック詳細 NN-<block>.md の作成/更新（スナップショット）
   └─ 4-6. 整合性セルフレビュー
   ↓
5. writing-plans（ブロック単位またはブロック横断で plan を作成）
   ↓
6. executing-plans / subagent-driven-development（実装）
```

## 設計上の主要な意思決定

### 決定1: スキル新設 vs 既存スキル強化

**選択**: 新スキル `feature-block-design` を1本新設する。

**比較した選択肢**:
- A. 単一新規スキル（採用）
- B. 2スキルに分離（`feature-block-decomposition` + `spec-partitioning`）
- C. スキル新設せず、原則拡張＋既存スキル強化＋instructions ルール追加のみ

**選択理由**:
- C はトリガーが弱く、AI が「知っているのに実行しない」既存問題を再生産する懸念が大きい。
- B は責務が綺麗に分かれるが、実運用ではほぼ常にセットで使うためハンドオフが過剰。
- A はフローが直線的で、「機能ブロック分割」と「仕様書分割」が同じスキル内で一貫し、トリガーも明確。

**懸念点と対策**:
1. brainstorming との責務重複 → スキル冒頭で「brainstorming は『何を作るか』、本スキルは『機能ブロック単位での詳細化と仕様書化』」と明文化
2. 形骸化（分割した気になるだけ）→ 粒度ガイドラインとセルフレビュー項目をスキル内に入れる
3. 過剰分割 → 適用要否判定のしきい値を明記、判定理由をユーザーに提示してから進む

### 決定2: 仕様書のファイル形式

**選択**: ディレクトリ分割形式（`docs/specs/YYYY-MM-DD-<topic>/00-overview.md`, `01-<block>.md`, ...）。

**比較した選択肢**:
- A. ディレクトリ分割（採用）
- B. 単一ファイル + セクション規約
- C. 規模に応じてAIが選択

**選択理由**: ユーザーの最大の課題（ドキュメント分割不足、概要→詳細の流れ欠如）に直接答える。AIが特定機能を編集する際に必要なファイルだけコンテキストに載せられる利点も大きい。既存の単一ファイル仕様書は過去資産として残置。

### 決定3: 仕様書のスナップショット規約

**選択**: 仕様書は常に「現時点のシステム全容のスナップショット」として維持し、差分のみを記載した別ファイル（変更差分仕様書）を作らない。

**理由**: 「なぜ変更したか」は ADR が担い、仕様書は「今どうなっているか」のみを担うことで、責務分離（原則2）と追跡可能性（原則1）が両立する。仕様書を1つ読めば現時点のシステム全容が分かる状態を保証する。

### 決定4: 適用要否判定の方法

**選択**: AI による自動判定（しきい値: 主要機能 ≥ 2 または想定モジュール/コンポーネント ≥ 3）。

**比較した選択肢**:
- A. 常に適用
- B. AI による自動判定（採用）
- C. ユーザーゲート

**選択理由**: A は小タスクで形骸化、C はユーザー負荷増。B は判定基準を明文化することで再現性を持たせ、判定理由をユーザーに提示する形で原則4（人間関与）も担保する。

### 決定5: 原則2の拡張

**選択**: 原則2「関心の分離」をエージェント設計に限定せず、エージェントが生成するコード・ドキュメント・仕様書にも明示的に適用範囲を広げる。

**理由**: 現状の原則2は「AIエージェントを『万能な1人』ではなく『責務を持った専門家』として設計する」とエージェント設計に限定されているが、本サブプロジェクトの根拠となる「コード・仕様書も責務分離せよ」という指針を支える上位概念が必要。Separation of Concerns はもともと普遍的概念であり、限定する理由はない。

### 決定6: copilot-instructions.md における原則引用の抽象度

**選択**: 「高凝集・疎結合」「単一責任」のような、パラダイムに依存しない普遍的な設計原則名のみを引用する。SOLID 全体・DDD 用語・DRY などのパラダイム依存度の高いものは引用しない。

**理由**: 本リポジトリは「AI を活用した様々なシステム開発に適用できるガイドライン」を提供する立場であり、特定の開発スタイルに縛る記述は避けるべき。一方で、原則名を一切引用せず具体ルールだけを書くと、AI が文脈を判断できず機械的になりやすい。普遍性の高い原則を1〜2個引用する形が両立点。

## スコープ外（YAGNI）

以下は本サブプロジェクトでは扱わない。

- サンプルシステムを題材にした参考実装例（ユーザー指示で除外）
- 既存の単一ファイル仕様書をディレクトリ形式へ移行する作業
- spec-partitioning を独立スキルとして切り出すこと（決定1 B案を不採用としたため）
- 仕様書の自動整合性チェックツール（手動セルフレビューで足りる）
