# ブロック01: folder-structure-definition — 定義本体ドキュメント

## 1. 対象ファイル

- `docs/overview/folder-structure.md`（新規作成）
- `template/docs/overview/folder-structure.md`（ブロック05 の同期機構でコピーされる。本ブロックでは原本のみ作成）

## 2. 責務

開発プロジェクトのフォルダ構成の規範を、単体で読んで運用できる1つのドキュメントとして定義する。本ドキュメントが分類判断の唯一の参照元（single source of truth）であり、organize-inbox スキルや CLAUDE.md の規範はここを参照する。

## 3. インターフェース（ドキュメント構成）

`docs/overview/folder-structure.md` は以下のセクションで構成する:

1. **この文書の目的** — プロジェクトの情報をどこに置くかの判断基準を定義する、という宣言
2. **情報分類体系** — 5分類の定義表（分類名 / 性質 / 代表例）。分類軸は「話題ではなく情報の性質（更新様式 × ライフサイクル）」であることを明記
3. **境界の配置判断基準** — 3つの基準:
   - オリエンテーション vs 参照知識: 「参画直後に全員が読むべきか / 必要時に引くものか」
   - 現在の正 vs 参照知識: 「システム・プロジェクトそのものの姿か / 作業を支える周辺知識か」
   - 追跡型の記録 vs 参照知識: 「出来事の時点記録（不変）か / 蒸留した再利用知識（改訂される）か」
4. **蒸留規則** — 同じ出来事から「記録」と「参照知識」の両方を別ドキュメントとして作ってよい。時点記録は書き換えず、再利用知識は別途起こす
5. **標準フォルダレイアウト** — `docs/{overview, current, working, records, reference, inbox}` のツリー図と各フォルダの説明。規約:
   - 種別サブフォルダはオンデマンド作成（空フォルダの先行作成禁止）
   - 列挙されていない新種別は、分類基準で判断して分類フォルダ直下または新サブフォルダに置く
   - 迷ったら `docs/inbox/` へ（organize-inbox スキルが処理する）
6. **代表的なドキュメント種別の配置表** — 仕様書・課題・handoff・実装計画・ADR・議事録・retrospective・リリースノート・インシデント報告・リリース手順・runbook・既知エラー・調査メモ・FAQ・用語集・体制図などの配置先一覧
7. **課題（issue）管理** — 詳細は下記「5. データモデル」の課題ファイル規約を記載:
   - `docs/working/issues/NNNN-<slug>.md`（4桁ゼロ埋め連番）＋インデックス `README.md`
   - Status: open → closed。対策方針決定時に ADR を作成して close する
   - 検討の長期化・多観点化時は `issues/NNNN-<slug>/` フォルダへ昇格できる（課題ファイルをフォルダ内 `README.md` とし、分析ファイルを並置する）
   - クローズ済みはその場に残す（アーカイブは分類ではなく状態）
   - 不確定情報には「TBD」を積極的に使う（確定事実との混同を防ぐ）
8. **コード領域の配置原則** — 抽象レベルの3原則:
   - コードとドキュメントは領域を分離する（コードを `docs/` に置かない、ドキュメントをコードツリーに散在させない）
   - コード領域の内部構成は言語・フレームワークの標準慣習に従う。ソースとテストは分離する
   - AI駆動システムの成果物（プロンプト定義、エージェント定義、評価データセット等）はコード領域に置きバージョン管理する。その背景説明・運用知識は docs 側の該当分類に置く

## 4. サブ機能 / 内部構成

なし（単一ドキュメント）。

## 5. データモデル（課題ファイル）

課題ファイル `docs/working/issues/NNNN-<slug>.md` のフォーマット:

```markdown
# Issue-NNNN: <タイトル>

- **Status**: open | closed
- **Opened**: YYYY-MM-DD
- **Closed**: YYYY-MM-DD（closed 時のみ）
- **関連**: ADR-NNNN 等（あれば）

## 課題内容

（何が問題か・なぜケアが必要か。TBD を積極的に使ってよい）

## 検討状況

（対策検討の経過。長期化したらフォルダ昇格を検討）

## 結論

（closed 時: 下した決定への参照。決定内容自体は ADR に書く）
```

インデックス `docs/working/issues/README.md` は1課題1行のテーブル（# / タイトル / Status / Opened）。

## 6. このブロック固有の制約・前提

- ツール非依存・プロジェクト性質非依存の表現で書く（特定言語・特定ツールの前提を持ち込まない）
- 記述言語は日本語
- このドキュメント自身が「参画直後に全員が読むべき情報」なので `docs/overview/` に置く（自己記述的）
- template 対象（他プロジェクトへ配布される）なので、本リポジトリ固有の事情（メタ・ガイドライン開発の文脈）を書かない
