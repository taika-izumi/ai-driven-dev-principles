# ブロック01: folder-structure-definition — 定義本体ドキュメント

## 1. 対象ファイル

- `docs/overview/folder-structure.md`（新規作成）
- `template/docs/overview/folder-structure.md`（ブロック05 の同期機構でコピーされる。本ブロックでは原本のみ作成）

## 2. 責務

開発プロジェクトのフォルダ構成の規範を、単体で読んで運用できる1つのドキュメントとして定義する。本ドキュメントが分類判断の唯一の参照元（single source of truth）であり、organize-inbox スキルや CLAUDE.md の規範はここを参照する。

## 3. インターフェース（ドキュメント構成）

`docs/overview/folder-structure.md` は以下のセクションで構成する:

1. **この文書の目的** — プロジェクトの情報をどこに置くかの判断基準を定義し、あわせて文書運用規約（仕様書の運用）を定める、という宣言
2. **情報分類体系** — 5分類の定義表（分類名 / 性質 / 代表例）。分類軸は「話題ではなく情報の性質（更新様式 × ライフサイクル）」であることを明記
3. **境界の配置判断基準** — 3つの基準:
   - オリエンテーション vs 参照知識: 「参画直後に全員が読むべきか / 必要時に引くものか」
   - 現在の正 vs 参照知識: 「システム・プロジェクトそのものの姿か / 作業を支える周辺知識か」
   - 追跡型の記録 vs 参照知識: 「出来事の時点記録（不変）か / 蒸留した再利用知識（改訂される）か」
4. **蒸留規則** — 同じ出来事から「記録」と「参照知識」の両方を別ドキュメントとして作ってよい。時点記録は書き換えず、再利用知識は別途起こす
5. **標準フォルダレイアウト** — `docs/{overview, current, working, records, reference, inbox}` のツリー図と各フォルダの説明。規約:
   - 種別サブフォルダはオンデマンド作成（空フォルダの先行作成禁止）
   - 列挙されていない新種別は、分類基準で判断して分類フォルダ直下または新サブフォルダに置く
   - 迷ったら `docs/inbox/` へ（organize-inbox スキルが処理する）
6. **代表的なドキュメント種別の配置表** — 仕様書・課題・handoff・実装計画・ADR・議事録・retrospective・リリースノート・インシデント報告・リリース手順・runbook・既知エラー・調査メモ・FAQ・用語集・体制図などの配置先一覧
7. **仕様書の運用規約** — 仕様書運用の 4 箇条（スナップショットとしての維持／書き換えでの更新／「なぜは ADR に、今どうなっているかは仕様書に」／中規模以上でのディレクトリ分割形式。しきい値の定義は `feature-block-design` スキルの適用要否判定が正）。`CLAUDE.md`（ドキュメント運用）から参照される（4 箇条の導入元は ADR-0008）
8. **課題（issue）管理** — 課題の起票・記録・フォルダ運用・クローズの規範は課題管理定義（`docs/overview/issue-management.md`）を正とし、本節は「やりたいこと → 読む節（課題管理定義）」の早見表とする（起票する／経過・再発を追記する／フォルダへ資料を置く・整理する／書式・記載分量を確認する／close する／インデックスを更新する／他リポジトリの課題を参照する、の7行）:
   - （パスの定義は §5 のツリーと §6 の配置表、採番規則は課題管理定義 §3 が正）
9. **運用例（代表シナリオ）** — 分類間を情報が流れる様子を示す具体例を1つ以上載せる。初版は「チーム開発での大規模リファクタリング」:
   - 課題起票（`working/issues/`, open。候補が複数なら課題ごとに起票し、インデックスが負債の棚卸し表になる）
   - フォルダ外に置くべき資料が生じた時、または課題ファイルがサイズ目安を超えた時に課題フォルダへ昇格し（課題管理定義の昇格条件）、検討ノート・時点資料を役割固定の命名で並置する
   - 合意形成（議事録は `records/minutes/`、合意した決定は ADR として `records/decisions/`、課題は結論から ADR を参照して close）
   - 合意後（仕様書 `current/specs/` を書き換え更新、実装計画 `working/plans/` を作成して実装へ）
10. **コード領域の配置原則** — 抽象レベルの3原則:
   - コードとドキュメントは領域を分離する（コードを `docs/` に置かない、ドキュメントをコードツリーに散在させない）
   - コード領域の内部構成は言語・フレームワークの標準慣習に従う。ソースとテストは分離する
   - AI駆動システムの成果物（プロンプト定義、エージェント定義、評価データセット等）はコード領域に置きバージョン管理する。その背景説明・運用知識は docs 側の該当分類に置く

## 4. サブ機能 / 内部構成

なし（単一ドキュメント）。

## 5. データモデル（課題ファイル）

詳細版・正本は課題管理定義（`docs/overview/issue-management.md` §8）。以下は folder-structure.md 側で参照していた当時の概要形。

課題ファイル `docs/working/issues/system|flow/NNNN-<slug>.md` のフォーマット:

```markdown
# Issue-NNNN: <タイトル>

- **Status**: open | closed
- **Opened**: YYYY-MM-DD
- **Closed**: YYYY-MM-DD（closed 時のみ）
- **起票元**: <起票のきっかけへの参照>（任意。振り返り由来なら「retrospectives/flow/YYYY-MM-DD-<topic>.md 課題#N」の形式）
- **関連**: ADR-NNNN 等（あれば）

## 課題内容

（何が問題か・なぜケアが必要か。TBD を積極的に使ってよい）

## 検討状況

（対策検討の経過。フォルダ外に資料が生じた時、または追記時のサイズ実測が目安値を超えた時にフォルダ昇格を提案。詳細は課題管理定義を参照）

## 結論

（closed 時: 下した決定への参照。決定内容自体は ADR に書く）
```

課題ファイルは `docs/working/issues/system|flow/` に分類配置する。インデックス `docs/working/issues/README.md` はフォルダ対応の2セクション構成で、各セクションは1課題1行のテーブル（# / タイトル / Status / Opened）。採番は両セクション通しの連番。

## 6. このブロック固有の制約・前提

- ツール非依存・プロジェクト性質非依存の表現で書く（特定言語・特定ツールの前提を持ち込まない）
- 記述言語は日本語
- このドキュメント自身が「参画直後に全員が読むべき情報」なので `docs/overview/` に置く（自己記述的）
- template 対象（他プロジェクトへ配布される）なので、本リポジトリ固有の事情（AI駆動開発ガイドライン開発の文脈）を書かない
