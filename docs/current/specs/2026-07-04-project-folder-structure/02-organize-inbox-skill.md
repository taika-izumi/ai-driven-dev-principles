# ブロック02: organize-inbox-skill — inbox 処理スキルと start-work 検知

## 1. 対象ファイル

- `skills/organize-inbox/SKILL.md`（新規作成）
- `skills/start-work/SKILL.md`（Phase 1 への inbox 検知追加。パス参照の更新はブロック03 の責務であり、本ブロックは検知ステップの追加のみを行う。適用順序は 03 → 02）

## 2. 責務

`docs/inbox/` に投入された未分類の情報を、1件ずつ分類基準（`docs/overview/folder-structure.md`）に照らして判断し、適切な場所へ反映する。start-work のセッション開始診断で inbox の滞留を検知し、実行を提案する。

## 3. インターフェース

### organize-inbox スキル

- **入力**: `docs/inbox/` 内のファイル群（形式不問）
- **出力**: 分類・反映済みのドキュメント群、更新されたインデックス、処理サマリー（ユーザーへの報告）
- **起動**: ユーザーの明示的実行、または start-work Phase 1 からの提案経由

### start-work への追加（Phase 1 状況診断）

リポジトリ状態確認の直後に以下のステップを追加する:

> `docs/inbox/` にファイルが存在するか確認する（ディレクトリ一覧の取得のみ。内容は読まない）。存在する場合、件数をユーザーに伝え、organize-inbox スキルの実行を提案する（強制はしない。ユーザーが後回しを選んだら handoff の「既知のブロッカー・懸念」に滞留件数を記録する）。

## 4. サブ機能 / 内部構成（organize-inbox の処理手順）

1. **一覧と確認**: inbox 内ファイルを列挙する。件数が多い場合（目安: 6件以上）は件数を提示し、全件処理するか対象を絞るかをユーザーに確認する
2. **1件ずつ処理**（以下を各ファイルで繰り返す）:
   1. 内容を読む。大きいファイルは分類判断に必要な範囲（冒頭部分・見出し構造）だけ読む
   2. 分類基準（5分類・境界判断基準・蒸留規則）に照らして処理方針を決める。処理方針は4種:
      - **移動**: ファイルを丸ごと適切な分類先へ移す
      - **分割**: 複数分類の情報が混在する場合、内容を分割して複数の分類先に配置する
      - **統合**: 既存ドキュメントに追記されるべき内容の場合、既存ファイルへ追記し、新規ファイルは作らない
      - **破棄**: 情報価値がない（重複・空・一時メモ）と判断した場合。破棄は不可逆操作なので必ずユーザー承認を得る（pre-action-review の高リスク扱い）
   3. 分類・処理方針が曖昧な場合は、選択肢＋推奨（ADR-0024 の規範）でユーザーに確認する。明確な場合は確認せず処理してよいが、処理内容はサマリーで必ず報告する
   4. 処理を実行する。移動・分割先に種別サブフォルダが必要でまだ無ければ作成する。配置先にインデックス（issues/README.md 等）があれば更新する
   5. 処理済みの inbox ファイルを除去する（統合の場合も、反映が完了したら inbox から取り除く）
3. **サマリー報告**: 処理結果（ファイルごとの処理方針と配置先）を一覧でユーザーに報告する
4. **ADR 候補検出**: 処理中に意思決定（分類基準自体への疑義など）が発生したら、通常どおり decision-log / 課題起票の対象とする

## 5. データモデル

なし（ファイル操作のみ）。

## 6. このブロック固有の制約・前提

- 分類基準の定義は持たない。常に `docs/overview/folder-structure.md` を参照する（基準の二重管理を禁止）
- トークン消費対策: 内容の読み込みは分類判断に必要な範囲に留める。全件一括読み込みをしない
- スキルはプラグイン配信対象であり `template.manifest` に追加しない（ADR-0016）
- README のスキル一覧への追加はブロック04 の責務
- 対応する原則: 原則2（関心の分離: 分類判断を独立した責務として自動化）、原則3（コンテキスト管理）、原則4（曖昧時・破棄時の人間の関与）
