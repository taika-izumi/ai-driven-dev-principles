# 作業記録→候補抽出→スキル化 3スキルパイプライン — 概要

## このドキュメントの読み方

本仕様は「現時点のシステム全容のスナップショット」である。以下のファイルで構成する:

| ファイル | 内容 |
|---------|------|
| `00-overview.md`（本書） | 背景・全体アーキテクチャ・処理フロー・意思決定参照・スコープ外・完了基準 |
| `01-worklog-store.md` | 共有データ層（中央ストアのレイアウト・スキーマ・識別子解決） |
| `02-skill1-record.md` | スキル1（記録） |
| `03-skill2-extract.md` | スキル2（候補抽出） |
| `04-skill3-skillify.md` | スキル3（スキル化） |

「なぜこの設計にしたか」は ADR（0044/0045/0046）に記載する。本仕様には「今どうなっているか」のみを書く。

## 背景・動機

メタ・ガイドライン運用で得られる「スキル化・ルール化する価値のある作業ノウハウ」を、複数プロジェクト横断で捕捉・抽出・スキル化する仕組みが存在しなかった。既存の retrospective はサイクル終端の課題抽出用であり、頻発・重要な作業手順やルールの継続的抽出には使えていない。

本システムは、AI に作業させた後の「差分（delta）＝AI がデフォルトでやることと実際に必要だったことの差」を継続的に記録し、横断的に抽出して、スキル/ルールへ昇華する3スキルのパイプラインである。対話モードのガイドライン拡張であり、ADR-0043 の凍結（ループ対応改修・2プロファイル構成）には抵触しない。

## 全体アーキテクチャ

### 機能ブロック一覧

| # | ブロック | 責務（1文） | 種別 |
|---|---------|------------|------|
| 01 | worklog-store | 中央ストアの物理レイアウト・エントリ/台帳スキーマ・プロジェクト識別子解決を定義する、3スキル共通のデータ契約 | データ契約（コードではなくフォーマット規約） |
| 02 | skill1-record | 節目で delta 核心のエントリを1件、id 採番・scope 暫定タグ・記録ゲート判定つきで追記する | スキル（`skills/`） |
| 03 | skill2-extract | ストアをオンデマンド走査→クラスタリング→評価→台帳で処理済み除外→候補提示→人間採否→Issue 草案化 | スキル（`skills/`） |
| 04 | skill3-skillify | 採用候補を writing-skills 委譲でスキル化。スコープ3分岐・実行環境ガード・Skill Creator 設計時借用 | スキル（`skills/`） |

### ブロック間関係

```
                 ┌─────────────────────────────┐
                 │  01 worklog-store（データ層）  │
                 │  projects.json / */log.jsonl  │
                 │  processed.jsonl（台帳）        │
                 └─────────────────────────────┘
                    ▲ append        ▲ read / append(台帳)
                    │                │
        ┌───────────┴──────┐   ┌─────┴─────────────┐
        │ 02 skill1-record │   │ 03 skill2-extract │
        │ （記録・追記）      │   │ （抽出・採否）       │──── Issue草案 ───┐
        └──────────────────┘   └───────────────────┘                 │
                                        │ 採用候補を渡す                  ▼
                                        └────────────▶ ┌───────────────────────┐
                                                       │ 04 skill3-skillify     │
                                                       │ （writing-skills 委譲）   │
                                                       └───────────────────────┘
                                                            │ append(台帳: skillified/merged)
                                                            ▼ 01 へ
```

依存は 01 のファイルフォーマット（インターフェース）経由のみ。依存方向は非循環（01 が土台、02/03 が読み書き、03→04 が候補受け渡し）。

## 主要な処理フロー

### フロー1: 記録（スキル1、各作業の節目）

1. メインエージェントが作業の節目（handoff マイルストーンと同じ）に到達
2. 記録ゲート判定（既存スキルで実施済みでない かつ AI 自律で毎回再現できない）
3. ゲート通過なら delta（friction または corrections の少なくとも一方）を核にエントリを構築
4. 識別子解決（`projects.json` upsert）→ id 採番 → scope 暫定タグ → delta 必須検証 → `<folderName>/log.jsonl` へ追記

### フロー2: 抽出（スキル2、ユーザーのオンデマンド実行）

1. `processed.jsonl` を読み、処理済み id（skillified/rejected/merged）を分析対象から除外。deferred はクラスタ根拠数とともに保持
2. サブエージェントで未処理エントリを1パス走査 → 類似エントリをクラスタリング
3. 各クラスタを評価（横断再発回数・出所プロジェクト数・delta 重み・scope 再判定・既存スキル重複排除）
4. deferred クラスタは新しい該当エントリが増えた場合のみ再提示
5. ランク付き候補リストを人間に提示 → 人間が採否
6. rejected/deferred は即 `processed.jsonl` へ追記。採用は Issue 草案化してスキル3へ

### フロー3: スキル化（スキル4＝スキル3、採用候補ごと）

1. 実行環境ガード（汎用パス かつ 本 repo でない → 警告＋ユーザー確認）
2. スコープ3分岐で振り分け先を決定（汎用→プラグイン配信スキル／固有→プロジェクトローカル／固有ルール→CLAUDE.md）
3. writing-skills へ委譲（Skill Creator 設計時借用の references を併用）
4. 作成/拡張完了後、`processed.jsonl` へ結果（skillified/merged）を追記

## 設計上の主要な意思決定

- **ADR-0044**: 3スキルパイプラインを中央集約アーキテクチャで新設（3スキル構成・スコープ3分岐・責務境界・overlap 対応）
- **ADR-0045**: スキル1のログは delta 核心スキーマ・JSONL・追記専用ライフサイクル（id・processed.jsonl・deferred）
- **ADR-0046**: スキル3は writing-skills 既定・Skill Creator 設計時借用・実行環境ガード
- **ADR-0047**: worklog-record は start-work の Post ラッパーに組み込み全プロジェクトへ伝播させる
- 決定履歴の全量（D1〜D17）は `docs/working/handoff/skill-pipeline-brainstorming-state.md`

## スコープ外（YAGNI）

- **スキル2の出力3（既存ルール・スキルの改訂候補発見）**: v2 へ延期。`applied_rules` の逸脱注記はデータとして捕捉するのみ
- **物理ファイル肥大時の archive 退避**: v1 では作らない
- **中央ストアの git 管理**: v1 ではオプション（素のファイル）
- **他プロジェクト失敗の自動 Issue 移行**: v2（v1 は既存の手動移行経路のまま）
- **git remote URL 等の強い識別子**: v1 はフォルダ名＋パス存在チェックのみ
