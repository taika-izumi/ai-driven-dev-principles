# サブエージェント委譲スキルと確定前レビュースキルの設計

- **対象**: `skills/subagent-dispatch/`、`skills/pre-finalization-review/`、`CONTRIBUTING.md` の新設の評価可能性
- **今回の設計状態**: ADR-0124・0125 に基づく設計。フル実施1回と差分再確認1回を終え、実質的な収束を確認。配布スキルへの実装は未着手。
- **今回の根拠**: ADR-0124（状況による方式・人数の推奨と既存の実施判断）、ADR-0125（追加物の費用比較）。両ADRはProposed。
- **起点課題**: Issue-0033（委譲プロンプトの定型項目が未定義）、Issue-0034（非コード成果物の確定前レビュー工程がない）
- **根拠 ADR**: ADR-0066（常時適用 / 条件発火の分割）、ADR-0067（新規スキル＋接続の記述）、ADR-0069（拡張先は自 repo）、ADR-0070（規範文で実装）、ADR-0071（条件発火の発火判定）、ADR-0072（確定前レビューの発動条件）、ADR-0073（根拠・世代の記録と規範の廃止条件）、ADR-0093（破壊的検証の委譲制約と受け取り時確認）、ADR-0117（前提実在観点・前提検査・受け取り時義務の追加）、ADR-0120（初回体数の型別既定・通算回数の分布外検知）

## 全体像

`subagent-dispatch` は委譲プロンプトの制約を組み立て、`pre-finalization-review` は計画・仕様の確定前レビューを担う。委譲の要否・タスク分割は呼び出し側のスキルが判断する。

2 スキルの関係は一方向である。`pre-finalization-review` は4観点を1〜4体の独立サブエージェントへ割り当て、その委譲プロンプトを `subagent-dispatch` で組む。逆向きの依存はない。追加する仕組みの費用はレビューの集約時に比較し、新設を含むADRへの記載要件は `CONTRIBUTING.md` が定める（ADR-0124・0125）。

```
（任意のスキル実行中に委譲が発生）
        │
        ▼
  subagent-dispatch ──── 委譲プロンプトの制約ブロックを組む
        ▲
        │ 観点の委譲に使う
        │
  pre-finalization-review ──── 計画・仕様の確定前レビュー
        ▲
        │ ユーザー指示で発動
   start-work Phase 2
```

## スキル1: `subagent-dispatch`

### 責務

サブエージェントへ委譲する直前に、委譲プロンプトへ入れる制約ブロックを組み立てる。委譲の要否・分割の仕方は扱わない（既存の superpowers スキルの責務）。

### 発動

委譲の直前。タスクの型を問わず毎回。`start-work` の作業前の確認から接続する。委譲は「作業意図」ではなくどのスキルの最中にも起きるため、Phase 2 のマッピング表（作業意図 → スキル）には載せない。

### 構成

**常時適用（無条件・4 件）**: 判断を挟まず毎回含める。禁止と報告義務であり、委譲先の作業量を増やさない（ADR-0066）。

1. 指示と実態が食い違ったら実態を優先し、理由を添えて報告すること
2. 既存（pre-existing）のファイル・ディレクトリの削除は事前承認を要すること
3. 本タスクの範囲外の作業（handoff 更新・ADR 作成など）はしないこと
4. 副エージェントを起動しないこと／起動する場合は制約を継承させること

**条件発火（6 条件 12 項目）**: 委譲先の作業量を増やすため、タスクの型で発火させる。6 行の表を毎回読み下ろし、判定結果を委譲プロンプト冒頭へ 1 行で残す（ADR-0071）。

判定行の形式:

```
条件発火判定: 検査=yes / ミューテーション=no / 並列書き換え=no / 計画実装=no / 長時間書き込み=no / 破壊的検証=no
```

該当した行の項目のみを本文へ展開する。

| 発火条件 | 展開する項目 |
|---|---|
| 検査・監査・走査を委譲するとき | 検査対象は全数走査し、対象の総数を明示すること / 実証を伴わない指摘は採用しないこと |
| ミューテーション検査を委譲するとき | **（適用例）** 変異対象の実在を先に確認してから指示すること / 各変異行に「その変異を検出できる入力」を併記させ、書けない行は等価変異として扱うこと / throw を投げるだけの検査を RED 件数から除外すること |
| 並列に委譲し、かつ委譲先がファイルを書き換えるとき | worktree または `git archive` による隔離コピーを与えること / 隔離コピー内でもすべてのファイル操作で絶対パスを使わせること |
| 計画に基づく実装を委譲するとき | 計画に書かれた期待値は以降のタスク増減で陳腐化するため、現在の実測値と計画の古い期待値の両方を渡すこと |
| 長時間かつ書き込みを伴う作業を委譲するとき | 複数コミットへ分割し、中断時の復旧単位を作らせること |
| 破壊的検証（書き換えを成果物として残さない検証・実験）を委譲するとき | サブエージェントを隔離コピー内で起動するツール機構を第一選択（プロセスの作業ディレクトリの隔離を確認）とし、手動複製はコピー元・コピー先・手段を明記。隔離コピーが現作業ツリー状態を含むことを確認し、並列は隔離を委譲ごとに分けること / 絶対パスを使わせ、破壊的な書き込み先が隔離ルート配下であることを照合させること / 対象範囲の内容ハッシュを前後比較させ、想定外の差分と復旧の有無を報告させること |

担保の本体は「委譲の時点で、その時点の表の**全行**を読み下ろし、判定行を残すこと」である。表の行構成そのものは固定ではなく、worklog の実測にもとづき見直してよい（ADR-0073。条件の追加・入れ替えは新しいプロジェクト型・作業様式の観測が根拠になる）。

破壊的検証の委譲では、委譲側は受け取り時に委譲先の報告のみへ依存せず、自ら状態比較を実行して確認する（ADR-0093）。検査・監査・走査の委譲では、受け取った指摘の採否で、実証を伴う指摘でも守るもの・前提の実在を委譲側が検査する（ADR-0117。確定前レビュー経路の正本は pre-finalization-review の `references/review-procedure.md` 手順 5）。実装、または実装時レビュー（仕様適合・コード品質等）の委譲では、`skills/start-work/references/plan-deviation-defaults.md`（計画逸脱判断の既定の正本）の注入項目を委譲プロンプトへ含めることを確認する（ADR-0119）。

「ミューテーション検査」条件に紐づく 3 項目は**拘束的規範ではなく適用例**である。根拠 8 件全件が単一プロジェクト（LoopForAlpha）のテスト運用出所のため、委譲側は例を出発点に対象プロジェクトのテスト文化へ合わせて調整する（ADR-0073）。

### 設計上の制約

- 各制約には**根拠を 1 行添える**。根拠のない禁止は委譲先が黙って迂回する。Issue-0033 の根拠エントリには、実装者が指示に黙って従っていれば品質が下がった例が 2 回記録されている
- 根拠の 1 行には**根拠エントリ id（または Issue 番号）と、その delta が観測されたモデル世代**を含める（ADR-0073）。項目を反証可能にし、廃止の判断の材料にするため
- **廃止規範**: 項目に対応する同型 delta が長期にわたり中央ストアへ現れない場合、その項目は廃止候補としてユーザーへ提案する。廃止の判断はユーザーが行う。検出の機械化（`worklog-extract` への組み込み）は Issue-0048（それまで検出は棚卸し時・ユーザー指示時の手動）
- 塞ぐのは**想起漏れ**（表を見ない）であり、**判定誤り**（見た上で間違える）は塞がない。両者は判定行の有無で証跡上区別できる

## スキル2: `pre-finalization-review`

### 責務

計画・仕様など非コード成果物について、確定前レビューを提示し、ユーザーの指示に応じて実証を伴う独立レビューを実施する。

| ファイル | 責務・読む時点 |
|---|---|
| `skills/pre-finalization-review/SKILL.md` | 確定点での提示、初回の強い推奨、方式・人数の判断、4観点。初回提示で読む |
| 同 `references/iteration-norms.md` | 反復提示、増設と回数の注意喚起、停止条件、実施方式、退避と継続レビュアー。反復提示・実施で読む |
| 同 `references/review-procedure.md` | 独立レビューの実施、実証、指摘ごとの前提・費用比較、修正と報告。実施時に読む |
| 同 `references/examples-and-evidence.md` | 非拘束の適用例、出所、モデル世代、廃止条件。観点の検討・廃止判断で読む |

推奨に使う共通の判断材料と短い説明の正本は SKILL.md に置く。反復側はこれを参照し、反復固有の注意喚起・実施・停止を定める。条文を両方に複写しない。

### 発動

**ユーザーが実施を指示したときのみ**（ADR-0072）。規模・不可逆性による自動必須化は行わない。`start-work` が確定点（spec 確定点 / plan 確定点）で**毎回提示する**（発動の判断はユーザーに残るが、判断の機会を作る責務は AI 側にある）。確定点の定義・提示内の推奨順位を含む発動・提示規則の正本は `pre-finalization-review` の「確定点での提示（提示規則）」である（ADR-0080）。

### 初回の強い推奨と方式・人数の判断（ADR-0124）

変更対象に未レビューの規範・手順内容を含む場合は、最低1回の独立したフル実施を強く推奨する。4観点を覆うことと人数は分け、担当は1〜4体で判断する。誤記修正・表現の圧縮・参照の張り替えだけの変更は対象外とする。実装計画自身の遂行指示を恒久的な規範と扱わない。レビュー済み上流から写した内容は重ねて未レビューとせず、反復は専用の提示手順で扱う。記録が確認できない場合と判定に迷う場合は、未レビュー側として強く推奨する。

方式・人数は、初回・反復とも次の材料を読んで判断する。材料ごとの点数・閾値・全欄記入は設けない。

- 何がレビュー済みで、何が未確認か。変更が追加・削除・修正のどれで、どこへ影響するか。
- 直近の指摘が元の設計から出ているか、直前の修正から出ているか。確認範囲を絞った場合に落ちる条件は何か。
- 残る懸念を機械検証・差分再確認・全体レビューのどれで確認できるか。後続検証に委ねる場合は、実在する検証がその懸念を扱うか。
- 独立した目を増やす便益と、重複確認・トークン・経過時間・利用者の関与の費用。実測でない見積りはその旨を示す。

初回の強い推奨を満たした後の反復では、新規の規範文があるという理由だけで全体レビューを固定推奨しない。初回・反復とも成果物の型だけで4体を固定しない。「締めモード」や「骨格安定」は方式を自動選択する条件にしない。判断に迷う場合は懸念の確認範囲を広く取る側（方式が未決ならフル実施、人数が未決なら観点分離）を推奨し、理由を短く示す。

成果物の2型分類と凍結・復元・迷い時の扱いは、通算回数の注意喚起に使用する。人数の自動選択には使わない。型・初回人数・概算費用の初回提示と既存の記録は維持し、1体兼務の記録先も変えない。

### 提示する内容

推奨する方式・人数とその理由、最も強い反対材料を1〜2文で示す。反対材料を特定できなければ、その旨と確認した出所を簡潔に添える。一般的な懸念を埋め草にせず、対象箇所・過去の実測を指す。

この短さは推奨理由の部分に適用する。未レビュー範囲、実施の選択肢、指摘採否と根拠、注意喚起の発火時情報を省略する根拠にはしない。詳細は既存の計画・課題ログ等を参照し、同じ情報を繰り返さない。指摘採否とレビュー実施の判断はユーザーに残す。

### 手順の骨子

1. 対象と4観点（敵対的・実装整合性・仕様適合・前提実在）を特定する。機構が守るもの・得るものを方針の正本と実体で確認する。
2. 判断した担当人数へ観点を割り当て、`subagent-dispatch` で制約を組む。モデルは成果物作成側と変える運用を維持する。前提実在観点には正本と実体の所在を渡す。
3. 計画中のコード・コマンドはスクラッチで実行し、指摘には実証を求める。
4. 書き込みを伴う検証の隔離・絶対パス・前後状態確認は `subagent-dispatch` の該当条件に従う。
5. 各指摘の前提と実体の確認箇所を確かめ、追加物を採用する案には次節の費用比較も添える。実証のない指摘を採用しない。採否は既存の反復提示で確定する。
6. 修正前に草稿を退避し、修正と採否・根拠を報告する。Accepted 済みADRの本文を改訂する場合は `decision-log` の改訂記録規定に従う。

### 追加する仕組みの採否（ADR-0125）

`review-procedure.md` の集約手順で、仕組みの新設・増設を採用する案に次を併記する。費用の比較は既存の指摘対応表・報告の中で行う。

| 判断材料 | 確認する内容 |
|---|---|
| 防ぐ失敗 | 発生の実測、または対象の実体で再現可能な到達経路。未発生であることだけを不採用理由にしない |
| 代替案 | 既存工程の文言修正、簡素化、リスク受容で要求を満たせるか |
| 費用 | 導入・運用・保守・副作用。今回だけ使うものか、継続して維持するものか。後者は将来の更新・実行・整合維持の負担も示す |

満たすべき要求を確認し、その要求を満たす案の費用を比較する。過去の事故が無いという理由で、実証された初回の失敗を放置しない。単に想像できるというだけの失敗や、架空の費用値を判断根拠にしない。

CONTRIBUTING.md の新設の評価可能性には、新設を含むADRの既存比較欄へ同じ観点を記載する要件を置く。比較義務の記録先・確認時点は同節の正本を使い、期待検出量・廃止条件を維持する。費用側の評価は既存の集約とADR記載へ組み込み、独立した審査工程・点数表・台帳は設けない。

### 反復の実施と歯止め

| 方式 | 確認範囲・担当 |
|---|---|
| フル実施 | 成果物全体を4観点で確認。1〜4体・新規レビュアー |
| 差分再確認 | 改訂箇所と前回指摘の対応表、および変更が影響する上流条件・限定列挙・完了基準。1体 |
| 機械検証 | 残る確認事項が機械判定できる場合に実行。レビュアーを立てず回数に数えない |

差分再確認の委譲時には、退避した草稿またはgit差分から改訂箇所を全数列挙し、影響する上流の確認箇所も渡す。上流側に差分が無くても対象から外さない。影響範囲を確定できない場合はその不確実性を全体レビュー側の判断材料とする。

継続レビュアーは差分再確認に限る。追送機能の能力条件、失敗時の新規レビュアーへの切り替え、新規規範文・設計を含む改訂での新規レビュアー優先、骨格安定時の既存例外は維持する。これらの実施条件を、推奨の自由度によって解除しない。改訂前退避の対象・保存場所・比較方法も現行規定を維持する。

増設を含む改訂が2回連続した場合は、増設の必要性と縮小余地を点検する。増設の計数は方式の種類を問わず、計数材料がセッションを跨いで失われた場合は直近の改訂差分（退避・git）から判断できる範囲で判断する。既存要求の充足や必要な検査を、追加物が自ら生む問題と区別する。合理的な縮小案がある場合は対象と失う保護を示し、設計縮小を選択肢に加える。無い場合は理由を短く示し、削減案を作るために上流要求を破らない。縮小の承認と反映後の再提示は維持する。増設が続けば次の提示でも直近の2回を材料に点検し、縮小の見送りだけで後続の必要性点検を免除しない。

フル実施と差分再確認の通算が通常型4回・規範改定型8回に達した後の各反復提示では、観測された回数の範囲を超えた注意喚起と、累積回数・続行で確認するものを示す。機械検証を通算へ数えないこと、型・回数の復元順序と不明時の注意喚起、迷い時は通常型の閾値を使うことは維持する。値は回数上限や費用の適正値ではなく、続行は選べる。

### 停止・採否・記録

反復の既存の停止条件は維持する。回数・少額・指摘件数だけで完了扱いにしない。

- 実質的な収束の第1経路: 新規の設計欠陥がなく、残指摘が直前の修正による機械検証可能なものだけである。
- 第2経路: 既存の骨格安定の判断下で、回を立てる締めの確認を1回以上行い、骨格への新規指摘がなく、全体の残指摘が機械検証可能なものか、不採用として実装時レビューへ引き継いだ精度型に限られる。

骨格安定の既存の目安（直近のフル実施2回で連続して骨格への新規指摘ゼロ、その後に骨格を変える改訂なし）、取り下げ条件、レイヤの判定、実装時レビューへ委ねる記録と採否は維持する。この判定は停止・継続レビュアーの既存条件であり、差分再確認を推奨できる唯一の入口にはしない。

指摘が無ければ再提示なしで確定へ進む。指摘を反映した場合と、不採用として確定したい場合は既存の反復提示を行い、ユーザー判断を得る。機械検証で問題を見つけて修正した場合も再提示へ戻る。実装時の独立レビューは確定前レビューの収束で代替しない。

記録先は `session-handoff` の既存書式を使う。`review=` の方式要素・回数・4種の終了状態・縮退規定、反復中の型・回数・モデル・保留中の判断・退避先・骨格安定の記載を維持する。今回専用の状態や記録欄を新設しない。

導入後の評価は、既存の計画・課題ログ・指摘対応表・ADRに残り、判断内容を復元できる事例に限る。会話だけに残る人数の推奨・上流確認箇所・費用比較まで網羅して保存する義務は追加しない。評価時は復元できた範囲と記録不足を区別し、復元不能な事例を「適用なし」「便益なし」として数えない。廃止条件の成否に必要な情報が欠ける場合は保留する（ADR-0124・0125）。

### 狙いの限定

レビューが狙うのは**構造的な誤り**である — タスクの順序、新旧の契約の食い違い、自分が足した制約が自分の検証工程を止めること、境界の抜け。

構文・スコープ・足場の接続といった局所的・機械的な誤りは主目標に置かない。直接実装すれば最初の実行で数分のうちに露見するため、計画に書いて検証を遅らせるほうが高くつく（ADR-0067、`LoopForAlpha#Issue-0054` の分析）。

## 完了基準と事例照合

仕様・ADR・実装で推奨、実施条件、停止条件を混同していないことを確認する。次の事例は今回の設計検証用であり、毎回の規範や自動テストにはしない。

| 事例・入力 | 期待する判断・動作 |
|---|---|
| 未レビューの規範内容 | 4観点の独立レビューを強く推奨するが、見送りを選べる。人数は型だけで4体に固定しない |
| 誤記のみ・レビュー済み上流の写し | 新しい未レビュー規範と誤認して初回推奨を重複させない |
| Issue-0107 事例1・14: 未確認部分や修正に懸念が集中 | 重点を絞ったフル実施や差分再確認を、規範文の有無にかかわらず推奨できる |
| 同事例2・7: 小さな必要検査と不要な中間工程 | 両者を増設回数だけで一括縮小しない。実証された初回失敗も検討対象になる |
| 同事例13・Issue-0124: 追加物の修繕が続く | 追加物の費用・簡素な代替を集約時に比較し、2回の増設後だけに検討を遅らせない |
| 移譲資料の事例7: 例外2種を4種へ変更 | 差分外の上流条件「2種に限る」を差分再確認の対象へ含める |
| 通常4回・規範改定8回、迷い時・回数不明時 | 既存の注意喚起が発火する。上限扱いで打ち切らない |
| 指摘ゼロ／指摘全不採用／機械検証後に修正 | それぞれ既存の確定・再提示経路と終了状態に従う |

実装後は各変更文書と生成物を読み、型別人数の固定推奨・新規規範文だけによる方式固定・合理性を問わない縮小推奨が残っていないこと、維持する条件と他スキルからの参照が失われていないことを確認する。既存の記法・生成物検査も通す。

部分修正対象の旧ADR5件には、新ADRへの注記があり、StatusがAcceptedのままであることを読み直して確認する。評価用の記録不足を適用機会ゼロと誤認しないことも点検する。

## 過剰適合点検（ADR-0079）

本節は今回の ADR-0124・0125 が変更する範囲の点検である。過去の委譲制約自体の再評価には拡大しない。

| 観点 | 判定 | 根拠 |
|---|---|---|
| 出所の偏り | 要是正→適用例は非拘束、方式の固定を解除 | 設計書とADRが直接引用する材料は2プロジェクトの10事例（MakeAiInstructions#Issue-0107 の1・2・4・5・6・7・8・13・14、移譲元LoopForAlpha#Issue-0109 の7）。Issue-0124は事例13と同じ観測で重複計数しない。モデル名を確認できた直接材料は claude-opus-5 と claude-sonnet-5 の2種、いずれも5世代系。記載のない事例のモデルは不明とし、多世代の再現性を主張しない |
| システム種別依存性 | 問題なし | 固定の点数や工程数を課さず、実在する要求・失敗経路を比較する。引用条件: ADR-0080の未レビュー規範への限定と除外、ADR-0107の確定前反復への限定、ADR-0120の2型・回数計数、ADR-0102の新設ADRへの限定、ADR-0119の実装時逸脱との境界を引き継ぐ |
| AIモデル/ツール依存性 | 問題なし | 推奨の適合性を特定モデルの性能へ固定しない。引用条件: 追送機能が確認できる場合のみ継続レビュアーを使う条件、実証・隔離の条件を維持する。独立性の運用は既存規範を維持し、今回の事例だけから特定モデルや人数を強制しない |
| 規範の廃止条件 | 定義済み | ADR-0124・0125の評価可能性の記載を用いる。既存の回数閾値やレビュー全体の廃止判断は `examples-and-evidence.md` の既存規定を維持する |
