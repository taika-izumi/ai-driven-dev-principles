# サブエージェント委譲スキルと確定前レビュースキルの設計

- **対象**: `skills/subagent-dispatch/`、`skills/pre-finalization-review/`
- **起点課題**: Issue-0033（委譲プロンプトの定型項目が未定義）、Issue-0034（非コード成果物の確定前レビュー工程がない）
- **根拠 ADR**: ADR-0066（A 群 / B 群の分割）、ADR-0067（新規スキル＋配線）、ADR-0069（拡張先は自 repo）、ADR-0070（規範文で実装）、ADR-0071（B 群の発火判定）、ADR-0072（確定前レビューの発動条件）、ADR-0073（根拠・世代の記録と退役経路）、ADR-0093（破壊的検証の委譲制約と受け取り時確認）

## 全体像

既存のスキル体系には、サブエージェントへの委譲を扱うスキルが「いつ委譲するか」「どう分割するか」の側にしかない（`superpowers:dispatching-parallel-agents` / `subagent-driven-development`）。**委譲プロンプトに何を書くか**を扱う工程と、**計画・仕様を確定させる前に独立レビューを通す**工程の 2 つが欠けている。この 2 つを新規スキルとして本リポジトリの `skills/` に立てる。

2 スキルの関係は一方向である。`pre-finalization-review` は 3 観点を独立サブエージェントへ委譲するため、その委譲プロンプトを `subagent-dispatch` で組む。逆向きの依存はない。

```
（任意のスキル実行中に委譲が発生）
        │
        ▼
  subagent-dispatch ──── 委譲プロンプトの制約ブロックを組む
        ▲
        │ 3 観点の委譲に使う
        │
  pre-finalization-review ──── 計画・仕様の確定前レビュー
        ▲
        │ ユーザー指示で発動
   start-work Phase 2
```

## スキル1: `subagent-dispatch`

### 責務

サブエージェントへ委譲する直前に、委譲プロンプトへ入れる制約ブロックを組み立てる。委譲の要否・分割の仕方は扱わない（既存の superpowers スキルの責務）。

### 発動

委譲の直前。タスクの型を問わず毎回。`start-work` の横断的ラッパー Pre から配線する。委譲は「作業意図」ではなくどのスキルの最中にも起きるため、Phase 2 のマッピング表（作業意図 → スキル）には載せない。

### 構成

**A 群（無条件・4 件）**: 判断を挟まず毎回含める。禁止と報告義務であり、委譲先の作業量を増やさない（ADR-0066）。

1. 指示と実態が食い違ったら実態を優先し、理由を添えて報告すること
2. 既存（pre-existing）のファイル・ディレクトリの削除は事前承認を要すること
3. 本タスクの範囲外の作業（handoff 更新・ADR 作成など）はしないこと
4. 副エージェントを起動しないこと／起動する場合は制約を継承させること

**B 群（条件発火・6 条件 12 項目）**: 委譲先の作業量を増やすため、タスクの型で発火させる。6 行の表を毎回読み下ろし、判定結果を委譲プロンプト冒頭へ 1 行で残す（ADR-0071）。

判定行の形式:

```
B群判定: 検査=yes / ミューテーション=no / 並列書き換え=no / 計画実装=no / 長時間書き込み=no / 破壊的検証=no
```

該当した行の項目のみを本文へ展開する。

| 発火条件 | 展開する項目 |
|---|---|
| 検査・監査・走査を委譲するとき | 検査対象は全数走査し、母数を明示すること / 実証を伴わない指摘は採用しないこと |
| ミューテーション検査を委譲するとき | **（適用例）** 変異対象の実在を先に確認してから指示すること / 各変異行に「その変異を検出できる入力」を併記させ、書けない行は等価変異として扱うこと / throw を投げるだけの検査を RED 件数から除外すること |
| 並列に委譲し、かつ委譲先がファイルを書き換えるとき | worktree または `git archive` による隔離コピーを与えること / 隔離コピー内でもすべてのファイル操作で絶対パスを使わせること |
| 計画に基づく実装を委譲するとき | 計画に書かれた期待値は以降のタスク増減で陳腐化するため、現在の実測値と計画の古い期待値の両方を渡すこと |
| 長時間かつ書き込みを伴う作業を委譲するとき | 複数コミットへ分割し、中断時の復旧単位を作らせること |
| 破壊的検証（書き換えを成果物として残さない検証・実験）を委譲するとき | サブエージェントを隔離コピー内で起動するツール機構を第一選択（プロセスの作業ディレクトリの隔離を確認）とし、手動複製はコピー元・コピー先・手段を明記。隔離コピーが現作業ツリー状態を含むことを確認し、並列は隔離を委譲ごとに分けること / 絶対パスを使わせ、破壊的な書き込み先が隔離ルート配下であることを突合させること / 対象範囲の内容ハッシュを前後比較させ、想定外の差分と復旧の有無を報告させること |

担保の本体は「委譲の時点で、その時点の表の**全行**を読み下ろし、判定行を残すこと」である。表の行構成そのものは固定ではなく、worklog の実測にもとづき見直してよい（ADR-0073。条件の追加・入れ替えは新しいプロジェクト型・作業様式の観測が根拠になる）。

破壊的検証の委譲では、委譲側は受け取り時に委譲先の報告のみへ依存せず、自ら状態比較を実行して確認する（ADR-0093）。

「ミューテーション検査」条件に紐づく 3 項目は**拘束的規範ではなく適用例**である。根拠 8 件全件が単一プロジェクト（LoopForAlpha）のテスト運用出所のため、委譲側は例を出発点に対象プロジェクトのテスト文化へ合わせて調整する（ADR-0073）。

### 設計上の制約

- 各制約には**根拠を 1 行添える**。根拠のない禁止は委譲先が黙って迂回する。Issue-0033 の根拠エントリには、実装者が指示に黙って従っていれば品質が下がった例が 2 回記録されている
- 根拠の 1 行には**根拠エントリ id（または Issue 番号）と、その delta が観測されたモデル世代**を含める（ADR-0073）。項目を反証可能にし、退役判断の材料にするため
- **退役規範**: 項目に対応する同型 delta が長期にわたり中央ストアへ現れない場合、その項目は退役候補としてユーザーへ提案する。退役の判断はユーザーが行う。検出の機械化（`worklog-extract` への組み込み）は Issue-0048（それまで検出は棚卸し時・ユーザー指示時の手動）
- 塞ぐのは**想起漏れ**（表を見ない）であり、**判定誤り**（見た上で間違える）は塞がない。両者は判定行の有無で証跡上区別できる

## スキル2: `pre-finalization-review`

### 責務

計画・仕様など非コード成果物を確定させる前に、実証を課した独立レビューを実施する。

### 発動

**ユーザーが実施を指示したときのみ**（ADR-0072）。規模・不可逆性による自動必須化は行わない。ただし `start-work` Phase 2 のマッピング表へ行を追加し、`writing-plans` / `feature-block-design` 完了後の次手として**毎回提示する**。発動の判断はユーザーに残るが、判断の機会を作る責務は AI 側にある。

### 手順の骨子

1. 対象成果物とレビュー観点 3 つを立てる（敵対的 / 実装整合性 / 仕様適合）
2. 各観点を独立サブエージェントへ委譲する。**モデルは前工程のレビューと変える**
3. **実証を課す** — 計画中のコードをスクラッチで実際に走らせる。「読んだ限り妥当」は成果物として受け取らない
4. レビュアーが写経実行等でファイルを書き換える場合の隔離・絶対パス・前後状態比較は、`subagent-dispatch` B 群の該当条件（破壊的検証・並列書き換え）に従う（ADR-0093）
5. 指摘を集約する。実証の伴わない指摘は採用しない
6. 対象文書を修正し、ユーザーへ報告する

### 狙いの限定

レビューが狙うのは**構造的な誤り**である — タスクの順序、新旧の契約の食い違い、自分が足した制約が自分の検証工程を止めること、境界の抜け。

構文・スコープ・足場の配線といった局所的・機械的な誤りは主目標に置かない。直接実装すれば最初の実行で数分のうちに露見するため、計画に書いて検証を遅らせるほうが高くつく（ADR-0067、`LoopForAlpha#Issue-0054` の分析）。

## 適用しなかった設計判断

- **フックによる A 群の機械注入**: 技術的には可能だが Claude Code 固有でツール中立性を欠くため採らない（ADR-0070）。調査結果は Issue-0047 に保存済み
- **`feature-block-design` の適用**: 主要機能 2 つで数の上では該当するが、2 スキルは独立した SKILL.md 1 ファイルずつで依存が一方向のみであり、ブロック間インターフェースの設計余地がない。ディレクトリ分割仕様書は作らない
