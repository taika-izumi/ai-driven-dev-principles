# 01: 出所識別子の記法規約

## 対象ファイル

- `CONTRIBUTING.md` — 規約本体と執行点を置く（新設節「全シナリオ共通: 配布対象ソースの記法規約」）
- `skills/extend-guidelines/SKILL.md` — 拡張フローから規約と執行点を参照する（手順 6 の拡張）

## 責務

配布対象ソースにおける出所識別子の書き方を、生成器が位置だけで判別できる形に規約化する。規約が守られていれば、識別子の除去は文脈解釈なしに機械的に実行できる。

## 出所識別子の定義

次の 5 種類を出所識別子と呼び、規約と変換の対象とする。

| # | 種別 | 形 | 例 |
|---|---|---|---|
| 1 | 決定記録番号 | `ADR-` ＋ 4 桁の数字 | `ADR-0080` |
| 2 | 課題番号 | `Issue-` ＋ 4 桁の数字 | `Issue-0033` |
| 3 | クロスリポジトリ修飾参照 | `<Repo>#` ＋ 上記 | `LoopForAlpha#Issue-0069` |
| 4 | worklog エントリ id | `<Project>-YYYY-MM-DD-NN`、およびプロジェクト名を省いた `-YYYY-MM-DD-NN` | `MakeAiInstructions-2026-08-07-04`、`-2026-08-01-03` |
| 5 | 出所注記 | `（出所: …）` の括弧全体 | `（出所: LoopForAlpha）` |

種別 4 には、同一行で 2 件目以降を書くときの省略形（`-2026-08-01-03`）を含める。この記法は `subagent-dispatch/SKILL.md` と `Issue-0033` で常用されており、省略形を除外すると配布物に残る。

種別 5 は、プロジェクト名のように型で書けない出所を入れる受け皿である。括弧ごと削除されるため、生成器がプロジェクト名の一覧を持つ必要がない。**種別 5 は括弧の内側ではなく括弧そのものが識別子である**ため、R1 では独立した位置として扱う（下記 (c)）。

### プレースホルダの判別

**プレースホルダは出所識別子ではない。** 判別規則は種別ごとに異なる。

| 種別 | プレースホルダの判別 |
|---|---|
| 1〜3 | 4 桁の数字を持たない（`ADR-NNNN` / `Issue-NNNN` / `<repo>#Issue-NNNN`） |
| 4 | プロジェクト名部が**中立名の許可リスト**（`X` / `Proj`）のいずれかである（`X-2026-01-01-01` 等） |
| 5 | 該当なし（出所注記に書式例を書かない） |

種別 4 は日付部に 4 桁の年を含むため、「4 桁の数字を持つか」では判別できない。中立名を明示列挙することで、サンプル値とテストフィクスチャを規約の外に置く。

**山括弧のプレースホルダ（`<project>-2026-01-01-01`）は使えない。** 種別 4 の正規表現はプロジェクト名部に英数字始まりを要求するため、この形は「プロジェクト名を省いた省略形」と解釈され、中立名の判別に到達しない（2026-08-08 実測。フェンス外なら R2、フェンス内なら R4 になる）。worklog id のサンプルは `X` か `Proj` で書く。

## 適用範囲

**配布対象ソース**にのみ適用する。判定は観測可能な 3 条件で行う。

1. `template.manifest` に記載されているファイル（現在 4 ファイル）
2. `skills/` 配下のファイル
3. `sync-template.ps1` が空インデックスを生成する 3 ファイル（`docs/records/decisions/README.md` / `docs/records/retrospectives/README.md` / `docs/working/issues/README.md`）。**判定対象は空インデックス化後の内容とする**

条件 3 の限定は必須である。ソースのままだと `docs/records/retrospectives/README.md` は一覧テーブルのデータ行が違反として大量に検出されるが、それらは空インデックス化で除去され配布物に届かない。

**スクリプトファイル（`.py` / `.ps1`）は機械判定の対象をコメント行のみとする。** コード中のテストフィクスチャ（`X-2026-01-01-01` 等の架空データ）を規約で縛らないため。

ただし**判定対象と規約の適用対象は一致しない**。スクリプト内であっても、**配布先の読み手・利用者が読むテキスト**——モジュールや関数の説明文字列（docstring）、実行時に出力されるメッセージ——は散文であってフィクスチャではないため、規約を適用し、出所識別子を含めない。機械判定が届かないため、これらは書き手が守る（検査の自動化は将来課題。Issue-0070）。

判定の届く範囲と規約の及ぶ範囲の対応:

| スクリプト内の箇所 | 機械判定 | 規約の適用 |
|---|---|---|
| `#` で始まるコメント行 | する | する |
| docstring・利用者へ表示する文字列 | しない | **する（書き手が守る）** |
| テストフィクスチャ・その他のコード | しない | しない |

`docs/` 配下のその他のファイルは適用外であり、従来どおり自由に書いてよい。

本規約は既存記述へ遡及適用する（ブロック 05）。本リポジトリ内の記述に遡及しない ADR-0068 とは適用対象が異なる。

## 規約

| # | 規約 | 理由 |
|---|---|---|
| **R1** | 出所識別子は 3 つの位置にのみ書く: **(a) 全角括弧 `（…）` の内側**、**(b) 出所リスト行**、**(c) 出所注記 `（出所: …）` の形** | 生成器が位置だけで判別できるようにする。(c) は括弧そのものが識別子であるため (a) とは別位置として扱う |
| **R2** | 本文の文法要素として出所識別子を使わない | `出力ファイルは ADR-0011（時系列追記型）に従い` は違反。`出力ファイルは時系列追記型（ADR-0011）に従い` と書く |
| **R3** | 出所リスト行は `- <識別子>: <説明>` のコロン形に統一する。複数の識別子は `/` または `〜` で連結し、その直後にコロンを置く（下記「複数識別子の記法」を参照） | 括弧形の手順文と機械的に区別する |
| **R4** | コードフェンス内に出所識別子を書かない | 配布先ファイルへ複写される書式テンプレートも、読まれるだけの例示データも対象 |
| **R5** | 書式例・サンプル値はプレースホルダまたは中立名で書く。**対象は識別子 5 種に限らず、実在のプロジェクト名・実在の絶対パス・実在の文書名を含む** | 実在を指す識別子を例示に使わない。書式例と実参照を「4 桁の数字を持つか」で区別できるようにする。識別子以外の実在の固有名も配布先では解決できないため同じく中立名にする |

### R5 の対象が識別子に限らない理由（実例）

R1〜R4 は識別子の位置の規約であり、生成器が機械的に判定できる。**R5 だけは位置規約ではなく、機械判定できない。** 対象を識別子 5 種に限ると、次のような書式例が検査を素通りして配布物へ出荷される（2026-08-08 の実測）。

```
違反: { "MakeAiInstructions": { "path": "D:/Dev/002_AiDev/MakeAiInstructions", … } }
適合: { "X": { "path": "/path/to/X", … } }

違反: - 書式: `<repo>#Issue-NNNN`（例: `LoopForAlpha#Issue-0069`）
適合: - 書式: `<repo>#Issue-NNNN`（例: `OtherProject#Issue-NNNN`）
```

実在のプロジェクト名も開発機の絶対パスも識別子 5 種のいずれにも当たらないため、生成器は違反として検出しない。**したがって R5 の確認は目視で行う。** 配布物のコードフェンス内のサンプル値を全数読み、実在の固有名が残っていないか確かめる（2026-08-08 の実測では、目視の 1 巡目で 1 件を拾い 1 件を取り逃がした。取り逃としは配布物を通読するレビューで検出された）。

### R3 が必要な理由（実例）

`skills/retrospective/SKILL.md:53` には次の行がある。

```
- ADR-0006（意思決定の継続検出ルール）は本スキル中も常時適用される。ただし retrospective 内では対策の採否を決めないため、retrospective 起因の ADR 起票は発生しない
```

行頭の形は出所リスト行と同じだが、中身は手順文である。「識別子で始まるリスト行を削除する」規則はこの手順を静かに削除する。R3 によって出所リスト行をコロン形へ固定すると、括弧形で始まる行は手順文と判定でき、生成器はそれを R3 違反として停止できる。

### 複数識別子の記法

```
適合: - ADR-0048〜0053: v1.1 改訂（model 必須・スキーマ版数・id 採番強化 ほか）
違反: - ADR-0048〜0053（v1.1 改訂: model 必須・スキーマ版数・id 採番強化 ほか）
```

**2 件目以降は 4 桁の数字だけを書く。** 前置（`ADR-` / `Issue-`）を繰り返した形と、異なる種別を連結した形は R3 違反になる（2026-08-08 の実測で判定を確認）。

```
適合: - ADR-0084/0085: 説明
違反: - ADR-0084/ADR-0085: 説明        ← 前置の繰り返し
違反: - ADR-0084 / Issue-0033: 説明    ← 異種の連結。行を分ける
違反: - ADR-0084                        ← 説明の省略
```

範囲記法（`〜`）は**一体の決定**に使う。独立した 2 つの決定を 1 行にまとめると、どちらの識別子がどちらの説明に対応するか読めなくなるため、行を分ける。

### 書式の細目

区切りは**半角コロン＋半角スペース 1 個**に統一する。全角コロン（`：`）やスペースなし（`:説明`）は生成器の判定を通過してしまうため、規約側で書式を指定する。

**出所リスト行は出所の索引であり、規範文・手順文を書く場所ではない。** 出所リスト行は配布物から行ごと削除されるため、手順文を書くと配布先で消える（下記「R3 が必要な理由」の実例がこの型である）。

## インターフェース

本ブロックは文書上の契約であり、実行時インターフェースを持たない。契約の消費者は次の 2 つ。

- **ブロック 02（配布物生成器）** — 規約を判定規則として実装し、違反を検出する
- **保守者** — 配布対象ソースを編集するときに従う

## 執行点

`CONTRIBUTING.md` に次を書く。

- **「全シナリオ共通: 配布対象ソースの記法規約」節** — 出所識別子の定義、適用範囲 3 条件、R1〜R5、実例
- **執行点** — 配布対象ソースを変更したら、コミット前に `scripts/build-dist.ps1` と `scripts/sync-template.ps1` を実行する。規約違反があればいずれかが非ゼロ終了するため、修正しない限りコミットできる状態にならない
- **陳腐化の検査** — コミット前に両生成器を `-Check` で実行し、生成漏れが無いことを確認する
- **既存シナリオへの配線** — 配布対象ソースを編集するシナリオのチェックリストへ、規約適合の確認項目を 1 行ずつ追加する（計 5 行）。`skills/` 配下を編集する 4 シナリオ（「Skillを新規作成・改定するとき」「ワークフロー起点スキル（start-work）を変更するとき」「機能ブロック駆動の設計スキル（feature-block-design）を変更するとき」「振り返りスキル（retrospective）を変更するとき」）は `build-dist.ps1` で確認する。`template.manifest` 記載ファイルを編集する「原則を追加・変更するとき」は `sync-template.ps1` で確認する（「CLAUDE.md を更新するとき」は手順に `sync-template.ps1` の実行が既にあるため配線済みとみなす）

`skills/extend-guidelines/SKILL.md` の手順 6（テンプレートの同期を案内する）を、配布物生成の案内へ拡張する。`skills/` を変更した場合も生成が必要になるため、現行の「テンプレート対象を変更した場合のみ `sync-template.ps1`」という案内では不足する。

## このブロック固有の制約・前提

- **R2 は自然な日本語の語順を一部禁じる。** 「ADR-NNNN に従い」と書けなくなるため、書き手に負担が生じる。この負担は、生成器が文脈解釈なしに動作するための対価である
- **規約は配布されない。** `CONTRIBUTING.md` は `template.manifest` に含まれないため、配布先プロジェクトがこの規約に拘束されることはない
- **ソース側は出所の累積記録として維持する。** 識別子をソースから消さないのは、後日ほかのプロジェクトで同型の事象が観測されたときに「単一プロジェクト由来」から「複数プロジェクト由来」への更新を判断できるようにするためである（ADR-0073 の見直し経路の前提）
- 規約の追加は ADR-0079 の過剰適合点検の対象である。点検結果は `00-overview.md` の該当節に記録済み
