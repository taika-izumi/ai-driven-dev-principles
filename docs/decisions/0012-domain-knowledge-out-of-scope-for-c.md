# ADR-0012: ドメイン知識抽出は次サイクル課題

- **Status**: Proposed
- **Date**: 2026-05-01

## Context

サブプロジェクトC（振り返りフェーズ導入）の brainstorming 中、ユーザーから「専門家とAIの会話に含まれるドメイン知識を抽出・整理することが重要ではないか」という論点が提起された。具体的にはビジネスルール、用語マッピング、歴史的経緯、不可視な制約、暗黙の標準、ステークホルダー嗜好などが該当する。

これらは:

- 公開コーパスで事前学習されたAIには含まれない
- コードや ADR には背景までは残らない
- 会話ログには散在するが構造化されておらず再利用困難

という性質を持ち、サブプロジェクト間で持ち越せる価値が高い。

問題は、これを本サブプロジェクトCのスコープに含めるかどうかである。

## Decision

ドメイン知識抽出は本サブプロジェクトCでは扱わない。**本サブプロジェクトC完了直後の初回 retrospective において、最重要 Improvement Draft として正式に提案議題化する**。実装はサブプロジェクトD（仮称: knowledge-distillation）として別サイクルで扱う。

## Alternatives Considered

- **α: retrospective テンプレートに「Domain Knowledge」セクションを1つ追加**: 暫定処置として最小コストだが、「暫定で入れたら永遠にそのまま」になりがちなアンチパターン。ドメイン知識の重要性に対してテンプレ1セクションは軽すぎる
- **β: 同時に knowledge-distillation スキルを設計・実装**: 効果的だが本サブプロジェクトCのスコープを膨張させ、原則2（関心の分離）に反する。サブプロジェクトCの設計途中で別スキル設計を始めると、retrospective スキル自体の設計品質も下がる
- **γ: 現スコープを維持し、初回 retrospective で議題化** = **採用**: 原則2を保ちつつ、retrospective スキル自体の実効性を「初回でドメイン知識抽出案が抽出される」という形で証明できる（ドッグフーディング）

## Consequences

- 本サブプロジェクトCのスコープが clean に保たれる
- 初回 retrospective の Improvement Drafts に「knowledge-distillation スキル新設」案が確実に含まれることになる（仕様書 §6.4 完了基準として明記）
- ドメイン知識抽出機能の実装は1サイクル遅れる。その間、ドメイン知識は引き続き会話ログに散在する状態が続く
- サブプロジェクトDの起点が決まる（次セッション開始時の handoff にも明記）
