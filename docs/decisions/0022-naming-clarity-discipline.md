# ADR-0022: AIの言葉遣いの明確性規範を copilot-instructions に追加

- **Status**: Proposed
- **Date**: 2026-06-15

## Context

ユーザーから、ハンドオフ等の成果物ドキュメントや対話の中で AI がプロジェクト固有の用語や、その場限りで定義のない略号・記号的呼称（例: 「Aモード」「Primary では入れず Secondary 検証へ降格」）を使い、後から見返した際に正確な意味をつかみ損ねるというフィードバックがあった（`docs/conversation_log.md` 206-208行目, Theme C）。

このフィードバックには2つの異なる問題が含まれていた:

- 問題A（成果物の用語）: プロジェクト固有のドメイン用語を一元管理する用語集（ユビキタス言語）の仕組みが無い。
- 問題B（AIの即興用語）: AI がその場限りの意味不明な略号・記号的呼称を使い、説明的でない。

この2つは対策の置き場も性質も異なるため、今サイクルで両方を一度に扱うかが論点となった。

## Considered Alternatives

スコープについて:

- **両方（A+B）を今サイクルで対応**: 用語集ドキュメントとその管理フロー（問題A）は置き場・作成タイミング・管理スキルの設計を要し、規模が大きい。Bと混ぜると1サイクルの焦点がぼやける。
- **問題Aのみ**: フィードバックの即時改善（AIの言葉遣い）が後回しになる。
- **問題Bのみ（採用）**: 小規模で即効性が高く、既存の個人メモリ（説明的名称を使う旨）をリポジトリのガイドラインへ昇格させるだけで完結する。

問題Bを置く層について:

- **アプローチA（採用）: Layer 2 のみ**。`.github/copilot-instructions.md` の「コンテキスト管理」セクションに行動規範を追加する。原則3（コンテキストの明示的管理）の系。`principles.md` は変更しない。「各層は独立して拡張可能・即時の全層反映は不要」という設計思想（ADR-0001）に沿う。Skill化は常時適用の単純な規範には過剰（YAGNI）。
- **アプローチB: Layer 1 ＋ Layer 2**。原則3本文に読み手への明示性を補足する。普遍原則として明文化できるが、原則3の責務が膨らむ。
- **アプローチC: 新原則を追加（5→6原則）**。表現規範は他原則（開発プロセス原則）と粒度が不揃いで過剰。

## Decision

Theme C のスコープを**問題B（AIの言葉遣いの明確性）に限定**し、問題A（用語集の仕組み）は別サイクルに送る。

問題Bへの対策として**アプローチA**を採用する。`.github/copilot-instructions.md` の「メタ・ガイドライン > コンテキスト管理」セクションに、以下2点の行動規範を追加する:

1. 対話・成果物ドキュメント（ハンドオフ/仕様書/ADR等）で用語を使うときは、文章だけを読んで意味が推測できる説明的な表現を用いる。「Aモード」「Primary/Secondary」のような、その場限りで定義のない略号・記号的呼称は使わない。
2. 初出のプロジェクト固有用語には簡潔な説明を添える。

適用範囲は対話と成果物ドキュメントの両方。`principles.md`（Layer 1）と Skill は変更しない。`copilot-instructions.md` は template 対象のため `scripts/sync-template.ps1` で同期する。

## Consequences

- 良い影響: ハンドオフ等を後から見返した際に意味をつかみ損ねる事態が減る。既存の個人メモリに依存していた規範がリポジトリ共有のガイドラインに昇格し、全コントリビューターに適用される。小規模変更で即効性がある。
- 良い影響: 原則を増やさないため、5原則の構成とリスクスケーリング表を維持できる。
- 留意点: 問題A（プロジェクト固有用語集の仕組み）は未対応のまま残る。別サイクルで設計するか、ハンドオフのバックログとして管理する。
- 留意点: 行動規範の遵守は AI の自律判断に委ねられ、強制力は copilot-instructions の指示の効きに依存する。
