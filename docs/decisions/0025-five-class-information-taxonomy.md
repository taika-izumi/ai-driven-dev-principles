# ADR-0025: 情報の5分類体系を導入し、ドキュメント構成を全面再配置する

- **Status**: Accepted
- **Date**: 2026-07-04

## Context

本ガイドラインのドキュメント配置規約（`docs/specs/`、`docs/plans/`、`docs/decisions/`、`docs/handoff/`、`docs/retrospectives/`、`docs/open-questions.md`）は各スキル・ADR に断片的に定義されており、開発プロジェクト全体のフォルダ構成を体系的に定義した規範が存在しない。このため、規約に列挙されていない種類のドキュメント（議事録、用語集、リリース手順など）の置き場が開発時のAIの都度判断に委ねられてしまう。

ユーザーが別プロジェクト（小規模・サービス展開済み・ソリューションPL体制）で「情報の更新頻度とライフサイクルの長さ」による情報分類（オリエンテーション層 / 現在の正 / 追跡型の記録 / 参照知識）を実践した経験があり、これを出発点として本ガイドラインに体系的なフォルダ構成定義を追加する。

要件:

- 開発するプロジェクトの性質（純粋なコード開発 / AI駆動システム開発など）に依存しない構成であること
- ソースコード等の配置についても、抽象度の高い原則レベルでは定義すること（完全にAIの都度判断に委ねない）
- 実際のシステム開発プロジェクトで発生しうる情報・ドキュメントを分類して保存しきれること

## Considered Alternatives

### 分類体系について

1. **4分類（オリエンテーション / 現在の正 / 追跡型の記録 / 参照知識）をそのまま採用** — ユーザーの別プロジェクトでの実績があるが、handoff・実装計画・課題（issue）のような「更新頻度が高く、寿命が短く、いずれクローズされる情報」の収まりが悪く、仕様書等の置き場が定義できない歪みが残る
2. **5分類に精緻化** — 4分類に「進行中の作業」を加える。実プロジェクトで発生しうるドキュメント種別（要件・仕様・設計、課題、handoff、計画、ADR、議事録、リリースノート、インシデント報告、runbook、既知エラー、調査メモ、FAQ 等）でストレステストし、網羅できることを確認した
3. **2軸マトリクス（更新頻度 × 確定度）** — 理論上は網羅的だが、日々の配置判断のたびに2軸を参照する運用コストが高い

### 既存 docs 配置規約との関係について

1. **既存パス維持＋体系付与** — 低リスクだが、既存ドキュメント間の内容重複（例: `docs/open-questions.md` と課題管理）が解消されず、分類の歪みが残る
2. **分類体系に基づく全面再配置** — 既存ドキュメントの内容を踏まえて情報を分類し直し、フォルダ構成を再編成する。スキル・テンプレートのパス修正を伴う

### 本リポジトリへの適用について

1. **本リポジトリ自身にも適用（ドッグフーディング）** — スキルのパス修正と実データ移行が同時に検証でき、体系の実用性を自分で確かめられる
2. **定義・スキル修正のみ先行** — サイクルは小さいが、移行までの間スキルと実フォルダが不整合になる
3. **新規適用プロジェクト専用** — 2体系並存でスキルの分岐が複雑化する

## Decision

以下の5分類を情報分類体系として採用する。分類の軸は「話題（トピック）」ではなく**情報の性質（更新様式とライフサイクルの長さ）**である:

1. **オリエンテーション** — プロジェクト参画直後のキャッチアップ情報（プロジェクト概要、用語集、ステークホルダー・体制）。低頻度更新・恒久。一時的なステータス情報は含めない
2. **現在の正** — 現時点のシステム・プロジェクトの姿（要件・仕様書、アーキテクチャ、ロードマップ）。書き換え型スナップショット・恒久
3. **進行中の作業** — 課題（issue）、handoff、実装計画。高頻度更新・短寿命・クローズされる。クローズ済み項目はステータス変更でその場に残す（アーカイブは独立分類ではなく本分類内の状態として扱う）
4. **追跡型の記録** — ADR、議事録、retrospective、リリースノート、インシデント報告。確定後不変・追記型・恒久。話題がプロジェクト全般（例: サービス運用体制の会議）であっても、時点記録という性質ならこの分類とする
5. **参照知識** — リリース手順、runbook、既知エラー、調査メモ、FAQ。低頻度改訂・恒久

あわせて以下を決定する:

- **境界の配置判断基準を定義に含める**: (a) オリエンテーション vs 参照知識 =「参画直後に全員が読むべきか / 必要時に引くものか」、(b) 現在の正 vs 参照知識 =「システム・プロジェクトそのものの姿か / 作業を支える周辺知識か」、(c) 追跡型の記録 vs 参照知識 =「出来事の時点記録（不変）か / そこから蒸留した再利用知識（改訂される）か。同じ出来事から両方を別ドキュメントとして作ってよい（蒸留規則）」
- 既存 docs 配置規約との関係は**全面再配置**とする。`docs/open-questions.md` は課題（issue）管理へ統合する
- 本ガイドラインの適用範囲はプロジェクト全体とし、ソースコード等（AI駆動システム開発におけるプロンプト・エージェント定義・評価データ等を含む）の配置は言語・パラダイム非依存の原則レベルで定義する
- **本リポジトリ自身にも新体系を適用**する（ドッグフーディング）

## Consequences

- 規約に列挙されていないドキュメント種別にも「性質で分類する」判断基準が機能し、置き場の都度判断がなくなる
- 課題管理と未決事項の重複が解消される
- パスを参照する全スキル（session-handoff、decision-log、retrospective、feature-block-design、start-work）とテンプレート・CLAUDE.md・CONTRIBUTING.md の修正、および本リポジトリの既存 docs の移行が必要になる（中規模以上の改修）
- 具体的なフォルダレイアウト・命名は本ADRのスコープ外であり、後続の設計判断で決定する
