# ADR-0019: ADR記述規律 — 決定のみ記載・未決事項の分離・承認の遅延昇格

- **Status**: Accepted（ADR-0025 で一部改定: 未決事項の置き場は docs/open-questions.md から docs/working/issues/ の課題管理へ統合）
- **Date**: 2026-06-15

## Context

ADR運用で2つの問題が観察された。

1. **未決事項の混入**: 仕様検討の議論を進める中で「まだこれから決めないといけない論点」が増えていき、それを下した意思決定とは別にADR本文へ書き込んでしまった。結果、ADRが「下した意思決定の記録」という本来の責務から逸脱した。
2. **早すぎる承認**: `decision-log` はADR作成直後に Accepted 化を促す。そのため brainstorming 中（議論が続いており決定が覆りうる段階）に Accepted となり、後で方針が変わった際に記録と実態の齟齬が生じた。

## Considered Alternatives

- **未決事項の置き場**: (a) ADR内に専用セクションで残す（現状 / 却下: ADRの責務逸脱）/ (b) 専用ドキュメント `docs/open-questions.md` に分離（採用）/ (c) 専用管理スキルを新設（YAGNI、将来未決事項が増えたら再検討）
- **未決事項のライフサイクル**: スナップショット型（解決したら行削除、採用）vs 台帳型（解決済みもResolvedで残す、二重管理になり却下）
- **承認タイミング**: (a) 即時承認のまま（現状 / 却下）/ (b) brainstorming限定で据え置き（部分対応）/ (c) 「ADRは原則Proposedで作成し、決定が確定したチェックポイントでAccepted昇格」と一般原則化（採用。既存の実装持ち越し・retrospective採用ADR運用と一貫する）

## Decision

1. **ADRには「下した決定」のみを記載する**。未解決の論点は `docs/open-questions.md`（スナップショット型: 現在未解決のものだけを映し、解決したら行ごと削除）に分離する。フォーマットと運用規約は `decision-log` スキルと `CONTRIBUTING.md` に定義する。`docs/open-questions.md` はオンデマンド作成とし、template同期はしない（リポジトリ固有の未決事項が新規プロジェクトのスターターへ流出するのを防ぐ）。
2. **ADRは原則 Proposed で作成し、その決定が確定（議論が収束）したチェックポイントで Accepted に昇格させる**。brainstorming 起点の決定は「設計承認時」を、実装持ち越し / retrospective採用ADRは「実装完了時」をチェックポイントとする。`decision-log` の承認プロンプトに「保留（議論継続中はProposed据え置き）」を追加し、探索の最中は保留を既定とする。

## Consequences

- **良い影響**: ADRが意思決定の記録に純化される。未決事項が一元管理され見落としが減る。Accepted が「確定済み」を意味するようになり、ステータスの信頼性が上がる。
- **コスト・悪い影響**: `docs/open-questions.md` の手動メンテ（解決時の行削除）が必要になる。承認が2段階（作成→昇格）になり昇格忘れのリスクが生じるため、`start-work` Phase 2 Post と各チェックポイント手順で昇格を促して補う。
- 既存ADR（0001-0018）は遡及修正しない。本規律は今後作成・更新するADRに適用する。
- **部分修正（ADR-0105）**: CLAUDE.md「意思決定の記録」の記述規律・Proposed 運用の箇条は decision-log への参照に置換され、昇格手順は 3 ステップへ束ね直された
