# ADR-0028: 振り返り課題を issue 管理へ全件起票し、issues を system/flow フォルダに分割する

- **Status**: Accepted
- **Date**: 2026-07-05

## Context

課題の置き場が2系統に分かれ、関係が未定義だった（フロー課題 #4、`docs/records/retrospectives/flow/2026-07-05-project-folder-structure.md`）。

1. **振り返り記録**（`docs/records/retrospectives/system|flow/`）: per-cycle・追記型・上書き禁止（ADR-0011 / ADR-0021）。retrospective スキルが抽出した課題が箇条書きで埋め込まれるが、open/closed のライフサイクル管理がない
2. **課題管理**（`docs/working/issues/NNNN-<slug>.md` + インデックス）: Status（open → closed）と ADR 参照による close を持つが（ADR-0019 / ADR-0025）、課題がフロー由来かシステム由来かを表す構造がない

このため、振り返り由来の課題にライフサイクル管理が適用されず、起票基準・相互参照の方法も決まっておらず、課題の見落とし・二重管理のリスクがあった。また配布先のシステム開発 repo では、どの課題が対象システム固有で、どの課題が開発フロー課題（対策はガイドライン repo 側）なのかを一目で判別できる必要がある。

## Considered Alternatives

- **(a) 起票基準**: ① 振り返り時に全件起票 / ② ユーザーが対策着手を決めた課題のみ起票 / ③ 起票せず参照規約のみ定義。→ **① を採用**。issues が唯一の課題一覧になり、全課題に open/closed ライフサイクルが付く。②③は未着手課題の一覧性・追跡が振り返りファイルと handoff に依存したまま残る。
- **(b) 配布先システム開発 repo でのフロー課題の扱い**: ① 分類を問わず全件ローカル repo の issues に起票 / ② フロー課題は起票せず `retrospectives/flow/` ファイルのみに留める。→ **① を採用**。起票ルールが1つで済み、ローカルでも追跡可能。フロー課題の close 条件は「ガイドライン repo へ申し送り済み（または対応済み）」とする。
- **(c) 分類の表現方法**: ① 課題ファイルに分類フィールド＋インデックスに分類列 / ② `docs/working/issues/` 配下を `system/` `flow/` の2フォルダに分割 / ③ インデックスを分類別セクションに分けるのみ。→ **② を採用**。ファイルツリーだけで分類が判別でき、振り返り記録の `retrospectives/system|flow/`（ADR-0021）と同じ2分類・同じフォルダ名で対称になる。配布先 repo からの申し送りも「`issues/flow/` の open 課題を見る」だけになる。全課題を通した時系列一覧性は下がるが、その必要がある場面はほぼ無いと判断した。①は課題ファイルを開くか列を読む必要があり、判別の即時性で劣る。
- **(d) 採番方式**: ① 両フォルダ通しの連番 / ② フォルダごとに独立採番。→ **① を採用**。Issue-NNNN の参照が repo 内で一意になる。②は同番号が併存し参照時に毎回フォルダ名の併記が必要になる。
- **(e) インデックスの形**: ① ルートに README 1つ（フォルダ対応の2セクション） / ② 各フォルダに README を置く。→ **① を採用**。採番の起点が1ファイルで済み、起票手順が単純に保てる。
- **(f) 起票の組み込み位置**: ① retrospective スキルのドラフト保存段階で起票 / ② start-work のセッション終了処理で未起票分を起票 / ③ 振り返りファイルの課題本文を issue へ一本化し振り返り側は番号一覧のみ。→ **① を採用**。初回書き込み時点で振り返りファイルに issue 番号を記載でき、上書き禁止規約（ADR-0011）と衝突しない。②は参照が片方向になり起票漏れリスクが残る。③は配布先→ガイドライン repo の申し送り（`flow/` ファイルを渡す運用）で課題詳細が欠け、振り返り記録単体の完結性も下がる。

## Decision

1. **`docs/working/issues/` 配下を `system/`（対象システム固有の課題）と `flow/`（開発フロー/ガイドライン課題）の2フォルダに分割する**。フォルダが分類を表すため、課題ファイルに分類フィールドは設けない。フォルダ名は振り返り記録の2フォルダ（ADR-0021）と揃える。フォルダ昇格（NNNN-<slug>/）は各フォルダ内で行う。
2. **採番は両フォルダ通しの連番（NNNN、4桁ゼロ埋め）とする**。インデックスはルートの `docs/working/issues/README.md` 1ファイルに集約し、フォルダに対応する2セクション（system / flow）で構成する。採番はインデックス全体の最大番号+1。
3. **retrospective で抽出した課題は、分類を問わず、その場で全件起票する**。起票は retrospective スキルのドラフト保存段階（Phase 2）の責務に追加する。起票は記録行為であり対策の設計・採否判断ではないため、抽出限定スコープ（ADR-0021）は維持される。
4. **振り返り由来の課題は、詳細記述（事象 / 原因 / 影響）を振り返りファイル側を正とし、issue ファイルは要約＋「起票元」参照に留める**。二重記述による内容乖離を避ける。振り返りファイルの各課題には起票した issue 番号を初回書き込み時に記載する（相互参照は双方向）。振り返り以外を起点とする課題（議論中の未決事項など。ADR-0019）は従来どおり課題内容を issue 本文に直接書く。
5. **配布先システム開発 repo でも同一ルールで全件ローカル起票する**。`flow/` の課題の close 条件は「ガイドライン repo へ申し送り済み（または対応済み）」とする。`retrospectives/flow/` フォルダが申し送りバックログであるという位置づけ（ADR-0021）は変更しない。

## Consequences

- **良い影響**: issues が唯一の課題一覧（single source of truth）になり、振り返り由来の課題にも open/closed ライフサイクルが適用される。起票漏れが構造的に発生しない。分類がファイルツリーとインデックスの両方から一目で判別できる。抽出（retrospectives/system|flow）と追跡（issues/system|flow）が同じ2分類軸で対称になる。
- **コスト・悪い影響**: retrospective 実行時の作業が増える（課題件数分の issue ファイル作成＋インデックス行追加）。既存課題（Issue-0001）のフォルダ移動と、未起票バックログ（2026-07-05 振り返りの6件等）の移行起票が必要。全課題を通した時系列の一覧はインデックス2セクションを跨いで見る必要がある。分類を変える場合はファイル移動＋インデックス修正になる。
- 波及更新: `skills/retrospective/SKILL.md` / `flow-template.md` / `template.md`、`docs/overview/folder-structure.md` §7（フォルダ構成・課題フォーマット・インデックス形式）、`docs/records/retrospectives/README.md`、`CONTRIBUTING.md`（未決事項・課題シナリオ / 課題対策シナリオ）、`skills/decision-log/SKILL.md`（未決事項の起票手順のパス）。template 対象は `scripts/sync-template.ps1` で同期する。
- **部分修正（ADR-0105）**: retrospective Phase 2 の起票サブ手順（採番・起票・インデックス行追加）は課題管理定義への参照に置換された
