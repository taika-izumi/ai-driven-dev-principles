# ADR-0031: 既存 open 課題の再発・進展は issue ファイルの「検討状況」へ一次記録する

- **Status**: Accepted
- **Date**: 2026-07-05

## Context

ADR-0028 は振り返り課題の全件起票フロー（新規課題の起票）を定義したが、**既存 open 課題が再発・進展した場合の記録方法**はスコープ外だった。実運用では、Issue-0004 の再発は実施エージェントの判断で issue ファイルの「検討状況」に追記され、同サイクルの Issue-0002・0006 の再発・再確認は振り返りファイルにのみ記録されるなど、記録場所が実施者依存になっていた（Issue-0010。起票元: retrospectives/flow/2026-07-05-retrospective-issue-integration.md 課題#2）。記録場所が分散すると、課題の深刻度（再発頻度）を後から追跡できなくなる恐れがある。

## Considered Alternatives

- **案A（採用）: issue ファイルの「検討状況」へ一次記録を一元化。** 再発頻度が issue ファイル1箇所で追跡できる。ADR-0028 の「新規課題は振り返りファイルが正・issue は要約」と役割が逆になるが、対象が異なる: 新規課題の事象/原因/影響は特定サイクルの産物（振り返りが正）、再発・進展は課題のライフサイクル情報（ライフサイクル管理を担う issue が正）であり、責務分離として自然。
- **案B: 振り返りファイルのみに記録。** 再発情報がサイクル横断で分散し、頻度追跡に全振り返りの走査が必要になる。また振り返りは merge 直後の1回だけであり、サイクル途中に気づいた再発の記録先がない。不採用。
- **案C: issue と振り返りの両方に正記録。** 二重管理になり、差異が生じたときにどちらが正か不明になる。不採用。

## Decision

案Aを採用する。

1. **一次記録先**: 既存 open 課題の再発・進展を検出したら、検出したその場で該当 issue ファイルの「検討状況」セクションに1行追記する（形式: `YYYY-MM-DD: 事象の要約（必要なら詳細への参照）`）。
2. **retrospective での扱い**: 既存 open 課題の再発は新規課題として起票しない。振り返りファイルで言及する場合は Issue-NNNN への参照を付け、一次記録は issue 側とする（振り返りファイルの追記型規約 ADR-0011 とは衝突しない: 振り返りには当該サイクルの言及のみを書き、再発履歴の蓄積は issue が担う）。
3. **反映先**: `docs/overview/folder-structure.md` §7（課題管理）に再発記録ルールを追記、`skills/retrospective/SKILL.md` に既存 open 課題の再発の扱いを追記。

## Consequences

- 良い影響: 再発頻度＝課題の深刻度が issue ファイル1箇所で追跡可能になり、対策着手の優先判断の材料になる。記録場所の実施者依存が解消される。
- 留意点: サイクル途中の再発検出時に issue ファイルへの追記という小さな割り込み作業が発生する（1行のため軽微）。
- 留意点: `docs/overview/folder-structure.md` は template.manifest 対象のため変更後に `scripts/sync-template.ps1` の実行が必要。skills/ の変更はプラグイン更新まで利用者に反映されない。
- **部分修正（ADR-0105）**: 既存課題への追記の一次記録規範は維持。retrospective の起票手順は課題管理定義への参照になり、folder-structure の節番号は「7. 仕様書の運用規約」新設で繰り上がった
