# ADR-0032: 規範・ADR の判定条件はエージェントが観測・実行可能な事実で書く（実行可能性チェックの定式化）

- **Status**: Proposed
- **Date**: 2026-07-05

## Context

ADR-0029 の起草時、撤去基準を「事象が発生しないモデルの利用が常態化した時点」と一度書いた。これはエージェントには判定不能な条件（他モデルの利用状況やユーザー画面の事象はエージェントから観測できない）であり、ユーザー指摘を受けて「ユーザーが判断し撤去を指示した時点」に書き直した。規範・ルール・ADR を起草する際に「その判定条件・動作をエージェントが実際に観測・実行できるか」をチェックする観点が `decision-log` スキルにも `CONTRIBUTING.md` のチェックリストにもなく、実行不能な規範の混入防止がユーザーレビュー頼みになっていた（Issue-0011。起票元: retrospectives/flow/2026-07-05-question-tool-display-norm.md 課題#1）。

## Considered Alternatives

- **案A（採用）: 起草プロセスにチェック観点を追記。** `decision-log` の記述規律と `CONTRIBUTING.md` の該当シナリオに1〜2行のチェック項目を追加する。起草者（エージェント）が自己確認できる最小限の変更で、既存フローを変えない。
- **案B: 規範レビュー専用スキルの新設。** 起草のたびに独立レビューを挟む。混入防止は強くなるが、規範起草の頻度に対して過剰であり YAGNI。不採用。
- **案C: 現状維持（ユーザーレビュー頼み）。** 捕捉漏れで実行不能な規範が混入すると形骸化した指示が残り続ける。不採用。

## Decision

案Aを採用する。以下のチェック観点を起草プロセスに定式化する。

1. **チェック観点**: 規範・ルール・ADR（特に撤去基準・発動条件・適用条件などの判定条件）を起草するときは、「その判定条件・動作を、実行主体であるエージェントが実際に観測・実行できるか」を確認する。エージェントが観測できない状態（例: 他モデルの利用状況、ユーザー画面上の事象、セッション横断の利用履歴）を判定条件にせず、観測可能な事実（例: ユーザーの明示指示、ファイル・設定の存在、コマンド出力）で書く。判定をエージェントができない場合は「ユーザーが判断し指示した時点」のように判断主体をユーザーに明示的に移す。
2. **反映先**: `skills/decision-log/SKILL.md` の記述規律に1項追加、`CONTRIBUTING.md` の「ADRを記録するとき」の記述規律と「CLAUDE.md を更新するとき」の注意事項に各1行追加。

## Consequences

- 良い影響: 実行不能な規範の混入防止が起草プロセスに組み込まれ、ユーザーレビューは最後の防衛線（一次防衛ではなく）になる。
- 留意点: チェックは起草者の自己確認であり、確実な防止を保証するものではない。ユーザーレビューを置き換えない。
- 留意点: skills/ の変更はプラグイン更新（`/plugin marketplace update ai-driven-dev-principles`）まで利用者に反映されない。`CONTRIBUTING.md` は template.manifest 対象外のため同期作業は不要。
