# ADR-0034: 実装計画の検証ステップ期待値と編集内容の整合を確認する規範を追加

- **Status**: Accepted
- **Date**: 2026-07-05

## Context

`superpowers:writing-plans` で作成する実装計画には、各タスクの編集内容とは別に「検証ステップ」（grep 件数の期待値、存在すべきファイル名、期待する出力など）を書く。しかし writing-plans のセルフレビュー観点（spec 網羅・プレースホルダ・型整合）には、検証ステップの期待値と各タスクの実際の編集内容を突合する観点が含まれない。

このため、検証期待値と編集内容が矛盾していても計画作成時に捕捉されない。実例として、記録プロセス規範一括対策サイクルの plan で、Task 6 の検証 grep 期待値（6ファイルに ADR 参照）が、Task 1 で意図的に ADR 番号を書かない CLAUDE.md の編集文面と矛盾していた（実行時に説明で吸収され実害は軽微だったが、検証期待値の誤りは「検証が通らない／誤って通る」双方のリスクを持つ）。この課題は Issue-0013 として起票済み。

writing-plans は superpowers 側のスキルで本リポジトリからは変更できないため、対策は本メタ・ガイドライン repo 側の運用規範（`CLAUDE.md`）で補う形をとる。

## Considered Alternatives

- **CLAUDE.md「検証」節に1項目追加（採用）**: 検証の正しさに関わる観点であり、既存の「複雑なタスクは小さなステップに分割し各ステップで正しさを確認」「変更後は既存の動作を壊していないか確認」という検証系の記述の流れに自然に接続する。
- **CLAUDE.md「タスク構造」節に追加**: plan のタスク定義品質の話として配置する案。ただし同節は「責務を混ぜない」「構造化データ」「高凝集・疎結合」「feature-block-design」等の粒度の話題で構成されており、検証期待値の整合という論点とは軸がやや異なる。
- **独立した plan 運用規範ドキュメントを新設**: plan 運用規約は現状 `CLAUDE.md` 以外に独立文書として存在せず、1項目のためだけに新設するのは過剰（YAGNI）。
- **Issue-0006（計画の網羅漏れ）と一括で規範化**: スコープが広がり軸が異なる（網羅性 vs 整合性）。今回は Issue-0013 に限定し、Issue-0006 は別サイクルに委ねる。

## Decision

`CLAUDE.md`「検証」節に、実装計画作成時のセルフレビュー観点として次の1項目を追加する:

> 実装計画を作成したら、各検証ステップの期待値（grep 件数・存在すべきファイル名・期待する出力など）が、その計画の各タスクが実際に行う編集内容と矛盾しないかを突合すること。矛盾があれば期待値かタスク定義のいずれかを修正してから計画を確定すること。

文面はエージェントが観測・実行できる事実で記述する（ADR-0032）。ツール非依存の表現とする（CONTRIBUTING）。`CLAUDE.md` は Layer 2 のテンプレート対象ファイルのため、変更後 `scripts/sync-template.ps1` を実行してテンプレートへ同期する（ADR-0033 により LF 書き出し）。

## Consequences

- 良い影響: 計画作成時に検証期待値と編集内容の矛盾を能動的に突合する観点が明文化され、「検証が通らない／誤って通る」リスクを低減できる。writing-plans のセルフレビューの死角を本 repo 側で補える。
- 良い影響: Issue-0013 を close できる。
- 制約・残存リスク: 規範は writing-plans を使う運用に依存する。規範は「突合する」観点の提示であり、突合の実行自体はエージェントの遂行に委ねられる（自動チェックではない）。
- Issue-0006（横断的なパス変更での網羅漏れ）は本 ADR のスコープ外で、open のまま残る。
