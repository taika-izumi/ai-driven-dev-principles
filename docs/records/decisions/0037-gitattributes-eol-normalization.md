# ADR-0037: .gitattributes で改行正規化を git 側に固定し、template へは配布しない

- **Status**: Proposed
- **Date**: 2026-07-05

## Context

リポジトリに .gitattributes がなく、テキストファイルの改行正規化が各貢献者のローカル git 設定（core.autocrlf）に依存していた（Issue-0014）。現環境（core.autocrlf=input）では LF が保たれるが、別環境の貢献者が CRLF のままコミットすると Issue-0002 と同種の改行ノイズが再発しうる。ADR-0033（sync-template.ps1 の LF 書き出し）では本件をスコープ外と明記していた。

現状調査では、リポジトリ内のファイルは md / json / ps1 / manifest のテキストのみで、インデックスは既に全ファイル LF（`git ls-files --eol` で確認）。したがって導入時の renormalize 差分はほぼ発生しない。

あわせて、起票時の rubber-duck レビュー指摘「配布物としての .gitattributes を template に含めるか（下流プロジェクトにも同じ正規化を配るか）」の判断も必要だった。

## Considered Alternatives

正規化ルールについて:

1. **`* text=auto` のみ** — git がテキスト判定したファイルをコミット時に LF 正規化。チェックアウト時の改行は各自の環境設定に委ねる。バイナリは自動除外され、拡張子の列挙保守も不要
2. **`* text=auto eol=lf`** — 1 に加えチェックアウト時も全環境で LF に固定。統一性は最も高いが、貢献者のローカル設定より強い制約を課す
3. **拡張子ごとの明示列挙** — 意図は最も明確だが、新しい拡張子が増えるたびに .gitattributes の保守が必要

template への配布について:

1. **含めない** — 下流プロジェクトの git 運用（バイナリ構成・改行方針）は下流の裁量とする
2. **含める** — 下流にも同じ正規化を最初から配る。ただし template のシード基準（ADR-0027: ユーザーが直接操作するフォルダ or 空インデックスが必要なフォルダ）に git 設定ファイルは該当せず、基準の拡張判断が必要になる

## Decision

- 正規化ルールは案1（**`* text=auto` のみ**）を採用する。リポジトリの実体が全テキストであり、最小の記述で「コミット時 LF 正規化の強制」という Issue-0014 の目的を達成でき、保守も不要なため
- 導入時に `git add --renormalize .` を一度実行し、以後の正規化を git 側に固定する
- .gitattributes は **template へ配布しない**（template.manifest に追加しない）。ADR-0027 のシード基準に該当せず、下流プロジェクトの git 運用は下流の裁量とするため。Issue-0014 のスコープ（本リポジトリ自身の改行問題対策）にも合致する

## Consequences

- 以後、貢献者のローカル git 設定（core.autocrlf）に関わらず、コミット時にテキストファイルは LF へ正規化され、Issue-0002 型の改行ノイズ再発が構造的に防がれる
- ADR-0033 で残存リスクとされた「別環境の貢献者による CRLF コミット」が解消され、改行問題が終息する（Issue-0014 close）
- チェックアウト時の改行（作業ツリー上の表現）は従来どおり各自の環境設定に委ねられる。作業ツリーが CRLF でもリポジトリには LF で入る
- 下流プロジェクトには改行正規化は配布されない。下流で同種の問題が起きる場合は、下流側で個別に .gitattributes を導入する判断となる
- 将来バイナリファイルを追加しても `text=auto` の自動判定により破損しない（明示指定が必要になった場合のみ .gitattributes へ追記する）
