# ADR-0040: CLAUDE.md 肥大化ガバナンスを計測スクリプト連動と CONTRIBUTING.md 手順で導入する

- **Status**: Accepted
- **Date**: 2026-07-06

## Context

CLAUDE.md はエージェントが毎セッション読み込む常時指示であり、template 経由で配布先全プロジェクトへ展開される。規範は対策サイクルのたびに単調増加している（2026-07-06 時点で 114 行・11,180 バイト・箇条書き 38 件、実測約 3.8k トークン）が、増える一方向のフローしかなく、(a) 肥大化の監視、(b) 追加時に常時指示への累積コストと課題の放置リスクを突合する事前判定、(c) 効かない・古びた規範を削除または Layer 3（スキル）へ退避する棚卸し、のいずれの仕組みも存在しなかった（Issue-0018）。

対策の方針検討に先立ち、CONTRIBUTING.md 手順4（ADR-0039）に従って環境・ツール設定による構造的解決を調査した。既存の自動機構は `scripts/sync-template.ps1` のみで、CLAUDE.md 変更時に必ず実行する運用規範が既に確立している。監視（計測・警告）は自動化可能、事前判定・棚卸しは判断業務のため手順側の領分と評価した。

閾値水準の検討では公開研究を参照した。指示数の増加による遵守率低下は最上位モデルでも観測されており（指示 150 件前後から劣化が始まる閾値型パターン。[IFScale, arXiv 2507.11538](https://arxiv.org/abs/2507.11538)）、入力長の増加による性能低下も数万トークン規模で全モデルに観測されている（[Chroma "Context Rot", 2025](https://research.trychroma.com/context-rot)）。ただし本件の規模（数十件・数千トークン）での影響を直接測定したデータは存在しない。

## Considered Alternatives

監視の実現方式として3案を比較した（事前判定・棚卸しの手順を CONTRIBUTING.md に置く点は3案共通）:

1. **独立計測スクリプト新設＋ sync-template.ps1 から自動呼び出し**: CLAUDE.md 変更時に sync-template.ps1 を必ず実行する既存運用に乗るため、追加の運用負荷ゼロで計測が必ず発動する。単体実行も可能で、事前判定・棚卸し時の実測にも使える
2. **スクリプトなし・手順のみの最小構成**: 実装コスト最小だが、実測が手順遵守頼みになり「監視の仕組みがない」という課題への答えとして弱い。環境・ツール設定による構造的解決を優先する ADR-0039 に反する
3. **git pre-commit hook ＋棚卸しスキル化の最大構成**: 強制力は最も高いが、hooks 管理機構の新規導入コストと環境依存が増える。棚卸しは発動頻度が低く手順の複雑さも小さいため、スキル化は現時点でオーバーキル

閾値水準は 15,000 バイト/50 件（約 5k トークン相当）と 12,000 バイト/45 件を比較し、保守的な後者を選んだ（IFScale の指示は単純なキーワード包含であり、本リポジトリの規範は条件分岐付き・解釈を要するため、より少ない件数から効き始める可能性を重視）。

## Decision

案1を採用する:

- **監視**: `scripts/check-claude-md-size.ps1` を新設する。リポジトリ直下 CLAUDE.md の UTF-8 バイト数（主指標）と行頭 `- ` の箇条書き件数を計測し、**閾値（バイト数 12,000 / 箇条書き 45 件、スクリプト内定数）** のいずれかを超過したら警告して棚卸し（CONTRIBUTING.md の手順）の実施を促す。超過の有無に関わらず現在値と閾値を毎回表示する。終了コードは常に 0（警告のみで追加や同期をブロックしない）。`sync-template.ps1` の末尾から自動で呼び出し、単体でも実行できる
- **事前判定**: CONTRIBUTING.md「CLAUDE.md を更新するとき」に手順小節を新設する。規範の追加を検討し始めた時点で計測スクリプトを**単体実行**して現在値と追加分を数字化し、放置リスク（静かに壊れて修復コストが高い失敗か、人間レビューで顕在化する失敗か）を評価し、配置先を「環境・ツール設定 → Layer 3 スキル → 発生箇所の手順書 → CLAUDE.md（最後の選択肢）」の優先順位で検討する。CLAUDE.md に置く場合は観測可能な発動条件でゲートする（ADR-0032）
- **棚卸し**: CONTRIBUTING.md に新シナリオ「CLAUDE.md を棚卸しするとき」を追加する。発動条件は「計測スクリプトの閾値超過警告（エージェントはユーザーに実施を提案し、要否・時期はユーザー判断）」または「ユーザーの指示」。箇条を由来 ADR と突合しながら「構造的置換 / 失効 / 退避（Layer 3 へ）/ 現役」の4分類で判定し、削除・退避・置換は ADR で記録する（元 ADR のステータス更新＋新 ADR）。棚卸し後も閾値内へ戻らない場合は閾値の引き上げをユーザーに提起する

閾値はデータから導出した危険水域ではなく、既知の劣化域（指示 150 件前後・入力数万トークン）から十分な安全マージンを取った**管理上のトリップワイヤー**である。運用して棚卸しが困難であれば引き上げを検討する。

スコープは上記3側面とし、template 更新を既存配布先へ反映する下り方向の配布経路は本対策の対象外とする（現状の手動運用を継続）。計測スクリプトは `template.manifest` に追加しない（CONTRIBUTING.md と同じく本リポジトリ固有のガバナンス機構であり、配布先には波及させない）。

## Consequences

- CLAUDE.md 変更時の既存運用動線（sync-template.ps1 必須実行）に計測が組み込まれ、新しい強制機構を導入せずに「変更のたびに必ず計測される」状態になる。事前判定を踏み忘れた編集や、個々には小さい追加の累積も、事後の自動計測が捕捉する
- 増える一方だったフローに、事前判定（入口）と棚卸し（出口）の双方向が定義され、累積の管理が可能になる
- 計測スクリプトの保守対象が1本増える。トークン数は直接測れないためバイト数による近似となる（日本語主体の本ファイルでは概ね 3 バイト ≒ 1 トークン）
- 閾値超過が実際に起きるまで棚卸し手順は発動しないため、手順の実効性の検証は超過発生時まで持ち越しになる
- 下り方向の配布経路は未定義のまま残る（手動運用を継続）
