# ADR-0041: ADR ステータス体系を完成させ（Rejected 新設）、置換対象の特定手順と台帳監査を定義する

- **Status**: Proposed
- **Date**: 2026-07-07

## Context

Issue-0019 への対策。`decision-log` スキルには Accepted 後の破棄・置換手順（`Deprecated` / `Superseded by ADR-XXXX`）が定義されている一方、**コミット済みの Proposed ADR を「不採用」で終える経路が未定義**だった。現行の「却下」手順はファイルとインデックスエントリの削除を指示しており、コミット前のドラフトにのみ適切で、コミット済み ADR に適用すると「なぜ採用しなかったか」の記録が消え、原則1（追跡可能性）と矛盾する。また `start-work` の Post チェックは Proposed の昇格漏れのみを見ており、不採用方向の見直しを促すトリガーがなかった。

検討の過程で2つの追加論点が浮上した:

1. **Superseded の検出コスト**: 「新規 ADR 起票時に置換対象の既存 ADR を特定するには全件調査が必要になり、台帳の成長とともにコストが膨張するのではないか」（ユーザー提起）。Deprecated / Superseded は定義済みだが適用実績ゼロであり、実行可能な特定手順が不在だった
2. **既存台帳の未監査**: 台帳全体（40件）のステータス正確性は一度も監査されておらず、実質置換済みの Accepted ADR が眠っている可能性がある（境界例: ADR-0015/0017、ADR-0016/0023、ADR-0003/0027、ADR-0010/0021）

対策方針の検討に先立ち、環境・ツール設定による構造的解決を調査した（ADR-0039）。本課題の核心（語彙・手順の不在）は定義の問題であり環境設定では代替できない。周辺の検出については機械化（滞留検出スクリプト）の余地があるが、後述のとおり今回は導入しない。

## Considered Alternatives

### 対策の枠組み

1. **ドキュメント定義のみで完結（採用）**: `decision-log` にステータス体系と手順を定義し、`start-work` の Post チェックを対称化し、`CONTRIBUTING.md` に台帳監査を定義する。新規ツールなし
2. **案1 ＋ 滞留検出スクリプト新設**: Proposed の滞留を機械的に警告する。現状 Proposed は3件で台帳を見れば一目で分かる規模であり、滞留日数の閾値にも根拠が薄く、メンテナンスコストが先行して YAGNI に反するため見送り。取りこぼしが実際に累積した時点で課題起票する（Issue-0018 と同じ「困った時点で起票」方針）
3. **語彙定義のみ（トリガーは触らない）**: Issue-0019 が明示する「不採用方向の見直しトリガーの不在」が未解決のまま残るため見送り

### Superseded の置換対象特定

1. **起票時に既存 ADR を全件調査**: 台帳の成長とともにコストが線形以上に膨張するため見送り
2. **変更箇所起点の特定（採用）**: 置換が起きるのは既存の決定を変更している場面であり、エージェントはそれを起票時に自覚している（既存の強トリガー6「既存の判断の変更」）。よって問題は「変更中の決定の導入元 ADR 番号を安く特定すること」に縮約される。一次経路（変更対象ファイルが引用する ADR 番号）と二次経路（採番時に必ず開くインデックスのタイトル走査）で特定し、コストを O(変更箇所) に抑える。網羅保証は追わず、取りこぼしは台帳監査を保険とする

### 台帳監査の発動条件

1. **ユーザー指示＋作業中の矛盾発見の2トリガー（採用）**: 観測可能な事実のみで構成される（ADR-0032）
2. **定期実行（Nサイクルごと・日数閾値）**: 閾値の根拠が薄く空振りコストが先行するため見送り

## Decision

以下を実装する。

### 1. ステータス体系の完成（`skills/decision-log/SKILL.md`）

4つの終端ステータスの意味境界を明文化する:

| ステータス | 意味 | 遷移元 |
|-----------|------|--------|
| Accepted | 承認され現役 | Proposed |
| Rejected（新設） | 承認前に不採用が確定 | Proposed |
| Deprecated | 承認後に廃止（置換先なし） | Accepted |
| Superseded by ADR-XXXX | 承認後に新 ADR で置換 | Accepted |

Rejected の手順: Status を `Rejected` に更新し、不採用の理由を Consequences に追記し、インデックスも更新してコミットする。ファイルは削除しない（同じ案が再浮上したときの再検討コストを下げる。MADR 等の一般的な ADR 運用とも整合）。

「ユーザーへの確認」の却下分岐を2つに分割する: 未コミットのドラフトは現行どおりファイル削除、コミット済みは Rejected 化とし、削除手順のコミット済み ADR への適用を禁止する。

### 2. 置換対象の特定ステップ（`skills/decision-log/SKILL.md`）

ADR 作成手順の採番ステップ（README テーブルを開くタイミング）に「この決定が変更・置換する既存決定の特定」を追加する:

- 一次経路: 変更対象ファイルが引用している ADR 番号を確認する
- 二次経路: 採番時に開いているインデックスのタイトルを同一トピックで走査する
- 置換対象が見つかったら、新 ADR の作成と同時に旧 ADR を `Superseded by ADR-XXXX` へ更新する

### 3. 不採用方向の見直しトリガー（`skills/start-work/SKILL.md`）

Post チェックの「Proposed の昇格漏れ確認」を対称化し、議論の結果不採用が確定した Proposed を Rejected へ更新する確認を同じチェックポイントに含める。

### 4. 台帳監査の定義（`CONTRIBUTING.md`「ADRを記録するとき」へ小節追加）

- 発動条件: ① ユーザーが監査を指示した時点、または ② エージェントが作業中に台帳の矛盾（引用先 ADR と実態の不一致等）を具体的に発見し、監査を提案してユーザーが承認した時点
- 手順: 全 ADR を「現役 / 部分修正あり（本体現役・状態変更なし）/ 実質置換（Superseded 化）/ 廃止（Deprecated 化）」で判定し、状態変更は `decision-log` の手順で記録する

### 5. 初回の台帳監査と Proposed 3件の処遇判断（本サイクル内で実施）

- 全40件のステータス監査（境界例の判定はユーザーと確認しながら行う）
- 据え置き Proposed 3件（ADR-0013 / 0014 / 0018）の処遇判断（採用継続 / Rejected / 据え置き）。「採用して実装」となった場合の実装は別サイクル

### 6. 変更しないもの

- `CLAUDE.md`: 変更なし（手順はすべて Layer 3 スキルと CONTRIBUTING.md に収まる。ADR-0040 の肥大化ガバナンスに従い常時指示を増やさない）
- 新規スクリプト: なし

## Consequences

- ＋ 4つの終端ステータスが揃い、コミット済み Proposed ADR を追跡可能性を保ったまま不採用で終えられる
- ＋ Superseded の適用が「変更箇所起点の特定手順」として実行可能になり、起票時コストが O(変更箇所) に抑えられる（台帳の成長で膨張しない）
- ＋ 台帳監査により、実質置換済みの Accepted ADR の取りこぼしを回収する保険が定義される
- − 起票時の特定は網羅保証を持たない。間接的な置換（ファイルを共有しない決定の前提を暗黙に無効化するケース）は監査まで検出されない
- − 台帳監査に定期トリガーがないため、ユーザー指示か矛盾発見がない限り実施されない。取りこぼしが実際に累積した場合は、滞留検出の機械化を課題として起票する
