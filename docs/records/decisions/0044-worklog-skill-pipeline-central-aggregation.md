# ADR-0044: 作業記録→候補抽出→スキル化の3スキルパイプラインを中央集約アーキテクチャで新設する

- **Status**: Accepted
- **Date**: 2026-07-16

## Context

メタ・ガイドライン運用で得られる「スキル化・ルール化する価値のある作業ノウハウ」を、複数プロジェクト横断で捕捉・抽出・スキル化する仕組みが存在しない。既存の retrospective はサイクル終端の課題抽出用であり、「頻発・重要な作業手順やルールの抽出」には使えていない（ユーザー実感、D2）。

本作業は対話モードのガイドライン拡張であり、ADR-0043 の凍結（ループ対応の改修・2プロファイル構成の設計）には抵触しない（守る境界: ループ対応改修をしない／2プロファイル設計を始めない）。

## Considered Alternatives

- **retrospective を拡張して兼ねる**: レンズが異なる（サイクル終端の課題抽出 vs 継続的なノウハウ抽出）。別スキルが要る（D2）
- **保存を各プロジェクト repo 内に置く**: 横断収集が困難でルート一覧の維持も要る。中央のユーザーレベル固定ルートへ集約する方が走査が単純（D7）
- **scope をフォルダで物理分離（案Y）**: 暫定分類が物理配置を固定し、誤分類時の移動コストと横断再発検出の全走査が残る。scope をエントリ内タグで持つ案X を採用（D7）
- **スコープ分類をスキル2（横断分析）でのみ行う**: 記録時点のメインエージェントは full context を持ちドメイン固有/汎用を判断できる。record 時に暫定タグを付け、スキル2が横断視点で最終確定する2段構えにした（D6）

## Decision

- **3スキル構成**: スキル1（記録）→ スキル2（候補抽出）→ スキル3（スキル化）の相互に連なるパイプライン
- **スキル1（記録）**: 既存 handoff と同じ節目で、メインエージェント本人がコンパクトな構造化エントリを1回追記する（D3）。記録ゲート＝(a) 既存スキルで既に実施している作業ではない かつ (b) AI が自律判断でも毎回同じに再現できる作業ではない（D4）
- **スキル1/2 の責務境界**: 重い横断分析（複数プロジェクト横断の再発頻度検出・既存スキルとの重複排除・優先順位付け）はスキル2へ遅延する。スキル1は record 時に scope 暫定タグ（`project-specific` / `general-candidate`）を付けるところまで（D6）
- **出口像＝スコープ3分岐**（D5）: 汎用（複数プロジェクトで再現・ドメイン非依存）→ 本 repo のプラグイン配信スキル ／ プロジェクト固有だが価値あり → そのプロジェクトのローカルスキル（`.claude/skills/`）／ 固有ルールでスキル化不要 → そのプロジェクトの CLAUDE.md。根拠: スキルのトリガー（description）はインストールされたスコープ内でのみ評価されるため、固有スキルをローカルに留めれば他プロジェクトでのトリガー誤爆が構造的に起きない
- **保存＝中央・プロジェクト分割・scope はタグ**（案X、D7）: 中央のユーザーレベル固定ルートに集約し、プロジェクト単位でフォルダ分割（出所属性）。scope は物理分離せずエントリ内タグで持つ。識別子＝各プロジェクトのルートフォルダ名＋集約ルートの `projects.json`（`フォルダ名 → 現在の絶対パス`）を upsert で自己修復（D8）
- **retrospective との overlap 対応**（D10）: スキル2の本 repo 向け汎用候補も、スキルを直接作らず Issue 草案として `docs/working/issues/` に起票する。重複排除は Issue 起票時にバックログ1箇所で行う（唯一の合流点＝dedup ゲート）
- **スキル3の位置づけ**（D11）: 汎用候補向けスキル3は独立の重いスキルにせず、既存「Issue → extend-guidelines → スキル作成」フローへの橋渡しとする（薄いオーケストレーション層）
- **v1 スコープ**（D12）: `applied_rules` の逸脱注記はデータとして捕捉するのみ。スキル2の出力3（既存ルール・スキルの改訂候補発見）は v1 で作らず v2 の明示拡張とする（コア目的＝スキル化とは別関心のため v1 スコープを絞る）

## Consequences

- **良い影響**: 複数プロジェクト横断のノウハウがスキル化パイプラインに乗る。誤分類はタグ書き換えで安く修正でき、横断再発は project で group-by するだけで検出できる。汎用候補の重複排除が Issue バックログ1箇所に集約される
- **コスト・留意**: 中央ストアが `docs/overview/folder-structure.md` の5分類の管轄外になる（スキル1 doc に「repo 外・中央に置く理由」を明記して records 誤解を予防）。3スキルの新規実装コストが発生する
- **後続**: 中規模以上のため brainstorming と writing-plans の間に feature-block-design の適用要否を判定する。spec はディレクトリ分割形式（`docs/current/specs/YYYY-MM-DD-<topic>/`）で作成する
- 詳細な決定履歴（D1〜D17）は `docs/working/handoff/skill-pipeline-brainstorming-state.md` を参照
