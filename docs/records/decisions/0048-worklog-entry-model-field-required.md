# ADR-0048: worklog エントリに delta 発生元モデル ID の必須フィールド model を追加する

- **Status**: Accepted（Issue-0031 で model の定義を「記録時のモデル」→「delta 発生元のモデル」へ訂正: 2026-07-18）
- **Date**: 2026-07-17

## Context

worklog エントリの核心である delta は「AI が**デフォルトで**やることと実際に必要だったことの差分」だが、その「デフォルト」は AI モデルに依存する（あるモデルが躓く作業を別のモデルは躓かない）。現行スキーマ（ADR-0045）には記録した AI モデルを残すフィールドがなく、抽出時（worklog-extract）に「この friction は特定モデル固有か、全モデル共通か」を判定できない。コスト最適化のためにモデルを使い分ける運用へ進むほどこの差は拡大する（Issue-0025）。

## Considered Alternatives

- **任意フィールドとして追加**: モデル不明のケースでも記録を阻害しない柔軟さはあるが、記録者（AI 自身）は自分のモデル ID を常に知っており記録コストは実質ゼロ。任意にすると書かれないエントリが混ざり、モデル別分析の信頼性が下がる
- **追加しない（rejected で close）**: モデル固有の躓きを全モデル共通と誤認して不要なスキルを作る、モデル変更で解消した friction を誤判定する、のいずれも防げない

## Decision

エントリスキーマに `model`（string、**必須**）を追加する。値は delta 発生元の AI モデル ID（例: `"claude-fable-5"`。記録時と発生元が異なる場合は発生元を優先）。欠落はエントリ検証で弾く。既存の v1 エントリ（model なし）は書き換えず、読み側が旧スキーマとして許容する（ADR-0049 の版数規約に従う）。

## Consequences

- 良い影響: worklog-extract が「モデル固有か全モデル共通か」をクラスタ評価の材料にできる。モデル使い分け運用への布石になる
- コスト・留意: 必須フィールドが 1 つ増える（記録コストは実質ゼロ）。サブエージェント経由の記録などでモデル ID の取得方法が自明でないケースでは、セッションのモデル表記をそのまま用いる
- モデルまたぎ運用（主作業＝高性能モデル / 事後処理＝安価モデル）では記録時と発生元が食い違う。1 エントリが複数モデルの delta にまたがる場合は ADR-0053 の記録単位（同一 context の delta 束）に従いテーマ分割し、各エントリを単一の発生元モデルに収める（Issue-0031）
- Issue-0025 は本 ADR で close する
