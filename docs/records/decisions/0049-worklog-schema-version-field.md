# ADR-0049: worklog の log.jsonl / processed.jsonl 両方にスキーマバージョン v を必須導入する

- **Status**: Accepted
- **Date**: 2026-07-17

## Context

作業ログ（log.jsonl）と処理済み台帳（processed.jsonl）は追記専用で長寿命だが、各レコードにスキーマバージョンを示すフィールドがない。中央ストアは全プロジェクト共有である一方、書き込み側スキル（worklog-record）の版はプロジェクトごとのプラグイン更新タイミングに依存するため、将来のフォーマット改訂時に新旧スキーマが同一ストアへ混在する期間が必然的に発生する（Issue-0026）。バージョンフィールドは後から導入するほど「フィールドなし = 初版」という暗黙規約が既存データに固定化されて移行判定が複雑になるため、導入するなら早いほど良い。本サイクル（worklog v1.1 改訂）でスキーマ自体が変わる（ADR-0048/0051）ことが導入の適機となった。

## Considered Alternatives

- **log.jsonl のみ導入**: 台帳はフィールド数が少なく改訂リスクが低いという見立てもできるが、台帳も追記専用・長寿命・全プロジェクト共有という同じ構造的リスクを持つ。片方だけ守る理由がない
- **導入しない（行形状で判別）**: フィールドの有無でスキーマ判別する方式は、改訂を重ねるほど判別ロジックが複雑化する

## Decision

- log.jsonl エントリと processed.jsonl 台帳レコードの両方に `v`（number、**必須**）を導入する。今回のスキーマ改訂後の版数は **2**（`"v":2`）
- 読み側規約を正典（store-format.md）に明文化する: **`v` フィールドなし = v1（初版スキーマ）と解釈する**。既存データは書き換えない
- 表記の注意: サイクル名「worklog v1.1」はパイプライン全体の改訂名であり、スキーマ版数 `v` とは別物（doc に注記する）

## Consequences

- 良い影響: 将来のスキーマ改訂時、読み側（worklog-extract）が行ごとの版数を機械判別できる。プラグイン更新タイミングのばらつきによる新旧混在に耐える
- コスト・留意: 全レコードに 1 フィールド増える。スキーマ改訂時は `v` のインクリメントと読み側の互換規約更新が必須手順になる
- Issue-0026 は本 ADR で close する
