# ADR-0050: worklog の id 採番衝突は追記直前の再カウントと追記後の読み直し検証で対処する

- **Status**: Accepted
- **Date**: 2026-07-17

## Context

id 採番は「`<folderName>/log.jsonl` を読み、同一 date のエントリ数 + 1 を NN とする」方式（ADR-0045）。同一プロジェクトで複数セッションを並行稼働させた場合（git worktree 運用・複数ウィンドウ・サブエージェント併用）、両セッションが同じ件数を読んで同じ NN を採番する競合がある（read-count-append の非原子性）。id は処理済み台帳との突合キーであり、重複 id は処理済み判定の誤りに直結する（Issue-0027）。現行は個人・単独運用で発生確率は低い。

## Considered Alternatives

- **id にセッション識別子・時刻を混入**: 一意性は構造的に保証されるが、人間可読性が下がり、id フォーマット変更が台帳突合キーへ波及する。発生確率の低さに対して過剰
- **運用回避の規範のみ**: コスト最小だが発生時の検出手段がなく、静かに壊れる
- **据え置き**: 同上の理由で検出手段がない

## Decision

スキーマ変更なしの二段構えで対処する:

1. **追記直前の再カウント**: エントリ構築後、追記の直前に log.jsonl を読み直して採番する（競合窓の最小化）
2. **追記後の読み直し検証**: 追記後に log.jsonl を読み直し、自行の id が他エントリと重複していないかを確認する（ADR-0038 の読み直し規範と整合）。重複を検出した場合、**自分が書いた行のみ id を再採番して書き直す**。これは追記専用原則の唯一の例外として正典に明記する（台帳突合レコードが発生する前・自分が書いた直後の行の修復に限るため安全）

## Consequences

- 良い影響: 発生確率の低いリスクに対し、スキーマ変更なし・既存規範（ADR-0038）との整合で検出・回復手段を持てる
- コスト・留意: 記録時の読み取りが 1 回増える。検証と回復の間にも理論上の競合窓は残る（完全排除ではなく検出・回復可能性の確保）。並行記録が常態化して実害が出た場合は id 一意化（識別子混入）を再検討する
- Issue-0027 は本 ADR で close する
