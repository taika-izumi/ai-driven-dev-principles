# ADR-0052: worklog の定性材料（AI の誤答側・損失規模）はフィールド追加でなく運用ガイドで扱う

- **Status**: Accepted
- **Date**: 2026-07-17

## Context

エントリスキーマの細部レビュー（Issue-0029 の指摘 1・3）で 2 つの素材欠落が指摘された:

1. corrections（人間の指示）は「正解側」しか残らず、「指示がなければ AI が何をしようとしていたか（誤答側）」が残らない。スキル化時の「〜するな、〜せよ」対比構造の前半素材が欠落する
2. 抽出ランキングの「delta 重み」の判断材料として損失規模（この躓きで何分ロスしたか等）の記録がない

いずれも任意フィールド追加（`ai_default` / `impact` 等）で構造化する案があった。

## Considered Alternatives

- **任意フィールドを追加する**: フィールドの存在自体がチェックリストとして働く利点はある。しかし (1) 読み手（worklog-extract）は LLM であり、定性的な読み物は本文から同精度で読み取れる（構造化が報われるのは group-by・件数集計に使う機械的キーのみ）、(2) 任意フィールドは記録者裁量で歯抜けになり、分析側は本文読解フォールバックを持つことになって二重管理になる、(3) 「context と ai_default のどちらに書くか」等の境界判断が記録のたびに発生し粒度の揺れ（Issue-0023 と同種の問題)を新たに作る、(4) v フィールド導入（ADR-0049）により後からのフィールド追加は安いが、一度足したフィールドの除去は高くつく（可逆性の非対称）

## Decision

フィールドは追加せず、worklog-record の運用ガイドとして明文化する:

1. **誤答側**: corrections を書くとき、AI の当初挙動が自明でなければ `context` に 1 行添える
2. **損失規模**: 損失が大きかった場合は `friction` 本文に規模感（手戻り回数・時間ロス等）を含めてよい

実運用で「本文からの読み取りでは不足」と判明した時点で、フィールド昇格を課題起票して再検討する。

## Consequences

- 良い影響: スキーマの契約表面を増やさずに素材欠落を埋める。記録時の境界判断負荷を増やさない
- コスト・留意: ガイドの遵守は記録者（AI）の運用に依存し、フィールドのような構造的強制はない。チェックリスト効果はスキル doc の手順明記で代替する
- Issue-0029 の指摘 1・3 は本 ADR で対処（指摘 2 は ADR-0051）。3 指摘の対処確定をもって Issue-0029 を close する
