# ADR-0056: retrospective を課題抽出記録に純化し、Went Well / Tech Notes 観点を worklog パイプラインへ委譲する

- **Status**: Accepted
- **Date**: 2026-07-31

## Context

worklog パイプライン導入（ADR-0044〜0047）以前に設計された `retrospective` スキルは、5観点（Done / Went Well / Struggled / Tech Notes / Issues）のヒアリングを既定手順としていた（ADR-0010、ADR-0021 で一部改定）。しかし実運用では乖離が拡大していた:

1. **簡易実施が多数派**: LoopForAlpha では 6 回中 5 回、本リポジトリでも直近 2 サイクル連続で、ユーザー指示により「AI が 5 観点の案を一括提示 → ユーザーは起票判断のみ」の簡易形式で実施された（Issue-0035。worklog 根拠エントリ `LoopForAlpha-2026-07-24-01` / `MakeAiInstructions-2026-07-18-03`）。
2. **簡易実施の形式が非定型で規約違反も発生**: 簡易実施 2 件は見出し構成が互いに異なり、`docs/records/retrospectives/README.md` インデックスへの行追加が 2 件とも漏れていた（何を省いてよいかが未定義だったため）。
3. **worklog との役割重複**: `worklog-record`（ADR-0044〜0047）が節目ごとに delta（friction / corrections）と skillification_hint を中央ストアへ記録し、`worklog-extract` が横断走査してスキル化候補に変換する消費経路が確立した。これにより Struggled / Tech Notes の記録価値は worklog 側とかなり重複した。
4. **Went Well / Tech Notes に読み手がいない**: retrospective ファイルの各観点を活用経路で棚卸しした結果、後続サイクルで実際に読み返されるのは「課題の詳細記録（issue 起票の正本。ADR-0028）」のみだった。Tech Notes の横断再利用の仕組みは存在せず（Issue-0021）、一方 worklog には extract という再利用装置が既にある。

さらに、スキル化に有用な知見が現行 worklog-record のゲートで捕捉できるかを検証した:

- Tech Notes の実体はほぼ「躓いて発見した罠・回避策」であり、発生した節目に friction として記録済みになる
- Went Well は「既存規範が機能した」（ゲート (a) で除外。既存ルールの動作確認でありスキル化素材ではない）「AI が自律でうまくやった」（ゲート (b) で除外。毎回再現できるならスキル化不要）「人間の指示で成功した」（corrections として記録済み）に分解され、スキル化に有用な成分は捕捉済みか、捕捉不要として意図的に弾かれている

## Considered Alternatives

- **(a) スコープ**: ① Issue-0035 の範囲で簡易モードを正式な選択肢として追加するのみ / ② worklog 導入後の文脈で retrospective の役割自体を再定義する / ③ 簡易形式へ全面統一し完全版を廃止する。→ **② を採用**。①は「毎回省かれる観点」を公式に温存し、重複の根本原因が残る。役割再定義の結論として形式を導くほうがスキルが小さくなる。
- **(b) 残す情報**: ① 課題詳細＋最小サイクル文脈の 2 情報に絞る / ② 5観点を維持し重複は粒度差（節目 vs サイクル）として許容する / ③ 課題抽出を核にしつつ Tech Notes だけ worklog 転記ゲートとして残す。→ **① を採用**。活用経路の棚卸しで読み手が確認できたのはこの 2 情報のみ。②は読み手不在の記録の二重化を温存する。③は観点名を温存しスキルが太る。
- **(c) worklog への誘導**: ① 手順末尾に「サイクル俯瞰で未記録 delta があれば worklog-record を呼ぶ」確認 1 行を置く / ② 誘導を置かず既存の start-work Post ラッパー配線に任せる。→ **① を採用**。Post ラッパーの視点は「直前の作業の delta」であり、サイクル全体を俯瞰した記録漏れの総ざらい視点は他に存在しない。1 行の安価な保険として追加する。
- **(d) rubber-duck 独立レビュー**: ① 既定は実施せずユーザー要求時のみのオプション工程とする / ② 既定で実施（現行維持） / ③ 条件付き実施（抽出 0 件時など）。→ **① を採用**。簡易実施 7 回（2 プロジェクト合算）で省略による実害の記録がなく、抽出漏れの主な安全網は Phase 0 の材料読み込みと AI の一括提示工程に移っている。③は発動条件の設計・判定が必要でスキルが複雑化する。
- **(e) 形式の数**: ① 単一形式に統一（開始時のモード選択なし） / ② 新形式を既定としつつ旧 7 セクション形式もユーザー明示要求時の選択肢として残す。→ **① を採用**。純化後のスキルは実質「旧簡易版の定型化」であり、2 形式維持は毎回の選択往復と使われない側の形骸化を生む。ヒアリングの厚みは形式ではなく会話の自由度で調整できる。②は旧形式の Went Well / Tech Notes が本 ADR の廃止決定と矛盾する。
- **(f) フロー課題の起票経路**: ① delta 型は原則 worklog 経路へ譲り、緊急時と構造観察型のみ retrospective から起票する振り分け規則を導入 / ② フロー課題の起票パスを retrospective から全廃する / ③ 振り分けせず両経路で起票し重複は合流規則（worklog-extract 手順 8 / ADR-0031）に任せる。→ **① を採用**。フロー課題は「delta 型」（作業時点の躓き・人間の指示として worklog の記録ゲートで捕捉できる。例: Issue-0015/0033〜0035）と「構造観察型」（作業時点の delta が存在せず、サイクル・体系の俯瞰で初めて見える欠落。例: Issue-0021。worklog の記録ゲートは friction / corrections を要求するため原理的に捕捉不能）に分かれる。③は同一情報の二重処理でトークンを浪費する。②は構造観察型の受け皿を失い、worklog-extract がオンデマンド・低頻度実行（単発エントリの扱いも未定義 = Issue-0036）であることから緊急対処も遅延する。

## Decision

1. **retrospective の役割を「サイクル末尾の課題抽出記録（issue 詳細の正本）」に純化する**。残す情報は次の 2 つに限定する:
   - **課題の詳細記録**（事象 / 原因 / 影響、および system / flow 分類）— issue が「要約＋ライフサイクル管理」、retrospective ファイルが「詳細の正」という分担（ADR-0028）は維持する
   - **最小のサイクル文脈**（対象サブプロジェクト・期間・merge コミット・関連 plan / ADR へのポインタ数行）— 課題詳細を将来単独で読んで理解するためのヘッダ
2. **Went Well / Tech Notes を retrospective の観点から廃止する**。これらのうちスキル化に有用な成分は worklog パイプライン（friction / corrections / skillification_hint → extract → skillify）が捕捉する。
3. **手順末尾に worklog 総ざらい確認を 1 行追加する**: サイクル全体を俯瞰し、未記録の delta（躓き・人間の指示）に気づいたら `worklog-record` を呼んで記録する。新しい観点セクションは設けず、worklog の語彙（delta）で統一する。
4. **rubber-duck 独立レビューはオプション工程とする**。既定では実施せず、ユーザーが求めた場合のみ実施する。レビュー観点は「課題の抽出漏れがないか・system / flow 分類が妥当か」に絞る。
5. **形式は単一とする**。開始時の形式選択（完全版 / 簡易版）は設けない。ヒアリングは「AI が Phase 0 の材料から課題案を一括提示し、ユーザーが修正・起票判断を行う」方式を標準とする。
6. **フロー課題に振り分け規則を導入する**。課題候補ごとに「作業時点の delta（躓き・人間の指示）として worklog に記録済み／記録可能か」を判定する:
   - **delta 型 かつ 急がない** → issue は起票しない。worklog 記録の有無を確認し、未記録なら worklog 総ざらい確認（決定 3）で記録する。仕組み化の要否は worklog-extract の再発裏付けに委ねる
   - **delta 型 だが ユーザーが早期対処を要すると判断** → 即起票する。後日 worklog-extract が同クラスタを検出した場合は既存 issue へ統合される（worklog-extract 手順 8 の合流規則）
   - **構造観察型（delta として表現できない）** → issue 経路で扱う（worklog の記録ゲートは friction / corrections を要求するため原理的に保持できない）。ただし発見の主経路は retrospective ではなく**サイクル中の随時起票**（decision-log の未決事項起票・作業中の気づきの即時起票。実績: Issue-0018 は設計議論中、Issue-0021 は ADR 台帳監査中に起票）。retrospective は発見装置ではなく**起票漏れの最終チェックポイント**として、課題案提示の末尾に「このサイクル中に言語化されたが未起票の気づきはないか」の確認 1 問のみを置く。システム体系全体を走査する構造チェック工程は設けない（毎サイクルのトークンコストが大きく、網羅走査は推測的・低品質な課題を量産するリスクが高い）

   対象システム固有の課題は従来どおり無条件で retrospective が起票する（worklog-extract の出力はスキル化・ルール化候補であり、対象システムのバグ・設計負債は扱わない）。

本決定は ADR-0010（5観点ヒアリング構成）と ADR-0021（決定 5: Tech Notes の汎用知見への限定）を一部改定する。ADR-0021 の決定 1〜4（課題抽出への限定・バックログ記録のみ・system/flow 分類・2 フォルダ出力）は本決定の前提として維持する。

## Consequences

- **良い影響**: 実運用の多数派（簡易実施)と規定が一致し、毎回同じ簡易化指示を出す往復コストが消える。読み手不在の記録が廃止され、知見の記録は消費装置（worklog-extract）を持つ worklog へ一本化される。Issue-0021（Tech Notes の横断再利用の仕組みがない）は「再利用すべき知見は worklog に置く」ことで解消方向となる。
- **コスト・悪い影響**: サイクル俯瞰での自由な言語化（Went Well の振り返り効果そのもの）が形式から消える。ユーザーが望む場合は対話として実施できるが、記録としては残らない（残す価値がある気づきは delta として worklog へ記録する運用に変わる）。
- 過去の retrospective ファイル（7 セクション形式・簡易形式）は ADR-0011 の上書き禁止規約に従い改変しない。新形式は本決定以降に作成するファイルから適用する。
- 波及更新: `skills/retrospective/SKILL.md` / `template.md` / `flow-template.md` / `docs/records/retrospectives/README.md` / `skills/start-work/SKILL.md`（マッピング表の文言）/ `CLAUDE.md`（検証節の retrospective 記述）。CLAUDE.md を変更する場合は `scripts/sync-template.ps1` の実行が必要。
- Issue-0035 は本決定＋実装で close 見込み。Issue-0021 は解消方向の再評価対象となる。
- **部分修正（ADR-0106）**: メイン記録テンプレートの Branch 欄は「merge済み: <sha>」から取り込み方式の明示欄（マージコミット / squash / fast-forward）へ改定された。最小サイクル文脈の骨格は現役のため、Status は Accepted のまま維持する
