# ADR-0057: Post ラッパーの消化結果を handoff に残し、未入場は事後突合で回収する

- **Status**: Proposed
- **Date**: 2026-08-01

## Context

Issue-0037 の対策検討にあたり、中央ストアと git 履歴を実測した結果、起票時の前提（「Post ラッパーへ戻る契機が構造的に存在せず発火が起きない」）が反証された。ADR-0047 の配線自体は成立しており、LoopForAlpha では 2026-07-17〜07-30 に handoff コミット 89 件に対し worklog エントリ 88 件が同一オーダーで連動している。

真の課題は**消化漏れの検出不能性**にある。`session-handoff` update は実行するとファイルが残るため漏れれば履歴の空白として現れるが、`worklog-record` は**未発火と記録ゲート（ADR-0044）による棄却が外形的に区別できない**。どちらも「中央ストアに行が増えない」という同一の結果になる。

観測された失敗モードは3種類（Issue-0037 に証拠つきで記載）。

- 失敗モード1（部分消化）: Post ラッパーには入ったが、handoff update を実施した時点で「区切りの記録は完了した」と判断し worklog-record を消し込まない
- 失敗モード2（完全未入場）: マイルストーンで Post ラッパー自体に入らず、handoff update と worklog-record が揃って漏れる
- 失敗モード3（発火契機の定義漏れ）: コンテキスト逼迫によるセッション切り替え直前が発火契機として定義されていない（本 ADR の対象外。ADR-0058 で扱う）

加えて、現在の高い発火率が**ガイドライン体系の外側の機構に依存している**ことが判明した。LoopForAlpha の Claude Code プロジェクトメモリに `feedback-follow-mandatory-steps`（2026-07-22 作成、失敗モード1 の発生直後）が存在し「Post ラッパーは項目を1つずつ明示的に消し込むこと」と記載されている。本リポジトリには該当するメモリがない。この機構はツール固有（Claude Code のみ）・プロジェクト固有・プラグイン配布の外側・不可視であり、体系の信頼性の根拠にはできない。

成功基準は利用者判断により「**漏れが後から検出できること**」とする。発火の強制（フック等の環境側機構）は必要性を認めた時点で別途扱う。

## Considered Alternatives

- **A: handoff への相乗りのみ** — `session-handoff` の update/finalize フォーマットに Post ラッパーの消化結果欄を追加し、`worklog-record` の判定結果を1行残す。失敗モード1 は「handoff を書く行為そのものが worklog の判定結果を要求する」形になるため構造的に潰れる。改定対象が2スキルに収まり最小。ただし失敗モード2 では欄ごと書かれないため検出できない
- **B: 中央ストアに棄却も記録** — `worklog-record` がゲート棄却時にも最小行を追記し、ストア単体で発火の有無を完全判別できるようにする。スキーマ v3 化（ADR-0045 / 0048〜0053 の改定）が必要。記録ゲートは大半を弾く設計のため棄却行が実記録を上回り、`worklog-extract` の走査母数を汚す。かつ失敗モード2 は依然検出できず、コストに対する利得が A を下回る
- **C: A ＋ 事後突合** — A に加え、`retrospective` Phase 3 の「worklog 総ざらい」を「サイクル中のマイルストーン数と worklog エントリ数の突合」まで具体化し、`start-work` Phase 0 で前回 handoff の消化結果欄の空白を検査する

## Decision

選択肢 C を採用する。失敗モード1 を前段（handoff への相乗り）で潰し、すり抜けた失敗モード2 を後段（事後突合）で回収する二段構えとする。具体的には以下の3点を定める。

1. **消化結果の記録**: `session-handoff` の update / finalize 操作のフォーマットに Post ラッパーの消化結果欄を設け、マイルストーンごとに `worklog-record` の判定結果を1行残す。記録した場合はエントリ id を、記録ゲートで棄却した場合はその旨を書く
2. **事後突合**: `retrospective` Phase 3 の worklog 総ざらいを、handoff の完了済みタスクおよび git のコミット履歴から数えたマイルストーン数と、中央ストアの当該サイクル分エントリ数を突合する手順として具体化する。差分があれば未記録の delta を洗い出す
3. **前回分の検査**: `start-work` Phase 0 でハンドオフを読む際、消化結果欄が空白のマイルストーンがないか検査する

失敗モード2 を**即時に**検出することは原理的に不可能である（書かれないものは検出できない）。これを受け入れ、外形的に必ず残るもの（git のコミット履歴）との事後突合で回収する設計とする。

## Consequences

- **良い影響**: 失敗モード1 が構造的に解消する（handoff の記入が worklog の判定を要求するため、「handoff を更新したから記録は済んだ」という思い込みが成立しなくなる）。失敗モード2 は事後突合で回収される。痕跡の置き場が handoff と中央ストアという既存の成果物であるため新規機構が増えず、git 管理・ツール中立で配布先へ可搬である
- **コスト・留意**: handoff のフォーマットが1欄増える。`skills/session-handoff/` `skills/start-work/` `skills/retrospective/` の3スキルを改定するためプラグイン更新が必要（ADR-0055）。事後突合は記録が末尾に寄るため delta の鮮度が落ちる（`context` や `procedure` の解像度低下、ADR-0053 の記録単位からの逸脱）。この鮮度低下は前段が機能する限り例外的に留まる想定である
- 発火の強制手段（フック等）は本決定の対象外とした。必要性を認めた時点で別途決定する
- 本決定は既存3スキルの挙動変更を伴う。実装完了・検証後に Accepted へ昇格する（ADR-0019）
