# ADR-0060: ADR 粒度の点検を決定追記の手順に組み込み、昇格前の一括点検を受け皿とする

- **Status**: Proposed
- **Date**: 2026-08-03

## Context

ADR-0059 が分割単位（後から探しに来るときの問い）を定めたが、その判定をいつ行うかは未定だった。実害の出た経路は起票時ではなく**起票後の追記**である。

LoopForAlpha の ADR-0034 は、起草（12:49）→ 独立レビュー反映で決定を追記（13:39）→ さらに追記（16:41）と肥大し、同日 17:09 にユーザー指摘で4本へ分割された。AI 側からの分割提案はなかった（中央ストア `LoopForAlpha-2026-07-19-02`）。起票時点の粒度は妥当だったため、起票時チェックだけでは捕まらない。

先送りコストは repo の様式で大きく変わる。

- 本リポジトリ: ADR は「根拠の出典」として ADR 単位で引かれる。決定の序数を指す参照は docs/skills 全体で5回しかなく、分割は「移動した決定を指す参照がどれか点検する」作業に留まる
- LoopForAlpha: spec / plan / テストが決定単位でトレースするため `ADR-0034 Decision 9` 形式の参照を用いる（docs 全体で275回）。分割は序数の振り直しを伴い、置換の適用順序を誤ると二重置換が起きる
- 先送りによる影響面の拡大も実測されている。ADR-0034 を参照するファイルは分割時点（起草の4時間20分後）で10ファイル、Accepted 昇格時点（5日後）で24ファイル、2週間後で40ファイルへ増えた

ガイドラインは配布物であり配布先の様式を選べないため、重い側（決定単位でトレースする repo）を前提に設計する。

## Considered Alternatives

- **起票時のみ点検する**: 実装は最小だが、実際に肥大した経路（起票後の追記）を塞げない
- **昇格前の一括点検のみ**: 消化項目を増やさず、不可逆点（コミットメッセージ・上書き禁止の振り返りファイル）の手前で1回だけ判定できる。ただし影響面が起草直後の約2.4倍に膨らんだ状態での分割になり、その間に書かれた spec / plan は肥大した ADR の枠組みを前提に構成される
- **追記手順への組み込み ＋ 昇格前の一括点検（採用）**: 肥大が生じる瞬間に、影響面が最小のうちに検出する。一括点検は追記を伴わない肥大の受け皿として残す

## Decision

粒度の点検を次の2箇所で行う。

1. **決定の追記時**: Proposed の ADR に決定を追記するとき、追記手順の一部としてタイトルと追記内容を突合する。タイトルがその決定にも答えていなければ、AI 側から分割を提案する。**独立した消化項目としては設けない**（追記という既に実行中の編集操作に内包させる）
2. **Accepted 昇格の直前**: `decision-log` の「承認の昇格（Proposed → Accepted）」手順の第1ステップとして、タイトルが本文の全決定に答えているかを突合する。答えていない決定があれば分割してから昇格する

規範の置き場所は `decision-log` に一本化する。昇格を促す側（`start-work` の Post ラッパー項目1、セッション終了処理）は「承認の昇格」手順を参照するに留め、点検内容を重複して記述しない。

追記時の点検を一次経路、昇格前の点検を受け皿とする。

## Consequences

- 肥大が生じる瞬間に検出するため、分割時の影響面が最小になる（LoopForAlpha の実測では10ファイル対24ファイル）
- 発火契機を新設しないため、Post ラッパーの消化項目は増えない（Issue-0037 で扱った消化漏れのリスクを増やさない）
- 昇格前の点検を `decision-log` 側に置いたことで、Post ラッパー経由でもセッション終了処理経由でも同じ点検が働き、規範の二重記述が生じない
- 追記のたびにタイトル突合が走るため、追記が頻繁なサイクルでは判定の回数が増える。ほとんどは「分割不要」で終わる
- 昇格前の点検で分割が生じた場合、その時点の参照は全件点検の対象になる。この経路のコストは一次経路の実効性に依存する
