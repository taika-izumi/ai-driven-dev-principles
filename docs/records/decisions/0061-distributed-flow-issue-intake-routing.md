# ADR-0061: 配布先の flow 課題は delta 型を worklog 経路へ委ね、構造観察型のみ手で取り込む

- **Status**: Accepted
- **Date**: 2026-08-05

## Context

ガイドライン配布先である LoopForAlpha に、開発フロー/ガイドライン課題（`docs/working/issues/flow/`）が 21 件 open で蓄積している（最古 2026-07-11）。`docs/overview/folder-structure.md` 7.3 は「配布先プロジェクトの `flow/` 課題は、ガイドライン repo へ申し送り済み（または対応済み）で close する」と定めており、全件が本リポジトリへの申し送り対象にあたる。しかし取り込みの**経路**は定義されていなかった。

本リポジトリは ADR-0056 で「delta 型（作業時点の躓きとして現れる）は worklog パイプラインへ、構造観察型（体系の俯瞰で初めて見える）は issue 経路へ」という振り分けを既に決めている。ただしこれは 1 リポジトリ内での `retrospective` と worklog の棲み分けとして定めたものであり、**リポジトリ間の取り込みには適用されていなかった**。

2026-08-05 に 21 件を手で読み、主題別にクラスタ化して検証したところ、次が判明した。

- 検証の検出力に関する 4 件（LoopForAlpha-0084 / 0069 / 0054 / 0034）は、**一般形が既に本リポジトリ側に存在していた**。0069 の対処は Issue-0033 の定型項目リスト項目 8 に、0054 は Issue-0034 の代表エントリ `LoopForAlpha-2026-07-28-11` と同一事象として、いずれも `worklog-extract` の 2026-07-31 走査が `adopted` 判定済みだった
- 0084 の一般核は中央ストアに `LoopForAlpha-2026-08-04-07`（`scope: general-candidate`、title「検出器の検出力を対照で確かめる」）として在庫しており、再走査すれば正規経路で上がる状態だった
- **手でのクラスタ化は `worklog-extract` が設計上担う仕事と重複していた**

一方、クラスタ C にあたる 6 件（LoopForAlpha-0085 ハンドオフ肥大 / 0086 振り返りカデンス / 0087 Status 値不整合 / 0042 規模再見積もり / 0008 免除条件 / 0013 素材消失）は、issue 自身が**構造観察型**と振り分け判定を明記しており、ADR-0056 の定義上 worklog では捕捉できない。

## Considered Alternatives

1. **全件を手で読み、一般形へ変換して本リポジトリへ起票する** — 網羅的だが、delta 型については worklog パイプラインと二重作業になる。配布先が増えると手作業が件数に比例して増え、パイプラインを作った意味が失われる
2. **全件を worklog 経路へ委ねる** — 構造観察型は作業時点の delta として現れないため worklog に載らず、取りこぼす。実測でも LoopForAlpha-0085/0086/0087 は retrospective の構造観察から起票されており、worklog エントリの裏付けを持たない
3. **issue 自身の振り分け判定に従って経路を分ける** — 採用

## Decision

配布先の `flow/` 課題は、その issue が持つ**振り分け判定**に従って処理する。

- **delta 型** — 手で運ばない。`worklog-extract` の再走査に委ねる。根拠エントリが中央ストアに在庫しているため、再発回数・出所プロジェクト数・`corrections` 比率という定量的な優先度指標つきで上がってくる
- **構造観察型** — 手で取り込む。worklog には載らないため、これが唯一の経路になる
- **振り分け判定の記載がない旧い課題**は、取り込み時に判定する

配布先の close は `folder-structure.md` 7.3 のとおり「申し送り済み」で行う。ただし **本リポジトリ側の受け皿（新規 issue、または既存 issue への追記行）が実在することを確認してから** close する。順序を逆にすると申し送りが蒸発する。

## Consequences

- **手で運ぶ対象が 21 件から構造観察型のみへ絞られる。** 作業量が減り、delta 型は優先度を定量的に測れる正規経路に乗る
- **配布先が増えても、手作業は構造観察型の件数にしかスケールしない。** 全件を手で読む案（代替案 1）はガイドラインの配布先数に比例して破綻するため、この差は配布先が 2 つ以上になった時点で効く
- **worklog パイプラインの稼働が前提条件になる。** `worklog-extract` / `worklog-skillify` が滞ると、delta 型の申し送りが全面的に滞留する。実際 2026-07-31 走査の `adopted` 4 件のうち 3 件（本リポジトリ Issue-0033 / 0034 / 0015）は、以後 3 サイクルにわたり着手されないまま open で残っている
- **振り分け判定は起票者（配布先で作業した AI）が行うため、誤判定はそのまま取りこぼしになる。** 構造観察型を delta 型と誤判定すると、worklog に根拠エントリが無いため再走査でも上がらず、どちらの経路からも落ちる
- 申し送りの起票経路・クロスリポジトリの Issue 参照形式・worklog 経路経由での close トリガーは本 ADR では決めていない（Issue-0041）
