# ADR-0063: 配布先からの申し送りを起票経路として定義し、受け皿の実在確認を close トリガーとする

- **Status**: Proposed
- **Date**: 2026-08-05

## Context

`docs/overview/folder-structure.md` 7.3 は「配布先プロジェクトの `flow/` 課題は、ガイドライン repo へ申し送り済み（または対応済み）で close する」と定めており、この規範は本リポジトリと配布先の両方に同一文で存在する。しかし一度も適用されておらず、LoopForAlpha の flow 課題は 20 件すべてが open のまま（最古 2026-07-11）だった。原因は規律違反ではなく、3 点の未定義である（Issue-0041）。

**(a) 起票経路が実態を反映していない。** 7.2 が定める起票経路は「振り返り由来」「議論由来」の 2 つのみで、実運用にある「worklog-extract 走査由来」（本リポジトリ Issue-0033 / 0034 の起票元がこれ）と「配布先からの申し送り由来」が無い。取り込み時に新規起票するか既存課題へ追記するかの基準も無い。

**(b) クロスリポジトリの参照形式が未定義で、既に衝突している。** 課題番号はリポジトリ内で一意に採番されるため（7.2）、無修飾の `Issue-NNNN` はリポジトリをまたぐと別の課題を指す。LoopForAlpha の `flow/0034`（編集ツールが不可視文字のエスケープ表記を正規化する）と本リポジトリの `flow/0034`（非コード成果物の確定前レビュー工程がない）は、番号が同じで内容の異なる別課題である。worklog 台帳（`processed.jsonl`）の `ref` フィールドもリポジトリ修飾のない相対パスで記録されており、slug を読まなければ判別できない。

**(c) worklog 経路に close の契機が無い。** 7.3 は「課題 → 課題」の申し送りを想定しているが、実際に起きたのは「worklog エントリ → ガイドライン repo の課題」であり、この経路には配布先を close する契機が誰にも割り当てられていない。`LoopForAlpha#Issue-0069` と `LoopForAlpha#Issue-0054` は、一般形が本リポジトリ Issue-0033 / 0034 として起票された時点で申し送り済みだが、配布先では open のまま残っている。ADR-0061 で delta 型を worklog 経路へ委ねると決めたため、これが主経路になる。

## Considered Alternatives

1. **close の条件を「ガイドライン側で解決済み」に変える** — 追跡は厳密になるが、配布先が解決を待って open を保持することになり、プラグイン更新で修正が自動的に届く実態と合わない。配布先が増えるほど追跡コストが線形に増える
2. **配布先の課題番号をガイドライン repo でも引き継ぐ** — 参照の衝突は解決するが、採番規則（リポジトリ内の通し連番）を壊す。配布先が 2 つ以上になると番号空間が競合して成立しない
3. **起票経路を 4 つに拡張し、参照はリポジトリ名で修飾し、受け皿の実在確認を close トリガーとする** — 採用

## Decision

- **起票経路を 4 つとする**（振り返り由来 / 議論由来 / worklog-extract 走査由来 / 配布先からの申し送り由来）。取り込み時、一般形が既存課題に含まれるなら新規起票せず「検討状況」へ追記し、無い場合のみ新規起票する。判断は起票前にインデックスと中央ストアの在庫を突合して行う
- **他リポジトリの課題参照は `<repo>#Issue-NNNN` で修飾する。** worklog 台帳の `ref` にもリポジトリ名を含める。既存の記述には遡及適用しない
- **配布先の close トリガーは「ガイドライン repo 側の受け皿が実在することを確認した時点」とする。** worklog 経路で申し送られた場合も、起票が済んだ時点で配布先の対応課題を close する

## Consequences

- **配布先の `flow/` セクションがバックログとして機能するようになる。** 現状は恒久的な駐車場になっており、20 件の open は「配布先で着手すべき作業」を 1 件も表していない
- **worklog 経路で申し送られた課題にも close の契機が生まれ、ADR-0061 が定める主経路が閉じる**
- **取り込みの初動コストが増える。** 起票前にインデックスと中央ストアの在庫を突合する手順が加わる。ただし重複起票の手戻りより小さい（2026-08-05 の検討では突合を後回しにしたため、配布先 20 件を精読した作業の大半が `worklog-extract` の仕事と重複した）
- **`<repo>#Issue-NNNN` 形式は既存の記述に遡及しない。** 過去の無修飾参照は残るため、読み手は文脈で判断する必要がある。移行期の曖昧さを受け入れる代わりに、既存文書の一括書き換えを避けた
- 配布先が構造観察型を delta 型と誤判定した場合、worklog に根拠エントリが無いため再走査でも上がらず、どちらの経路からも落ちる（ADR-0061 の Consequences と同じリスク。本 ADR では解消しない）
