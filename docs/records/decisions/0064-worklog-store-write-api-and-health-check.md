# ADR-0064: 中央ストアの書き込みは行終端を明示できる API に限定し、健全性検査は正負の対照を同梱する

- **Status**: Proposed
- **Date**: 2026-08-05

## Context

中央ストアは ADR-0054 で「UTF-8・BOM なし・LF 固定」と契約されている。しかし契約を満たす手段として示されていた `Add-Content -Encoding utf8NoBOM` は、`-Encoding` がエンコーディングのみを制御し行終端子を制御しないため、Windows では CRLF を書く。**契約と、契約を満たすために示された手段が直接矛盾していた**（`LoopForAlpha#Issue-0050`）。

実測では `LoopForAlpha/log.jsonl` に CR が混入しており、その数は起票時（2026-07-27）の 3 行から 2026-08-05 時点で 5 行へ増えていた。累積している。混入していたのは 2026-08-01〜03 に書かれた 5 エントリ（L89〜92, 94）で、いずれも PowerShell 経路で書かれたものだった。

読み側については `worklog-extract` 手順 2 が「BOM・CRLF・非 UTF-8 を検出して報告・停止する」と規定していたが、**具体的な検出手段が定義されていなかった**（Issue-0032）。結果としてこの検査は 2026-07-31 の走査で CR を素通りさせている。規範として書かれた検査が、一度も発火を確かめられていない状態だった。これは `LoopForAlpha#Issue-0084`（検出器自身の検出力が確かめられず「常に 0 件を返す検査」が生まれる）が主張する事象そのものであり、本リポジトリのスキル内で成立していた。

同じ罠は本リポジトリ内で既に一度解かれている。`scripts/sync-template.ps1` は ADR-0033 で `[System.IO.File]::WriteAllText` + `UTF8Encoding($false)` へ切り替えており、「書き込み API の既定の行終端は明示しない限り環境に依存する」という知見は存在していた。worklog スキル側へ伝播していなかった。

## Considered Alternatives

1. **契約側を緩め、行終端を問わないことにする（読み側を universal newlines に統一）** — 安価だが、`references/store-format.md` の「LF 固定」を信じて素朴な行分割（`split("\n")` の各要素をそのまま文字列比較する等）を実装した後続が静かに壊る。契約を緩めるなら読み側の規律を別途課す必要があり、正味の複雑さは減らない
2. **書き側手段だけを直す** — 入口は塞がるが、既存の混入と、将来の別経路（別ツール・別 OS・別スキル）からの混入を拾えない。混入は検出されない限り累積する（実測で 3 → 5 行）
3. **書き側の手段を限定し、読み側に実行可能な検査を置き、その検査に正負の対照を同梱する** — 採用

## Decision

- **書き側**: 行終端を明示できる API に限定する。**`Add-Content` は使わない**。Python は `open(path, "a", encoding="utf-8", newline="\n")`、PowerShell は `[System.IO.File]::AppendAllText` と `UTF8Encoding($false)`、POSIX シェルは `>>`
- **読み側**: `skills/worklog-extract/scripts/check-store-health.py` を実行可能な検査として置く。BOM・CR・非 UTF-8・JSON パース不能行を検出し、1 件でもあれば終了コード 1 で走査を止める。バイト列を直接数える（grep 系では CR を検出できない）
- **検出器の検出力**: 検査へ `--self-test` を同梱する。既知の欠陥を含む入力 5 種（CRLF / 先頭 BOM / **中途 BOM** / 非 UTF-8 / 壊れた JSON）で発火すること（正の対照）と、正常な入力および JSON 文字列値の内部に U+FEFF を含む入力を誤検出しないこと（負の対照 2 種）を確かめる。検査スクリプトを変更したら対照を走らせてから使う
- **BOM の探索範囲**: ファイル先頭だけでなく**各行の先頭**を見る。ストアは追記専用のため、BOM は追記チャンクの先頭＝行頭に混入しうる（Issue-0032 が明記していた要求）。一方で全バイト走査にはしない。JSON 文字列値の内部に現れる U+FEFF を誤検出するため、行頭に限定することで検出漏れと誤検出の両方を避ける
- 既存の CR 混入は、内容不変のバイト正規化としてユーザーの明示 opt-in のもとで除去する（ADR-0054 の規定どおり）

## Consequences

- **契約と手段が一致し、以後の混入が止まる。** 既存の混入も 1 度の正規化で解消した（実測: CR 5 → 0、エントリ 106 件で内容不変を検証、バックアップ `log.jsonl.bak-before-crlf-normalize` を保持）
- **検査が緑であることに意味が戻る。** 正負の対照が無い間、`worklog-extract` の健全性検査は「実行され、緑を返し、しかし何も固定していない検査」だった。導入時の実測では self-test が正の対照 5 件すべてで発火し、実ストアに当てて既知の CR 5 個を検出して `exit=1` を返すことを確認している
- **対照そのものが検出器の盲点を暴いた。** 初版の実装は BOM をファイル先頭でしか見ておらず、Issue-0032 が明記していた中途 BOM の要求を満たしていなかった。にもかかわらず初版の self-test は PASS していた（正の対照が先頭 BOM しか持たなかったため）。**対照の網羅性が不足していれば、対照があっても検出器の欠陥は見えない**。この一件自体が `LoopForAlpha#Issue-0084` の再現であり、対照を書くときは「元の要求が挙げている失敗の形をすべて対照にしたか」を確認する必要がある
- **不可視文字を対照に使うときは入力側のガードが要る。** 負の対照へ U+FEFF を仕込む際、エスケープ表記が編集ツールによって生の文字へ正規化された（`LoopForAlpha#Issue-0034` の事象）。`chr(0xFEFF)` で構成し直したうえで、書き出したファイルにそのバイト列が実在することを検査するガードを対照へ同梱した。アサーション側だけでは入力側の欠落を検出できない
- **検査スクリプトが Python に依存する。** PowerShell を主とする本リポジトリの慣行から外れるが、バイト単位の読み書きと行終端の明示が確実である点を優先した。配布先で Python が無い環境では検査が実行できない（現時点で該当なし）
- **対照の同梱は検査を書くコストを上げる。** この規律を他の検査へどこまで一般化するかは本 ADR では決めていない（`LoopForAlpha#Issue-0084` として `worklog-extract` の再走査経由で上がる見込み）
- **スキル間の知見の伝播漏れは解消していない。** ADR-0033 で得た知見が worklog スキルへ届かなかった構図そのものは残っており、`LoopForAlpha#Issue-0044`（既知の gotcha が観察記録止まりで参照文書へ反映されない）と同型である
