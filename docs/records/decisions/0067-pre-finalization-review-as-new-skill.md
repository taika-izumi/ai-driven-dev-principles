# ADR-0067: 非コード成果物の確定前レビューは新規スキルとして立て、`start-work` から配線する

- **Status**: Accepted
- **Date**: 2026-08-05

## Context

Issue-0034 は「計画・仕様など非コード成果物の確定前に、実証を課した独立レビューを挟む工程がない」課題である。`worklog-extract` の初回走査で採用（`adopted`）され、根拠 7 件・`corrections` 比率が全クラスタ最高（人間が繰り返し「レビューは行われたか」を差し込んでいる型）・3 世代のモデルにまたがって再発している。

課題本文は対策の方向を 3 案挙げていた。

1. `requesting-code-review` の射程を非コード成果物へ広げる
2. `writing-plans` / `feature-block-design` の末尾に独立レビュー工程を必須ステップとして足す
3. 新規スキルを立てる

ADR-0069 により、案 1 と案 2 のうち `requesting-code-review` / `writing-plans` は選べない。いずれも superpowers プラグインのスキルであり、自リポジトリの編集対象にならない。**残る選択肢は「`feature-block-design` のみを拡張する」か「新規スキルを立てる」の 2 つ**である。

## Considered Alternatives

1. **`feature-block-design` を拡張する** — 自リポジトリのスキルなので編集できる。ただし `feature-block-design` が産出するのは**仕様**（`docs/current/specs/`）であり、**計画**（`docs/working/plans/`）は産出しない。計画を作るのは `writing-plans`（編集不可）である
2. **新規スキルを立て、`start-work` の Phase 2 から配線する** — 採用

## Decision

**非コード成果物の確定前レビューを新規スキルとして立てる。** `feature-block-design` の拡張では足りない。

決め手は根拠の所在である。Issue-0034 の**代表エントリ `LoopForAlpha-2026-07-28-11` は計画に対するレビューの記録**であり、`LoopForAlpha#Issue-0054` として配布先にも起票されている同一事象では、独立レビューが**計画中のテストコードを写経して実行し、10 件すべてが `CommandNotFoundException` で 1 件も動かないことを検出**している。`feature-block-design` だけを拡張すると、**最も強い根拠が指している成果物（計画）が対象から漏れる**。

配線は `start-work` の Phase 2 マッピング表に行を追加し、`writing-plans` および `feature-block-design` の完了後の次手として提示する。`start-work` は自リポジトリのスキルであり、superpowers 側の編集を要しない。

スキル本体の authoring は次サイクルに残る（ADR-0065）。authoring の入力として、根拠エントリと `LoopForAlpha#Issue-0054` から次を引き継ぐ。

- **観点は最低 3 つ**（敵対的／実装整合性／仕様適合）を立て、**モデルは前工程のレビューと変える**（Issue-0034 の根拠エントリ由来の運用ヒント）
- **「計画中のコードをスクラッチで実際に実行せよ」まで課す。** 自己レビューは記載内容の誤りは検出するが、載せる項目の選定漏れと既存コードとの相互作用は 1 件も検出できていない（実測）
- **レビューが狙うのは構造的な誤り**（タスクの順序 / 新旧の契約の食い違い / 自分が足した制約が自分の検証工程を止める / 境界の抜け）である。局所的・機械的な誤り（構文・スコープ・足場の配線）は直接実装したほうが最初の実行で数分のうちに露見するため、レビューの主目標に置かない（`LoopForAlpha#Issue-0054` の分析）
- **観点を並列で回す場合は隔離が要る**（ADR-0066 の B 群「並列に委譲し、かつ委譲先がファイルを書き換えるとき」）

## Consequences

- **計画と仕様の両方を 1 つの工程で覆える。** 成果物の種類ごとに別々のスキルへ分散させずに済む
- **superpowers への依存を増やさずに射程を広げられる。** 既存スキルの穴を、自リポジトリ側のスキルで補完する形（ADR-0069 の方針と整合。本 ADR はその第 1 例になる）
- **スキル数が増える。** `start-work` Phase 2 の選択肢が 1 つ増え、ナビゲーションの判断が 1 段複雑になる
- **発動条件（どの規模から必須にするか）は本 ADR では決めていない。** 3 観点の独立レビュー＋実証の実行はコストが大きく、閾値の設計を誤ると小規模な作業まで重くなる。authoring 時の設計事項として Issue-0034 に残す
- **`feature-block-design` は変更しない。** 新規スキルが仕様・計画の双方を受けるため、既存スキルへの二重の記述を避ける（ADR-0080 の実装で同スキルへ変更が入ったが、内容は提示規則への参照追加であり、レビュー手順の二重記述には当たらない。本条項の趣旨は維持される）
- **部分修正（ADR-0080）**: 本 ADR が定めた配線先の提示点「`writing-plans` および `feature-block-design` の完了後」は、ADR-0080 により spec 確定点（3 通り）と plan 確定点の 2 種へ一般化された。新規スキルとして立てる決定と `start-work` へ配線する決定は現役のため、Status は Accepted のまま維持する
