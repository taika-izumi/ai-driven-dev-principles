# ADR-0074: ハンドオフ剪定で落とした情報の受け皿は git 履歴のみとし、明示アーカイブを設けない

- **Status**: Proposed
- **Date**: 2026-08-06

## Context

Issue-0049（ハンドオフが単一ファイルへの時系列追記で肥大し、完了情報の剪定規約がない）の対処設計において、剪定した情報の受け皿をどこに置くかが論点になった。配布先（LoopForAlpha）ではハンドオフが 573 行・約 77KB に達し、セッション開始時の読み込みが分割読みを要する状態になっている。

剪定を規約化するには「落とした情報をどう復元可能にするか」を先に決める必要がある。ハンドオフはブランチごとに git 管理されており（ADR-0005）、Issue-0053（セッション再起動での振り返り素材消失）が示すとおり、剪定は素材消失と逆方向のリスクを持つ。

## Considered Alternatives

1. **git 履歴のみを受け皿とする（明示アーカイブなし）** — ハンドオフは git 管理なので、剪定で落とした情報はコミット履歴に必ず残る。新しい管理対象を増やさない。発見性は低い（どの版にあったかを探すコストが高い）
2. **アーカイブファイルを設ける**（`docs/working/handoff/archive/` へサイクル単位で退避） — 発見性は高いが、管理対象・規約が増える。アーカイブ自体が肥大し、問題の場所が移るだけになるリスクがある
3. **受け皿を情報の種類で分ける**（完了経緯は git 履歴、再利用価値のある申し送りは正本ドキュメントへ昇格、振り返り素材は retrospective ファイルへ） — 情報ごとに正しい行き先へ流れるが、剪定のたびに分類判断と複数ファイル更新が発生し、規約が複雑化する

## Decision

案 1 を採用する。**剪定で handoff から落とした情報の受け皿は git 履歴のみとし、明示的なアーカイブファイルは設けない。**

理由: 長期的な記録として必要な情報は、ハンドオフ以外の正本（ADR / issue / retrospective / worklog / spec）に既に記録されているはずであり、handoff 固有の記述（進行状態・申し送り）は役目を終えれば最悪失われてもよい。git 履歴から復元できれば十分である（ユーザー判断、2026-08-06）。

ADR-0005 の Consequences が示唆していた「`docs/handoff/archive/` への移動機構」は導入しない。

## Consequences

- 剪定の実行が単純になる（ファイル内の削除のみ。退避先への転記・分類判断が不要）
- アーカイブファイルの管理・肥大という二次問題を持ち込まない
- 落とした情報の発見性は git 履歴頼みになる（`git log -p docs/working/handoff/<branch>.md` での探索）。頻繁に掘り返す運用になった場合は受け皿の再設計が必要
- ハンドオフ以外に正本がない情報を剪定すると実質消失する。剪定規約側で「正本が他にあるもの / 役目を終えたもののみ落とす」基準を持つ必要がある（本 ADR の対象外。剪定規約の設計で扱う）
