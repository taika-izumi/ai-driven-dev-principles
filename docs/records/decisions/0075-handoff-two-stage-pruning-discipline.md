# ADR-0075: ハンドオフの剪定は二段階で行う（セッション境界で基準付き圧縮、サイクル境界で初期状態への書き換え）

- **Status**: Accepted
- **Date**: 2026-08-06

## Context

Issue-0049: `session-handoff` はブランチごとの単一ファイルを時系列追記で運用しており、完了した情報が落ちる仕組みがない。削除規約は「Post ラッパー消化記録」（ADR-0057 の finalize 時削除）のみで、他の節には剪定規約がない。配布先（LoopForAlpha）では handoff が 573 行・約 77KB に達し、セッション開始時の読み込みが分割読みを要した。

根本原因は剪定機会の不足ではなく、**剪定の許可と基準が明文化されていないこと**である。「申し送りは実測済みの価値があり削ると再発する」という制約下では、基準なしにエージェントが自発的に削ることはない。

制約: 単純な短縮で解かない（申し送りの実測価値を守る。Issue-0049 の留意）。剪定は素材消失（Issue-0053）と逆方向のリスクを持つ。受け皿は git 履歴のみ（ADR-0074）。

## Considered Alternatives

1. **二段階剪定** — セッション境界（finalize）で基準付き圧縮、サイクル境界（retrospective 完了時）で初期状態への書き換え。長いサイクル中の肥大とサイクル跨ぎの蓄積の両方に効く
2. **サイクル境界のみ** — retrospective 完了時のみ書き換え。規約はシンプルだが、長いサイクル中の肥大に無防備（配布先の実測はサイクル中の蓄積も含む）
3. **毎操作の節別剪定のみ** — update / finalize のたびに保持基準を適用。「サイクルの経緯を落とす」大きな判断が毎操作の小さな判定に分散し、実行が不安定になりやすい

## Decision

案 1 を採用する。剪定は次の二段階で行う。

**セッション境界（finalize 時）: 基準付き圧縮**。無条件の要約はしない。圧縮してよいのは次の 2 種のみ:

- 詳細が他の正本（ADR / issue / worklog / plan / spec / コミット履歴）に記録済みのもの → handoff には 1 行要約＋正本への参照を残す
- 役目を終えた状態情報（解消済みブロッカー、消化済みの記録行 = ADR-0057 と同型）→ 削除

正本が handoff 以外にないもの（進行中タスクの状態・残り、現役の申し送り・懸念）は触らない。同一サイクル内の引き継ぎは「情報の削減」ではなく「重複の参照への置き換え」として行う。

**サイクル境界（retrospective 完了時）: 初期状態への書き換え**。完了サイクルの経緯（完了タスク詳細・消化記録・完了サイクル固有の記述）を落とし、handoff を次サイクルの初期状態へ書き換える。このとき**申し送り（既知のブロッカー・懸念）は 1 件ずつ現役性を点検し、現役のものだけを残す**（一括削除も一括温存もしない）。

## Consequences

- 剪定の許可と基準が明文化され、エージェントが自律的に剪定を実行できる（ADR-0032 の観測可能な発動条件: finalize 実行時 / retrospective 完了時）
- 参照先を開くコストが 1 ホップ増える。参照を辿らない見落としの失敗モードが残るため、参照は安定識別子で書く規約（ADR-0077）とセットで運用する
- `session-handoff` と `retrospective` の 2 スキルの改定が必要（プラグイン更新を要する。ADR-0055）
- 剪定の実行品質は基準の運用に依存する。配布先での効き目は handoff サイズの実測で確認する
