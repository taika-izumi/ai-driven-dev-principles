# ADR-0079: ガイドライン拡張の全経路に過剰適合点検を課し、点検結果の記録を義務化する

- **Status**: Proposed
- **Date**: 2026-08-07

## Context

本ガイドラインは、開発対象とするシステムの種類・性質を限定せず、利用する AI モデルも限定しないことを前提に設計されている。特定のシステム種別に過剰適合した手順・ルールは他種のシステム開発で非効率・不合理になり、特定の AI モデルに過剰適合した手順・ルールは将来のモデルの性能発揮を阻害するためである。

しかしこの前提はどこにもルールとして明文化されておらず、2026-08-05 の Issue-0033/0034 スキル化サイクルで実際に違反しかけた。worklog 由来の規範項目のうちミューテーション検査 3 項目（根拠 8 件全件が単一プロジェクト LoopForAlpha のテスト運用出所）が、汎用スキルの拘束的規範として spec 承認まで進み、設計承認後のユーザーレビューでの指摘（「現行モデルへの過剰最適化・将来モデルやプロジェクトへの不適合では」）で初めて 3 点の過剰適合の芽が確認された（ADR-0073 で個別修正済み）。

問題は、この検出がプロセスではなくユーザーの目視に依存したことである。ADR-0073 は当該サイクルの成果物（委譲制約の規範項目）への個別対処であり、「ガイドライン拡張全般で過剰適合を点検する」一般ルールは存在しない。当時の worklog `MakeAiInstructions-2026-08-05-07` にも「観測事例を規範へ昇格させる工程（worklog-skillify / extend-guidelines）に『出所の偏り評価』『退役経路の設計』を定型観点として置けるか」という示唆が残されていた。

## Considered Alternatives

**適用範囲**:

1. **ガイドライン拡張の全経路に適用する** — CONTRIBUTING.md の全シナリオ（原則追加・CLAUDE.md 更新・スキル新規作成/改定）共通の点検とする。採用
2. 観測事例→規範昇格の経路（worklog-skillify / 課題対策サイクル）に限定する — ルールは軽くなるが、過剰適合は拡張の入口を問わず起こりうる（今回の事例は issue 経由、CLAUDE.md の構造化質問ツール規範はモデル固有事象経由）

**強制力**:

1. **点検結果の記録を義務化する** — 拡張の設計成果物に点検結果を定型ブロックで残す。採用。記録が残る形にしないと実施有無を外形的に確認できず、「ユーザーの目視頼み」に戻る（ADR-0057 の消化記録と同じ発想）
2. チェックリスト追加のみ — 軽いが実施の証跡が残らない
3. 独立レビュー工程（pre-finalization-review 型）まで課す — 最も強いが全拡張に課すと重い

**配置**:

1. **CONTRIBUTING.md に横断節を新設し、関連スキルへ工程を配線する** — 採用。拡張ルールの正本に規則を置き、スキルは参照する現行アーキテクチャに整合し、スキルを経由しない拡張にも効く
2. Layer 1（principles.md）に原則として追加する — 5 原則は「AI と協働して開発を進める」ための原則であり、ガイドライン自体の拡張規律はメタレベルの関心で階層が合わない。template 同期で配布先へ波及するが、配布先ではガイドライン拡張を行わないため波及の意味も薄い
3. スキル内のみで完結（extend-guidelines / worklog-skillify に直接記述）— 拡張ルールの正本が CONTRIBUTING.md であるという既存構造に反し、スキルを経由しない拡張に効かない

## Decision

ガイドライン拡張（原則・CLAUDE.md・スキルの追加/改定で規範・手順・観点を追加または強化するもの）の全経路に、以下の過剰適合点検を課す。

**点検の観点（3 点）**:

1. **出所の偏り**: 根拠となった観測・課題の出所プロジェクト数とモデル世代を数える。単一出所の教訓を拘束的規範へ昇格させていないか
2. **システム種別依存性**: 特定のシステム種類・技術スタック・テスト文化を暗黙の前提にしていないか
3. **AI モデル/ツール依存性**: 特定モデル・ツールの挙動や制約を暗黙の前提にしていないか。将来のより高性能なモデルの性能発揮を縛らないか

**過剰適合が見つかったときの是正パターン（既存 ADR の型の一般化）**:

- 拘束的規範ではなく適用例へ降格し、出所を明記する（ADR-0073 (a) の型）
- 前提を観測可能な発動条件としてゲートする（ADR-0032 の型。モデル依存の規範は確認済みモデルを列挙し、未確認モデルには適用しない）
- 根拠と世代を添え、退役経路を持たせる（ADR-0073 (c) の型）

**記録義務**: 点検結果（観点ごとの判定と根拠）を、spec を作る拡張では spec の定型ブロックに、spec を作らない小規模拡張では当該 ADR の Context または Consequences に残す。点検ブロックの無い拡張 spec は確定させない。

**配線**: CONTRIBUTING.md に横断節「過剰適合の点検」を新設して上記を定義し、各シナリオのチェックリストから参照する。`extend-guidelines` の手順に点検工程（設計承認前）を追加し、`worklog-skillify` に出所の偏り評価を追加する。

## Consequences

- 過剰適合の検出がユーザーの目視から、記録を伴う定型工程になる（実施有無を外形的に確認できる）
- 拡張 1 件あたり点検ブロック分の authoring コストが増える（観点 3 点 × 判定と根拠の各 1 行程度）
- ADR-0073（個別対処）・ADR-0032（観測可能ゲート）・ADR-0040（CLAUDE.md 事前判定）は現役のまま、本 ADR がそれらの型を拡張全経路へ一般化する位置づけになる
- 点検の品質は自己評価の誠実さに依存する。設計承認前のユーザーレビューが最終ゲートである構図は変わらない（本 ADR は検出をユーザーだけに依存させないための多重化である）
- CONTRIBUTING.md は template 対象外のため配布先への同期作業は発生しない
