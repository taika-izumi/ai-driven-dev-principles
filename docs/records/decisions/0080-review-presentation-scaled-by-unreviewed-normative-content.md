# ADR-0080: 確定前レビューは spec/plan 確定点で提示し、未レビューの規範・手順文書の変更を含む成果物では推奨側に倒す

- **Status**: Accepted
- **Date**: 2026-08-07

## Context

ADR-0072 は確定前レビュー（`pre-finalization-review`）について「発動はユーザー指示のみ・AI は `writing-plans` / `feature-block-design` 完了後に毎回提示する」ことを定めたが、**成果物の性質による推奨の強弱を定めていない**。そのため AI は「上流で自己レビュー済み」といった一般論から非推奨側へ倒しうる。2026-08-07 の ADR-0079 サイクルで実際に発生し、AI が「writing-plans へ進む（推奨）」を先頭に置いた spec に対し、ユーザー指示で実施した独立レビューが Critical 3 件・Major 8 件を検出、spec は設計骨格の全面改訂に至った（Issue-0062 / worklog `MakeAiInstructions-2026-08-07-04`）。

見落とされていた構造: **コードには「実装して最初に実行すれば数分で露見する」安全網があるが、規範・手順・文書型の成果物には無い。** 欠陥はそのルールが誤発動・空振りする数サイクル後まで潜伏し、実装時レビュー（タスク単位で spec への忠実性を見る）は spec 自体の欠陥をむしろ忠実に実装する。

また、現行の提示点（`feature-block-design` 完了時・`writing-plans` 完了時の 2 点）は `feature-block-design` 適用サイクルに偏っている。規範・手順の拡張は同スキルの適用基準に達しない小規模サイクルで行われることが多く、その型では spec 相当の成果物（brainstorming の設計文書、または設計文書を兼ねる ADR ドラフト）の確定点への提示が**規範の裏づけを持たない**。ADR-0079 サイクルでは AI が自発的に提示していたが、推奨順位を誤った——規範が定めるべきは提示の有無ではなく、この順位である。

なお plan 作成時の写像欠落（spec の要件が plan から落ちる）については、下流に**規範化された**検知経路は無い（ADR-0079 サイクルでは plan 末尾のファイナルレビューが spec 39 チェックポイントの全数突合を実践したが、これは規範ではなく当該 plan の設計である）。ただし写像欠落そのものの直接実測は中央ストア・issues に存在せず、機構（自己レビューが「載せる項目の選定漏れ」を検出できない一般限界。Issue-0034）からの推論に留まる。この状態で対策機構を規範化することは見送った（Considered Alternatives 6）。

## Considered Alternatives

1. **推奨条件を「plan の検証手段の有無」で判定する** — ADR-0079 サイクルの spec には grep 検証が存在した（それが検出力欠陥だった）ため、実測事例を「検証手段あり→中立」と誤判定する。不採用
2. **推奨条件を文面ベース（拘束的文言の有無）で判定する** — plan のタスク指示（「コミットは必ずパス指定で行うこと」等）も拘束的文言であり、実在 plan で確認したところこの読みでは全 plan が常時発火する。不採用
3. **文書型成果物一般を発火条件にする** — 実測は規範・手順文書のみであり、過剰適合点検の観点 1（出所の偏り）に抵触する。不採用
4. **推奨の強弱を両方向で定める（安全網の有る成果物では非実施側を推奨と明文化）** — レビュー抑制側の規範を実測なしで書くことになる。不採用
5. **発火サイクルでは spec / plan の両確定点で常にフルレビューを推奨する** — サブエージェント 3 体×2 回のコストが常態化し、ADR-0072 が回避した「重すぎる規範の形骸化」に近づく。不採用
6. **軽量レビュー枝（spec レビュー済みの写像 plan に、仕様適合単観点の spec→plan 網羅突合を推奨する）** — 設計段階で一度採用したが、本 ADR 自身への独立レビューで 2 観点が独立に根拠の崩壊を指摘し撤回した。根拠に挙げた Issue-0006 は spec に明示されない横断参照側の漏れであり spec 起点の突合では原理的に拾えず、隣接根拠 `LoopForAlpha-2026-07-29-10` は独立レビューではなく自己突合の記録だった。直接実測ゼロの機構を規範化しない（ADR-0079 是正パターン「規範化の見送り」）。**写像欠落の同型 delta（spec の要件が plan から脱落し、確定後に発覚した記録）が中央ストアへ現れた時点で、再導入を検討する**。不採用
7. **提示点は現行 2 点のまま維持する** — 小規模サイクルの spec 確定点の抜けが残る。改修対象がプロジェクト管理下のスキルで済むため、一般化のコストは小さい。不採用

## Decision

ADR-0072 の骨格（発動はユーザー指示のみ・AI は提示にとどめる・自動必須化しない）は維持する。**いずれの確定点でも提示は毎回行う（ADR-0072）。以下は提示内の推奨順位の規則である。**

規則の正本配置: 確定点の定義・推奨判定・差分明示（Decision 1〜3）の正本は `skills/start-work/SKILL.md` Phase 2 に置く（判定はそこで行われ、判定時にロードされているのは start-work だから）。`skills/pre-finalization-review/SKILL.md` にはレビューの実施手順と適用例を置く。発火条件の判定文はスキル本文へインライン展開する（配布先プロジェクトでは本 repo の ADR・CONTRIBUTING.md を参照できないため。ADR 番号は出所注記に留める）。

**1. 確定点の定義（提示点）**: 確定前レビューの提示点を「spec 確定点」と「plan 確定点」の 2 点とする。

- spec 確定点 =
  - (a) `feature-block-design` 適用サイクル: 同スキルの完了時
  - (b) `feature-block-design` が適用要否判定で非該当終了したサイクル: その判定を提示した直後（対象は直前に確定した brainstorming の設計文書。設計がファイル化されない場合はユーザーの設計承認の発言をもって確定とみなす）
  - (c) 設計文書ファイルを作らない拡張（ADR が設計文書を兼ねる型。CONTRIBUTING.md「spec を作らない拡張」）: 設計を確定させた ADR ドラフトのコミット直前
- plan 確定点 = `superpowers:writing-plans` 完了時
- brainstorming 完了直後には提示しない（`feature-block-design` の適用要否が内部判定される前で、確定点がどちらの型か未確定のため）。brainstorming 自体を省略する小規模経路では spec 確定点は生じず、plan 確定点のみとなる

**2. 推奨判定**: 各確定点で次を判定する。確定しようとする成果物が記述する**変更対象**に、将来の作業・挙動を拘束する規範・手順文書（原則、エージェント向け指示文書、スキル、プロセスルール、運用手順書・規約、出力構造を規定するテンプレート・雛形）の新設・改定が含まれ、かつ**その内容が独立レビューを受けていない**場合、**フルレビュー（3 観点）を選択肢の先頭（推奨）に置き**、理由（この型の成果物には実行による安全網が無く、欠陥は数サイクル後まで潜伏する）を添える。見送り・他の次手も並記する。

判定の但し書き:

- 誤記修正・表現圧縮・参照張替えのみの変更は対象外（出所: ADR-0079 の適用対象定義）
- plan 自身のタスク遂行指示・検証手順の文言は「規範・手順文書」に数えない（確定後に成果物として残る文書ではないため）
- レビュー指摘を反映した改訂差分は「未レビューの内容」に数えない（再発火ループの防止）。差分の再確認の要否はユーザー判断とし、選択肢として並記する
- 上流の spec がその確定時点で独立レビューを受けている場合、そこから写像された内容はレビュー済みとして扱う（サイクル・セッションを跨いでよい）
- 判定に迷う場合は「未レビューの規範内容を含む」側（フル推奨）へ倒す
- 該当しない場合は従来どおりの提示を行う（確定前レビューを選択肢に含め、推奨順位は当該サイクルの他の次手との比較で判断する。CLAUDE.md の推奨提示規範に従う）

**3. 差分明示**: 発火サイクル（＝いずれかの確定点で判定が真になったサイクル）の各確定点では、「本サイクルで何がレビュー済みで、この成果物の何が未レビューか」を提示に含める（実施判断はユーザーに残るため、その判断材料を規範側が供給する）。spec レビュー済みの写像 plan の確定点では「写像欠落（spec 要件の plan からの脱落）は独立レビューでのみ捕捉可能」の注意書きを添える。差分明示を伴う提示は長文になるため、構造化質問ツールの制約（CLAUDE.md「ユーザーへの質問と意思決定要求」）に従いテキストのみのターンで提示する。

**3-2. 反対材料の併記**: 発火サイクルの確定点提示では、次の 2 つを満たす。

- **(a) 推奨の由来の明示**: 推奨が Decision 2 の既定（判定に迷う場合はフル側へ倒す規定）に由来する場合は、**その旨を明示し**、判定を迷わせた両側の事情を提示する。内容判定による推奨と、既定による推奨とが、提示を読んだだけで区別できるようにする
- **(b) 反対材料欄の常設**: 提示に「推奨と逆を示す材料」の欄を設ける。認識している材料があればそれを書き、無ければ「特定できた反対材料: なし」と明記する（**不在の判定も出力に残す**）。材料は成果物の具体箇所・実測 id を指すこと。成果物に紐づかない一般論を反対材料として書かない（定型句化と、両論併記の体裁だけを整えることの防止）

推奨理由だけを書いて反対材料を落とさないこと。片側だけの提示は、本 ADR が塞ごうとしている「AI のフレーミングがユーザーの判断を誘導する」偏り（Issue-0062 の機構）と同型であり、推奨の向きを直しても説明が片側のままでは同じ誘導が残る。

適用範囲は**発火サイクルの確定点提示に限る**。非発火の確定点提示への拡大、およびあらゆる推奨提示への一般化（CLAUDE.md への昇格）は、実測が本 ADR のサイクル 1 件に留まるため行わない（是正パターン「適用範囲の降格」）。拡大は同型 delta が他プロジェクト・他モデルで観測された時点でユーザーへ提案する。

（(b) の欄の常設は、「反対材料を含むか」という不在の証明をエージェントの内心判断に委ねると、材料を認識しながら偽と申告した場合に出力から区別できないため。Decision 2 の但し書きが「判定に迷う場合はフル側へ倒す」「記録が確認できない場合は未レビューとみなす」で同型の不在判定を塞いだのと同じ扱いにする。ADR-0032）

**4. 欠陥クラスの適用例記載**: 一次資料の欠陥クラス 3 種（選定漏れ型・文書間相互作用型・検出力欠陥型）を、拘束的列挙ではなく根拠 id 付きの適用例として `skills/pre-finalization-review/SKILL.md` に記載する。

**5. 判定材料の記録**: 確定点を通過したら、確定前レビューの提示結果（フル実施 / 差分再確認 / 見送り / 非発火＝推奨判定が偽）を handoff の「Post ラッパー消化記録」の当該マイルストーン行に併記する。`session-handoff` の update 手順にこの併記を、finalize の「圧縮しないもの」に本サイクルのレビュー実施・見送りの記録を追加し、read の未消化検査に `review=` の欠落を、finalize の削除規定に本サイクルの `review=` 行の除外を加える。記録が確認できない場合は**未レビューとみなす**（片方向規範のため安全側に倒れる）。「本サイクル」とは現 feature ブランチの作業単位（cycle-reset まで）を指す。

**変更対象**: `skills/start-work/SKILL.md`（Phase 2。判定規則の正本）、`skills/pre-finalization-review/SKILL.md`（frontmatter description・「いつ使うか」・適用例・根拠と世代）、`skills/feature-block-design/SKILL.md`（適用要否判定の非該当終了時の「writing-plans への直行を推奨し」を、確定前レビューの提示を経由する文言へ改める。Issue-0062 と同型の推奨文言が新提示点に残るため）、`skills/session-handoff/SKILL.md`（Decision 5 の記録規範）。

## Consequences

- **最もレビュー価値が高い場面（規範・手順文書の確定点）で、提示の推奨方向が構造の実測に基づいて固定される。** AI の一般論による非推奨側への誘導（Issue-0062 の事象）が規範で塞がれる
- **コストの典型は spec 確定点でのフル 1 回（3 体）。** plan が spec に無い規範文書の変更を新たに導入した場合やユーザーが spec レビューを見送った場合は、plan 確定点でもフル推奨があり得る（3＋3 は上限規定ではなく、判定の帰結として許容される）
- **小規模サイクルの spec 確定点（設計文書確定時・ADR ドラフト確定時）に、規範の裏づけを持つ提示が生まれる。** superpowers 側の改変は不要（提示はすべて start-work / 本 repo スキルの責務）
- **非発火サイクル（コード中心の作業）には何も変わらない。** 片方向規範のため、後段検知が働く領域に新たな拘束を加えない
- **写像欠落は本 ADR では規範で塞がない。** 差分明示の注意書き（Decision 3）で判断材料の供給に留める。同型 delta が実測された時点で軽量枝（Considered Alternatives 6）の再導入を検討する
- **ADR-0072 / ADR-0067 は、Decision 本文中の提示点の列挙（「`writing-plans` および `feature-block-design` の完了後」）のみ本 ADR が部分修正する。** 実装時に両 ADR の Consequences へ部分修正の追記を行い、Status は Accepted のまま維持する（ADR-0073 の部分修正の型）
- 対照型（期待値ズレ・構文誤り等、後工程でも機械的に拾える誤り）は `pre-finalization-review` 既存のスコープ規定（「局所的・機械的な誤りは主目標に置かない」）が既に除外しており、本 ADR で重ねて規定しない
- 判定は handoff の記録（Decision 5）に依存する。記録の欠落は安全側（フル推奨）に倒れるため、判定不能で事象が再現する経路は塞がれる
- 退役経路: `pre-finalization-review` 既存の退役規範（同型 delta が長期にわたり中央ストアへ現れなければ簡素化・退役をユーザーへ提案）に相乗りする
- **部分修正（ADR-0087）**: Decision 5 の「本サイクル」定義（現 feature ブランチの作業単位）は「前回 cycle-reset から次の cycle-reset までの作業単位」へ改められた（master 直接開発ではブランチ基準で保持範囲が定義できないため）。判定材料の記録規範そのものは現役のため、Status は Accepted のまま維持する

## 過剰適合点検（ADR-0079）

レビュー指摘の反映（判定 2 撤回・発火条件の再定義・記録規範の追加）と、その後に追加した Decision 3-2（反対材料の併記）を受けた再点検済み（ADR-0079 の再点検規定）。
