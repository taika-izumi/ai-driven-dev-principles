# ADR-0080: 確定前レビューは spec/plan 確定点で提示し、未レビューの規範内容を含む成果物では推奨側に倒す

- **Status**: Proposed
- **Date**: 2026-08-07

## Context

ADR-0072 は確定前レビュー（`pre-finalization-review`）について「発動はユーザー指示のみ・AI は `writing-plans` / `feature-block-design` 完了後に毎回提示する」ことを定めたが、**成果物の性質による推奨の強弱を定めていない**。そのため AI は「上流で自己レビュー済み」といった一般論から非推奨側へ倒しうる。2026-08-07 の ADR-0079 サイクルで実際に発生し、AI が「writing-plans へ進む（推奨）」を先頭に置いた spec に対し、ユーザー指示で実施した独立レビューが Critical 3 件・Major 8 件を検出、spec は設計骨格の全面改訂に至った（Issue-0062 / worklog `MakeAiInstructions-2026-08-07-04`）。

見落とされていた構造は次の 2 点である:

1. **コードには「実装して最初に実行すれば数分で露見する」安全網があるが、規範・手順・文書型の成果物には無い。** 欠陥はそのルールが誤発動・空振りする数サイクル後まで潜伏し、実装時レビュー（タスク単位で spec への忠実性を見る）は spec 自体の欠陥をむしろ忠実に実装する
2. **plan 作成時の写像欠落（spec の要件が plan から落ちる）には下流の検知経路が無い。** 落ちた要件にはタスクも検証ステップも生成されないため、実装・テスト・完了前検証のいずれも対象自体を持たない。plan 段階の網羅漏れは実測がある（Issue-0006）ほか、自己レビューが「載せる項目の選定漏れ」を検出できない一般限界は 2 プロジェクト・3 モデル世代で反復実測されている（Issue-0034 クラスタ 7 件）

また、現行の提示点は `feature-block-design` 完了時と `writing-plans` 完了時の 2 点だが、`feature-block-design` は中規模以上でのみ適用されるため、小規模サイクル（brainstorming の設計文書が実質の spec になる型）では spec 確定点に提示が無い。規範・手順の拡張は小規模サイクルで行われることが多く、この抜けは実際に効く。

## Considered Alternatives

1. **推奨条件を「plan の検証手段の有無」で判定する** — ADR-0079 サイクルの spec には grep 検証が存在した（それが検出力欠陥だった）ため、実測事例を「検証手段あり→中立」と誤判定する。不採用
2. **推奨の強弱を両方向で定める（安全網の有る成果物では非実施側を推奨と明文化）** — レビュー抑制側の規範を実測なしで書くことになる。不採用
3. **発火サイクルでは spec / plan の両確定点で常にフルレビューを推奨する** — 取りこぼしはゼロだがサブエージェント 3 体×2 回のコストが常態化し、ADR-0072 が回避した「重すぎる規範の形骸化」に近づく。不採用
4. **写像欠落は中立提示＋注意書きに留め、実測が出た時点で拡張する** — 最も保守的だが、写像欠落は下流検知経路が無い欠陥クラスであり、plan 網羅漏れの実測（Issue-0006）と機構の反復実測（Issue-0034）が既にある。軽量単観点レビュー（1 体）でコストを抑えつつ塞ぐ方を採る。不採用
5. **提示点は現行 2 点のまま維持する** — 小規模サイクルの spec 確定点の抜けが残る。改修対象が start-work Phase 2（プロジェクト管理下）で済むため、一般化のコストは小さい。不採用

## Decision

ADR-0072 の骨格（発動はユーザー指示のみ・AI は提示にとどめる・自動必須化しない）は維持したまま、提示の仕方を次のとおり定める。規則の正本は `skills/pre-finalization-review/SKILL.md` に置き、`skills/start-work/SKILL.md` Phase 2 は要約と参照を持つ。

**1. 提示点の一般化**: 確定前レビューの提示点を「spec 確定点」と「plan 確定点」の 2 点と定義する。

- spec 確定点 = `feature-block-design` 完了時（適用サイクル）、または brainstorming の設計文書確定時（`feature-block-design` 非適用サイクル）
- plan 確定点 = `superpowers:writing-plans` 完了時

**2. 推奨の強弱（片方向・二段階）**: 各確定点で次の順に判定する。

1. 確定しようとする成果物に「規範・手順・観点の追加または強化」（ADR-0079 の定義を参照。誤記修正・表現圧縮・参照張替えは対象外）が含まれ、その内容が本サイクルで独立レビューを受けていない → **フルレビュー（3 観点）を選択肢の先頭（推奨）に置く**。推奨理由として「この型の成果物には実行による安全網が無く、欠陥は数サイクル後まで潜伏する」旨を添える
2. 発火サイクルで、上流（spec）は独立レビュー済みかつ当該成果物に未レビューの規範内容が無い → **軽量レビュー（仕様適合単観点・サブエージェント 1 体による spec→plan 網羅突合・母数＝spec 要件数を明示）を推奨側に置く**。フル実施・見送りも並記する
3. 上記いずれでもない → 中立提示（従来どおり）

**3. 差分明示**: 提示には「本サイクルで何がレビュー済みで、この成果物の何が未レビューか」を必ず含める（実施判断はユーザーに残るため、その判断材料を規範側が供給する）。

推奨条件を「未レビューの規範内容を含むか」に置くことで、spec レビュー済みの写像 plan では推奨が自然に軽量側へ降り（コスト懸念への応答）、plan が spec に無い拘束的文言を新たに導入した場合やユーザーが spec レビューを見送った場合はフル推奨が維持される（取りこぼし懸念への応答）。

## Consequences

- **最もレビュー価値が高い場面（規範・手順文書の確定点）で、提示の推奨方向が構造の実測に基づいて固定される。** AI の一般論による非推奨側への誘導（Issue-0062 の事象）が規範で塞がれる
- **発火サイクルの推奨コストは「spec でフル（3 体）＋plan で軽量（1 体）」が上限になり、両段階フル（3＋3）を避けられる**
- **小規模サイクルの spec 確定点に提示が生まれる。** brainstorming 設計文書確定時の提示は `start-work` Phase 2 の変更で実現し、superpowers 側の改変は不要
- **非発火サイクル（コード中心の作業）には何も変わらない。** 片方向規範のため、後段検知が働く領域に新たな拘束を加えない
- **写像欠落の検査が独立した目による突合になる**（自己突合の選定漏れ盲点は実測済み・Issue-0034）。Issue-0006（横断洗い出しの網羅漏れ）への部分対策になるが、spec に明示されない横断洗い出しまでは単観点突合で拾いきれないため、同 issue は close しない
- **判定には「本サイクルで独立レビューを実施したか」の履歴が要る。** セッションを跨ぐ場合は handoff の記録に依存する
- `pre-finalization-review` に観点を絞る規定（軽量モード）が加わり、手順がわずかに複雑になる

## 過剰適合点検（ADR-0079）

| 観点 | 判定 | 根拠 |
|------|------|------|
| 出所の偏り | 要是正→根拠と世代＋退役経路 | フル推奨枝の直接実測は本 repo 1 サイクル（Issue-0062 / worklog `MakeAiInstructions-2026-08-07-04`・claude-fable-5）。機構（自己レビューの選定漏れ盲点）は 2 プロジェクト・3 モデル世代（Issue-0034 クラスタ 7 件: claude-opus-4-8 / claude-fable-5 / claude-opus-5）。軽量枝の直接実測は Issue-0006 の 1 件＋隣接 `LoopForAlpha-2026-07-29-10`。是正として、一次資料の欠陥クラス 3 種は拘束的列挙にせず根拠 id つき適用例として `pre-finalization-review` に記載し、枝ごとの退役経路を対にする |
| システム種別依存性 | 問題なし | 発火条件「規範・手順・観点の追加/強化」は成果物の内容で判定し、システム種別・技術スタックに依存しない。コード中心プロジェクトでは発火せず現状（中立提示）が維持される。片方向規範のため非発火側に新たな拘束を加えない |
| AIモデル/ツール依存性 | 問題なし | 判定材料は成果物の内容と本サイクルのレビュー実施履歴で、モデル・ツール固有の挙動に依存しない。推奨は提示にとどまり実施判断はユーザーに残るため、将来モデルの性能発揮を拘束しない。根拠は 3 モデル世代にまたがる |
| 退役経路 | 定義済み | `pre-finalization-review` 既存の退役規範（同型 delta が長期に中央ストアへ現れなければ簡素化・退役をユーザーへ提案）に相乗りする。軽量レビュー枝は「写像欠落・plan 網羅漏れの同型 delta（Issue-0006 型を含む）が現れない場合」に同経路で個別に退役候補とする |
