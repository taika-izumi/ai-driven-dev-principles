# ADR-0081: 配布物から除くのは「配布先で解決できない参照」であり、決定記録番号に限らない

- **Status**: Accepted
- **Date**: 2026-08-07

## Context

ガイドラインの配布先プロジェクトへ届く成果物に、本リポジトリの文脈でしか意味を持たない参照が含まれている。

当初は決定記録番号（`ADR-NNNN`）の**番号衝突**だけを問題として捉えていた。配布先では同じ表記がその配布先自身の記録を指し、配布先が記録を書き進めれば番号は必ず重複するためである。しかし配布物を走査すると、同じ性質の参照が他に 3 種類あることが分かった。

| 種別 | 実測 | 配布先での解決可能性 |
|---|---|---|
| 無修飾の決定記録番号・課題番号 | 190（`skills/` 171 ＝ ADR 159 ＋ 課題 12、`template/` ソース 19） | 解決できるが**別の記録を指す**（衝突） |
| `<repo>#` 修飾済みの他リポジトリ課題参照（実参照） | 7 | 衝突はしないが、参照先リポジトリが配布されないため**開けない** |
| worklog エントリ id（`<Project>-YYYY-MM-DD-NN` および省略形 `-YYYY-MM-DD-NN`） | 9 | 中央ストアは `<home>/.ai-dev-worklog/` にありリポジトリ外・配布対象外のため**原理的に解決不能** |
| 散文中のプロジェクト名 | 2 | 配布先に無関係な私的プロジェクト名 |

衝突という切り口では 2 番目以降が対象外になる（`LoopForAlpha#Issue-0069` は修飾済みで誰も自分の課題と読み違えない）。しかし**配布先の読み手にとって使えるか**という切り口では、4 種類すべてが同じ側に立つ。判断基準を後者へ統一しないと、同一の成果物に 2 つの基準が同居することになる。

散文中のプロジェクト名について補足する。実測 2 箇所はいずれも「根拠 8 件全件が単一プロジェクト（LoopForAlpha）の…」「7 件はすべて LoopForAlpha 由来」の形で、**配布先で効いているのは件数と分布であり、プロジェクトの識別ではない**。過剰適合の判定（ADR-0079）に必要なのは「単一由来か複数由来か」であって名前ではない。

ただし**ソース側では名前が要る**。ADR-0073 は根拠が累積することを前提に設計されており、`subagent-dispatch` は「表の行構成は worklog の実測にもとづき見直してよい（条件の追加・入れ替えは新しいプロジェクト型・作業様式の観測が根拠になる）」と定めている。ソースから名前を落とすと、後日ほかのプロジェクトで同型の事象が起きたときに「既存の根拠はそのプロジェクト由来だったのか」が判定できず、「単一プロジェクト由来」を「複数プロジェクト由来」へ更新してよいかが分からなくなる。したがってプロジェクト名も、他の識別子と同じく**ソースには残し配布物からは除く**扱いとする。

一方、これらと外形が似ていて**残さなければならない**ものがある。書式を教えるための例示（`docs/overview/folder-structure.md` の課題ファイルひな形にある `Issue-NNNN`、`<repo>#Issue-NNNN` の記法例、`store-format.md` の台帳レコード例、`check-store-health.py` のテストフィクスチャ）である。これらは配布先が自分の番号を埋めるための型であり、除去すると配布物が機能を失う。

## Considered Alternatives

1. **番号衝突のみを対象にする（当初案）** — `template/` と `skills/` の無修飾参照 190 箇所だけを扱う。範囲は明確だが、配布先で解決できない参照が 16 箇所残り、同じ設計判断を後でもう一度行うことになる
2. **`template/` のみを対象にする** — 規模は最小だが、量の多い `skills/` 側が手つかずで残る
3. **「配布先で解決できない参照」を基準に、4 種類すべてを対象にする** — 採用
4. **起票のみ行い対策は別サイクルへ回す** — 対処が遅れる

## Decision

案 3 を採用する。**配布物から除くのは「配布先で解決できない参照」とし、判定基準を 1 つに統一する。**

対象は次の 4 区分、計 208 箇所とする（`01` の種別番号では 5 種類。決定記録番号と課題番号が別種別になるため）。

| 区分 | 件数 | 扱い |
|---|---|---|
| 無修飾の決定記録番号・課題番号 | 190 | 変換時に除去 |
| `<repo>#` 修飾済みの実参照 | 7 | 変換時に除去 |
| worklog エントリ id の実参照 | 9（うち 2 件はプロジェクト名を省いた省略形） | 変換時に除去 |
| 散文中のプロジェクト名 | 2 | 変換時に除去。ただし現在の語順では除去すると文が壊れるため、ソース側で括弧内の出所注記へ移す（`…単一プロジェクトのテスト運用出所（出所: LoopForAlpha）`） |

**5 種類すべてを「出所識別子」として同一に扱う。** ソースには保持し、配布物からは除く。除去は位置規約（ADR-0083 の R1）にもとづく機械変換で行うため、ソース側の記述は識別子を括弧内または出所リスト行に置く形へ揃える必要がある。

**根拠の散文は残す。** 除去するのは出所の識別子であり、「10 タスク中 7 回ずれた」「根拠 8 件全件が単一プロジェクト由来のため拘束的規範ではなく適用例」「世代: claude-opus-4-7〜claude-opus-5」といった記述は配布先で規範の拘束力と適用範囲を判断する材料になるため保持する（ADR-0073 の要求もこの散文が担う）。

対象に含めないものを次のとおり定める。

- **書式例・プレースホルダ** — `ADR-NNNN` / `Issue-NNNN` / `<repo>#Issue-NNNN` のような、実在を指さない型の表記。および台帳レコード例・テストフィクスチャのサンプル値。配布先が使う型そのものであるため保持する。実番号を例示に使わないことは規約で担保する（ADR-0083）
- **`template/CLAUDE.md` のプラグイン名 `ai-driven-dev-principles` とインストール元リポジトリ `taika-izumi/ai-driven-dev-principles`** — 配布先が環境を準備するために必要な情報であり、本リポジトリ固有であること自体が正しい
- **`docs/` 配下の参照** — 配布対象ではない（プラグインキャッシュへ物理的に複製されるが、スキルとしてロードされず配布先の作業指示にならない）
- **空インデックス生成で除去される行** — `sync-template.ps1` が `docs/records/retrospectives/README.md` 等のデータ行を落とすため、配布物に届かない

本 ADR が答えるのは対象範囲の問いのみである。配布体制は ADR-0082、ソース側の記法規約と検査は ADR-0083 が答える。

## Consequences

- 判定基準が「配布先で解決できるか」の 1 つに統一され、種別ごとに別の理由づけをしなくてよくなる
- 対象が 206 箇所へ増え、サイクル規模が案 1 より膨らむ
- **`<repo>#Issue-NNNN` を「跨いだときは修飾する」と定めた ADR-0068 との関係が非対称になる。** 本リポジトリ内の記述では修飾が有効な解決である一方、配布物では修飾しても解決できないため除去する。ADR-0068 は撤回しない（適用対象が異なる）
- **ソース側と配布物側で情報量が異なる状態を意図的に作る。** 保守者は識別子つきのソースを読み、配布先は散文だけの生成物を読む。両者の差は生成器が担保する（ADR-0082 / ADR-0083）
- **ソースは出所の累積記録として機能し続ける。** 後日ほかのプロジェクトで同型の事象が観測されたとき、既存の根拠が何プロジェクト由来だったかを数え直せるため、「単一プロジェクト由来」から「複数プロジェクト由来」への更新判断ができる（ADR-0073 の見直し経路の前提）
- 移行作業は「一般化」ではなく「識別子を括弧内へ移す語順の変更」となり、規範の内容を変えない（ADR-0083 のブロック 05 の制約と衝突しない）
- ADR-0068 は「既存の記述には遡及適用しない」と決めているが、本 ADR は 206 箇所へ遡及適用する。両者は対象範囲が異なる（前者は本リポジトリ内の記述、後者は配布物）ため矛盾しないが、同一リポジトリ内に遡及方針の異なる 2 つの判断が並ぶ
- 書式例と実参照は外形が似ているため、両者を機械的に区別する規約が必要になる（ADR-0083 が担当）
