# ADR-0082: 保守者向けの根拠注記はソースに残し、注記を除去した生成物を配布する

- **Status**: Accepted
- **Date**: 2026-08-07

## Context

`skills/` には決定記録・課題への参照が 171 箇所（ADR 159 ＋ 課題 12）ある。これらは配布先のためではなく**保守者のため**に置かれている。ADR-0073 は「委譲制約の規範項目には根拠と観測世代を添え、実測にもとづく退役経路を持たせる」ことを義務づけており、`subagent-dispatch` の根拠列はその実装である。規範のすぐ隣に「どの実測から来たか」が書かれていることは、本リポジトリの保守にとって機能している。

問題は配布経路にある。マーケットプレイス定義は `"source": "./"` で、プラグインキャッシュにはリポジトリ全体の完全コピー（743KB。`skills/` だけでなく `docs/` `CONTRIBUTING.md` `README.md` `scripts/` `template/` を含む）が置かれる。**変換ステップが存在しない**ため、保守者向けの注記がそのまま配布先へ届く。

配布先での実害は 2 段階ある。大半の箇所は「配布先のエージェントが読み、自プロジェクトの同番号 ADR へ誤って解決しうる」に留まるが、`skills/session-handoff/SKILL.md` のハンドオフ書式テンプレート内にある 2 箇所は、**配布先プロジェクトの実ファイル（`docs/working/handoff/<branch>.md`）へ複写される**。

一方、配布先が本リポジトリの ADR 本文を読む必要のある運用は存在しない（配布物を走査して確認済み）。判断に効く情報（出所プロジェクト数・観測世代・実測内容）は散文として現地に書かれているか、隣接する記述に重複している。

## Considered Alternatives

1. **ソースから注記を削る** — 配布物は最もクリーンになるが、ADR-0073 が設計した退役判定の材料が保守側からも失われ、改定のたびに文脈復元のコストが発生する
2. **注記を残したまま、配布先向けの読み替え宣言を各ファイルへ 1 行加える** — 編集は約 18 行で済むが、注記は配布先に残り続ける。ハンドオフ書式テンプレート経由で配布先の実ファイルへ複写される型は宣言行では塞げない
3. **参照をリポジトリ名で修飾する（`ai-driven-dev-principles#ADR-0080`）** — 190 箇所の書き換えで誤解決は塞げるが、配布先に価値のない情報を「正式な参照」へ格上げすることになり、可読性の代償に見合わない
4. **ソースと配布物を分離し、変換で生成した配布物を配る** — 採用

## Decision

案 4 を採用する。**開発用ソースは根拠注記を保持し、注記を除去した生成物をプラグインとして配布する。** `template/` が `sync-template.ps1` で生成されている既存の型を、`skills/` へ水平展開する。

構造は次を第一候補とする（構造 A）:

```
skills/                            開発用ソース（人が編集する。注記あり）
dist/.claude-plugin/plugin.json
dist/skills/                       生成物（注記なし）
.claude-plugin/marketplace.json    "source": "./dist"
```

マーケットプレイスの `source` にサブディレクトリを指定できないことが実機で判明した場合は、構造 B へフォールバックする（`skills-src/` を開発用ソース、`skills/` を生成物とし、プラグイン設定を変更しない）。判定は実装時に `/plugin marketplace update` を実行してスキルがロードされるかを観測して行う。

本リポジトリのセッションが生成版（注記なし）をロードすることは受け入れる。スキルを改定するときは対象ファイルを直接読むため注記は参照でき、スキルを実行するときに必要なのは手順であって注記ではない。

## Consequences

- 保守側の根拠注記と配布先の可読性が両立する。ADR-0073 の退役判定の材料は失われない
- 構造 A が成立する場合、配布物が必要分に絞られる（現状はリポジトリ全体 743KB が配布先マシンへ複製されている）
- **生成物の陳腐化という新しい失敗様式が生じる。** ソースを変更して生成を忘れると、配布先も本リポジトリ自身も古いスキルを実行する。この経路は検査で塞ぐ必要がある
- 生成物が `template/` に続いて 2 つ目になり、生成の実行忘れが起きうる経路が 2 つになる
- 本リポジトリのセッションでは、スキル実行時に根拠注記が見えなくなる
- 変換器が扱えない書き方がソースに残っていると生成が壊れるため、ソース側の記法を規約化する必要が生じる（別 ADR）
