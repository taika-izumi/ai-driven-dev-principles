# ADR-0083: 配布対象ソースの出所識別子は位置で規約化し、生成器が規約適合の検査を兼ねる

- **Status**: Proposed
- **Date**: 2026-08-07

## Context

ADR-0082 で、根拠注記を除去した生成物を配布する体制を決めた。ADR-0081 で、除去対象を「配布先で解決できない参照」5 種類（決定記録番号・課題番号・`<repo>#` 修飾参照・worklog エントリ id・出所注記〔プロジェクト名などを収める〕）と定めた。生成器がこれらを機械的に除去できるためには、ソース側の書き方が判別可能な形になっている必要がある。

現状の書き方を全件分類した実測（`skills/` 171 箇所・`template/` ソース 19 箇所、決定記録番号と課題番号のみの母数）:

| 型 | 例 | 件数 |
|---|---|---|
| 括弧単独 | `記録先へ1行残す（ADR-0057）` | 89 |
| 括弧内混在 | `（ADR-0073。条件の追加は新しい観測が根拠になる）` | 54 |
| 出所リスト行 | `- ADR-0026: inbox の導入` | 30 |
| 本文溶け込み | `出力ファイルは ADR-0011（時系列追記型）に従い` | 13 |
| コードフェンス内 | ハンドオフ書式テンプレート／worklog サンプル | 4 |

素朴な変換規則が壊れる実例が 3 種類ある。

1. `skills/retrospective/SKILL.md:53` の `- ADR-0006（意思決定の継続検出ルール）は本スキル中も常時適用される。…` は、行頭が出所リスト行と同じ形でありながら中身は手順文である。「番号で始まるリスト行を削除する」規則はこの手順を静かに削除する
2. `docs/overview/folder-structure.md` の課題ファイルひな形にある `Issue-NNNN` は、配布先が自分の番号を埋めるプレースホルダである。実在の番号と同じ正規表現に当たるが、除去すると配布物が機能を失う
3. `docs/overview/folder-structure.md:149` の `（例: `LoopForAlpha#Issue-0069`）` は `<repo>#` 記法の書き方を教える例示である。実参照と外形が同じだが、これは残す必要がある

ADR-0068 は同型の規範を導入したとき、Consequences に「機械検査はない。規範の遵守は書き手に委ねられており弱い」と自ら記した。同じ弱点を繰り返さないことが本 ADR の設計制約である（ADR-0039 の「環境・ツール設定による構造的解決を規範追加より優先する」とも整合）。

## Considered Alternatives

1. **規約を設けず、変換器に賢い判別を持たせる** — ソースの書き方を制約しない代わりに判別が文脈依存になる。上記 3 種の実例をいずれも確実には区別できず、静かな削除や書式例の破壊が起きる
2. **規約を文書で定め、遵守は書き手に委ねる** — ADR-0068 と同じ形。新規の違反が混入しても検出されない
3. **位置で規約化し、変換器が規約違反をエラーにする** — 採用

## Decision

案 3 を採用する。

### 出所識別子の定義

次の 5 種類を出所識別子と呼び、規約と変換の対象とする。

| # | 種別 | 形 |
|---|---|---|
| 1 | 決定記録番号 | `ADR-` ＋ 4 桁の数字 |
| 2 | 課題番号 | `Issue-` ＋ 4 桁の数字 |
| 3 | クロスリポジトリ修飾参照 | `<Repo>#` ＋ 上記 |
| 4 | worklog エントリ id | `<Project>-YYYY-MM-DD-NN`、および 2 件目以降の省略形 `-YYYY-MM-DD-NN` |
| 5 | 出所注記 | `（出所: …）` の括弧全体（プロジェクト名など、型で書けない出所をここへ入れる） |

**プレースホルダは出所識別子ではない。** 判別規則は種別ごとに異なる。種別 1〜3 は「4 桁の数字を持たない」（`ADR-NNNN` 等）、種別 4 は「プロジェクト名部が中立名の許可リスト（`X` / `Proj` / `<project>`）に一致する」（`X-2026-01-01-01` 等）で判別する。種別 4 は日付部に 4 桁の年を含むため、種別 1〜3 と同じ規則では判別できない。

### 規約（適用対象は配布対象ソース）

適用対象は次の 3 条件のいずれかに該当するファイルとする。

1. `template.manifest` に記載されているファイル
2. `skills/` 配下のファイル
3. `sync-template.ps1` が空インデックスを生成する 3 ファイル（判定対象は空インデックス化**後**の内容）

| # | 規約 |
|---|---|
| R1 | 出所識別子は 3 つの位置にのみ書く: (a) 全角括弧の内側、(b) 出所リスト行、(c) 出所注記 `（出所: …）` の形（括弧そのものが識別子であるため (a) とは別位置） |
| R2 | 本文の文法要素として出所識別子を使わない（`ADR-0011（時系列追記型）に従い` ではなく `時系列追記型（ADR-0011）に従い` と書く） |
| R3 | 出所リスト行は `- <識別子>: <説明>` のコロン形に統一する。複数の識別子を並べる場合は `/` または `〜` で連結し、その直後にコロンを置く |
| R4 | コードフェンス内に出所識別子を書かない |
| R5 | 書式例・サンプル値はプレースホルダまたは中立名で書く（実在を指す識別子を例示に使わない） |

### 変換規則

判定は次の順序で行う（順序を規約の一部として固定する）。

1. プレースホルダ（種別ごとの判別規則に一致するもの）は対象外として素通しする
2. コードフェンス内に出所識別子があれば R4 違反として停止する
3. 出所リスト行（`- <識別子>(/〜<識別子>)*:` で始まる行）は行ごと削除する。削除の結果その節にリスト項目が 1 つも残らなければ、見出し行と直前の空行も削除する
4. `（出所: …）` の括弧は中身ごと削除する。この括弧に囲まれた識別子は次のステップで内側扱いとする
5. 括弧内の出所識別子は、トークンと隣接する区切り（`。`／`、`／`・`／`/`／`〜`／空白／`項目N`）とともに除去する。括弧の中身が空になれば括弧ごと削除する
6. **上記のいずれにも当たらない位置に出所識別子があればエラーで停止する**

判定と生成物の自己検査は、同じ適用範囲・同じプレースホルダ判別を用いる（`.py` / `.ps1` はコメント行のみ）。自己検査だけ範囲が広いと、配布物に含まれるテストフィクスチャを検出して常に失敗する。

**規則 6 により、生成器が規約適合の検査を兼ねる。** 規約違反は生成の失敗として必ず顕在化し、silent tolerance は起きない。別途の lint を設けない。

あわせて、生成物がソースから再生成した結果と一致することを検査する（ADR-0082 が生む「生成物の陳腐化」を塞ぐ）。

## Consequences

- 規約違反が機械的に検出される。ADR-0068 が受け入れた弱点（書き手任せ）を本件では回避する
- 5 種類の識別子が単一の位置規約で覆われ、種別ごとの例外規則を持たずに済む
- **プロジェクト名の除去に名前の一覧を要しない。** `（出所: …）` という定型を丸ごと削除する形にしたため、将来ほかのプロジェクト名が増えても生成器を変更しなくてよい
- 書式例と実参照を「4 桁の数字を持つか」で区別するため、**書式例に実番号を使えなくなる**（R5）。既存の例示 1 箇所の書き換えが必要になる
- ソース側の書き方が制約される。とくに R2 は自然な日本語の語順を一部禁じるため、書き手に負担が生じる
- 判定順序を規約の一部として固定したため、実装が判定順を推測する余地がない。一方、順序を変えると挙動が変わるため、変更時は規約の改定として扱う必要がある
- 規約は配布対象ソースにのみ適用され、`docs/` 配下は従来どおり自由に書ける。適用範囲の判定は観測可能な 3 条件で行う
- 生成器がエラーで止まると配布物が更新できなくなるため、規約違反は必ず修正が必要になる（迂回路を用意しない）
