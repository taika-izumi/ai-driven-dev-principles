# ADR-0084: 記法規約の適用範囲は機械判定の範囲より広く取り、差分は書き手が守る

- **Status**: Proposed
- **Date**: 2026-08-08

## Context

ADR-0083 は、配布対象ソースの出所識別子を位置で規約化し、生成器が規約適合の検査を兼ねる体制を定めた。この体制は「規約違反は生成の失敗として顕在化させ、別途の lint を設けない」という執行モデルを持つ。検査で止まらないものは規約の外にある、という対応関係が前提になっている。

スクリプトファイル（`.py` / `.ps1`）については、テストフィクスチャの架空データ（`X-2026-01-01-01` 等）を規約で縛らないため、機械判定の対象を `#` で始まるコメント行に限定していた。

Task 7 の完了後、生成された配布物を読んだところ、この限定が意図より広く効いていた。`check-store-health.py` に次の 3 件が残っていた。

| 箇所 | 内容 |
|---|---|
| モジュールの説明文字列 | `中央ストアのバイト健全性を検査する（ADR-0054 の契約: …）` |
| 関数の説明文字列 | `混入しうる（Issue-0032）。頭だけを見る実装では…` |
| 実行時に出力するメッセージ | `違反 N 件。走査を中止する（ADR-0054: silent tolerance はしない）` |

いずれもフィクスチャではなく散文であり、配布先の読み手・利用者が読むテキストである。3 件目は配布先で実行するたび画面に表示される。ADR-0081 が定めた判定基準「配布先の読み手が解決できるか」に照らせば、これらは除去対象である。

同種の隙は書式例にもあった。`store-format.md` の `projects.json` の例が実在のプロジェクト名と開発機のローカル絶対パス（`D:/Dev/002_AiDev/MakeAiInstructions`）で書かれていたが、識別子 5 種のいずれにも当たらないため生成器は素通しした。同じファイルの 60 行離れた台帳レコード例では同じ値が中立名へ置換済みで、手本が 2 通りに割れていた。

## Considered Alternatives

**案 A: 機械判定の範囲を広げ、規約と一致させ続ける。** docstring と文字列リテラルを構文解析で抽出し、フィクスチャと利用者向け文字列を判別する。検査と規約が一致する状態を保てるが、判別に構文解析が要り、フィクスチャとの区別も自明でない。今サイクルの作業量が大きく増える。

**案 B: 規約の適用範囲を機械判定に合わせ、残存を許容する。** 現状維持。実装は変わらないが、配布先で実行時に決定記録番号が表示される状態が残り、ADR-0081 が塞ごうとした問題そのものが配布物に残る。

**案 C: 規約の適用範囲を機械判定より広く取り、差分は書き手が守る。** 規約は「配布先の読み手が読むテキスト」に及び、機械判定はそのうち検査できる部分だけを見る。検査で止まらない領域が規約の内側に生じることを明示し、その領域は目視で確認する。

## Decision

**案 C を採る。記法規約の適用範囲と機械判定の範囲を別のものとして定義し、両者の対応を明示する。**

スクリプトファイルについての対応:

| スクリプト内の箇所 | 機械判定 | 規約の適用 |
|---|---|---|
| `#` で始まるコメント行 | する | する |
| docstring・利用者へ表示する文字列 | しない | **する（書き手が守る）** |
| テストフィクスチャ・その他のコード | しない | しない |

書式例についての対応: R5（記法の例示はプレースホルダを使う）の対象は識別子 5 種に限らない。**書式例に置いた実在のプロジェクト名・実在の絶対パスも配布先では解決できないため中立名にする。** R5 は位置規約ではないため生成器が検出できないので、コードフェンス内のサンプル値は全数目視で確認する。

検査の届かない領域が規約の内側に残ることは、この決定が引き受ける負債である。機械化は Issue-0070 として分離し、対策の採否は次サイクル以降で判断する。

## Consequences

**良い影響:**

- 配布先で実行時に決定記録番号が表示される状態が解消した。配布物から実在の固有名・絶対パスが全数走査で 0 件になった
- 規約が「配布先の読み手が解決できるか」という ADR-0081 の原理に沿った範囲を持つようになった。検査の実装可能性が規約の範囲を決める、という逆転がなくなった
- 検査が届かない領域を明示したことで、その領域を目視で確認する必要があることが手順に書ける

**悪い影響・引き受けるリスク:**

- **逆戻りを生成器が検出できない。** 新しい docstring や表示メッセージに識別子を書いても検査は通る。規約適合していても配布物が壊れる型として潜伏する
- ADR-0083 が確立した「検査で止まらないものは規約の外」という単純な対応が崩れる。規約を読む人は、検査を通ったことが適合の証明にならない領域があると知っている必要がある
- 目視確認は実行のたびに人の注意力を要する。Task 7 では実際に 1 件を拾って 1 件を取り逃がしており（`folder-structure.md` は是正、`store-format.md` は取り逃がし）、目視の信頼性には限界がある

**関連する課題:**

- Issue-0070: 機械判定をスクリプト内の散文へ広げる方法の検討
- Issue-0071: 識別子 5 種に当たらない解決不能な参照（配布されない文書への必須参照）の扱い。本 ADR と同じく、原理と実装の隙から生じている
