# ADR-0087: handoff の剪定・移設はサイズ実測トリガーと作業単位完了の二系統で発火させる

- **Status**: Proposed
- **Date**: 2026-08-13

## Context

Issue-0078: cycle-reset の発火点は「サブプロジェクトの master マージ後（retrospective の仕上げ）」だけであり、サイクルが長期化する運用ではサイクル内の蓄積を制御する機構がない。LoopForAlpha の実測（2026-08-13）: 防止策（ADR-0074/0075）は展開・実行されているが、増加約 10KB/日が finalize の圧縮（約 10% 縮小）を上回り、cycle-reset 後 7 日で 23KB→97KB。リセット間隔（数週間）と増加速度の積が防止策の射程外にあり、運用側では規範外の手動刈り込み（2026-07-24）が発生していた。

ユーザー決定（2026-08-13）: サイズの定量目安と観測可能なトリガーを規範に含める。数値の根拠が単一プロジェクトの実測に偏るため、デフォルト値扱い（プロジェクト調整可）とする。

## Considered Alternatives

1. **サイズ実測トリガーを主機構とし、cycle-reset の発火点定義を一般化する（採用）** — 発火条件が完全に観測可能（ファイルサイズ）で、増加が速いほど早く発火するためサイクル長と無関係に上限が効く。儀式を増やさない
2. **phase-reset（サイクル内の中間リセット点）を新設する** — 「フェーズ完了」の判定がプロジェクトの運用語彙に依存し観測可能性が弱い（ADR-0032 の懸念）。1 段階が数週間続く運用では発火自体が稀で主因に効かない。儀式が 3 種に増え使い分けの判断コストが乗る。不採用
3. **現状維持（cycle-reset の間隔短縮を運用へ要請）** — サイクル長は開発の実態が決めるものでガイドラインが強制できない。射程外の構造が残る。不採用

## Decision

案 1 を採用する。

1. **サイズ実測**: `session-handoff` の read / finalize の手順冒頭で handoff ファイルのサイズを実測する（シェルコマンドで観測可能。専用スクリプトは設けない）
2. **目安値**: デフォルト **20KB**。根拠は LoopForAlpha 実測（健全時 6.9KB・肥大時 99KB・cycle-reset 直後 23KB）から「1 サイクル分の正常な蓄積を許容しつつ肥大の初期に発火する」水準として設定。プロジェクトが調整する場合は自プロジェクトの指示文書（CLAUDE.md 等）に調整値を明記し、それを優先する
3. **read 時に超過**: ハンドオフ要約の提示に移設・剪定の提案を添える（実施はユーザー判断）
4. **finalize 時に超過**: 移設工程（ADR-0086）を必須実施する。移設候補がなく、基準付き圧縮（ADR-0075）を再適用しても超過が解けない場合は、目安値の調整をユーザーへ提起する（閾値内へ戻すか目安を上げるかをユーザーに問う型）
5. **cycle-reset 発火点の一般化**: 「サブプロジェクトの master マージ後」を「作業単位（サブプロジェクト・段階）の完了時」へ改める。retrospective の起動粒度（サブプロジェクト単位）自体は変えない

## Consequences

- サイクル内の蓄積に、サイクル境界と独立な安全網がかかる（増加速度 10KB/日でも約 1〜2 週間で発火し、100KB 規模への成長を防ぐ）
- 閾値到達までの蓄積は許容される（平時の増加は対応表に従った書き分けと節別規範 = ADR-0086/0088 が抑える前提）
- 数値はデフォルト値であり、プロジェクトの調整値が優先される。デフォルト値の妥当性は配布先の実測で検証し、必要なら改定する
- サイズトリガーが長期にわたり未発火（肥大が構造的に再発しない）で、同型の delta が中央ストアへ現れない場合、本トリガーの簡素化・退役を候補としてユーザーへ提案する。判断はユーザーが行う
