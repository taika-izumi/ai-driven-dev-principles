# ADR-0087: handoff の剪定・移設はサイズ実測トリガーで発火させる

- **Status**: Proposed
- **Date**: 2026-08-13

## Context

Issue-0078: cycle-reset の発火点は「サブプロジェクトの master マージ後（retrospective の仕上げ）」だけであり、サイクルが長期化する運用ではサイクル内の蓄積を制御する機構がない。LoopForAlpha の実測（2026-08-13）: 防止策（ADR-0074/0075）は展開・実行されているが、増加約 10KB/日が finalize の圧縮（約 10% 縮小）を上回り、cycle-reset 後 7 日で 23KB→97KB。リセット間隔（数週間）と増加速度の積が防止策の射程外にあり、運用側では規範外の手動刈り込み（2026-07-24、154KB→6.9KB）が発生していた。

ユーザー決定（2026-08-13）: サイズの定量目安と観測可能なトリガーを規範に含める。数値はデフォルト値扱い（プロジェクト調整可）とする。

閾値設定の実測データ: cycle-reset 直後のクリーンな handoff は LoopForAlpha で 23KB、ガイドライン配信元リポジトリで 15.3KB。健全に完了したサイクルの handoff は 23.9KB（同リポジトリ実測）。当初案の 20KB はクリーン状態が初日から超過するため成立しない（確定前レビューで検出）。

## Considered Alternatives

1. **サイズ実測トリガーを主機構とする（採用）** — 発火条件が完全に観測可能（ファイルサイズ）で、増加が速いほど早く発火するためサイクル長と無関係に上限が効く。儀式を増やさない
2. **phase-reset（サイクル内の中間リセット点）を新設する** — 「フェーズ完了」の判定がプロジェクトの運用語彙に依存し観測可能性が弱い（ADR-0032 の懸念）。1 段階が数週間続く運用では発火自体が稀で主因に効かない。儀式が 3 種に増え使い分けの判断コストが乗る。不採用
3. **cycle-reset の発火点を「作業単位（段階）の完了時」へ一般化する** — 当初案に含めたが確定前レビューで撤回。発火のゲートは呼び出し元 retrospective の発動条件にあり、session-handoff 側の「呼ばれるタイミング」文言を変えても動作が変わらない。仮に retrospective を経ずに段階完了で発火させると、retrospective の worklog 総ざらい（消化記録が唯一の情報源）と確定前レビュー判定材料（`review=` 行）の保持を壊す。「段階の完了」自体が案 2 と同じ観測可能性の弱さを持つ。呼び出し関係の一般化は Issue-0050（retrospective の起動粒度）の検討へ委ねる
4. **現状維持（cycle-reset の間隔短縮を運用へ要請）** — サイクル長は開発の実態が決めるものでガイドラインが強制できない。射程外の構造が残る。不採用

## Decision

案 1 を採用する。

1. **サイズ実測**: `session-handoff` の read（対象ファイルの存在確認の直後）と finalize（手順冒頭）で handoff ファイルのサイズを実測する。専用スクリプトは設けず、シェルで行う（例: PowerShell `(Get-Item <path>).Length`、POSIX `wc -c < <path>`）。単位は 1KB = 1000 バイト
2. **目安値**: デフォルト **40KB**。根拠: cycle-reset 直後のクリーンな実測（23KB / 15.3KB）に、実測された 1 サイクル分の健全な増分（15.3KB→23.9KB ＝ 約 8.6KB）を積んだ水準（約 32KB）へ、プロジェクト差の余裕を持たせて設定。ガイドライン配信元リポジトリの handoff 全 20 ファイル（最大 23.9KB）への適用試算では発火 0 件＝現状の健全なファイルをすべて許容し、実測された肥大（97〜99KB）は確実に捕捉する。実測級の異常増加（10KB/日）が再発した場合はリセット後 2 週間前後で発火し、100KB 規模への成長を止める。節別規範（ADR-0088）が守られる平時は発火しない設計である
3. **調整値の置き場**: プロジェクトが目安値を調整する場合は、自プロジェクトの CLAUDE.md（エージェント向け指示文書）に調整値を明記する。スキルはそこに記載があればデフォルトより優先する
4. **read 時に超過**: ハンドオフ要約の提示に移設・剪定の提案を添える。ユーザーが受諾した場合は、移設手順（ADR-0086 決定 2）をその場で実行する
5. **finalize 時に超過**: 移設手順を必須実施する。移設候補がなく、基準付き圧縮（ADR-0075）を再適用しても超過が解けない場合は、目安値の調整をユーザーへ提起する
6. **「本サイクル」定義のブランチ非依存化**: 消化記録の保持規則等が使う「本サイクル」の定義を「現 feature ブランチの作業単位」から「**前回 cycle-reset から次の cycle-reset までの作業単位**」へ改める（`session-handoff` と `start-work` の該当文言）。master 直接開発では feature ブランチが存在せず、保持範囲が定義不能になるため

## Consequences

- サイクル内の蓄積に、サイクル境界と独立な安全網がかかる。発火条件・実測手段・調整値の参照先がすべてエージェントに観測可能（ADR-0032）
- Issue-0078 の対策方向のうち「cycle-reset の発火点を master 直接開発でも発火するよう広げる」は本 ADR では見送り、Issue-0050 へ委ねる（撤回理由は Considered Alternatives 3）。サイクル内の実効制御はサイズトリガーが担う
- 数値はデフォルト値であり、プロジェクトの調整値が優先される。デフォルト値の見直しは、ユーザーが配布先の実測を持ち込んだ時点で行う（エージェントは配布先の実測を観測できないため、判断主体をユーザーに置く）
- サイズトリガーが長期にわたり未発火（肥大が構造的に再発しない）で、同型の delta が中央ストアへ現れない場合、本トリガーの簡素化・退役を候補としてユーザーへ提案する。判断はユーザーが行う
