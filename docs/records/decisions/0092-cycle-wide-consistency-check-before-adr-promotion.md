# ADR-0092: 仕様・規範文書を編集したサイクルでは、決定の Accepted 昇格前に AI 自身によるサイクル全体整合検査を必須とする

- **Status**: Accepted
- **Date**: 2026-08-14

## Context

タスク単位のレビュー（spec 準拠＋品質の二段）を全タスクが通過しても、タスクをまたいで累積するずれは残る。実測では 2 サイクルで計 7 件の欠陥が、タスク単位レビュー通過後の「サイクル全体を読む 1 工程」で初めて検出された:

- 複数文書にまたがる規範の経路が閉じていない型 4 件（記録の書き込みが値の確定より先に走る配線 / 確定点の重複発火と経路依存の発火条件 / フックの単一配置による正規経路からの迂回 / 引用元の条件付き規範の無条件化）。同型の課題は Issue-0065 として起票されている
- 仕様が実装のスナップショットになっていない型 3 件（実作業が仕様に無い / 稼働する規範が仕様にも決定にも無い / 完了基準の数値が正本・下位仕様・実装で食い違う）。同型の課題は Issue-0074 として起票されている

原因は、タスク単位のレビューでは実装者もレビュアーも当該タスクの編集箇所しか読まないことにあり、「経路が閉じるか」「累積のずれ」はタスクの外側にしか現れない。一方、決定の昇格チェックポイント（承認の昇格）は粒度の点検を含むが、仕様との整合検査を含まない。

対策の設計に先立ち、構造的解決（スクリプト・自動検査）の可否を調査した。欠陥型はいずれも意味の突合（どの記述とどの実装が同じ事実を指すかの判定）を要し、文脈解釈なしの機械化は成立しないため、スキル手順への工程追加で対処する。

本ドラフトは確定前に 3 観点（敵対的・実装整合性・仕様適合）の独立レビュー（claude-opus-5）を受け、Critical 3・Major 15・Minor 12（重複統合前）の指摘を反映して改訂した。

## Considered Alternatives

1. **`decision-log`「承認の昇格」手順への工程追加（採用）**: 昇格手順の定義は decision-log に一本化されており（skills/ 全 13 スキルの走査で昇格を実行する箇所は decision-log と、その手順を参照する start-work のみ）、定義 1 箇所で全経路をカバーできる。ただしレビューで「承認の昇格」を明示参照しない昇格記述（start-work セッション終了処理・CONTRIBUTING の課題対策手順・再昇格経路）が実測されたため、これらへの参照の明示を本決定の変更対象に含めて経路を閉じる
2. **`start-work` Post ラッパーへの配置**: Post ラッパーを経ない昇格・コミット経路が正規に存在する（CLAUDE.md は「検出した瞬間に decision-log を呼ぶ」と定め、セッション終了処理にも昇格記述がある）。実測欠陥型「フックの単一配置による正規経路からの迂回」を再生産するため不採用
3. **検査専用スキルの新設**: 責務分離は明確だが、呼び出しフックを複数箇所へ配線する必要があり、配線漏れが迂回経路を再生産する。スキル数の増加も YAGNI に反するため不採用
4. **`pre-finalization-review` への昇格前確定点の追加**: 「発動はユーザー指示のみ」（ADR-0072）が根幹にあり、必須工程化とは原理が合わない。ADR-0072 を覆す変更コストが最大のため不採用
5. **独立サブエージェントレビューの必須化**: 検出力は最大だが、ADR-0072 の方針を覆し毎サイクルのコストも大きい。実測 7 件は全件 AI 自身の全体レビューで検出されており、必須工程としては AI 自身の検査で足りるため不採用
6. **提示のみ（実施はユーザー判断）**: 最軽量だが、実施の確実化（Issue-0065 の論点）に届かないため不採用
7. **タスク単位レビューの射程拡大（`subagent-dispatch` の委譲制約で各タスクレビュアーに全体読解を課す型）**: レビュアー数×全体読解でコストが乗算になり、かつ「タスクの外側」がどのタスクレビュアーの責務にもならない構造自体は変わらないため不採用（Issue-0065 が対比した「実施の確実化」側を採る）

## Decision

`decision-log`「承認の昇格」手順に**サイクル全体整合検査**を追加する。

### 配置と経路の閉鎖

- 検査は昇格手順の**第 1 ステップ（粒度の点検の前）**に置く。検査による修正・書き戻しで ADR へ決定が追記されても、後続の粒度点検が通常順序で再突合できるようにするため（記録・点検の順序を値の確定より後に置く）
- 「承認の昇格」節の冒頭に「本節の手順は Status が Accepted へ遷移するすべての場合（見直し後の再昇格を含む）に適用する」を明記する
- 「承認の昇格」を明示参照しない既存の昇格記述に参照を張る: `start-work` セッション終了処理 手順 2 と CONTRIBUTING.md「振り返りで抽出された課題に対策するとき」手順 8 へ「`decision-log`「承認の昇格」の手順に従う」を追記する。`decision-log`「ステータス変更」の但し書き（初回昇格のみを「承認の昇格」へ送る限定）は「Accepted へ遷移する場合（再昇格を含む）は「承認の昇格」に従う」へ改め、再昇格の入口からの導線を閉じる。`start-work` Post ラッパー項目 1 の「昇格の手順には粒度の点検が含まれる」の一文は「粒度の点検を含む点検工程が含まれる（内容は `decision-log` 側にあり重複記述しない）」へ一般化する

### 発動契機と発動条件（観測可能な事実で定義）

- **契機**: 実装（コード・文書の実体変更）を伴う決定の Accepted 昇格時。実装前（設計承認時等）に昇格する決定では検査せず、実施済みにも数えない。実装前に昇格を済ませた決定が同一サイクルに存在する場合は、実装完了のチェックポイント（`start-work` Post ラッパー項目 1 の昇格処理時）に検査のみを実施する
- **サイクルの定義**: 前回 cycle-reset から次の cycle-reset までの作業単位（`start-work`「確定前レビューの提示規則」の既存定義に従う。二重定義しない）
- **差分の列挙**: サイクル期間のコミット列＋未コミット変更を対象とする。ブランチ作業では `git merge-base <既定ブランチ> HEAD` を分岐点とする `git diff --name-only <分岐点> HEAD`、既定ブランチ直接作業では `git diff --name-only <前回 cycle-reset コミット>..HEAD`。**いずれも `git status --porcelain` の出力（ステージ済み・未ステージ・未追跡を含む）を併合する**（昇格はコミット前に走るため、コミット済み差分だけでは検査対象が空になる）
- **必須条件**: 上記の列挙に、仕様書（現在の正。標準: `docs/current/specs/` 配下）または規範・手順文書の変更が含まれる場合に検査必須。規範・手順文書の型は `start-work`「確定前レビューの提示規則」の推奨判定が定める既存定義（原則、エージェント向け指示文書、スキル、プロセスルール、運用手順書・規約、出力構造を規定するテンプレート・雛形）を参照し、本決定で再定義しない（固有ファイル名の列挙は配布先プロジェクトで解決できないため行わない）
- 含まれない場合は検査本体を実施せず、判定結果のみ記録する

### 実施主体と手段

AI 自身のインライン検査とする。独立サブエージェントレビューは従来どおりユーザー指示時のみとし、ADR-0072 は変更しない。検査は対象ファイルの実体の読み直し（Read/grep）で行い、差分表示や過去の作業記憶で代替しない（CLAUDE.md 検証節の節目直前確認の適用）。

### 検査観点（固定 5 項目。実測 7 件から抽出）

1. **仕様のスナップショット性**: サイクル中の実作業・レビュー由来の変更が上流仕様に反映されているか。突合は上流仕様側の全体読解を伴う
2. **規範の書き戻し**: サイクル中に新設・改定され稼働している規範が、仕様と決定に記載されているか
3. **数値・完了基準の整合**: 件数・期待値が正本・下位仕様・実装の間で一致しているか。該当する数値が現れる全文書を同時に読んで突合する（1 文書の差分だけでは三すくみを検出できないため）
4. **経路の閉じ**: 新設・改定した規範を 1 サイクル机上実行し、(a) 全到達経路にフックがあるか、(b) 同一内容へ複数の発動条件が同時に真になり二重発火しないか、(c) 発動条件がイベント依存で特定経路のみ偽にならないか、(d) 記録の書き込み順序と値の確定順序が整合するか。完了基準: 到達経路を全列挙し、各経路の発火有無と記録タイミングを 1 行ずつ書き出す
5. **引用の条件保存**: 他文書の規範を参照・引き写した箇所で、引用元のゲート（適用条件・発動条件）を落として無条件化していないか

### 重複実施の抑止

同一サイクルで本検査を実施済み（消化記録に後述の `cyclecheck=` がある）かつ以後の差分が無い場合に限り、再実施を省略する。差分がある場合、観点 4 は差分に関わる規範のみの再検査でよいが、観点 1・2・3・5 は突合対象文書の全体を読み直す。本検査以外のレビュー（独立レビュー・最終レビュー等）は、実施形態が既存スキルに定義されておらず同等性を観測可能に判定できないため、同等検査とみなさない。昇格処理そのものが生む差分（ADR の Status 更新・決定インデックスの行更新・close する課題・handoff への記録）は「以後の差分」に数えない（検査→昇格→再検査のループに停止条件を与えるため）。

### 検査結果の扱い

- 仕様・決定の追従漏れはその場で修正してから昇格する（スナップショット規範の回復）
- 修正が規範の文言・適用範囲に及ぶ場合は、過剰適合点検を当該差分について再実施し点検ブロックを更新する（CONTRIBUTING.md の再点検規定の適用）
- 修正が配布対象ソースに及ぶ場合は、CONTRIBUTING.md の執行点 4 手順を再実行してから確定コミットする
- 新たな設計論点は課題として起票に留め、本サイクルで対策設計に入らない

### 記録

「Post ラッパー消化記録」の行形式に新フィールド **`cyclecheck=`** を追加する。値は判定結果＋安定識別子に限定する: `実施（指摘なし）` / `実施（修正: <コミットハッシュ or Issue 番号>）` / `非該当（対象文書の変更なし）` / `非該当（実装前昇格）`。Accepted 昇格処理を含むマイルストーン行と、検査のみを実施したマイルストーン行（実装前昇格の後追い検査）に書く。**Accepted 昇格処理を含むマイルストーンは、名称に `Accepted 昇格` を含める**（欠落検査が対象行を観測可能な文字列一致で識別するため）。`session-handoff` の形式定義（形式行・書式例・命名規約）・節別記載規範・update 手順（記録項目）・read 手順（名称ラベルによる欠落検査）・finalize（削除例外・「圧縮しないもの」保護リスト）へ `cyclecheck=` を加える改定を本決定に含める（記録だけ増やして欠落検査の射程外に置くと、本 ADR が対策対象とする「フックの単一配置」型を記録面で再生産するため）。

### 変更対象（実装ファイル）

`skills/decision-log/SKILL.md`（本体。「承認の昇格」への工程追加・「サイクル全体整合検査」新節・「ステータス変更」の但し書き改定）/ `skills/session-handoff/SKILL.md`（形式行・書式例・命名規約・節別記載規範・update・read・finalize の削除例外と「圧縮しないもの」保護リスト。finalize は本サイクルの `cyclecheck=` 行を圧縮で落とすと重複実施の抑止の判定材料が消えるため）/ `skills/start-work/SKILL.md`（セッション終了処理の参照明示・Post 項目 1 の文言一般化）/ `CONTRIBUTING.md`（手順 8 の参照明示）/ `.claude-plugin/plugin.json`・`.claude-plugin/marketplace.json`（version bump。ADR-0090）/ `dist/`（執行点 4 手順で再生成）。スキルへの写像時は配布対象ソースの記法規約（R1-a: 全角括弧に識別子のみ・R1-b: 全角括弧）と配置の分類名参照（ADR-0089。例: 現在の正（標準: `docs/current/specs/`））に従う。

## Consequences

- 良い影響: タスク単位検査の構造的死角（累積ずれ・経路の閉じ）が、毎サイクル必ず通る昇格チェックポイントで検査される。検査観点 5 項目は実測 7 件の全型（スナップショット漏れ 2 型・数値不整合・記録順序・重複発火/経路依存発火・フック迂回・引用元ゲート脱落）をカバーする
- 悪い影響: 仕様・規範文書を編集したサイクルの昇格時に 1 パス分（typical 数分〜十数分）のコストが加わる。対象文書の変更が無いサイクルでも差分の判定と記録の作業は生じる（検査本体は生じない）。`decision-log` の責務がレビュー方向へやや太り、`session-handoff`・`start-work`・CONTRIBUTING.md への連動改定を要する
- 退役経路: 退役の判断と時期は「ユーザーが判断し指示した時点」とする。AI は判断材料として、cycle-reset で消えない残存記録（retrospective・worklog・Issue・検査由来の修正コミット）に検出実績が現れていない事実を棚卸しや retrospective の際に観測した場合、簡素化・退役を候補として提案する
- 部分修正（ADR-0099・2026-08-16）: 検査観点 5 は名称を「引用の条件保存」から「引用の整合」へ改め、対象に同一 ADR 内の Context 実測と Considered Alternatives の対応を、判定に主張の向きの一致を、完了基準（引用箇所の列挙と 1 行ずつの判定）を加えた。本 ADR は現役のまま維持する（正本は `decision-log` スキル側）
- **部分修正（ADR-0105）**: サイクルの定義の参照先は start-work から session-handoff「「本サイクル」の定義」へ張り替えられた
- **部分修正（ADR-0108）**: 本 ADR とその実装が導入した再昇格関連の記述 3 箇所（decision-log「ステータス変更」の「（初回昇格・見直し後の再昇格とも）」の括弧書き・再昇格時の Consequences 追記規定・「承認の昇格」の「（見直し後の再昇格を含む）」の括弧書き）は削除された（Accepted → Proposed の差し戻しを用いない運用への一本化。ADR-0108）。サイクル全体整合検査の規範本体は現役のため Status は Accepted のまま維持する

## 過剰適合点検（ADR-0079）

独立レビュー（spec 段階・plan 段階の 2 巡）の反映後差分（発動条件の精緻化・観点 5 の追加・記録フィールドの新設と命名規約・重複抑止の停止条件・連動改定の追加）を含めて再点検した。

| 観点 | 判定 | 根拠 |
|------|------|------|
| 出所の偏り | 問題なし | 出所 1 プロジェクト・2 サイクル・7 件（モデル世代: claude-fable-5 / claude-opus-5）。単一プロジェクト由来のため、無条件規範とせず発動条件（仕様・規範文書の編集を含むサイクル）でゲートし、未検証のコード実装サイクルには拘束を広げない |
| システム種別依存性 | 問題なし | 前提は「仕様書・規範文書と実装を併走させる開発」と git の利用のみ。対象文書を編集しないサイクルでは発動しないため、前提が崩れるプロジェクトでは自然に無効化される |
| AIモデル/ツール依存性 | 問題なし | 特定モデルの挙動を前提にしない。検査は git コマンド出力とファイル読解のみで実行可能。文書型の定義は既存規範の参照で固有ファイル名に依存しない |
| 退役経路 | 定義済み | 判断主体をユーザーへ明示的に移譲（Consequences 参照）。判断材料は cycle-reset で消えない残存記録に限定し、観測不能な条件を置かない |
