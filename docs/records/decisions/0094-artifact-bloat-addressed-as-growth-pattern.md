# ADR-0094: 成果物の肥大化（Issue-0088）は用途別対応ではなく成長様式への対策として扱う

- **Status**: Proposed
- **Date**: 2026-08-15

## Context

配布先での実測（旧版ガイドライン・2026-06〜07 頃の版を業務のシステム開発マネジメントに利用）で、Issue の肥大化が報告された（Issue-0088。観測データは業務 PC 上にあり参照不可＝報告者の記憶ベース）。事象は 2 つ: (1) Issue ファイル本体へ検討経緯が時系列追記され続けて内容把握が困難になった、(2) Issue フォルダ内にファイルが場当たり的に増えて所在が分からなくなった。

本リポジトリの実測（2026-08-15）では、肥大化抑制機構を持つ成果物（handoff・CLAUDE.md）と持たない成果物が混在する（worklog 中央ストアは worklog-extract という消費装置を持つが、サイズ・件数を抑制する規約は持たない）。抑制機構を持たない側のうち、Issue ファイルの「検討状況」節は同じ時系列追記型で成長中（節の最大 9.1KB、当該ファイル全体は 10.3KB）、フォルダ昇格は定義済みだが昇格後の体系規約が無く実例 0 件、plans フォルダは 31 件・847KB が残置、各インデックスは件数増加型で 16〜25KB。つまり報告された事故は現行版でも構造的に再現しうる。

対処の枠組みとして「マネジメント用途をスコープに含めた用途別設計」にするか、「用途を限定しない成長様式への対策」にするかの選択が必要だった。

## Considered Alternatives

1. **マネジメント用途をスコープへ明示的に含め、用途向け運用（情報収集・関係者調整の記録）まで設計する** — 実体験に最も直接対応するが、単一プロジェクト・記憶ベースの観測を用途別規範へ昇格させることになり、ガイドラインの前提（開発対象・用途を限定しない）から外れる。過剰適合点検（ADR-0079）の「出所の偏り」に正面から抵触する
2. **対処しない（Issue-0088 に経緯を記録して close）** — 本リポジトリでは顕在化していないため先送りは可能。ただし現行版はフォルダ昇格後の体系規約を欠いたままで、事故構造が温存され、配布先で再発したときの検出手段も無い
3. **用途を限定せず、成果物の成長様式（時系列追記型・件数増加型）への対策として扱う（採用）**

## Decision

Issue-0088 には対処する。ただし枠組みは「マネジメント用途対応」ではなく**成果物の成長様式への対策**とする。

理由: 肥大化は用途固有ではなく成長様式に由来する。検討が長期化した Issue は開発用途でも同じ追記経路をたどり（本リポジトリでも観測済み）、マネジメント用途は発火頻度が高いだけと整理できる。この枠組みなら、単一用途の観測を根拠にしつつも規範自体は用途非依存に設計でき、ガイドラインの前提と過剰適合点検に整合する。

## Consequences

- 対策の設計は成長様式で対象を選定するため、Issue に限らず同じ様式を持つ成果物へ一般化して検討できる。本サイクルの棚卸し処分は次のとおり:
  - Issue ファイル・Issue フォルダ → 本サイクルで対処する（ADR-0095/0096/0097）
  - インデックス 3 種（issues 16.8KB / decisions 18.4KB / retrospectives 24.5KB）・plans 残置（31 件・847KB）・worklog 台帳 → 本サイクルでは対処しない。Issue-0090 として起票し、実害の観測を再検討の条件とする
- handoff 対策の部品のうち、正本の分離・移設・サイズ実測トリガー・節別記載規範の 4 つを流用する。Issue-0088 が候補に挙げた「基準付き剪定」（ADR-0075）は流用しない（Issue の検討経緯は再発・進展の一次記録として恒久保存が要求され、handoff の「役目を終えた状態情報の削除」に相当する対象が無いため。詳細は ADR-0096 の検討経緯ログの節）
- マネジメント用途に固有の要求（関係者調整の記録形式など）は本サイクルでは設計しない。必要になった場合は別課題として起票する
- 根拠観測が単一プロジェクト・記憶ベースである事実は消えないため、設計時の過剰適合点検（ADR-0079）で明示的に扱う
- 本 ADR は枠組み・スコープの決定であり拘束的規範を追加しないため、過剰適合点検ブロックの記録対象外とする（点検は ADR-0095〜0097 で実施する）
