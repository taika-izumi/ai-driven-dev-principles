# ADR-0095: 長期化した Issue の関連情報は「検討中はフォルダ集約・close で性質別置き場へ移設」で配置する

- **Status**: Accepted
- **Date**: 2026-08-15

## Context

Issue-0088 の対策設計（枠組みは成長様式への対策。同型の決定は ADR-0094）。検討が長期化した Issue では、関連情報（調査結果・比較分析・関係者とのやり取りの記録など）の置き場が問題になる。配布先の実体験では「関連情報は一か所にまとまっていた方が確認しやすい」という動機で Issue ごとのフォルダ集約が採られたが、フォルダ内の無秩序化と Issue ファイル本体の肥大が起きた。

分析の結果、フォルダ集約の継続には 4 つの誘発問題が特定された: (1) 性質別 5 分類との配置基準の二重化（場当たり配置の一因）、(2) close 後の再利用可能な知見の埋没（`docs/reference/` の索引から外れる）、(3) 複数 Issue にまたがる資料の行き場、(4) 集約か分散かと独立に Issue ファイル本体の追記肥大は残ること。

一方、handoff の肥大化対策（ADR-0086）が同型の問題——進行中の作業文書に寿命の異なる情報が混ざって追記される——を「現在の状態と参照のみを残し、正本を性質別の置き場へ移設する」形で解決済みである。

## Considered Alternatives

1. **フォルダ集約の体系化のみ**（フォルダ内の命名・役割・索引の規約を足して集約運用を公式化する） — 最も単純だが、誘発問題 (1)〜(3) が残る。特に close 後の知見の埋没は件数の増加とともに静かに進行する
2. **ハブ＆スポーク**（集約をやめ、資料は最初から性質別の置き場に置き、Issue ファイルは状態と参照だけの薄いハブにする） — 分類体系と完全に整合するが、「検討中は一か所で確認したい」という実測された利用実感に正面から反し、検討中のブラウズ性が最も悪い
3. **ライフサイクル分離のハイブリッド（採用）** — 検討中はフォルダ集約を許し、close で移設する

## Decision

検討が長期化した Issue の関連情報は、次のライフサイクル分離で配置する:

- **検討中**: Issue フォルダ（フォルダ昇格）への集約を認める。フォルダ内は役割固定の体系に従う（体系と命名は ADR-0096）
- **close 時**: handoff で実証済みの独立手順「移設」と同じ型で移設判定を行う。義務判定は close 時のみとし、open 中の定期走査は行わない。判定の対象と行き先:
  - 恒久価値のある知見（再利用可能な調査結果・ノウハウ）→ 性質別の置き場（`docs/reference/` 等）へ移し、Issue 側は参照に置き換える
  - 未解決の別論点 → 新規 Issue の起票、または既存 Issue の「検討状況」への追記へ振り出す
  - 一時的な作業材料・検討経緯ログ → フォルダに残して凍結する
- **移設操作の付随則**: 移設した材料の索引行を移設先パスへ書き換える / 移設先の本文冒頭または索引行に出所（Issue-NNNN）を 1 行残す / 検討経緯ログから決定へ至った分岐を Issue ファイルの結論節へ 5 行以内で要約する

**フォルダの境界規則**（何を集約してよいか）:

- **置くもの＝方針決定に至るまでの材料・経過（未確定側）**: 問題の調査・原因分析、設計判断に必要な前提情報の収集・整理、選択肢の比較検討、関係者への説明資料・合意記録（スライド・PDF 等の任意形式を含む）
- **置かないもの＝確定した成果物と指定席のある情報種**（Issue ファイル（`NNNN-<slug>.md`）の索引から外部参照 1 行で辿る）:
  - 確定した仕様 → `docs/current/specs/`（スナップショット。分割軸は機能ブロックであり、検討のトピック切りの軸を仕様へ持ち込まない）
  - 下した決定 → ADR / 実装計画 → `docs/working/plans/`
  - 5 分類で指定席が既にある情報種（議事録 → `docs/records/minutes/`、インシデント報告 → `docs/records/` 等）
  - コードの実体（PoC 含む）→ リポジトリのコード側（ブランチ等）。Issue フォルダには結果報告のみ置く
  - 確定済みで複数 Issue にまたがる資料・再利用可能な知見 → 性質別の置き場
- **未確定の検討材料が複数 Issue にまたがる場合**: 主たる Issue のフォルダに置き、他方の Issue の索引から参照 1 行で辿る（物理位置は一方に固定し、重複コピーを作らない）

境界の軸は「設計に関する内容か否か」ではなく「**未確定の検討材料か、確定したスナップショットか**」である。物理的集約の代わりに、Issue ファイルの索引がフォルダ内・外の全材料を 1 件 1 行で束ね、「この Issue の情報はどこにあるか」への答えを Issue ファイル 1 枚に保つ（ハブ原則）。

理由: 検討中の確認しやすさ（実測された価値）を保ちながら、実体験の 2 事故（経緯追記の肥大・フォルダ内の無秩序）と誘発問題（埋没・分類衝突）の両方を塞げる。「Issue 関連の議事録はフォルダへ」のような Issue 関連性による分岐を作ると、配置基準の二重化（場当たり配置の原因と診断した構造）が情報種ごとに再発するため、指定席は無条件に優先する。

## Consequences

- close 時に移設の一手間が発生する（handoff の finalize と同種のコスト）
- 指定席・外部成果物へは索引経由の 1 ホップ間接参照になる（配置判断の一意性の対価として受け入れる）
- 検討中と close 後で情報の所在が変わるため、参照は移設後も辿れる形（Issue 側に参照を残し、移設先に出所を残す）で維持する
- 性質別 5 分類の配置判断と「検討中の一時集約」の関係が「例外」ではなく「ライフサイクルの段階」として整理され、配置基準の二重化が解消される
- 指定席側（`docs/records/minutes/` 等）にファイル命名・索引の規約が無い問題が顕在化した。本サイクルでは決めず、課題として起票した（Issue-0089）
