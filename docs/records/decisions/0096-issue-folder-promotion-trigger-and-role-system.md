# ADR-0096: Issue のフォルダ昇格は観測可能な条件で提案し、フォルダ内は 4 役割・番号接頭辞の固定体系とする

- **Status**: Accepted
- **Date**: 2026-08-15

## Context

配置モデル（ADR-0095）の具体化。現行規約（`docs/overview/folder-structure.md` 7.3）のフォルダ昇格は「検討が長期化・多観点化したら」という観測不能な条件で、導入以来実例 0 件。昇格後のフォルダ内体系・命名の規約も無く、配布先の実体験ではファイルが場当たり的に増えて所在不明になった（Issue-0088）。また現行の「課題ファイルをフォルダ内 README.md とする」規則は、複数 Issue のフォルダを開いたときエディタ上で区別できないファイル名の重複を生む。同じ重複は `log.md` のような固定名にも起きる。

確定前レビュー（4 観点・claude-opus-5、2026-08-15）が次を実証した: (1) 追記経路 9 本のうち folder-structure の課題管理定義に到達するものは 0 本で、「各スキルが参照している」という間接経路は実在しない、(2) 既存 Issue 86 件の「検討状況」エントリの 33% が 200 字を超えており、200 字規範を単一ファイル Issue に強制すると約 3 割の Issue で昇格提案が誤発火する、(3) close は decision-log 以外にも CONTRIBUTING の 2 シナリオ・配布先の申し送り close の経路がある。本改訂はこれらを織り込んでいる。

## Considered Alternatives

1. **昇格条件を現行のまま（長期化・多観点化）とする** — 判定主体が観測できる事実でなく、実例 0 件が続くと見込まれる（ADR-0032 の実行可能性チェックに反する）
2. **Issue ファイルを README.md に改名する現行方式の維持** — GitHub のフォルダ表示で自動レンダリングされる利点はあるが、タブ・検索結果での識別不能と、改名による参照切れリスクがある。本リポジトリでは実例 0 件のため変更コストが無い（配布先には移行が生じうる。Consequences の経過措置を参照）
3. **番号接頭辞なしの役割別命名（`log.md` / `note-<slug>.md`）** — フォルダ内では簡潔だが、タブ・grep 出力・移設後にどの Issue のファイルか判別できず、README.md を廃止した理由と同じ問題が再発する
4. **昇格条件の観測可能化＋ 4 役割・番号接頭辞の固定体系（採用）**

## Decision

### 昇格条件（提案型）

次のいずれかを満たしたとき、AI はフォルダ昇格を**提案**する（判断はユーザー）:

- (a) Issue ファイルの外に置くべき資料（任意形式の時点資料や、独立に育つ検討ノート）を作る必要が生じた時
- (b) Issue ファイルへの追記時にサイズをシェルで実測し、目安値 **10KB**（デフォルト。単位は 1KB = 1000 バイトで ADR-0087 と同じ。プロジェクトの CLAUDE.md に調整値があれば優先）を超えていた時

### 昇格操作

フォルダ `NNNN-<slug>/` を作り、Issue ファイル `NNNN-<slug>.md` を**同名のまま**中へ移動する（README.md への改名はしない）。インデックスのリンク先を更新する。追記禁止の記録類（retrospective 等）に残る旧パス参照は壊れを許容する（安定識別子 Issue-NNNN は不変であり、そちらで辿れる）。

### フォルダ内の 4 役割と命名

| 役割 | 命名 | 内容と成長の扱い |
|---|---|---|
| Issue ファイル | `NNNN-<slug>.md`（昇格前と同名） | 状態・課題内容・**現在地の要約**（書き換え。追記しない）・結論・**索引** |
| 検討経緯ログ | `NNNN-log.md` | 時系列の一次記録（`YYYY-MM-DD: 事象・判断`）。**現在地の判断には使わない**（現在地は Issue ファイルが正）が、**経緯の追跡ではこれを読む**。サイズ上限なし |
| 検討ノート | `NNNN-note-<slug>.md` | **決めるべき問い 1 つ**の検討材料（前提整理・選択肢比較）。冒頭に問いを明記。slug は問いの要約。論点が生きている間は追記・更新し、決着したら結論を Issue ファイル（と必要なら ADR）へ書いて凍結する |
| 時点資料 | `NNNN-YYYY-MM-DD-<slug>.<拡張子>` | 書き切りの記録（調査結果の時点スナップショット・説明スライド・合意記録等）。**任意形式**（pptx / pdf / 画像等）。作成後は原則不変。同名衝突時は末尾に `-2` からの連番を付す |

番号接頭辞 `NNNN-` は全ファイルに付け、ファイル名単体を自己識別的にする。番号直後の予約トークンで役割が名前だけで読める（`NNNN-log.md` は**完全一致**で判定 / `note-` は前方一致 / 日付 / それ以外＝Issue ファイル）。役割外の自由ファイルは置かない。フォルダ内のソートでは役割ごとにまとまる（先頭に来るのは時点資料であり、入口の Issue ファイルではない点に留意）。

- **検討経緯ログの受け皿妥当性（ADR-0074 との突合）**: log は剪定で落とした情報の受け皿（ADR-0074 が却下したアーカイブファイル）ではなく、再発・進展の一次記録——「一次記録は issue の検討状況」と定めた既存規範（ADR-0031）の宛先——が昇格後に分離したものである。handoff の「役目を終えた状態情報」と異なり恒久保存が要求されるため、「受け皿は git 履歴のみ」（ADR-0074）とは対象が異なる。同じ理由で基準付き剪定（ADR-0075）も流用しない。**昇格後、一次記録（再発・進展の 1 行追記）の宛先は `NNNN-log.md` とする**（Issue ファイル側は現在地の要約を書き換える）
- **判別規則**: ノートか時点資料か迷ったら「この後も更新し続けるか?」で判定する。それでも迷ったら時点資料に置き、索引の一言説明で補う（既定の受け皿）
- **索引義務**: フォルダ内ファイルの作成・外部成果物（指定席送り・確定成果物）の確定のたび、Issue ファイルの索引へ 1 行（パス＋日本語の一言説明）を追加する。**単一ファイル Issue でも、外部成果物を確定したときは「関連資料」節（無ければ新設）へ参照 1 行を追加する**。所在の一次手がかりはファイル名、二次手がかりは索引の説明とする

### 記載規範（単一ファイル Issue にも適用）

- 「検討状況」（昇格後は「現在地の要約」）の 1 エントリは 200 字（全角換算）以内を**目安**とする。昇格済み Issue では超過分をノート・時点資料・log へ移し、参照を置く。**単一ファイル Issue では超過を禁止しない**（成長の制御は昇格条件 (b) のサイズ実測が担う。既存 Issue の実測でエントリの 33% が 200 字超であり、強制すると約 3 割の Issue で昇格提案が誤発火するため）
- 外部参照は安定識別子（ADR-NNNN / Issue-NNNN / ファイルパス / コミットハッシュ）で書く（ADR-0077 と同じ規範）。他リポジトリの課題は `<repo>#Issue-NNNN` で修飾する（ADR-0068 の条件を保存する）

### 規範の定義場所と配線（境界原則 = ADR-0098 に従う）

**構造・命名・分量の定義**の正本は、新設する `docs/overview/issue-management.md`（課題管理定義。template 配布対象へ追加）に置く。現行 folder-structure §7 は早見表＋課題管理定義への参照（15 行程度）へ縮約する。課題管理定義には、スキルから参照される定義に「スキルが参照する」旨の注記を付ける。

**発火条件・手順**はスキル側に置く（実行者に継続更新経路で届く場所。確定前レビューが「文書側の間接経路は実在しない」ことを実証したため）:

- `skills/decision-log/SKILL.md` ライフサイクル節の close 手順へ移設判定のフック 1 行
- 同スキル 152 行目の旧昇格条件（「長期化・多観点化」）を新条件（提案型 2 トリガー）の要約＋課題管理定義への参照へ書き換える
- `skills/retrospective/SKILL.md` の「検討状況」追記手順・`skills/session-handoff/SKILL.md` の既存課題追記行・`skills/worklog-extract/SKILL.md` の既存 issue 統合手順へ、「追記後にサイズを実測し、目安超過なら昇格を提案する（定義は課題管理定義を参照）」の 1 句を既存行に追加する（発火条件表への行追加ではないため、Issue-0087 の表肥大とは別）
- `CONTRIBUTING.md` の close を含む 2 シナリオ（未決事項の記録・振り返り課題への対策）の close 手順へ移設判定の参照 1 句
- 各フックには、参照先の定義が見つからない場合のフォールバック（デフォルト値での提案とユーザーへの報告）を明記する
- close のスキル配線は decision-log の 1 経路のみとする。申し送り済み close・対処なし close にはスキル手順が存在しないため配線せず、課題管理定義の close 条項（経路を問わない判定）を正とする（スキル経路が新設された時点で配線を追加する）
- 索引の一言説明は「プロジェクトの記述言語で書く」とする（原案の「日本語」から一般化。配布先の記述言語を限定しないため）

## Consequences

- 昇格条件が観測可能になり、かつ発火点がスキル側の実経路に配線されるため、規範が実際に発火しうる状態になる。導入時点で本リポジトリの Issue-0044（10.3KB）が目安値を超えており、即座に 1 件の較正機会がある
- **改定対象**: `docs/overview/issue-management.md` 新設と `template.manifest` への 1 行追加 / folder-structure の §7.1（構造図）・§7.3（昇格条件と README.md 化規則・close 条項）・§7.4（フォーマットへ「現在地の要約」「索引/関連資料」節と記載規範を反映）・§7.5（インデックスのリンク形式を昇格形 `system|flow/NNNN-<slug>/NNNN-<slug>.md` に対応）・§8（運用例の旧条件）の縮約・書き換え / スキル 4 本（decision-log・retrospective・session-handoff・worklog-extract）への配線 / CONTRIBUTING 2 シナリオ / 仕様スナップショット（`docs/current/specs/2026-07-04-project-folder-structure/` と `2026-07-05-retrospective-issue-integration/` の該当 3 ファイル）の更新。実装計画の検証には旧文言の残存ゼロ確認（`README.md とし` / `長期化・多観点化` の grep）を置く
- **経過措置**: 既存 Issue は遡及改修しない（既存フォーマットのまま有効。次回の追記時に条件 (b) が判定される）。旧方式（README.md 化）でフォルダ昇格済みの Issue を持つ配布先は、次回そのフォルダを触る時に新命名へ移行する（一括移行は求めない）
- **配布**: スキル変更の反映には version bump と `dist/` 再生成が必要（ADR-0090 / ADR-0082）。課題管理定義は template 配布（新規作成時の 1 回コピー）のため、既存配布先へは手動反映が必要
- 転記時は配布対象ソースの記法規約（R4/R5）に従い、例示は `NNNN-` 系プレースホルダのみとする（実在の Issue 番号・実在ファイル名を書式例に使わない）
- 番号接頭辞のぶんファイル名が数文字延びる
- 時点資料に任意形式を許すため、大きなバイナリのコミットが起きうる。制限は設けず、実害が観測されたら対策を検討する
- **部分修正（ADR-0105）**: Decision が名指しする folder-structure の節番号（課題管理早見表ほか）は「7. 仕様書の運用規約」新設で繰り上がった（規範内容は不変。retrospective 側のサイズ実測記載は既に参照形のため不変）

## 過剰適合点検（ADR-0079）

| 観点 | 判定 | 根拠 |
|------|------|------|
| 出所の偏り | 要是正→観測可能な発動条件でゲート・根拠と世代＋退役経路 | 出所は 1 プロジェクト（記憶ベース・利用時のモデル世代不明）＋本リポジトリの兆候 1 件（Issue-0044、10.3KB。2026-08-05〜15 の蓄積、個別エントリの世代は未集計）。目安値 10KB は本リポジトリの実測 1 点由来のため調整可能なデフォルトに留め、昇格は提案＋ユーザー判断とする。200 字は既存 86 件・182 エントリの実測（33% 超過）を踏まえ単一ファイルでは目安へ降格した |
| システム種別依存性 | 問題なし | 命名・役割の規約はファイル種別・技術スタックに依存しない。時点資料は任意形式を許可済み。索引義務・役割固定・番号接頭辞は文書運用の一般則で、特定の開発体制を前提にしない |
| AIモデル/ツール依存性 | 問題なし | サイズ実測は handoff 規範と同じシェル実測。特定モデルの挙動を前提にしない |
| 退役経路 | 定義済み | ADR-0095 と共通（昇格発火 0 件の長期継続＋同型事象なしで簡素化・退役を提案。判断はユーザー） |
