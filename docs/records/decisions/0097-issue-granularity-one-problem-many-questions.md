# ADR-0097: Issue の粒度は「1 Issue ＝ 1 問題」とし、複数の問いの内包を認める

- **Status**: Accepted
- **Date**: 2026-08-15

## Context

検討ノートの導入（ADR-0096）により「1 ノート＝ 1 つの決めるべき問い」の粒度が定まった結果、複数ノートを持つ Issue は複数の問いを内包することになり、「そもそも Issue ごとに決めるべき問いを 1 つに絞るべきではないか」という粒度の論点が生じた。

一方で、(a) 起票時点では解決に要する問いの数は予見できない、(b) 関連する問いを別 Issue に分散させると特に人間が情報を追いづらくなる、という反対事情がある。本リポジトリの実績も後者を支持する: handoff 肥大化という 1 つの問題（Issue-0049）の対策は 3 つの決定（ADR-0074/0075/0077）を生んでおり、「1 Issue ＝ 1 つの問い」を強制していれば起票時の分割は不可能で、事後分割していれば問題の全体像を追う場所が失われていた。

## Considered Alternatives

1. **1 Issue ＝ 1 つの問い（起票後に問いが増えたら都度分割）** — 起票時に問い数を予見できない以上、恒常的な事後分割運用になる。関連する問いが分散し、問題単位の全体像を追う場所が消える
2. **複数の問いの内包を認め、ノート新設時に「この問いは本 Issue の解決に必要か」の独立性テストを課す** — スコープ肥大（1 Issue が複数の問題を吸い込む型）へのガードになるが、吸い込みの実測は本リポジトリにも worklog にも無く、観測されていない失敗に対する毎回発火の常設ガードは過剰適合点検の設計哲学（実測に基づかない拘束を避ける）と矛盾する。検討の結果撤回した
3. **複数の問いの内包を無条件に認める（採用）**

## Decision

粒度規範をレイヤーごとに置く:

- **1 Issue ＝ 1 問題**（解決したい事象。追跡の粒度）
- **1 検討ノート ＝ 1 つの決めるべき問い**（検討の粒度。ADR-0096）
- **1 ADR ＝ 1 つの問い**（決定の粒度。既存の decision-log 粒度規範）

Issue は問題の解決に要する複数の問いを内包してよい。ノート新設時の独立性テストは置かない。

スコープ肥大（関連するが分離可能な別問題の混入）への備えは、既存の下流機構に委ねる: close 時の移設判定にある「未解決の別論点 → 新規 Issue の起票または既存 Issue への追記へ振り出す」（ADR-0095 の Decision）と、起票時の「新規起票と既存課題への追記の使い分け」（課題管理定義の起票節）である。決定側の ADR 粒度点検（タイトルが答えない決定の分割提案）は ADR の分割機構であり Issue のスコープは見ないため、備えには数えない。

なお「1 ADR ＝ 1 つの問い」の正本は decision-log スキルの粒度規範（ADR-0059/0060 由来）のままとし、課題管理定義へ正本化するのは「1 Issue ＝ 1 問題」「1 ノート ＝ 1 問い」の 2 層のみとする（配布経路の異なる二重正本を作らない）。

## Consequences

- 起票時に粒度判断で迷う場面が減る（問題単位で切ればよい）
- スコープ肥大が実際に観測された場合（worklog delta・retrospective・ユーザー指摘のいずれか）、その時点で独立性テスト等の規範化を再検討する（監視条件）
- 「問い」の可視化はノートのファイル命名（`NNNN-note-<slug>.md`）が担うため、Issue が内包する問いの一覧は Issue ファイルの索引から機械的に読み取れる
