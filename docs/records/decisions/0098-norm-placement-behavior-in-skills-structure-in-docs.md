# ADR-0098: 規範の記載先は「発火条件・手順はスキル、構造・命名・分量の定義はプロジェクト文書」で分け、境界をまたぐ複写を禁止する

- **Status**: Accepted
- **Date**: 2026-08-15

## Context

本ガイドラインの規範は 2 つの配布経路に載る。スキル（プラグイン配布・全プロジェクト共通・継続更新）と、プロジェクト側文書（template 配布・作成時 1 回コピー・プロジェクト所有で調整可能）である。「スキルはスキル内で完結しているのが理想だが、異なるフォルダ構成のプロジェクトでも使えるよう外部ファイルへ手順・ルールを外出ししてきた。この依存を増やし続けてよいか」という問題提起がユーザーからあった（Issue-0088 対策サイクル中）。

同サイクルの確定前レビュー（4 観点・claude-opus-5、2026-08-15）が、境界の引き間違いによる失敗 3 型を実証した:

1. **挙動を文書側に置くと発火しない**: 昇格チェックの発火を「各スキルが folder-structure を参照する」間接経路に委ねた設計に対し、追記経路 9 本のうち文書の該当節へ到達するものは 0 本だった
2. **境界をまたぐ複写は乖離する**: `skills/decision-log/SKILL.md` 152 行目が folder-structure の旧昇格条件を複写しており、文書側を改定してもプラグインには旧条件が残って配布され続ける構造だった
3. **template 正本の更新は既存配布先へ届かない**: template は作成時 1 回コピーで、継続更新経路を持つのはプラグイン（`dist/skills/`）のみ

パス解決についてはスキルが分類名で書き具体パスは文書に従う責務境界が既にある（ADR-0089）。本決定はそれを規範一般へ拡張する。

## Considered Alternatives

1. **スキル自己完結へ寄せる（構造・パスもスキルへ焼き込む）** — 発火は確実になるが、フォルダ構成を調整したプロジェクトでスキルが壊れ、プロジェクト側の調整余地が消える。方針変更のたびに全プロジェクト一斉のプラグイン更新を強制する
2. **外部文書へ寄せる（発火条件・手順も文書側に置く）** — 本サイクルで発火経路 0 本が実証された型。文書にしか書かれていないトリガーは発火しない
3. **内容で分ける（採用）** — 挙動はスキル、構造定義は文書

## Decision

規範をどこに書くかは、規範の内容で決める:

1. **発火条件・手順（いつ・何をするか）はスキル側に置く**。実行主体に継続更新経路で届く場所が発火の前提である
2. **構造・命名・分量の定義（何が・どこに・どんな形で）はプロジェクト側文書に置く**。人間の手引きであり、プロジェクトごとの調整点であるため
3. **境界をまたぐ参照は、分類名・文書名・節の主題によるポインタに限る。条件文・規範文の複写を禁止する**（複写は乖離の実測がある失敗型）
4. スキル側に規範を書くときは「デフォルト値＋プロジェクト側での上書き点の明示」を標準形とする（例: 目安値はデフォルトを示し、プロジェクトの CLAUDE.md の調整値を優先する）
5. **フォールバックの明記**: スキルのフックには、参照先の定義が見つからない場合の動作（デフォルトでの提案・実行と、ユーザーへの報告）を書く。プロジェクト文書側には、スキルから参照される定義に「スキルが参照する」旨の注記を付け、書き換える編集者に影響を可視化する

これにより、配布先がプロジェクト文書を書き換えてもスキルは壊れない（書き換え後の定義に従うか、定義が失われた場合はデフォルト動作＋報告に劣化する）。

## Consequences

- 既存スキルの一括改修は行わない。本原則は本サイクルで触る範囲（Issue 管理の配線）から適用し、以後のスキル新設・改定時に順次適用する
- 「外部ファイル依存を増やしてよいか」への運用上の答えが定まる: 挙動の依存は増やさない（スキルへ置く）。構造定義の依存は、複写禁止を守る限り増えてよい
- スキルと文書の間で同じ内容を二重に保守する箇所が原理的に消える（ポインタのみになるため）
- フォールバックと参照注記のぶん、フック 1 箇所あたりの記述が 1〜2 文増える

## 過剰適合点検（ADR-0079）

| 観点 | 判定 | 根拠 |
|------|------|------|
| 出所の偏り | 問題なし | 根拠は本リポジトリの独立レビュー実測 3 件（発火経路 0 本・複写乖離・template 非伝播。検出はclaude-opus-5 のレビュアー、設計は claude-fable-5。いずれも 2026-08-15）と ADR-0089 の先行決定。単一プロジェクト出所だが、失敗機構は配布アーキテクチャ（プラグイン＝継続更新 / template＝1 回コピー）の構造に由来し、プロジェクトの性質に依存しない |
| システム種別依存性 | 問題なし | 開発対象の種別と無関係な、ガイドライン自身の配布アーキテクチャに関する規範である |
| AIモデル/ツール依存性 | 問題なし | 特定モデルの挙動を前提にしない。「文書にしか無いトリガーは発火しない」は参照読み込みの省略という一般的挙動に基づく |
| 退役経路 | 定義済み | 配布アーキテクチャが変わり（例: プロジェクト文書にも継続更新経路ができる）、前提が消えた時点で見直しをユーザーへ提案する。判断はユーザーが行う |
