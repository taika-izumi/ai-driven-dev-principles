# ADR-0100: ガイドライン全体棚卸し（Issue-0092）は、常時発火規範の全数台帳と二トラック判定による一回限りの監査として実施する

- **Status**: Accepted
- **Date**: 2026-08-16

## Context

本ガイドラインの直近の改修サイクルは、ほぼすべて「前サイクルのレビュー・振り返りで見つかった穴を、新しい検査・記録・規範で塞ぐ」型だった。「AI の出力は確率的に決定されるため、検査を重ねても逸脱・矛盾は残る」という前提（ADR-0099 Context で初明文化。「必ず残る」という強調は Issue-0092 の表現）を持たずに積まれた蓄積分には、期待検出量に見合わない過剰な手順が含まれている可能性がある（Issue-0092）。

監査の設計には次の制約・実測がある:

- 「検出実績なし」は少なくとも三通りに読める: (i) 規範が不要、(ii) 発火機会がまだ無かった、(iii) 検査は発火していたが検出力がゼロだった（検出器が壊れている型。Issue-0042 に 5 モデル世代・16 件の実測がある）。判定は検出実績の絶対数ではなく発火機会数に対する比で行い、発火機会が少ない規範は保留側へ倒し（Issue-0092 起票時のユーザー指摘）、比を使う前に分子の検出力を実証する
- 直近追加された規範の多くは本リポジトリのガイドライン拡張作業でしか動いておらず、配布先プロジェクトの実運用に晒されていない（設計時のユーザー再提起・2026-08-16）。便益側（検出実績）のデータが欠ける一方、コスト側（発火頻度 × 1 回あたりの読解・記録量）は本リポジトリのドッグフーディングで毎サイクル実測できている。ただし配布先の実測データが皆無ではない（worklog 中央ストアには配布先プロジェクトのエントリが実在する）ため、露出の有無は決め打ちせず台帳で規範ごとに実測する
- 検出実績が実在する規範もある（確定前レビューは 2026-08-16 サイクルでも Critical 2 件を捕捉）。サイクル全体整合検査については、導入根拠の実測 7 件は規範導入前に別工程（アドホックな全体読解）が検出したものであり（ADR-0092 Context）、導入後の実績は 4 回の発火で修正 1 件（retrospectives README の 2026-08-15〜16 の 4 行）。導入根拠と導入後実績は区別して扱い、一律削減ではなく規範単位の判定とする
- 監査自体が重い工程を新設しては本末転倒になる。監査は 1 回限りの調査として実施し、常設の工程を増やさない（Issue-0092 留意）

## Considered Alternatives

1. **対象範囲を Issue-0092 の仮説 3 領域（検査三層・証跡台帳系・Post ラッパー）に限定する**: 軽量だが、仮説の外にある過剰を検出できない。全数列挙してこそ領域横断の重複（同じ成果物を別工程が読む型）が見えるため不採用
2. **対象範囲を全規範（発火機会が毎サイクル観測できない単発・稀な条件発火を含む ADR 0001〜0099 の導入規範すべて）とする**: 網羅的だが、フル 1 サイクルの見積りを超えるおそれがある。発火機会が稀な規範は今回の判定材料が揃わないため不採用（ただし台帳の行としては残し、対象・対象外の判定を行単位で明記して漏れと区別する。決定 1）
3. **露出不足の規範を一律保留とし、露出十分な規範だけ比で判定する**: 最も安全だが、直近追加分（過剰が最も疑われる領域）が丸ごと判定対象外になり、監査の主目的が半分空振りするため不採用
4. **全規範を本リポジトリの発火実績のみで一律に比判定する**: 露出不足の規範まで、単一プロジェクト・ガイドライン拡張作業のみという偏った文脈の比で判定する点が「配布先実運用に晒されていない規範は保留側へ」の留意と矛盾するため不採用。なお採用案でも比判定の分母は本リポジトリ実測に限る（この限界は Consequences に記す）。差分は、比を判定に使うのを露出が十分な規範に限り、分子には配布先由来の検出実績も取り込む点にある
5. **一気通貫（インベントリから分類案まで一括作成し、最後に一度だけユーザー判断）**: 往復は最小だが、インベントリの漏れ・トラック誤割当があると集計・分類ごと手戻りになる。集計は監査で最も高くつく工程のため不採用
6. **領域別スライス（領域ごとに収集→分類→判断を回す）**: 部分成果は早いが、領域横断の重複こそ本命の検出対象であり、スライスすると見えにくい。判定の一貫性も領域間で揺れるため不採用
7. **監査結果の対策実施（規範の削除・統合の改修）まで本サイクルに含める**: 往復は減るが、「1 回限りの調査」の留意に反してサイクルが肥大し、判断と実装の境界が曖昧になるため不採用

## Decision

Issue-0092 の全体棚卸しを、次の方法による一回限りの監査として実施する。

### 1. スコープと規範の単位

対象は「毎サイクル 1 回以上の**発火機会**がある工程・規範」の全数とする。発火機会とは規範の発動条件が評価される機会を指し、ゲート（発動条件）付きの規範も、ゲートの評価が毎サイクル起きるなら対象に含める（発火機会数の計数はゲートが真になった回数で行う。「常時発火」とゲート付きを混同しない）。例: CLAUDE.md の行動指示、start-work の Post ラッパー、消化記録のフィールド群・命名規約・欠落検査・圧縮例外規定、検査三層〈過剰適合点検・サイクル全体整合検査・確定前レビュー提示。いずれもゲート付き〉、worklog ゲート、handoff の様式規範、subagent-dispatch の A 群・B 群等。

発火機会が毎サイクル観測できない規範（真に単発・稀な条件発火）は判定の対象外とするが、台帳から外さず 1 行として残し、「対象・対象外」列で判定を明記する（漏れと意図的除外の区別を行単位で担保する）。

規範の単位は「退役・簡素化の操作が実際に適用できる最小単位（＝退役条項が書かれている単位。例: subagent-dispatch は項目単位）」とする。Phase A の中間確認に台帳の行数見積りを含め、人間のレビュー可能量を超える場合はその場でスコープを再交渉する。

本サイクルは監査＝台帳作成・分類・ユーザー判断の記録までで閉じる。個別規範の改修（削除・統合・文言変更）は次サイクル以降へ委ね、改修が決まった規範は Issue として起票する。歯止め（ADR-0099 の複雑化抑制制約の一般規範化）も本サイクルでは方針案の提示とユーザー判断までとし、規範文書への反映は次サイクルの拡張作業として Issue 起票する（その拡張 ADR は過剰適合点検〈ADR-0079〉の適用対象となる）。

### 2. 二トラック判定

**トラック割当**: Phase A で分母（発火機会数）を先に実測してから行う。比判定トラックに入る露出の閾値は Phase A で数値として提案し、中間確認で固定する。露出が十分でも分母が実測できない規範（例: subagent-dispatch の委譲回数はリポジトリに記録が残らない）は構造判定トラックへ移す。分母を代替指標（サイクル数等）で近似する場合は、その旨と限界を台帳に書く。集計期間は各規範の導入 ADR の日付以降とする。検出実績の収集はトラックによらず全行で行う（構造判定トラックでは比を判定に使わないだけ）。

**比判定トラック**（露出が閾値以上で分母が実測できる規範）:

- 前置きとして分子の**検出力を実証する**: 当該規範が導入根拠とした欠陥事例（またはその同型）を現在の手順に当てて検出できるかを 1 件確認し、確認できない規範は比を判定材料にせず「検出力未実証」として保留（観測継続）へ倒す（再判定条件に検出力の実証を含める）。検査の 0 件・全緑は「欠陥が無い」と「検出器が壊れている」を区別できないため（Issue-0042 の実測 16 件）
- 検出実績は規範の型で定義する: **検査型**＝検出件数と「検出のあった発火回数」の 2 列（閾値は回数側に当て、件数は重み情報として併記する。1 発火で 45 件検出する工程と 1 件検出する工程を同じ閾値で並べないため）。**記録・証跡型**（消化記録・handoff 様式等）＝欠落・不整合の検出件数（欠落検査等が捕捉したもの）。**予防・閾値型**（サイズ実測トリガー・字数規範等）＝比では判定せず、逸脱率（違反件数 ÷ 適用機会）で判定する（うまく機能するほど検出が 0 になる型を、比が退役側へ誤誘導しないため）。規範の型は Phase A で台帳に記入し、中間確認で固定する
- 分母（発火機会数）は本リポジトリのサイクル実測に限る。分子（検出実績）は配布先プロジェクト由来の検出実績（worklog 中央ストア・配布先の課題記録）を含みうるため、出所プロジェクトを台帳に併記する

**構造判定トラック**（露出不足、または分母が実測できない規範）は、発火データ不要の構造的基準で見る:

- (a) 他規範との重複（同じ成果物を別工程が読む等。具体的な重複先の明示を要する）
- (b) 導入根拠の出所の広がり（出所プロジェクト数・モデル世代数・事例数の実数 3 列。二値判定にしない）
- (c) 導入 ADR の Considered Alternatives に「変更ゼロ・受容のみ」の代替案が実在するか、その見送り理由が現時点でも成立するか（ADR-0099 の複雑化抑制制約の遡及適用を検証可能な形にしたもの）
- (d) 退役条項が**観測可能な条件**で書かれているか（「ユーザーが判断し指示した時点」への判断主体の移譲のみの条項は「観測可能でない」と判定する）

**既存退役条項の優先**: 退役条項を持つ規範では、本監査を当該条項の**初回行使**とする（ADR-0073 が「検出は手動（棚卸し時・ユーザー指示時）」と定めた棚卸しに本監査が当たる。機械化は Issue-0048 の管轄であり本監査では行わない）。条項が定める判定条件・判断材料（例: サイクル全体整合検査の条項は「検査由来の修正コミット」を含む残存記録を材料に指定する。過剰適合点検の条項は 2 条件の連言）を台帳の「既存退役条項」列に転記し、条項の条件の成否を先に判定する。比・構造的基準はそれを補う材料とする。実測の材料には検査由来の修正コミットを含める。

**判定区分と保留規則**: 判定区分は keep / 簡素化 / 統合 / 退役候補 / **保留（観測継続）** の 5 区分。構造判定トラックの既定区分は保留（観測継続）とする。退役候補へ振れるのは、(a) の重複が具体的な重複先とともに示せる場合、または (c) で「受容のみ」案の見送り理由が崩れていると判定できる場合に限り、(b)(d) 単独では退役候補にしない。保留には「何を数えれば再判定できるか（計測点）」と「再判定の条件」を観測可能な形で必ず付し、「今は判定できない」を「いずれ判定可能になる」へ変換する。保留 Issue を消費する常設工程は本サイクルでは新設せず、その要否（retrospective への接続、worklog-extract への退役候補走査〈Issue-0048 の設計〉等）は歯止めの方針案と同時に Phase B のユーザー判断項目へ含める。

**閾値の後決めの抑止**: 判定の向き（どちら向きの値が退役側か・どの値なら keep か）は Phase A で規範ごとに台帳へ事前登録する。Phase B の提示は「分布・ランキングの提示 → 閾値の提案 → その閾値による機械的分類」の順で根拠を分離して示し、分類案から閾値を逆算した形と外形的に区別できるようにする。実測の出所はすべて安定識別子（ADR・Issue・worklog id・コミットハッシュ）で記す。

### 3. 二段階プロセス

- **Phase A（インベントリ確定）**: 正本群を走査して全数列挙し、規範ごとに単位・発火条件（ゲート）・分母（発火機会数）の実測値と可測性・規範の型・トラック割当・判定の向き・既存退役条項の転記を記入した台帳骨格を作成する。正本群は次の 18 ファイルの確定リストとする（「等」で閉じない）: `skills/*/SKILL.md` 全 13 本・`CLAUDE.md`・`CONTRIBUTING.md`・`docs/overview/principles.md`・`docs/overview/folder-structure.md`・`docs/overview/issue-management.md`。台帳骨格の作成後・中間確認の提示前に正本群を再走査して発火指示の取りこぼしを突合し、その結果（走査したファイルと取りこぼしの有無）・行数見積り・露出閾値の提案を**ユーザー中間確認**の材料に含める。全数性の完了基準: 台帳の「正本の所在」列に現れるファイル集合が上記 18 ファイルを被覆していること（規範単位の網羅は保証できないが、文書単位の網羅は機械的に保証する）
- **Phase B（集計・分類・判断）**: 確認済みの台帳に沿って分子（検出実績・逸脱率）と検出力実証を集計し、決定 2 の提示順（分布 → 閾値提案 → 機械的分類)で分類案を提示する。歯止め（ADR-0099 の複雑化抑制制約の一般規範化）の方針案と、保留 Issue の消費装置の要否を併せて提示する。ユーザー判断の結果は Phase B 終了時の別 ADR に記録し（これを正本とする）、次サイクル向けの Issue を起票する

### 4. 成果物と配置

- 監査台帳と報告: `docs/records/audits/2026-08-16-guideline-process-audit/` に `ledger.md`（台帳）と `report.md`（分類案と根拠＝台帳から導いた集計・比・構造判定、および Issue-0092 の仮説 3 領域〈検査三層の重複・証跡台帳系の増殖・Post ラッパー 4 項目〉それぞれの検証結果〈支持／不支持／判定保留と根拠行 id〉）。ユーザー判断の結果の正本は Phase B の別 ADR とし、`report.md` には ADR 番号へのポインタのみ置く（境界をまたぐ複写を禁じる ADR-0098 と同じ型）
- `docs/records/audits/` は本監査で新設し、索引 `README.md` を置く（`docs/overview/folder-structure.md` の運用規約「種別サブフォルダはオンデマンド作成」「列挙されていない新種別」に従う配置であり、同文書の改定・template 同期は不要）。索引は監査記録の一覧であり、本監査のために以後更新されることはない（将来別の監査が実施された場合に行が足されるのみ）
- 台帳の様式（1 行＝決定 1 の規範単位）: id / 規範名（単位） / 正本の所在 / 導入 ADR / 発火条件（ゲート） / 対象・対象外の判定 / 規範の型 / 1 回あたりコスト / 発火機会数（実測値と可測性・近似の別） / 検出実績（検出件数・検出のあった発火回数・出所 id） / 比または逸脱率 / 検出力実証 / 構造的基準 (a)〜(d) / 既存退役条項（所在と条件） / 判定の向き / トラック / 分類案 / 根拠
- `ledger.md`・`report.md` は Phase B のユーザー判断の記録をもって確定とし、以後不変とする（追跡型の記録）。監査は 1 回限りとし、常設工程・恒常運用する台帳を作らない。保留（観測継続）の再判定も常設工程にせず、条件付きの Issue として backlog に置くのみとする

### 5. 隣接課題との棲み分け

- **Issue-0045**（open 課題の実行可能性点検）: 対象が異なる（あちらは課題バックログ、こちらは稼働中の規範）。監査で重なる知見が出た場合は Issue-0045 へ追記する
- **Issue-0042**（検出器の検出力未実証）: 決定 2 の検出力実証の根拠。監査で得た検出力の実証・反証の実測は Issue-0042 へ追記する
- **Issue-0048**（退役候補検出の worklog-extract 機械組込み）: 本監査は退役条項の手動の初回行使であり、機械化は行わない。「長期」の定義など Issue-0048 の未解決論点に対して監査の実測が材料になる場合は同 Issue へ追記する
- **ADR-0073**（委譲制約の根拠・世代の記録と退役規範）: 退役条項の定義元の一つ。本監査が同条項の初回行使にあたる

## Consequences

- 良い影響: 「感覚で削らない」を満たす実測ベースの判定材料が全数分揃う。露出不足の規範も構造的基準と保留（観測継続）区分で監査の射程に入り、直近追加分が対象外にならない。検出力の実証を比判定の前置きに置くことで、壊れた検査を「不要な規範」と誤読する経路（Issue-0042 の型）を塞ぐ。既存退役条項の初回行使を兼ねるため、条項と監査が別々の結論を出す衝突を防ぐ。判断（本サイクル）と実装（次サイクル）が分離され、判断の質が保たれる
- 悪い影響: 監査自体に 1 サイクル分のコストがかかり、分母実測とトラック割当を Phase A へ前倒ししたぶん Phase A は重い。比判定の分母は本リポジトリ単独の実測であり、判定は偏った文脈のデータに基づく限界を持つ（構造判定トラック・保留区分・分子への配布先実績の取り込みで緩和するが、解消はしない）。保留（観測継続）区分が多くなる見込みで、その分だけ退役・簡素化の即断は少なくなる。保留 Issue の消費装置は Phase B のユーザー判断に委ねるため、それまで backlog 滞留のリスクが残る（open 課題の滞留は実測されている: 2026-08-16 時点の最古 open は起票から 42 日）
- 実装の同期対象: 決定インデックス・課題インデックスへの行追加は空インデックス生成対象（CONTRIBUTING.md の配布対象ソース定義）に触れるが、生成物（template の空インデックス）に差分を生まないため執行点 4 手順は空振りとなる（先例: コミット `7a1bc54` / `de4ad6d`）。plugin version bump は配布対象（`dist/` に入るファイル群）を改定しないため非該当（ADR-0090）。`skills/`・`dist/`・`template/` への変更はない
- 過剰適合点検（ADR-0079）の適用対象判定: 本 ADR の拘束的記述は本監査 1 回の実行手順に限定され、Layer 1〜3（`docs/overview/principles.md`・CLAUDE.md・`skills/`）のいずれにも規範を追加・強化しないため、適用対象外とする。ただし ADR が設計を確定させる文書を兼ねるため、確定前レビューの提示は spec 確定点 (c) として行った（(c) 該当性を ADR に明記する様式は ADR-0090 の先例に従う）
- 監査の判定結果とそれに基づく決定の正本は、本 ADR ではなく Phase B 終了時の別 ADR に記録する
- 本 ADR は確定前に 3 観点（敵対的・実装整合性・仕様適合）の独立レビュー（claude-opus-5）を受け、Critical 4・Major 17・Minor 16（重複統合前・計 37 件）の指摘を反映して改訂した（35 件採用・2 件は軽量形で部分採用）
