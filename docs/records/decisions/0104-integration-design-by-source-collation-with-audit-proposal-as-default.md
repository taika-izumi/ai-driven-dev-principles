# ADR-0104: 統合仕様は監査の統合先案を既定とし、正本読み合わせで重複側固有の条件を写像してから確定する

- **Status**: Accepted
- **Date**: 2026-08-17

## Context

Issue-0093 の統合 22 行（13 クラスタ）の実装にあたり、統合仕様（各クラスタの統合先・重複側の処理）をどう確定するかの方式を決める必要があった。監査報告（report 1-6）はクラスタごとの統合先案を持つが、これは監査時の案であり「実装時に再検討してよい」とされている（Issue-0093）。また監査の (a) 欄が確認したのは重複の「同一性」であり、重複箇所どうしの文言・ゲート・適用条件が完全に一致していることまでは保証していない。

本プロジェクトでは「引用・引き写しの際に引用元のゲート（適用条件）を落とす方向の誤りは自己判定で検出しにくい」ことが実測されており（CONTRIBUTING 過剰適合点検の観点 2・3 の突合要求、ADR-0099 の引用整合検査）、統合＝重複側の削除はこの型の事故（条件の取りこぼし）が起きやすい。

## Considered Alternatives

1. **監査の統合先案を既定とし、クラスタごとに正本を読み合わせて統合形を確定する**（採用）: 監査成果を再利用しつつ、監査が保証していない「重複側固有の条件の写像」だけに設計コストを使う
2. **統合先のゼロベース再設計**: 監査 Phase B の検討の二度払いになる（読み合わせで統合先案を覆す材料が出た場合は、決定 1 のクラスタ単位の理由記録で扱う）
3. **重複側の機械的削除のみ（統合先の文言は触らない）**: 最速だが、重複側だけが持つ条件・ゲートが失われる写像欠落のリスクが高い

## Decision

統合仕様の確定は次の方式で行う:

1. report 1-6 の統合先案を既定として採用する（覆す場合はクラスタ単位で理由を記録する。クラスタ内の一部の行のみを覆す部分的な覆しでは、行ごとに理由を記録する）
2. クラスタごとに、重複する全レコードの正本箇所を実際に読み（Read/grep。記憶・台帳記述で代替しない）、重複側にしかないゲート・条件・固有の対象指定を洗い出す
3. 洗い出した固有条件を統合先へ吸収した上で、重複側を「完全削除」または「参照 1 行に置換」のいずれにするかをクラスタ単位で決める
4. K3（サイズ実測トリガー）・K13（安定識別子）で監査の統合先案が示す共通規範新設の採否は、新設先の配置・配布経路（フォールバック要否）・評価可能性の記載要件（CONTRIBUTING「全シナリオ共通: 新設の評価可能性」）を含めて設計段階で確定する（採否の結論と理由は設計 ADR 側に記録する）

## Consequences

- 22 行分の正本読み合わせが必要で、設計文書（設計を兼ねる ADR）作成のコストは機械的削除より高い
- 写像欠落（重複側固有の条件の取りこぼし）を設計段階で検出でき、確定前レビューにも「読み合わせで洗い出した固有条件の一覧」を判定材料として渡せる
- 統合先案を覆したクラスタは理由が記録されるため、監査台帳（確定後不変）と実装の差分を後から追跡できる

なお、本 ADR が定める手順は本サイクル限りの作業方式であり、確定後に成果物として残る規範・手順文書への追加・強化ではないため、過剰適合点検の適用対象外である（点検は設計 ADR-0105 側に記録する）。
