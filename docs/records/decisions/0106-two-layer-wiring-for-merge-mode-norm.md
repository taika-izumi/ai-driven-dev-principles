# ADR-0106: マージコミットを残す規範の再発防止は予防・検出の 2 層配線とローカル git 設定の併用で行い、検出した fast-forward は履歴のやり直しで是正する

- **Status**: Proposed
- **Date**: 2026-08-17

## Context

retrospective スキルは「feature ブランチを master へ `--no-ff` マージした直後」の実施を前提とし、振り返り記録はマージコミットの SHA でサイクル境界を辿る慣行を持つ（本リポジトリの振り返りインデックスはサイクル行 37 件中 36 件が merge SHA を記録。配布物ではインデックスは空で出荷され、慣行の担い手は `skills/retrospective/template.md` の Branch 欄の様式である）。しかしこの規範は同スキルの前提文にしか書かれておらず、マージを実際に実行する完了フロー（`superpowers:finishing-a-development-branch`。外部プラグインで直接改変不可）には配線されていない（Issue-0084）。完了フローは `start-work` Phase 2 マッピング表に行を持たず、`superpowers:executing-plans` / `superpowers:subagent-driven-development` から必須サブスキルとして直接呼ばれる経路のみを持つ。その手順（選択肢 1）は `git pull` → `git merge` → feature ブランチ削除を含む。

実測（`git log --merges` と振り返り記録の突合。Issue-0084 検討状況には faa9187 のサイクル行が記載漏れのため git 実測で補正）: 起票契機の 2026-08-14 サイクルを含む観測 9 サイクルで fast-forward マージが 2 回発生した。起票後の 8 サイクルでは、適用の担い手は規範文ではなく担い手の issue 既読であり（うち 7 回適用・1 回破れ）、8 サイクル目の再発(2026-08-17)は push 前のやり直し `be8d6bd` で復旧した（順序は reset → 再マージ → 振り返り記録コミット）。手動適用の連鎖は担い手のコンテキストに依存すると実証された。構造的解決の調査（CONTRIBUTING.md「振り返りで抽出された課題に対策するとき」手順 4）では、`git config branch.master.mergeoptions` が未設定であることを確認した。

## Considered Alternatives

1. **リスク受容（配線せず手動適用を継続）**: 追加コストゼロだが、観測 9 サイクルで ff 2 回という再発率が実測済みで、再発のたびに push 前やり直し（または履歴の不整合の恒久化）が発生する。慣行の担い手がコンテキスト依存であることも実証済みのため不採用
2. **既存規範文の文言拡張のみ**: CLAUDE.md の「サブプロジェクトを master へマージした直後に retrospective を起動」の箇条、または retrospective「いつ使うか」前提文へ `--no-ff` を書き足す案（起票元は CLAUDE.md の完了処理規範への配線も候補に挙げていた）。CLAUDE.md は常時指示の最も高価な置き場で配置優先順位の最後の選択肢（ADR-0040）。前提文はマージ実行の制御経路上になく、起票後 8 サイクルの適用が前提文でなく issue 既読に依存した実測がそのまま反証になる。単独では不採用（前提文の表現整合は決定 2 に含める）
3. **本リポジトリ限定の構造的解決のみ（git config）**: 最小コストで即効だが、ローカル設定はクローン・配布先へ波及しない。マージコミット前提（retrospective の慣行）自体が配布物にあるため、配布先で同じ欠陥が再現する
4. **配布スキルへの配線のみ（git config なし）**: 配線一本に絞れるが、エージェントが配線を読み落とすと再発する。担い手のコンテキスト依存という実測済みの弱点そのもの
5. **予防単層（start-work への配線のみ）**: マッピング表に完了処理の行が存在しないため、これは文言拡張ではなく工程の新設にあたる。マージ実行前に効くが、読み落とし時の安全網がない。2026-08-17 の再発は「規範を知らずに ff 実行」型であり、予防単層では同型の破れを検出できない
6. **検出単層（retrospective 起動時チェックのみ）**: ff 実行自体は防がず、検出のたびにやり直しの手戻りが発生する
7. **採用: 予防＋検出の 2 層配線（配布スキル）＋本リポジトリへの git config 併用**

## Decision

Issue-0084 の対策として次の 3 点を実施する。

**共通手続き「慣行判定」（3 値: 慣行あり / マージコミットを残さない運用 / 未定義）**: 決定 1・2 が参照する。手続きの正本は `start-work` Phase 2 内の独立小節「完了処理のマージ方式確認」（決定 1 で新設。マッピング表直下ではなく独立見出しにするのは、表の再編でポインタが切れることを防ぐため）に置き、`retrospective` 側は節の主題によるポインタ 1 行で参照する（判定条件の複写はしない。境界をまたぐ複写の禁止に従う）。

- 前提: 既定ブランチは、まず `git config --get ai-dev.defaultbranch` を読み、値があり当該ブランチが実在すればそれを採用する。未設定なら `git symbolic-ref refs/remotes/origin/HEAD` で解決し、不能なら `git rev-parse --verify` で `master` / `main` の実在を確認（一意に定まる場合のみ採用）、それでも不定ならユーザーへ確認する。解決・確認の結果は `git config ai-dev.defaultbranch` へ永続化し、以後の照会を省く。永続化値のブランチが `git rev-parse --verify` で不在なら値を破棄して再解決する。`ai-dev.*` キーの書き込みは可逆かつ git の挙動に影響しないため低リスク（ログのみ）として扱う
- (a) 設定を見る。第一に `git config --get ai-dev.mergepractice`（(c) の回答の永続化先）: `merge-commit` なら**慣行あり**、`none` なら**残さない運用**、これら以外の値は解釈せずユーザーへ照会する。未設定なら `git config --get-all branch.<既定ブランチ>.mergeoptions` と `git config --get merge.ff`: `--no-ff` / `false` を含めば**慣行あり**、`--ff-only` / `only` なら**残さない運用**、これら以外の値が設定されていれば解釈せずユーザーへ照会する
- (b) (a) がすべて未設定なら、per-cycle 振り返り記録（`docs/records/retrospectives/system/` 直下の `YYYY-MM-DD-*.md` に一致するファイルのみ。ファイル名降順で直近 5 件。5 件未満なら存在する全件を母数とする）の Branch 行を読む。**評価順序: まず除外行を落とし、残った有効行に判定を適用する。** 除外行 = 「fast-forward」の記載を含む行（慣行からの逸脱とも慣行なしの通常運用とも判別できないため中立）・Branch 行の欠落・未知の方式値・選択肢が未削除の行・方式欄も merge SHA も持たない行。有効行の判定: 取り込み方式欄に「マージコミット」の行が 1 件でもあれば**慣行あり**。「squash」等マージコミットを残さない方式の行のみなら**残さない運用**。方式欄が無く merge SHA の記載のみの旧様式の行は、**有効行がすべて旧様式の場合に限り**マージコミット方式とみなす（新旧混在時は新様式の行のみで判定する。旧様式の一律読み替えは本リポジトリ固有の履歴事実の持ち込みであり配布先では誤るため）。除外後に有効行が 0 件なら (c) へ
- (c) **未定義**: ユーザーへ 1 問で確認する。回答は肯定なら `merge-commit`、否定なら `none` として直ちに `git config ai-dev.mergepractice` へ書いて永続化する（同一クローンでの再質問を抑止。慣行判定の照会は同一サイクル内で決定 1・2 を通じて 1 回とする — (c) が書いた設定を 2 回目以降は (a) が読むため自然に満たされる）。振り返り記録の取り込み方式欄への反映は、当該サイクルの振り返り記録を作成する時点（retrospective の記録書き出し工程）で行う（完了処理前の発火時点では記録ファイルがまだ存在しないため、時点を分離する）

1. **予防（配布スキル: `start-work`）**:
   - Phase 2 マッピング表に行を追加する。作業意図「feature ブランチの完了処理（既定ブランチへの取り込み）」/ 推奨スキル `superpowers:finishing-a-development-branch` / フォールバック「インラインで慣行確認＋マージ手順を案内」。Phase -1 の依存検出リストにも同スキルを加える
   - Phase 2 内に独立小節「完了処理のマージ方式確認」を新設し、慣行判定の正本とマージ方式の確認注記を置く。内容: 完了処理の実行直前に慣行判定を行い、**慣行あり**なら `--no-ff` を適用、**未定義**ならマージコミットを残す方式（`--no-ff`）を推奨する（「常に `--no-ff`」の無条件規範にはしない）。**残さない運用**なら方式確認を行わず完了フローの既定に委ねる。慣行あり・または未定義でユーザーが `--no-ff` を選択したとき、branch 設定が未検出なら `branch.<解決した既定ブランチ>.mergeoptions "--no-ff"` と `pull.ff true` の適用を当該サイクルから提案する（決定 3 は本リポジトリでの同内容の適用。新しいクローン・新規導入プロジェクトへの設定適用はこの経路が担う）。実行そのものの承認取得は既存の `pre-action-review` 条項が担い、本小節は方式の確認のみを担う（役割が異なり重複しない）
   - 横断的ラッパー **Pre** には追加条項として発火条件「完了処理〈既定ブランチへの取り込み〉を行うスキル・手順の実行直前」と「確認内容は Phase 2 の小節「完了処理のマージ方式確認」が正」の配線 1 行のみを置く（同内容の複写はしない）。条項内に「本条項は共通適用範囲文の例外として、delegate 済みスキルが内部で呼ぶ必須サブスキルの実行直前にも適用される」を明記する（適用範囲が delegate 境界より広い点は `subagent-dispatch` と同じ構造だが、同スキルではその宣言を被参照スキル側の「いつ使うか」が担っており、`start-work` の条項内に例外を明記するのは本条項が最初である）。**共通の適用範囲文と Post ラッパーの発火粒度は現行のまま変えない**（適用範囲文の一般化は Post の発火点も広げ、handoff 肥大化対策に逆行するため）。同一セッション内の同一完了処理につき確認は 1 回とし、マッピング表経由で確認済みなら Pre 側は省略する
   - セッション終了処理の「master へ merge 済みかの確認」は事後確認であり、本配線（実行前の方式確認）とは役割が異なる旨を 1 行注記する
2. **検出（配布スキル: `retrospective`。SKILL.md と template.md の両方を改定する。flow-template.md は Branch 欄を持たないため同期不要）**: Phase 0（前提収集）の git log 読み込み手順に接続して検証を追加し、Phase 0 の収集対象に直近の per-cycle 振り返り記録（慣行判定の入力）を加える
   - **template.md の Branch 欄を取り込み方式の明示欄へ改定する**。記入例は 1 パターンのみ示し（例: `（取り込み方式: マージコミット <sha>）`）、値の語彙は「マージコミット / squash / fast-forward」とし、該当する 1 つだけを書く旨の記入指示を欄に含める（選択肢の列挙を残させない）。ff 検出時の代替記録もこの様式で「fast-forward」を明記し、merge SHA と機械的に区別できるようにする。インデックス一覧の Branch 列にも同形で書き、その書式は `retrospective` SKILL.md の Phase 2 の行追加手順に 1 句として書く（インデックスの運用規約文書は改定しない。慣行判定の入力は per-cycle 記録のみとする）
   - 発動ゲート: 慣行判定に従う。**慣行あり**の場合のみ ff 判定を実施する。**未定義**の場合は判定を出さず慣行を 1 問確認するに留める（回答が「マージコミットを残す」なら当該サイクルから判定を実施し、決定 1 と同様に設定適用を提案する）。**残さない運用**の場合は発動しない
   - 判定手段: 先端 SHA を後述の手続きで先に確定してから判定する。reflog 走査で ff が確定した場合は祖先確認・親走査は行わない。対象 feature ブランチの先端 SHA について、まず既定ブランチの到達可能集合に含まれるかを `git merge-base --is-ancestor` で確認する（祖先でなければ未マージ〈または squash〉であり、ff とは判定せず報告のみ）。祖先である場合、既定ブランチ上のマージコミットの**第 2 親以降のいずれかの親**として存在するか（`git rev-list --parents <既定ブランチ>` の走査。octopus マージで第 2 親限定が誤るため）を確認し、存在しなければ ff と判定する。対象ブランチ名はユーザー入力を第一とする（ff 発生時は「直近 merge コミットからのブランチ名推定」が機能しないため）。先端 SHA は、ブランチが現存すれば `git rev-parse <ブランチ名>`。削除済みなら **`git reflog show <既定ブランチ>`** を新しい順に走査し（HEAD reflog は worktree ごとに分かれ、完了フローがメイン側で実行されると feature 側から見えないため、やり直し条件 4 と同じ既定ブランチの reflog に統一する）、**ブランチ名で限定された 2 パターンのみ**を判定材料にする: `merge <ブランチ名>: … Fast-forward` の行はその SHA が先端（ff 確定）、`merge <ブランチ名>: Merge made by` の行は ff でないことが確定するため検出を終了する（この行の SHA はマージコミットであり先端ではない）。`pull` 由来の記録行（`pull` で始まる行 — reflog は pull の引数をそのまま含むため `pull:` / `pull -q:` / `pull origin master:` 等の形を取る — と、pull の競合解決が作る `commit (merge):` 行）はブランチ名を持たないか無関係なマージを指すため判定材料にしない。該当行が無い場合は判定不能としてその旨を報告し、**`HEAD` や既定ブランチ先端で代用してはならない**。reflog から得た短縮 SHA は `git rev-parse <短縮 SHA>^{commit}` で完全形へ正規化してから用いる。ff 時の Phase 0 の git log 範囲は、後述で確定する分岐点 SHA から先端までを用いる
   - fast-forward 検出時のやり直し: 次の 5 条件をすべて満たす場合に限り提案する — 未 push / 既定ブランチへの追加コミットなし / feature 先端が参照可能 / 分岐点が既定ブランチの reflog から SHA として確定できる（当該 ff エントリの**直前のエントリの SHA**〈`<既定ブランチ>@{n+1}`〉を分岐点とする。reflog は per-clone・期限付きのため、別クローン・clone 直後では不成立になる）/ 作業ツリーの追跡ファイルに未コミット変更が無いか、変更を対象パス限定の `git stash push` で退避した（**退避手段は stash のみとし、既定ブランチへの先行コミットは用いない**。先行コミットは条件 2 を自ら破り、直後の reset で履歴から外れて内容を失うため）。条件 1・2 は機械判定する——未 push は、既定ブランチのリモート追跡 ref が存在する場合に `git merge-base --is-ancestor <先端 SHA> <リモート追跡 ref>` が偽であること（追跡 ref が無ければユーザーへ確認する）。追加コミットなしは `git rev-parse <既定ブランチ>` が先端 SHA と一致することで確認する。手順: 分岐点を**先に SHA として確定・提示し、以後は確定 SHA のみを使う**（相対参照は再実行で ff 状態へ戻るため。`git merge-base` は ff 後に feature 先端を返すため用いない）。リスク段階の判定によらず本手順は承認必須とする（手順固有の上乗せであり、リスク分類の定義は変更しない）。承認後、(1) `git branch <一時名> <先端 SHA>` で一時 ref を張る（gc による先端消失の窓を塞ぐ。名前は日付と先端短縮 SHA を含む形とし、既存と衝突したら既存を消さず別名を採る）、(2) 退避を実施し **`git status --porcelain --untracked-files=no` の出力が空であることを確認する。空でなければ reset へ進まず中止する**、(3) `git reset --hard <確定 SHA>`、(4) `git merge --no-ff <一時 ref 名>`（コミットメッセージはプロジェクトの慣行に従う）、(5) 退避の復元と一時 ref の削除。以上を **Phase 0 の検証直後・Phase 1 の前に完了させる**（2026-08-17 の実測復旧と同順序。記録が先に master へ載るとゲート条件を自ら失効させ、Branch 行に書く merge SHA も確定しないため）。このやり直しは当該サイクルの完了処理の訂正であり、retrospective「スキル内ではコミットしない」前提の**明示例外**として同前提文にその旨を追記する（抽出限定スコープ〈対策設計をしない〉は維持する）
   - 5 条件を満たさない場合（push 済み・追加コミットあり・分岐点不能等）は、やり直しを提案せず、上記の代替記録様式（fast-forward 明記）で記録する扱いをユーザーへ提示するに留める
   - あわせて「いつ使うか」の `--no-ff` 前提文を、マージコミットを残す運用を前提とするゲート付き表現へ揃える（無条件形とゲート付き注記の併存で配布先の解釈が割れることを防ぐ）
   - 実装の完了基準に、一時リポジトリでのスモーク検証を含める（本リポジトリでは決定 3 により ff が起きず、検出経路が実運用で実行されないまま配布されるため）。検証項目: (i) **慣行判定の入力側** — (b) の主要構成（マージコミットあり / squash のみ / fast-forward のみ / 旧様式のみ / 新旧混在 / 0 件）をダミー記録で再現し、(c) の照会・設定書き込み・再質問抑止まで 1 度通す（(a) 固定の前に実施する。本リポジトリでは決定 3 適用後 (b)(c) が到達不能になり、実運用で検証されないため）。(ii) **判定経路** — 慣行判定を (a) の設定で慣行ありに固定したうえで ff / `--no-ff` / 競合解決マージ / squash / ブランチ削除済みの各状態を再現し、判定・ゲート・やり直し手順の文言どおりの動作を確認する。やり直し手順は承認ステップを省いた dry-run で検証し、承認要件は文言レビューで確認する。「分岐点不能」は「ブランチ削除済み」と独立に再現できないため、判定不能報告の確認で足りる
3. **構造的解決（本リポジトリ）**: `git config branch.master.mergeoptions "--no-ff"` と `git config pull.ff true` を併せて設定する。後者は、完了フローの手順が `git pull` を含み、mergeoptions 単独では pull が余分なマージコミットを作ってサイクル境界の可読性を損なうことが実測されたための併設である（検出の判定手段は親走査であり pull 由来マージの影響は受けない）。実施はエージェントが行い、`git config --get-all` の読み直しで適用を確認する

選定理由: 予防と検出は発火時点が異なる二重化（マージ実行前 / サイクル末）だが、どちらも規範テキストの読解に依存する点で破れモードは同型である。読解から独立した阻止は git config 層のみが提供し、それは本リポジトリ限定である（既存の慣行を持つ配布先へは決定 1 の設定適用提案で、新規導入プロジェクトへは慣行判定 (c) の初回確認と設定への永続化経由で波及させる）。構造的解決を行動規範より優先する既存方針（ADR-0036/0039）に従い、行動規範側の 2 層はその補完とする。

評価可能性（新設 6 件）:

- 慣行判定（共通手続き）: 発火機会は完了処理ごと＋retrospective 起動ごとに各 1 回（対象期間: 次回棚卸しまで。計数手段: 決定 1・2 の各発火機会に同じ）。捕捉したい欠陥型は「慣行の有無の誤判定（慣行のない配布先での誤発動・慣行のある配布先での不発動）」。退役条件は「棚卸し時に (a) の設定が既定ブランチで設定済みと確認できた環境では (b)(c) の経路を退役候補として提案する」
- 既定ブランチ解決（`ai-dev.defaultbranch` 永続化を含む）: 発火機会は慣行判定ごとに 1 回（初回のみ解決、以後は設定読み。対象期間・計数手段は慣行判定に同じ）。捕捉したい欠陥型は「既定ブランチの誤同定（誤ったブランチでの親走査・誤った設定適用）」。退役条件は「`refs/remotes/origin/HEAD` が解決可能と確認できた環境ではフォールバックと永続化を退役候補として提案する」
- 決定 1（予防行・確認小節）: 発火機会はサイクル完了処理ごとに 1 回（対象期間: 次回棚卸しまで。計数手段: 振り返り記録の Branch 行〈取り込み方式欄〉と `git log --merges` の突合。handoff の消化記録は cycle-reset で全行削除されるため計数手段にしない）。捕捉したい欠陥型は「慣行未確認のまま完了フローの既定で fast-forward マージする操作」。本リポジトリでは決定 3 が ff を阻止するため、ff 件数から決定 1 単独の効果は分離できない（交絡として受容する）
- 決定 2（検出チェック）: 発火機会は retrospective 起動ごとに 1 回（対象期間: 次回棚卸しまで。計数手段: 振り返りインデックスの追加行数）。捕捉したい欠陥型は「予防層をすり抜けた fast-forward マージ」。検出件数の期待値は 0（決定 1・3 が機能している状態。0 は成功の向きであり退役の根拠にしない。検出経路の生存確認は上記スモーク検証が担う）。検出が 1 件以上あれば構造観察型の flow 課題として新規起票して記録・計数する（振り分け規則との整合。計数は本リポジトリ側の運用であり、配布スキル本文には計数指示・課題番号を書かない）
- やり直し手順（5 条件・一時 ref・退避・承認必須の上乗せ）: 発火機会は ff 検出時のみ（期待値 0。対象期間: 次回棚卸しまで。計数手段: 振り返り記録の取り込み方式欄が「fast-forward」の件数と、やり直し後の merge SHA の対応）。捕捉したい欠陥型は「退避漏れ・分岐点誤りによる未コミット変更や履歴の喪失」。退役条件は上流 `finishing-a-development-branch` の標準装備確認時、または慣行廃止時に手順ごと撤去
- 取り込み方式欄（template.md の様式新設）: 発火機会は振り返り記録の作成ごとに 1 回（対象期間: 次回棚卸しまで。計数手段: `system/` 直下の記録のうち方式欄を持つ件数）。捕捉したい欠陥型は「方式の記録漏れ・誤記」。退役条件は「マージコミットでサイクル境界を辿る慣行の廃止時に欄ごと撤去」
- 退役条件（全体）: 上流 `finishing-a-development-branch` がマージ方式の確認を標準装備したことを確認した時点（確認の契機は棚卸し時、および慣行判定が未定義・照会を返した回とする）で決定 1 を退役候補としてユーザーへ提案する。マージコミットでサイクル境界を辿る慣行自体を廃止した場合は 2 層とも退役側。決定 3 の設定は、本リポジトリが squash 運用を採用した時点または慣行廃止時に撤去する

## Consequences

- 良い影響: マージ方式の適用が担い手のコンテキスト（Issue-0084 を読んでいるか）から独立する。本リポジトリでは明示フラグなしの `git merge` に限り ff が設定レベルで阻止される。配布先には予防・検出の 2 層が、squash/PR マージ運用と衝突しない慣行判定ゲート付きで届く
- 阻止の限界: 明示的な `--ff` / `--ff-only` を伴うコマンドは設定を上書きするため、決定 3 の阻止は「明示フラグなしの `git merge`」に限る（実測済み）。また `branch.master.mergeoptions` 設定下では master への `git merge --squash` が fatal になる（本リポジトリに squash 運用はない。採用する場合は決定 3 の設定を撤去する）
- 受容する残存経路: `start-work` を経由しないセッション（ユーザーが直接マージを指示した場合等）では予防層は発火せず、検出層と git config 層（本リポジトリのみ）でカバーされる。検出は retrospective の対象 feature ブランチ単位であり、同サイクルの他ブランチのマージは検査されない。retrospective をユーザーが繰り延べた場合、その間の追加コミット・push によりやり直し条件は失われ、代替記録側の扱いになる。本リポジトリは `refs/remotes/origin/HEAD` が未設定のため、既定ブランチ解決は初回にフォールバック（`master` の実在確認で一意に解決）を経て `ai-dev.defaultbranch` へ永続化される
- コスト: 配布スキル 2 件の改定（`start-work` は SKILL.md、`retrospective` は SKILL.md と template.md。`.claude-plugin/plugin.json` と `.claude-plugin/marketplace.json` の version bump 0.1.8 → 0.1.9〈`dist/` 側は build-dist.ps1 が複写〉・執行点 4 手順・配布物の目視が必要）。現行仕様書 `docs/current/specs/2026-05-01-retrospective-design.md` へは Phase 0 節・記録様式（Branch 欄）・Phase 2 の行追加手順・末尾のコミット非実施行（明示例外の追記）を同期する（スナップショット性の維持。最小サイクル文脈の行は方式欄化後も成立するため変更不要）。start-work 側の旧設計仕様書の図示は既存の乖離があり本件では同期対象にしない（既存乖離は実装サイクル中に flow 課題として起票し、本サイクルでは対策しない）。`sync-template.ps1` の生成実行（執行点手順 1）は不要だが、手順 2 の `-Check` は変更範囲によらず両生成器で実施する。git config はクローンごとに再設定が必要で、再適用の担い手は決定 1 の設定適用提案と慣行判定 (c) の永続化とする
- ADR-0056（retrospective の記録様式を定めた決定）へ部分修正注記を付す（Branch 欄の様式を取り込み方式欄へ改定するため）
- 既発生分（2026-08-14 サイクルの ff。先端 `9259eec` の代替記録）は、振り返り記録の追記型規約（過去行の編集禁止）により是正せず残す。同行は「fast-forward」を明記しているため、慣行判定 (b) では中立の除外行として扱われる（判定は他の行と設定が担う）
- 次サイクルの retrospective で、Issue-0084 対策の初回運用結果を「既存課題の再発・進展」に記録する
- Issue-0084 は本 ADR の Accepted 昇格時に close する（Status を closed へ、結論に ADR-0106 を記載、課題インデックスの行も更新。フォルダ未昇格のため close 時移設判定は非該当）。同 issue 検討状況の faa9187 サイクル行の記載漏れは close 前の追記で補正する
