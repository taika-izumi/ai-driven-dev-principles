# ADR-0113: 生成器の JSON 入力異常に対する診断強化は、Codex 生成物の入力ガードと同じコミットへ統合する

- **Status**: Proposed
- **Date**: 2026-08-25

## Context

Codex 対応の実装計画（`docs/working/plans/2026-08-25-codex-support-implementation.md`）の Task 1 で、`scripts/build-dist.ps1` に version 一致検査を計画どおり実装した（コミット `29bc6ff`）。仕様適合レビューは要求 12 件中 12 件充足で通過した。

続くコード品質レビュー（独立サブエージェント・claude-opus-5）が Critical 0 / Important 3 / Minor 6 を報告した。Important 3 件はいずれも「`exit 1` で安全側に倒れるが診断が不正確」という性格で、正しさの欠陥ではない。指摘の根拠となる PowerShell の挙動は、本セッションで非破壊に再現確認した（PowerShell 7.6.5）:

- `@($null).Count` は `1`。`plugins` キーが欠損した marketplace.json や空ファイルでは、実在しない `plugins[0] () = ` の version 不一致として報告される（Important-2）。`$srcVersion` 側は同一コミット内で `$null` を明示検査して `version not found in ...` と正しく報告しており、非対称になっている
- `'' | ConvertFrom-Json` は `$ErrorActionPreference = 'Stop'` 下でも例外を投げず `$null` を返す
- 不正 JSON では `ConvertFrom-Json` が ParserError を投げ、`[build-dist]` 接頭辞のない生の例外スタックが出る（Important-3）。同ファイル 35 行目の既存コメント（M-6）と、Task 1 で追加した 27-28 行目のコメントが掲げる「例外スタックを生で出さず接頭辞つきの診断で止める」方針と矛盾する
- `plugins: []`（空配列）は version ゲートを 0 回反復で無言通過する（Important-1）

計画の Task 2 は、同じ領域（`Get-JsonProperty` 直後・`$marketplaceObj` の利用箇所）に `New-CodexMarketplaceContent` を追加し、`source` の型・`plugins` 0 件・`name` 空の 3 つの入力ガードを置く設計であり、Step 13 がその期待出力まで定めている。Important-1（`plugins: []`）は Task 2 到達時点で `no plugins found in ...` として塞がれるため、恒久的な穴ではなく Task 1〜Task 2 間の 1 コミット分の一時的な間隙である。

本計画自体は確定前レビュー（フル巡 2＋機械検証 1＋差分確認巡 2＋機械検証 1・指摘 44 件全採用）を通過して確定しており、計画からの逸脱には判断を要する。

**追記（Task 2 実装後）**: 下記 Decision の 4 点を反映した Task 2 の実装（コミット `015e79e`）に対するコード品質レビューが、同種の穴をさらに 2 件報告した。いずれも隔離コピーでの実測つきである。

- 型・欠損ガードが `plugins[].source` にしか無く、**同じ故障モードが 5 値に残る**（marketplace の `name`、plugin の `name` / `version` / `description` / `author.name`）。`ConvertTo-JsonStringValue` の `param([string]$Value)` が PSCustomObject を `@{...}` へ、`$null` を空文字へ黙って変換するため、`description` を object 化すると `"description": "@{ja=説明; en=desc}"` を無診断で出荷して `exit 0` になる。`-Check` は「生成器の出力 vs 生成物」の自己突合であるため、壊れた値は自己一致して恒久的に通り続ける（強制変換の機構は本セッションで再現確認済み）
- `New-CodexMarketplaceContent` の呼び出しが「規約違反レポート」より前にあるため、規約違反と marketplace の不正が同時に存在すると**規約違反が一度も表示されない**。Task 2 の前は必ず表示されていた

同レビューはこのほか Minor を 4 群報告した（C0 制御文字の未エスケープ・`.agents/` 配下の stale 未検出・保守性 4 件）。

## Considered Alternatives

1. **Task 1 を追加改訂して即時に塞ぐ**（`29bc6ff` を amend、または追加コミット）: 各コミット時点での健全性は最も高い。しかし Task 2 が同じ領域を再度編集するため作業が二度手間になり、計画からの逸脱点が 2 コミットに分散する。Important-1 のために置くガードは Task 2 のガードと重複する
2. **全指摘を不採用とし Issue 起票のみ**: 確定済み計画の逐語実装を貫き、逸脱をゼロにできる。しかし Important-2・3 は計画が扱っていない恒久的な診断品質の穴であり、Task 2 が同種のガードを置く直後の位置に残り続ける。同一ファイル内で「入力異常を診断つきで止める」箇所と「生の例外を出す」箇所が併存する
3. **Important-3（不正 JSON の生スタック）のみ即時対応**: ファイル自身のコメントとの矛盾だけを解消する最小案。Important-2 の非対称（`$srcVersion` は `$null` 検査あり／`plugins` は無し）が残る
4. **（採用）Task 2 のコミットへ統合する**

## Decision

案 4 を採用する。Task 1 のコミット `29bc6ff` は計画どおりのまま確定させ、採否は次のとおりとする。

**Task 2 のコミットへ統合して反映するもの**:

- Important-2: `plugins` の件数・存在ガードをループ前に置き、`plugins` キー欠損・空配列・空ファイルを事実に即した診断で止める。Task 2 が追加する 3 ガード（`source` 型・0 件・`name` 空）と同じ位置・同じ書式に揃える
- Important-3: JSON 読み込みを診断つきのヘルパへ寄せ、不正 JSON で `[build-dist]` 接頭辞つきの診断を出して止める
- Minor-3: `$pluginIndex` を marketplace 側の添字と分かる名前へ改める（このファイルの `$plugin*` 系は既存のすべてが plugin.json を指すため、Task 2 で `$pluginObj` / `$marketplaceObj` を並べて扱う際の読み違えを避ける）
- Minor-4: `plugin.json` の二重読み込みを 1 回にまとめ、検査した版と複写する版の同一性を保証する

**個別対応しないもの**:

- Important-1（`plugins: []` の無言通過）: Task 2 の `New-CodexMarketplaceContent` の 0 件ガードが同一コミットで塞ぐため、追加の実装を置かない。Important-2 の件数ガードとも重複する
- Minor-1・2・5・6（中止メッセージの文言・詳細行のヘッダ・`Get-JsonProperty` の大文字小文字非区別と `-AsHashtable` 非対応・位置引数呼び出し）: 好みの範囲であり、計画のコード片をそのまま採る

**検証**: Task 2 の Step 13（正本の異常入力でガードが働くことの確認）に「`plugins` キー欠損」「不正 JSON」の 2 ケースを追加し、いずれも `[build-dist]` 接頭辞つきの診断と非ゼロ終了になることを実測する。

### 追加決定（Task 2 実装後のコード品質レビューを受けて）

Context の追記で挙げた 2 件も、同じ Task 2 のコミットへ統合して反映する（`015e79e` を amend する）。採用の基準は次の 2 つに限り、以後この線を動かさない。

- **(i) 検出機構が構造的に効かない型**: 型・欠損ガードの非対称がこれにあたる。`-Check` が自己突合であるため壊れた値は永久に自己一致し、Task 11 の検証にも捕捉するステップが無い。「後で見つかる」経路が存在しない
- **(ii) 本コミット自身が持ち込んだ後退**: 規約違反レポートの隠蔽がこれにあたる。Task 2 の前は必ず表示されていた挙動であり、逸脱というより修繕である。組み立てブロックを違反レポートの後ろへ移すだけで戻り、不変性は変わらない

修正の形は、これまで無ガードだった 5 値（marketplace の `name`、plugin の `name` / `version` / `description` / `author.name`）の取り出しを共通ヘルパへ寄せ、同一の診断で止める。**既存の `plugins[].source` / `plugins[].name` のガードは変更しない**——この 2 つの診断文言は計画 Task 2 の Step 13 ケース 1・3 の期待出力に逐語で組み込まれており、共通ヘルパへ吸収すると検証済みの期待値が成立しなくなるため。ガードの網羅性はこれで達成される（無ガードだったのは上記 5 値のみ）。

**採用しないもの**: 残る Minor 3 群（C0 制御文字の未エスケープ・`.agents/` 配下の stale 未検出・保守性 4 件）は Issue-0108 として起票し、実装時レビューまたは次サイクルへ委ねる。いずれも本サイクルの Task 11 の検証範囲外であることを Issue に明記した。

## Consequences

- 計画からの逸脱点が Task 2 の 1 コミットに集約され、逸脱の範囲と根拠を 1 箇所で追跡できる
- 入力異常に対するガードが `.claude-plugin/` の 2 正本すべてについて同じ位置・同じ書式で揃い、同一ファイル内に「診断つきで止める箇所」と「生の例外が出る箇所」が併存する状態が解消される
- Task 1 のコミット `29bc6ff` 単体の時点では、`plugins: []` が version ゲートを無言通過し、`plugins` キー欠損では事実と異なる診断が出る状態が残る。この間隙は Task 2 のコミットで閉じる。中間状態でのみ露出するため、`git bisect` 等でこのコミットを単独チェックアウトした場合に限り観測されうる
- Task 2 の実装量とレビュー範囲が計画時点の想定より増える。Task 2 の仕様適合レビューでは、計画の逐語コード片との差分が「本 ADR で承認した 4 点に限られること」を判定対象に加える必要がある
- 生成器の入力ガードの設計方針そのもの（正本 JSON の異常を検出したら黙認せず止める）は ADR-0112 および ADR-0054 の枠内であり、本 ADR はその反映先とタイミングのみを定める。ADR-0112 の Decision は変更しない
- 追加決定により、Task 2 の計画からの逸脱は計 6 点になった。仕様適合レビューの判定対象（「逸脱が承認済みの N 点に限られるか」）はそのぶん広がる。採用基準を (i)(ii) の 2 つに固定したのは、レビューのたびに採用範囲が膨らむことを防ぐためである
- 正本 JSON への手編集ミス（キーの欠損・型の取り違え）が、無診断の配布物としてではなく生成時の診断として現れるようになる。ただしこの守りが働くのは異常時のみであり、本サイクルの計画内タスクが必然的に踏む経路ではない（Task 8 の `description` 更新は正常な文字列への書き換えであり、ガードは発火しない）
- Issue-0108 に委ねた 3 群は、`scripts/build-dist.ps1` を次に編集するサイクルまで未対応のまま残る。とくに C0 制御文字の穴は、このリポジトリ内のどの検査でも検出できず Codex CLI 側でのみ露見する性質を持つ
