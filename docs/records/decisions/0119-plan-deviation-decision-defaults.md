# ADR-0119: 確定済み計画からの逸脱判断に型分類と採用基準の既定を置き、references 正本と計画側宣言で常設する

- **Status**: Accepted
- **Date**: 2026-08-30

## Context

Issue-0110: 確定前レビューを通過して確定した計画に対し、実装時レビューが Important/Major 級の指摘を出すたびに「計画どおり逐語実装するか / 逸脱して直すか」の設計判断が発生する。feature/codex-support サイクルでは 4 回発生し、いずれもユーザー判断を仰いだ。採用範囲は回を追って広がった。回 1・2 は ADR-0113 が採用基準 (i)(ii) を事後に固定して膨張に歯止めをかけたが、回 3・4（ADR-0114）は (i)(ii) を「生成器の入力ガードに固有の基準」とみなし、「規範文書の欠陥は実行による安全網が無く数サイクル後まで潜伏する」という別基準で裁いた。すなわち採用基準はサイクルごと・領域ごとに事後に組み立てられており、汎用の既定は存在しない。

委譲した LoopForAlpha の実測（ADR-0118。Issue-0113 = LoopForAlpha#Issue-0096 の観測群）が対策設計の前提を与える:

- **確定前レビューと実装時レビューは補完関係**: 両型を通した 4 事例すべてで、確定前レビュー通過後の実装から実装時レビューが追加の Critical/Major を検出した。確定前レビューは計画を単体で読むため、写す先ファイルの既存規約との整合は原理的に視野に入らない
- **ただしレビュー要否・逸脱の発生は成果物型に依存する**: 「実装時の独立レビューを 0 にはできない」（Issue-0113 資料）は無条件には成立せず、実行による安全網が厚い小規模成果物では前倒しレビュー単独・またはレビューなし＋TDD で実装手戻り 0 の後発観測が 3 件ある。Issue-0110 の「逸脱ゼロが正解ではない」（逸脱を許さなければ実在の欠陥が残る）は規範命題としてこれと両立する
- **残存欠陥の型は出所のレビュー重量が異なる**: 期待値の陳腐化・射程の脱落は最重量のレビュー（フル 3 巡・写経実行つき）を通しても残り、写す先規約との不整合はフル 1 巡構成、根拠の事実誤認は 3 観点・写経実行つき構成（巡数の記録なし）のフェーズで残った
- **記録された計画コードからの逸脱は 3 件**（機械的な適応 1・事実誤り / 期待値の陳腐化の訂正 2）で、いずれも設計の変更に当たらないと判断されている（うち 2 件は逐語で明記）。設計の変更級の逸脱の実例は本リポジトリの ADR-0113/0114 が担う。「期待値に実体を合わせる」反射で正しい記述を壊しかけた実例があり、訂正の向きは自明でない。また ADR-0114 の決定 1・3 の 2 件と Issue-0113 資料のフェーズ 4 欠陥 1 は「計画の記述・コードが自ら明示した意図を満たさない」型で、事実誤り型の一部として扱う必要がある
- **前倒し型計画の格下げ安全弁は規律として宣言されているが、発火実績は 0 件**（逸脱 3 件はいずれも発火に至らず。うち 2 件は閾値未満と明示判断、1 件は「設計の変更ではなく訂正」と判定されており、引用元の文言〈機械的な適応を超えたら〉では発火対象になり得たが不発だった）。閾値の妥当性は未検証である。前倒し型の判定 3 条件のうち「実行による安全網が無い」は、前倒し型を採用した実測 2 回ではいずれも二値判定に失敗している（「半分だけ真」「N/A」。別に偽と確定できて前倒し型を採らなかった 1 回がある）
- Issue-0110 の対策方向のうち「確定前レビューの観点に実装時レビューで出そうな型を含める」（同 Issue「対策の方向」2 つ目の箇条）は、補完関係の実測が反証している
- Issue-0114 の軸 1 実測のうち本設計に関わるのは「実装者の自己変異は生存 0 ＝ 自己検証はレビューの代替にならない」で、前倒し型の格下げ既定の未検証宣言と代替検出の限界の記述に反映した。層別実測の本体（レビュー深度の層別再設計の材料）は Issue-0114 / Issue-0103 の射程であり本 ADR では用いない

## Considered Alternatives

対策の骨格:

1. **汎用既定＋計画側宣言のハイブリッド（採用）** — 採用基準と型分類の既定をガイドライン側に常設し、計画側は宣言欄で既定の利用または上書きを示す。指摘のたびの判断が「基準への当てはめ」へ縮む。逸脱許容範囲のタスク単位の宣言（逐語厳守 / 意図準拠）は前倒し型タスクに限定して採用し、一般タスクは計画単位の宣言で足りると判断した
2. **計画側の先置きのみ** — 計画確定時に毎回基準を書く。汎用基準が無いため、毎計画で基準を組み立てるコストが残る
3. **汎用既定のみ** — 一律の既定だけ置く。前倒し型（逐語厳守が要る）と通常型の差を吸収できない
4. **既存工程の文言拡張・リスク受容で足りないか（新設回避の比較）** — 隣接する既存規範は 4 系統ある。`subagent-dispatch` 手順 6 は検査委譲の指摘受け取り時に前提の実在検査を課すが、これは手続き義務であり採否**基準**を持たない。`superpowers:receiving-code-review` は指摘の技術的採否（YAGNI・push back）を扱うが、確定済み計画からの逸脱の可否と採用範囲の膨張抑止は扱わず、外部プラグインのため改変できない。`superpowers` の実装スキル群（subagent-driven-development の implementer プロンプト・executing-plans）は「計画の想定外に触れたら停止して人間へエスカレートする」規範を持つが、エスカレート後の採否基準を持たない（本 ADR はそのエスカレートの受け側を定める関係にある）。`pre-finalization-review` は確定点の提示・4 観点レビューの実施・確定点前の反復が管轄で、実装時レビュー由来の改訂を明示的に対象外としている。よって「計画逸脱の採否基準」の受け皿は既存に無く、文言拡張では足りない。リスク受容（現状維持）は判断コストが指摘回数に比例し続けることの受容であり、実測 4 回/サイクルの介入がある以上採らない
5. **確定前レビューの観点への前倒しで吸収する（不採用）** — 補完関係は原理的で、前倒しでは吸収できない（Context の実測）

規範の置き場所:

1. **start-work の references/ 正本＋予防・検出の 2 層（採用）** — 正本の置き場はマージ方式確認（ADR-0106・`references/merge-practice.md`）と同じ型。配線も同先例の 2 層（予防層＝start-work 内の Pre 条項とマッピング表、検出層＝実行点側の検査）に合わせる。先例は予防単層（start-work への配線のみ）を「読み落とし時の安全網が無い」として不採用にしており、本 ADR の検出層は Decision 5 が担う
2. **新設スキルとして独立** — フロー内で適用される規範であり、ユーザーが能動的に呼ぶ型ではないため呼び忘れリスクが高い
3. **subagent-dispatch の制約ブロックへ組み込み** — 採否の裁定主体は委譲元でありレビュアー向け制約（B 群）に置くのは責務がずれる。ただし委譲時の注入項目の想起担保として、同スキル手順へ本参照へのポインタ 1 行は置く（Decision 6。採否基準本体の移設ではない）
4. **AGENTS.md（Layer 2）** — 発動条件が特定状況に限られるため、配置優先順位（環境設定 → Layer 3 → 手順書 → AGENTS.md）で最後の選択肢

## Decision

骨格は案 1（ハイブリッド）、置き場所は案 1（references 正本＋予防・検出の 2 層）を採用する。`skills/start-work/references/plan-deviation-defaults.md` を新設し、以下を正本として定める。

**1. 適用対象と前処理**: 確定済み実装計画の実行中（plan 確定点の通過後に発生した指摘・改訂）に、実装時レビュー（独立レビュー）または実装者検証が「計画どおりでは欠陥が残る」型の指摘を出したとき。確定前レビューの反復（確定点前）は対象外（pre-finalization-review の領分。同工程内の指摘は同工程の既存記録に委ね、逸脱記録行は残さない）。非ゼロ終了で工程を止める阻止型の検査（-Check 等）が捕捉した事象も対象外とする（実装が計画・規約を満たしていない状態であり、修正必須。逸脱判断の余地がないため逸脱記録行も残さない）。前処理は 2 つ: (a) 検査委譲の指摘には `subagent-dispatch` 手順 6 の前提検査を先に通し、実装者検証由来の指摘には委譲元（委譲を伴わない場合は実装を進めている本人）が同旨の前提検査を行う。(b) 確定前レビューが「実装時レビューへの引き継ぎ対象」として正本に残した指摘（所在は宣言欄に書く）は、型分類に入る前に当該一覧と突合する。一致した指摘は、前巡の不採用理由が実装後の実体で覆っていると実証できた場合に採否をユーザーへ提示し、それ以外は不採用のまま逸脱記録行に残す（一致・実証の判定に迷う場合は提示側へ倒す）。本既定の適用対象として検討したうえで対象外と裁定した指摘も、逸脱記録行へ残す。

**2. 指摘の型分類と既定の扱い**（委譲先は候補としての型分類を添えて報告し、確定分類は委譲元が行う。型の判定に迷う場合・複数型にまたがる場合は「設計の変更」側へ倒す）:

| 型 | 定義 | 既定の扱い |
|---|---|---|
| 機械的な適応 | 計画の意図を写す先の実体（ファイル慣習・既存規約）に合わせて実現する調整。設計は不変 | 採用可。逸脱として数え、逸脱記録へ 1 行（他型との差は記録の軽さのみ） |
| 事実誤り・期待値の陳腐化の訂正 | 計画の根拠・期待値・記述が、実体**または計画自身が明示した意図**と食い違う場合の訂正。直す向きは自明でないため、編集前に全数列挙・実測で向きを決める | 採用可。実測根拠を添えて逸脱記録へ |
| 設計の変更 | 条件・分岐・機構・契約に触れる逸脱（訂正型であっても条件・分岐・契約に触れるものを含む） | 下記 3. の採用基準で判定 |
| 計画の射程外の既存欠陥 | 計画が扱っていない既存の欠陥（逸脱ではなくスコープ追加） | 既定で issue 起票（逸脱記録にも 1 行。帰結は「不採用」とし第 3 欄に Issue-NNNN。統合採用時は「採用」）。採用基準 (i) に該当し、同一領域を触るタスクが計画内にある場合に限り統合採用可（統合の形は ADR-0113 の型。(i) のゲートは本 ADR の追加） |

**3. 設計変更級の採用基準**:

- **(i) 検出資産の不在**: 当該計画とリポジトリが現に持つ検出資産のいずれにも捕捉される経路が無い型 → 採用可。検出資産とは「当該計画の完了後も、当該欠陥型を毎回検査するものとしてリポジトリに残る資産」（自動テスト・機械検査・計画内の検証 Step のうち恒久化されるもの・配布物検査・後続タスクの再測）を指す。**レビュー委譲は反復頻度によらず検出資産に数えない**。(i) の判定には不在の根拠（走査した資産名と、それが当該欠陥型を捕捉しない理由）を当該 ADR または当該サイクル正本（課題ログ等）に残し、逸脱記録行の第 3 欄にはその識別子のみを書く（実証要件。pre-finalization-review の前提実在観点と同水準）
- **(ii) 当該コミット（委譲実装では当該タスクの成果物）自身が持ち込んだ後退** → 採用可（逸脱というより修繕）
- 採用時の記録: 設計変更の採用は decision-log の強トリガー（方針の変更）で ADR 化される（発火・手順の正本は同スキル）。本既定が足すのは逸脱記録行に ADR 番号を残すことのみ（範囲・根拠の記載は ADR の通常フォーマットが担う）
- **基準外 → 既定で不採用**。次サイクルで判断が要るものは issue 起票する（いずれの帰結でも逸脱記録へ 1 行残す）
- **基準は計画確定時に固定し、変更（拡大・縮小のいずれも）にはユーザー承認と ADR を要する**（宣言欄の実装中の変更も本要件に従う）
- 判断を求めるユーザー介入は主に「基準への当てはめに迷う場合」「ADR の確定」「宣言欄の実装中の変更」へ縮む（ほかに 1.(b) の突合提示がある）。不可逆操作・大規模変更の確認（pre-action-review）等の既存の確認ゲートは本既定の対象外で従来どおり適用される

**4. 計画側の宣言**: 計画に「逸脱判断の既定」欄を置き、既定どおりなら参照 1 行に plugin 版数を添える（版数は**どの版の既定で判断したかの事後追跡の記録**であり、実行中に正本が改定された場合に改定を当該計画へ適用するかはユーザーが判断する——基準を広げる改定は 3. の承認・ADR 要件に従う）。上書きが要る計画はここで基準を追加・強化し、確定前レビューからの引き継ぎ一覧の所在もここに書く。判定 3 条件（設計が確定している・実コード全文を計画に載せられる規模・実行による安全網が無い）が**すべて揃う**前倒し型のタスクは「逐語厳守＋設計の変更に至ったら当該タスクをタスク別独立レビューへ格下げ」を既定とする。3 条件のいずれかが判定不能・部分成立のまま前倒し型工程（タスク別独立レビューを置かない工程）を採る場合は、逐語厳守は課さず**格下げ安全弁のみ維持する**（未検証の逐語厳守既定に依存せず、保護が減らない側へ倒す）。格下げの発火判定は再分類後の型で行う（型 2 から設計の変更へ昇格した訂正は格下げ対象になる）。機械的な適応・昇格に至らない訂正は格下げ対象外とし、記録して続行する（発火閾値を引用元の「機械的な適応を超えたら」から「設計の変更に至ったら」へ意図的に狭めた——実測 3 件の逸脱がいずれも格下げ不発で運用された実態に合わせた校正であり、狭めた後の機構も発火実績 0 の未検証機構として評価対象に含める）。宣言欄が無い計画（既存計画・置き忘れ）では既定どおり（現行版）として扱い、前処理 (b) は引き継ぎ一覧を特定できないため非適用とし、その旨を最初の逸脱記録行に残す。

**5. 逸脱記録と検出層**: 本既定を適用した**全帰結**は、計画ファイルの当該タスク（是正を適用したタスク。指摘が生じたタスクと異なる場合は生じた側にポインタ 1 行）の最後の Step の直後へ「逸脱記録」行を 1 行残す。書式は固定する: 行頭から `逸脱記録: <型> / <帰結> / <識別子・根拠>` で始め、箇条マーカー・インデント・チェックボックスを前置せず、直前の行との間に空行を 1 行置く。型は 2. の 4 型名または「対象外」、帰結は「採用 / 不採用 / 対象外」の 3 値、第 3 欄に識別子（Issue-NNNN / ADR-NNNN / 実証の所在 / 格下げ: 発火 or 不発）と短い根拠を書き、`/` を根拠テキストに含めず、第 3 欄内の複数要素は読点（、）で区切る。当てはめがユーザーに覆された場合は行末へ ` / 覆し: <日付> <覆し後の帰結>` を追記する。**行の書き込みは委譲元が行う**（委譲先は報告のみ。隔離コピー・並列委譲下で記録が実リポジトリへ届かない事故と同時編集の衝突を避けるため）。書き込みは帰結確定時に行い、当該タスクの実装時レビューを委譲する時点で既知の帰結はすべて記録済みにする（当該レビュー由来の指摘は帰結確定時に追記する）。計画がファイル化されない経路（インライン簡易 plan）では、`docs/working/plans/` へ宣言欄とタスク列挙を持つ最小の計画ファイルを起こすことを既定とする（記録先と計数を 1 系統に保つため）。記録先を計画本体とするのは cycle-reset で消えないためであり、handoff の消化記録は計数手段にしない。検出層: **タスク別の仕様適合レビューを置く工程型では**、そのレビューの委譲プロンプトの判定対象に「計画との差分が逸脱記録の列挙に限られるか」を含める（委譲元が本参照に従い注入する）。**置かない工程型（前倒し型・インライン TDD）では**、タスク完了時に委譲元が計画との差分（git diff 等）と逸脱記録行を突合する自己検査で代替し、タスク完了報告へ「逸脱突合: 一致 / 差分あり」の 1 行を残す。自己検査が拾えるのは記録漏れであり、型分類の甘さ（自己に有利な分類）は拾えない——後者は覆しの観測・委譲先の候補型分類報告・タスク別仕様適合レビューを置く工程型の検出層が補完する。

**6. 配線（予防層）**: (a) start-work の横断的ラッパー Pre へ条項 1 行 — 「計画作成（writing-plans またはインライン簡易 plan）へ進む直前、および実装系スキル（executing-plans / subagent-driven-development またはインライン TDD）へ delegate する直前に、`references/plan-deviation-defaults.md`（逸脱判断の既定の正本）を読んで適用する。適用は委譲中に発生する指摘受領時に及ぶ（delegate 済みスキルが内部で回すレビューの指摘受領時にも適用される例外規定。マージ方式確認の Pre 条項と同型。Post ラッパーの発火粒度は現行のまま変えない）」。宣言欄・報告義務などの実体規範は正本側にのみ書き、start-work 本文はポインタに徹する（条文複写の禁止）。(b) Phase 2 マッピング表の該当行（既存仕様からの計画作成・既存 plan の実装・コードレビュー対応〈確定済み計画の実行中である場合に限る旨の条件句つき〉）のセル内ポインタ。読み込みと宣言欄確認は**同一セッション内**の同一発火点（計画作成 / 実装着手）につき 1 回とし、マッピング表経由で当該発火点を実施済みなら Pre 側は省略する（二重発火の抑止。セッション再開時は正本と宣言欄を読み直す）。(c) `subagent-dispatch` の手順へポインタ 1 行を足す — 「実装・実装時レビューの委譲では `skills/start-work/references/plan-deviation-defaults.md` の注入項目を確認する」（注入の想起担保。採否基準は移設しない）。実装を委譲する委譲プロンプトへの注入文は「機械的な適応・昇格に至らない訂正は実態優先で適用し、型分類を添えて事後報告する。設計の変更・計画の射程外の既存欠陥に該当しうる候補、および型判定に迷う候補は、自ら採否を決めず候補の型分類を添えて委譲元へ報告する（A 群 1 の実態優先は前二者〈機械的な適応・昇格に至らない訂正〉に限って適用する。報告は DONE_WITH_CONCERNS 相当の状態で返してよい）」とし、優先関係を注入文自体に含める。

**7. 射程宣言**: 採用した是正案自体の妥当性検証は本既定の射程外とする（実装者検証と多層レビューの役割分担〈Issue-0112〉へ委ねる）。レビュー・検査既定の層別再設計は Issue-0114 / Issue-0103 の射程であり本サイクルでは扱わない。

## Consequences

- 実装時レビュー指摘のたびの判断が「基準の組み立て」から「基準への当てはめ」へ縮む。**削減されるのは 1 回あたりの審議コストであり、設計変更級の ADR 確定というユーザー介入自体は残る**（実測 4 回/サイクルのうち介入の重さが縮む）
- 採用範囲の膨張（「今回はこれも直す」の積み上がり）が、基準の計画確定時固定と変更時の承認・ADR 要件により止まる（抑止の実効性はサイクル末の覆し記録で評価する）
- 検出層の実効性は工程型に依存する。タスク別仕様適合レビューを置く工程型では判定対象の明文化として機能するが、前倒し型・インライン TDD では委譲元の自己検査で代替するため検出力が落ちる（自己検査は記録漏れのみを拾う）。この残余は受容し、格下げ既定・自己検査の実効性を評価対象に含める
- 採用基準の固定により仕様適合レビューの判定対象の点数増は抑えられる一方、逸脱記録の列挙は毎レビューの走査母数に加わる
- 計画の宣言欄・逸脱記録行・start-work / subagent-dispatch の配線・委譲プロンプト注入ぶんの読み込み・記録コストが毎サイクル加わる。型判定に迷いを表明した瞬間に「設計の変更」側へ倒れ、前倒し型では格下げ（タスク別独立レビューの新設）という高コスト操作が起動しうることも受容する
- 型分類・採用基準が実態と割れる場合（覆しの記録が積み上がる場合）は、Issue-0107（推奨規範の乖離）と同型の乖離記録が発生しうる。退役条件で受ける
- 委譲（第 1 段）で受け皿となった Issue-0107 / 0112 / 0113 / 0114 と、相互参照で更新した Issue-0103 の**対策**は本 ADR の射程外であり open のまま残す。隣接課題 2 件との関係: Issue-0073（計画の検証期待値の陳腐化）は「事実誤り・期待値の陳腐化の訂正」型の**採否側**を本 ADR が既定化するが、**検出側**（期待値の再測をどの時点の手順に置くか）は未対策のまま open。Issue-0063（実装中に確定した文言を計画へ反映するかの規約）について、Decision 5 は plan への実装中書き込みを逸脱記録行の 1 種類だけ規定するが、一般の同期規約の設計は射程外で open
- **配布**: 配布対象ソースの変更（references 正本の新設・start-work / subagent-dispatch の配線）のため、plugin version bump（0.1.14 → 0.1.15）と執行点 4 手順（生成器実行・両 -Check・生成物同コミット・配布物目視）を実施する
- **課題の帰結**: Issue-0110 は本 ADR の Accepted 昇格時に close する
- 新設の評価可能性（ADR-0102）: 期待検出量 = 発火機会は本既定を適用した逸脱記録行の件数。計数手段 = `docs/working/plans/` 配下の行頭 `逸脱記録:` 行の grep（インライン経路も最小計画ファイルを起こすため同一系統で数える）。対象期間 = 次回棚卸しまでの各サイクル。見込み = 設計変更級の判断局面 3〜5 件/サイクル（直近実測 4 回）、全帰結行はその 2〜3 倍（直近実測の帰結数は逸脱点 10＋不採用・起票分）。捕捉したい欠陥型 = 採用範囲の膨張・逸脱判断の審議の頻発。退役条件（向き・窓つき）= 型「設計の変更」「計画の射程外の既存欠陥」の当てはめ直近 10 件（計画ファイルの日付昇順・同一ファイル内は行出現順）のうち 3 件以上に「覆し:」が記録された場合、本既定の改良・退役を候補として提案する。覆しの観測経路はタスク完了報告での逸脱記録行の提示と ADR 確定時のユーザー修正で確保し、覆しの向き（覆し後の帰結）も行に残す。あわせて「不採用とした指摘が後続サイクルで issue / ADR として再浮上した件数」を退役判断の際の判断材料に添える（基準が厳しすぎる側の失敗の観測）。格下げの発火 / 不発は逸脱記録行の第 3 欄トークン、自己検査の実施はタスク完了報告の「逸脱突合:」行で計数する。覆しが現れない限り存置。判断はユーザー
