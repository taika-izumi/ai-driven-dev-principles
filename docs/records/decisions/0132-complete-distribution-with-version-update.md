# ADR-0132: 配布内容が整ったら版を更新し、公開後の修正は次の版で出す

- **Status**: Accepted
- **Date**: 2026-09-07

## Context

Issue-0129の対策設計。Issue-0126では版据え置きのまま終了し、追加依頼で更新した。今回も317e25bの配布内容変更後、0.1.21のまま両生成器のCheckが合格した。生成器は正本2定義の版一致と生成物の同期を検査するが、前回配布版からの更新は判定しない。

先行するADR-0090は、版据え置きでは利用側キャッシュが更新されなかった実測に基づき、配布時の正本2定義の版更新・既定patchを既に定めている。本件は版更新義務の新設ではなく、既存決定を実行手順へ接続し、更新時点と公開前後の修正の扱いを具体化する改定である。

ユーザーは早すぎる版更新を避けたい一方、手順の複雑化も懸念した。一般的なバージョン運用を確認したうえで、「実装・レビュー・検証後に版更新、公開前の追加修正は同じ版、公開後は次の版」という簡素化案を承認した。振り返り・引き継ぎの全完了を待つ案は採らない。

参考は一次資料の[SemVer 2.0.0](https://semver.org/)と[npmの版更新・公開手順](https://docs.npmjs.com/updating-your-published-package-version-number/)。SemVerは公開済み版の内容を変更しない規則を定めるが、マージや振り返りとの厳密な前後関係は定めていない。0.xの細かな増分運用は本プロジェクトの方針として定める。

## Considered Alternatives

1. **配布内容の準備完了時に更新する（採用）**: 必要な修正と検証を済ませた配布内容に版を付ける。既存の拡張完了手順へ組み込み、利用者への追加の完了承認や管理機構は設けない。AIは直前の公開版との比較を行う。公開後に微修正があれば新しい版を出す負担を受容する。
2. **振り返り・引き継ぎまで全部終わる最終段階へ遅らせる**: 同じ公開に修正をまとめやすいが、配布内容と無関係な記録作業まで版更新の条件に結び付く。追加依頼が来ないことも保証できず、今回の簡素化要求に合わない。
3. **生成器に履歴との版比較を追加する**: 自動検出は可能だが、比較元の指定・履歴なし環境への対応・追加テストの保守が必要。まず既存手順の拡張で対処し、手順未実行の自動検出までは求めない。
4. **個別依頼が来るまで更新しない**: 実装費用は最小だが、Checkが通った後の版据え置きを利用者が発見する負担が残り、Issue-0129を解消しない。

## Decision

版更新の運用は次の3点とする。

1. **配布する変更の実装・必要なレビュー・検証が済んだら版を上げる**。着手時や最初の編集では上げず、振り返り・引き継ぎの全完了まで待つことも必須にしない。作業中の生成・検証は旧版のまま行ってよい。記録文書だけ、templateだけ、出所番号だけでプラグイン配布内容が変わらない変更では版を上げない。
2. **公開前の追加修正は、同じ予定版へ含めて再検証する**。版更新をやり直したり、公開を遅らせるためだけに待機・確認を増やしたりしない。
3. **公開後の追加修正は、新しい版で公開する**。公開済み版の内容を差し替えない。通常の互換性を保つ微修正はパッチ（末尾）を1つ上げ、機能追加や互換性に影響する変更は内容に応じて版を選ぶ。

ここで公開とは、利用者が取得する配布先へその版を反映すること。READMEのGitHub経由では取得元リポジトリの配布対象ブランチへ版付き生成物が反映された時点（通常の本リポジトリではリモートmasterへのpushまたはPRマージ）とし、ローカルmasterへのマージだけでは公開済みとしない。ローカルパス経由では、利用者に配布用として提供している取得元へ版付き生成物を配置・更新した時点とする。開発用ブランチや検証用コピーへの変更だけでは公開済みとしない。版更新時は利用している配布経路の直前公開版を確認し、公開前後が不明で選ぶ版が変わる場合に限り確認する。

実装先はCONTRIBUTING.mdとextend-guidelines手順6。上記規則と具体的な生成手順はCONTRIBUTING.mdを正本とし、手順6から配布内容の準備完了時に実施する。start-workの完了工程や外部superpowersへ版規則を複写せず、新しい工程・スクリプト・状態台帳を作らない。

`.claude-plugin/plugin.json`と`.claude-plugin/marketplace.json`の版を揃え、既存生成器で再生成する。両Checkと配布本文の確認を行い、正本と生成物を同じコミットへ含める。正本間の版一致と生成物の同期はbuild-distの既存検査へ委ね、別の手動一致確認を課さない。AIが追加で確認するのは予定版が直前の公開版より進んでいることだけであり、途中コミットでのCheck合格を配布更新の完了とは扱わない。

今回の直前版は0.1.21で、Issue-0128・0129を0.1.22にまとめる。公開前に追加微修正があれば0.1.22へ含め、公開後の微修正なら0.1.23として出せる。pushは実行ごとに宛先・対象・変更内容を示して承認を得る。Gitタグ・GitHub Release・利用側キャッシュ更新は別途要求時に扱う。

### ADR-0090との関係

- 保持: Decisionの「配布時に正本2定義の版を揃えて更新する」「既定patch」「生成物を直接編集しない」と、反映手順1の生成・検証・commit・push。
- 具体化: 「同じ区切り」の更新時点を上記3原則で定め、公開前後の追加修正を区別する。
- 部分変更: 反映手順2・3の利用側更新・供給本文確認は、利用環境への反映まで依頼された場合に行う手順として保持する。すべての配布更新の完了条件には含めず、配布先への公開と利用環境への導入確認を区別する。
- 本ADRの確定にあたりADR-0090のConsequencesへ部分修正の参照を追記した。ADR-0090はAcceptedのまま維持し、索引の既存行も状態を変えず関係を示した。旧Decision本文は書き換えていない。

## Consequences

- 既存の完了手順で版更新を実施でき、利用者が更新漏れを発見して依頼し直す負担を減らす。手順自体の未実行は自動検出できない。
- 全終了作業との厳密な順序や、今後追加修正が来ないことの確認は不要になる。公開後に修正が必要なら再生成・検証・公開をもう一度行う費用を受容する。
- 評価機会は次の3配布内容変更サイクルで各1回を見込む。既存の配布定義・git履歴・公開記録から確認できる範囲で版更新漏れを数え、公開状態が復元できなければ不明とする。新しい必須記録欄や定期監視は設けない。

## 検証するケース

| 状況 | 期待結果 |
|---|---|
| 配布内容を改修中 | 旧版で生成・検証し、版更新を急がない |
| 実装・レビュー・検証済み、振り返りや引き継ぎは未完了 | 0.1.22へ更新・再生成・検証できる |
| 版更新後、配布先へ未公開の追加微修正 | 同じ0.1.22で再生成・検証する |
| 0.1.22公開後の互換性を保つ微修正 | 0.1.23で再生成・検証して公開する |
| 開発用ブランチにpush済み、利用者の配布先には未反映 | pushだけで公開済みと判定しない |
| ローカルmasterへ統合済み・リモート配布先には未反映／リモート配布対象ブランチへPRマージ済み | 前者は未公開、後者は公開済みとして版を選ぶ |
| ローカルパスの利用者向け配布元へ版付き生成物を反映 | 公開済みとして、以後の配布内容修正には次の版を使う |
| 記録文書・templateだけ、またはプラグイン配布内容が変わらない変更 | 版更新不要。対象側の生成・検証は従来どおり |
| 正本2定義の不一致・生成物の更新漏れ | 既存生成器・Checkで失敗。修正して再検証する |
| 版更新前後ともCheckは合格する | 更新前より版が進んだことを別途確認してから配布更新完了とする |
| 公開準備済み・push未承認 | 送信内容を示し、そのpushの承認後に実行する |

## 過剰適合点検（ADR-0079）

| 観点 | 判定 | 根拠 |
|---|---|---|
| 出所の偏り | 要是正→適用範囲を限定 | 出所は1プロジェクト、ADR-0090のキャッシュ更新不成立・Issue-0126の終了漏れ・今回のCheck通過の3場面。過去のモデル世代は記録から未確定。配布元の実在する生成工程と今回のユーザー合意に限定 |
| システム種別依存性 | 問題なし | 配布元固有の版更新手順。引き写し箇所: extend-guidelinesの配布元限定、CONTRIBUTINGの対象別生成・両Check・生成物同時コミット・目視を維持 |
| AIモデル/ツール依存性 | 問題なし | 特定AIの癖を条件にしない。引き写し箇所: superpowersの検証・統合とユーザーの操作承認は維持。ADR-0090の版更新義務は保持し、利用側更新の適用範囲は上記で明示的に部分変更。SemVerの公開版不変を参照するが、マージ順序や0.xの増分規則を標準の義務とは主張しない |
| 規範の廃止条件 | 定義済み | 配布内容と版を一体で更新・検証する仕組みが導入され、版据え置きを本手順なしで阻止できたら重複する手動判定を簡素化・廃止する。阻止できない間は存置側 |
