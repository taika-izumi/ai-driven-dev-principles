# ADR-0140: ガイドライン整備は重要な先行修正から開発実証へ進み、実証後に汎用化する

- **Status**: Proposed
- **Date**: 2026-09-08

## Context

ユーザーはOpen Issueの優先度についての分析を踏まえ、開発ガイドライン整備のロードマップ作成を依頼した。2026-09-08のインデックスではOpenは68件。今回の依頼は文書化までで、個別Issueの実装やロードマップの採用確定は含まない。

Issue-0136には検査委譲先によるリポジトリ外の破損と既存記録の削除、Issue-0138には完了基準を妨げる既存欠陥の扱い、Issue-0124には費用比較の規範が配布後も適用されない再発が記録されている。人の介入を減らす実証では優先して扱う理由がある。

同日の追加要件として、整備期間中も他プロジェクトは現行ガイドラインで開発を継続するため、手順として使える時点の配布と、実運用データ収集が必要になった時点の配布を考慮するようユーザーが提示した。初版は両者の途中配布の条件が不十分だったため、整備段階の具体化として本ドラフトとロードマップへ反映する。

さらにユーザーは、長期セッションによる文脈と費用の増大、複数担当が意図に反する抜け穴を利用して見かけの達成を作る懸念について、先行運用者の実態と対処の必要性を調査してから運用方法を決めるよう依頼した。調査を今後のロードマップへ組み込み、以後の整備の起点として引き継ぐ指示を受けた。現象の実在や対策の採用をこの依頼から推定しない。

## Considered Alternatives

| 案 | 利益 | 費用・制限 |
|---|---|---|
| 先行修正を絞り、実証で残りを判断する（推奨案） | 実害と自律進行の判断漏れに対処し、未経験の運用から材料を得られる | 個別修正と実証の境界管理が必要 |
| Open Issueを広く解決してから実証する | 対話型手順の整備が進む | 実証前に情報到達・レビュー制度等の広い再設計を抱え、移行時期が定まらない |
| 先行修正なしで直ちに自律運用へ進む | 実証を早く始められる | 既知の破損や判断漏れを人の都度対応に戻す負担がある |

## Decision

2026-09-10、ユーザーのロードマップ更新指示に基づき、先行順序はADR-0163へ更新した。直近はIssue-0140、0124と既存委任の適用確認。0136は中断を維持し再開後に能力確認、0138は実証前に必要な対処を具体化し、各Issueの合意範囲の実装・検証・配布・実証環境への反映を確認して、小さな開発ループへ進む構成とする。低リスクの文書調査や計画作成は先行修正と並行できる。

Issue-0042の検出力とIssue-0053の素材保存は、実証対象の終了条件と中断記録に取り込む。両Issueの全面解決を前提にせず、未解決の残余を保つ。その他のIssueは、実証の安全性・完了判定・記録保存を妨げる場合に限って先行範囲の追加を判断する。編集先が同じという理由だけで束ねない。

対話／自律ループを進行方法、単独／複数担当を役割分担として扱い、AI組織を第3モードにはしないという仮説で試す。配布する2プロファイル構成の確定はADR-0043どおり実証後とする。

配布はタスク完了単位で自動判断せず、依存する変更を含めて開発手順が成立する単位で判断する。通常利用向けの修正は各段階で配布でき、全先行課題の完了を待つ必要はない。実運用データが必要な場合は、最低限の動作・停止・記録・復帰を確認し、収集目的と利用条件を合意して限定試用する。試用版を通常の更新経路で意図せず配らない。汎用化前の試用材料と通常配布を区別し、実証後の抽出開始の判断は維持する。

段階2では、具体的な組織運用方法の決定より先に、文脈管理と見かけの達成に関する先行事例を調査する。根拠・効果・負担・限界を比較し、対処不要や限定的な対処も候補に含める。役割と同じセッションを継続する期間は分けて設計し、調査結果から運用仮説と実証方法を選ぶ。調査内容と完了条件はロードマップ4.1節を参照する。

## Consequences

- **部分修正（ADR-0166）**: 2026-09-10、Issue-0140・0124の完了後の次手をモデル裁量と既存手順の比較準備へ変更した。段階2で比較し、広い先行事例調査と独自の役割設計は必要性を確認して段階3で行う。通常利用の保全・操作承認・限定試用・実証後の汎用化は維持する。最新の順序と初回2題材・1モデル4実行の比較案はロードマップ2節・4.0節を参照する。本ADRはProposedのままとする。

段階ごとの成果物・移行条件・ユーザーの関与・後続Issueの扱いは[ロードマップ](../../current/development-roadmap.md)に集約する。ADR-0139は実行基盤の選び方を担う。いずれの文書も承認前に現行規範を上書きしない。

最初の開発実証で、範囲の明確な不具合修正1件と、ファイル間の連携を含む小さな機能追加1件を候補にし、開始前に比較対象・品質条件・実行上限を合意する。目的は統計的な優劣の確定ではなく、独立検査・停止・再開・記録の欠落を見つけること。実行件数と人の介入は実証記録から確認する。

既存対話手順に比べて必要な品質を満たせない場合、または負担だけが増えて改善経路が見えない場合は自律範囲を縮小する。実証を阻害しない新規課題が増えたことだけでは、先行対応を延長しない。

配布目的の区別には、版・設定の特定と試用参加先の管理が必要になる。既存の計画と公開記録へ添え、専用の常設台帳は先に作らない。最初の試用配布で、通常利用へ混入しないことと、必要な記録が収集できることを確認する。通常更新に試用変更が混ざる、復帰できない、または判断に必要な記録が得られない場合は配布拡大を止め、経路や収集方法を見直す。

## 過剰適合点検（ADR-0079）

| 観点 | 判定 | 根拠 |
|---|---|---|
| 出所の偏り | 要是正→段階案に限定 | 優先3課題は2プロジェクトの記録に由来する。今回読んだ課題本文では0136・0138の発生モデルが確定できず、0124の直近再発はclaude-opus-5。今回の再現実験は0件。恒久的な順位にはしない |
| システム種別依存性 | 要是正→開発実証で確認 | 戦略探索と一般ソフトウェア改修を区別。通常利用の継続はユーザーの明示要件。引き写し箇所: ADR-0043の実証先行・抽出開始の判断を維持し、汎用化前は実証材料の限定試用とする |
| AIモデル/ツール依存性 | 要是正→配布経路を実測 | 優先理由は破損・目的不達・費用膨張。試用の分離・版固定は名前だけで保証せず段階2で確認する。引き写し箇所: ADR-0133の委任範囲と操作承認の区別を維持 |
| 規範の廃止条件 | 定義済み | 実証で品質未達または負担増だけが確認された構成は縮小・撤回側へ見直す。先行修正で別の重大な阻害が見つかった場合は順序の変更をユーザーへ提案する |
