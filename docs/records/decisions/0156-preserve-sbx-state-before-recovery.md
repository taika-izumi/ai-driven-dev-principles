# ADR-0156: sbxの旧状態領域を退避して起動復旧を試す

- **Status**: Proposed
- **Date**: 2026-09-09

## Context

sbxの内部接続障害を調査し、一度の再起動で残留ソケットの削除失敗が判明した。新規ソケットの対照試験は成功した。ユーザーは削除だけで解決するかを確認し、起動障害と最初の接続障害を区別した説明を受けた後、「OKです。先ほどの提案は1で進めましょう」と回答した。承認対象は`docs/records/experiments/2026-09-09-sbx-smoke.md`末尾の退避案。

## Considered Alternatives

1. 旧状態領域を別名で残して起動を試す。旧データを保全し、残留ソケットに起因する起動障害を切り分けられる。
2. 状態を変更せず復旧を保留する。新たな変更はないが、試験を再開できない。

## Decision

ユーザーの個別承認に基づき案1を実施する。停止を確認し、`C:/Users/d12an/AppData/Local/DockerSandboxes/sandboxes/state/sandboxd`を同じ親の`sandboxd-preserved-20260909-02`へ移動する。退避先が存在したら上書きせず停止する。新しい状態領域で起動後、認証・VM一覧・deny-allを確認し、不一致なら固定試験へ進まない。

その後、通常ターミナルのソケット対照だけが成功した根拠に基づき、03への退避と通常ターミナルでのsbx起動比較を提示。ユーザーは「1で。実行しました」と回答し、当該スクリプトの起動結果を確認した。追加の個別承認と操作の記録はsbx-smoke実施記録20:21節。これを今後の無制限な退避・起動反復の許可とは扱わない。

## Consequences

- 旧データは削除しない。config/data/cache、Docker Desktop、他worktreeを操作しない。
- SSH鍵等の再生成がありうる。元へ戻す際も新旧状態の保全が必要で、自動で戻さない。
- 自己接続障害の解消を保証しない。同じ障害が再発したら反復せず結果を記録する。
- reset、削除、版入替え、保護緩和、モデル起動を承認へ含めない。
