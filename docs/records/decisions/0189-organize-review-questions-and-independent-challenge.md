# ADR-0189: レビューを3つの確認領域と独立した反証に整理し、品質項目の担当を明示する

- **Status**: Accepted
- **Date**: 2026-09-12

## Context

Issue-0143に対して、現行4観点、一般的な品質項目、過去ADRの失敗事例と採用理由を照合した。ユーザーは、敵対的レビューを独立させる価値、要求・根拠・成立性の各担当を分ける4体案、全体目的との整合の保持を提起し、最後に「ここまで出た観点や問いを改めて見直して、重複などがなければこれで確定」と依頼した。

初期確定時の判断の分担は、上記依頼に基づく観点・問いの最終点検、重複整理、問題が解消された内容の設計確定に限る。スキル実装・追加モデル実行・外部送信・公開への包括許可とはしない。承認基準は同日までの本会話と、以下の比較記録の内容を本ADRへ統合したものとする。

- `docs/records/reviews/2026-09-12-four-review-perspectives-coverage.md`
- `docs/records/reviews/2026-09-12-reusable-review-insights-from-adrs.md`
- `docs/records/reviews/2026-09-12-review-scope-reassessment.md`

重複の中心は、要求の不足と対策の欠落、検証の期待値の根拠と検証の動作、設計案の妥当性と実装の成立である。同じ品質項目でも比較対象が違うため分担できるが、同一の欠陥を別名で報告・採用し続ける必要はない。敵対的は品質項目と同列の分類ではなく、独立した立場から各領域の失敗条件を探す役割である。

2026-09-12、独立フルレビュー1回・差分再確認1回の結果と未適用補足案の提示後、ユーザーは「必要であれば変更していただいて構いません」と許可した。この許可に基づき、主担当が原文と採否案を照合して補足を反映した。4領域・問いの被覆・独立性・毎回4体を必須にしない方針は維持し、旧評価を新設計の実装待ちへ遅らせない。新しい独立レビュー実行・公開はこの変更許可から自動起動しない。

## Considered Alternatives

1. 3つの確認領域と独立した反証に整理し、品質項目の担当・必要な証拠を明示する。過去の有用な問いを保持しつつ、重点と境界を説明できる。委譲時の分担と共通資料の読解・集約負担はある。
2. 現行の4観点名を維持し、定義と適用例だけを追加する。変更範囲は小さいが、実体との一致と利用・運用の成立、事実の実在と推論・設計判断の妥当性の区別が伝わりにくい。現行にも重なりの説明があるため、単なる追記では改善を保証できない。
3. 品質項目ごとに専任観点・担当を増やす。専門化は可能だが、読解・重複確認・集約・将来の変更負担が増える。すべての題材で固定増員する根拠は無い。
4. 現行のままリスクを受容する。最も安いが、定義の弱化、初見利用不能、根拠と主張の不一致等の既存記録に対処しない。

案1を採用する。効果の実証は今後の検証と区別し、今回の採用だけで全欠陥の捕捉や4体の費用対効果を保証しない。

## Decision

### 1. 確認領域と担当の重点

| 領域・役割 | 中心の問い | 主に見るもの・境界 |
|---|---|---|
| **目的・要求の妥当性** | 成果物と今回の範囲は、プロジェクト全体の目的・方針に沿い、今回の要求を適切に満たしているか | 目的、利用者、要求、成功指標、必要な品質条件、未記載の欠落、承認済みの限定理由。要求への一致と要求自体の十分性を確認する |
| **根拠・設計判断の妥当性** | 前提と推論は結論を支持し、選んだ仕組み・構造は要求に対して適切か | 原文・実体・測定、引用の条件と意味、必要性、重複・保護の欠落、過剰一般化、代替案・構造・将来の変更負担。最終採否は既存の集約手順で判断する |
| **動作・検証・運用の成立性** | 記述した仕組みは関係する実体・契約の下で動き、検証でき、利用・運用できるか | 接続、順序、数値、データ、テストの有効性、初見の利用手順、運用・観測、移行・復旧、複数機構の組合せ。実行していない動作を成功認定しない |
| **独立した反例・失敗経路の探索** | 他の確認とは独立に、目的・要求・根拠・設計・運用を破る条件や見落としはないか | 未記載の前提、境界・並行・中断・再開・迂回・部分失敗等。成立条件と害を根拠で示し、反論数を成果にしない |

プロジェクト全体の目的・方針は全担当に共有する。直近の依頼・Issue・spec・作成者の要約だけで代替しない。全体目的に必要な対象の取りこぼし、方針との矛盾、目的を超える負担を見る一方、承認済みの段階的な限定は理由とつながりから評価し、自動的に範囲を広げない（ADR-0185）。

### 2. 重複を解く境界と意図して残す重なり

| 重なる問い | 分担 |
|---|---|
| 要求不足／保護の欠落 | 要求担当は「何を満たす必要があるか」、根拠担当は「その必要をどの対策が覆い、何が不足するか」を確認 |
| 前提の誤り／実装不一致 | 根拠担当は対策理由や結論への影響、成立性担当は実際の契約・経路・動作への影響を確認 |
| 設計品質／動作・保守の成立 | 根拠担当は構造の選択と代替案、成立性担当はその構造の下での変更・操作・運用の実際の経路を確認 |
| 期待値の正しさ／テストの有効性 | 根拠担当は期待値・評価設計の根拠、成立性担当は正常例と想定欠陥を区別できるかを確認 |
| 一般の確認／敵対的確認 | 同じ対象を異なる文脈・姿勢から確認する意図的な重なり。同一の欠陥は集約時に1件へ統合し、独立に検出した経路と根拠は保持 |

観点は排他的な分類ではない。分類先を唯一一致させるために指摘を落とさない。反証担当へ「他の担当が扱わないすべて」を委ねず、確認が必要な品質項目の主担当を定める。

### 3. 品質項目の割当て

以下は対象の性質に応じて既存の委譲文へ含める確認項目であり、すべてを全案件へ課す固定の検査一覧ではない。関係する項目の未確認を「問題なし」へ含めない。表の「照合」「分担」は各担当が共通の原文を自分の重点から独立に確認することを指し、結果の照合は主担当が既存の集約手順で行う。初回判断前の担当同士の協議を要求するものではない。

| 品質項目 | 主な確認責任 |
|---|---|
| 目的・要求・範囲、利用者、成功条件、適用される外部制約 | 要求担当。要求自体に不足がないかも確認 |
| 前提・推論・引用・測定条件、設計構造、過剰設計・一般化、対策の必要性と費用 | 根拠担当。機会不足・記録不足を不要としない |
| 正常動作、API・データ・単位・時刻、変更前後の互換性、仕様と実体の同期 | 成立性担当。要求担当と契約変更を照合 |
| 信頼性・移行・復旧、運用・観測、設定・依存の更新 | 成立性担当。構造の維持負担は根拠担当と分担 |
| 利用可能性・アクセシビリティ・文書 | 要求担当が利用者と必要条件、成立性担当が具体的な操作・読解経路 |
| 検証の有効性・期待値・再現可能性 | 根拠担当が評価の妥当性、成立性担当が検出力と実行可能性 |
| 性能・規模・資源・費用 | 要求担当が条件と許容値、根拠担当が見積り・測定、成立性担当が達成と限界 |
| セキュリティ・プライバシー・安全 | 要求担当が保護対象、根拠担当が脅威の前提、成立性担当が制御、反証担当が迂回・失敗条件 |

大規模な設計変更や、専門性の高いセキュリティ・統計評価等では、担当量・必要な知識・使える検査手段に応じて担当の追加・組替えを検討する。専門名を付けたエージェントの存在だけで専門検査済みとはしない。書式等を既存機械検査が扱える場合、その結果を利用し、人手相当の同じ検査を全員へ重ねない。

### 4. 過去ADRから保持する問いと制約

- 未記載の欠落、文書間・工程間の相互作用、検証の検出力を、今回も検査対象にする（ADR-0067・0080・0092）。既存のサイクル全体整合検査を全担当へ複写しない。
- 引用元の条件保存と、原文・実測から結論へ至る意味の向きを確認する（ADR-0099）。当時限りの新工程禁止まで一般化しない（ADR-0101）。
- 必要・不要・重複・欠落・前提誤りの区別を保持する（ADR-0117）。不要な対策の削減だけでなく、必要な保護の欠落も見る。「前提誤り」は仕組みの必要性はあるが説明の事実が誤る場合であり、必要性まで証明されていなければ断定しない。
- 条件・分岐・ゲート・記録・接続・データ経路・禁止事項も仕組みに含む。特に疑う6類型は既存適用例へ到達できるようにする。統計設計等は事実の実在だけでは決まらず、必要な専門的検査を別に行う（ADR-0117）。
- 規範の過剰一般化、効果の評価可能性と簡素化・廃止の条件、導入・運用・保守・副作用の比較を保持する（ADR-0079・0101・0102・0125・0165）。最終の対策採否は既存の集約に残し、全員に同じ費用審査を行わせない。
- 文脈のない読み手が所在・条件・順序を理解して使えるかを、文書・手順の成立性として見る。規範・手順の利用可能性が確認対象なら、レビュー担当が文書に従って代表作業を試し、詰まる箇所を確認する。机上の経路確認と許可された実行を区別し、実行できない部分は未確認とする。Issue-0075の初見利用の確認はこの成立性領域で扱い、専任の新観点は増設しない。定義を全箇所へ複写することで解決しない（ADR-0091）。

### 5. 共通の入力・証拠・報告と人数

共通入力は全体目的・方針の原文の所在、今回の対象版・変更範囲・要求・限定理由、根拠への入口、担当と必要な品質項目、許可された操作・未確認範囲である。担当がアクセス可能な追加資料は自力で探せるようにし、全資料の一律読破は要求しない。アクセス不能・原文未特定・矛盾は明示する。資料の探索可能性と外部への送信許可は別に扱う（ADR-0185・0186・0188）。

原文対比は文書上の不一致の証拠、実行結果はその条件での動作の証拠として区別する。「未確認」「仮定内の結論」「実環境の事実」を混同しない。不在の結論には探索先と確認範囲を付す。各指摘は対象箇所・問題・根拠・影響を既存の報告へ残す。動作や失敗経路を根拠とする指摘には成立条件を添え、原文対比で示せる文書不一致には対比箇所を示す。将来作成することが計画に明記された部品は、現在ないだけで不整合・前提誤りにせず、既存扱いの誤りがないか、作成・接続・検証の担当と順序が揃うかを確認する。

体制は、3領域を別担当へ割り当てた上で独立した反証担当を置く4体分担を基本の候補とする。4体を毎回必須とする決定ではなく、実行時は対象・必要な専門性・未確認範囲・費用から人数と分担を選ぶ。独立した反証を実施する場合、その担当に他担当の初回所見を見せずに初回判断を回収する。同じエージェントに兼務させた場合は独立した反証とは称さない。人数を減らしても3領域の問いと反例・失敗経路の探索は保持し、誰が兼務するかを委譲文に示す。必要な確認範囲を削る理由に人数や費用を用いない。人数が未決なら、既存規定の「観点分離」を引き継ぎ、領域を分離する側を推奨する。3領域を別担当にし独立した反証担当を置く4体案は、その具体候補であり毎回の固定人数ではない。兼務時の既存記録は、担当数と兼務範囲が分かる形で引き継ぐ。

### 6. 設計確定と適用状態

このADRで確定するのは観点・問い・分担の設計である。実装はpre-finalization-reviewの定義・入力・実施・方式・適用例、subagent-dispatchの参照、対応する現行仕様と配布物を整合させる必要がある。実装計画では観点名に依存する参照を走査し、start-workのplan-deviation-defaults.mdにある実証水準への参照、README等の案内、関連ADRの注記も用途に応じて整合させる。別工程の一般的な「仕様適合」や他の4観点を一括置換しない。現在の配布済みスキルは変更しておらず、Issue-0143は未完了とする。旧ADR-0186の4観点定義とADR-0117の観点配置はこの設計で見直すが、既存の要求・保護・実証・採否の規範を無条件に解除しない。置き換えるのは観点の名称・配置・担当境界で、ADR-0186の共通入力・原文・未確認・報告の契約とADR-0117の5判定等は存続するため、旧ADR全体の置換ではなく部分修正として扱う。ADR-0185の全体目的確認は維持し、観点構成への参照には再編先の注記を残す。

レビューの確認契約という主要機能1つの設計で、役割4つは独立したソフトウェア部品の新設ではないため、feature-block-designの分割しきい値には該当しない。設計本文は本ADRに集約し、現行仕様の差分だけを別の現行仕様書として作らない。

## Consequences

重点と境界を明文化し、全体目的・既存の検査類型を保持できる。品質項目を選び、担当・証拠を示す負担は増えるが、別の常設台帳・採点器・必須の多段工程を新設しない。担当分離で共通読解と集約の費用が増え得るため、4体の便益は未実証として扱う。

評価は実装後の最初の3件の対象レビューで、既存報告から復元できる妥当な独自指摘・重複・誤指摘・未確認・読解と集約の負担を確認する。発火機会はその3件で、少なくとも1件の役割境界・欠落検出を評価できる機会を見込む。欠陥数を約束せず、機会・記録が足りなければ未評価とする。既存の確認と全件重複し、判断や検出を改善せず負担だけが確認された項目は簡素化・元の表現へ戻す候補にする。取りこぼしが続く場合は担当や問いの修正を検討する。評価専用の必須保存行や自動監視は追加しない。本設計の実装前は、ADR-0186の評価を元の起点・条件と既存の実施状況に従って扱い、本設計の実装待ちを理由に延期しない。実装後の定義・混同・参照負担の評価は本設計の3件で扱い、同じ対象・版の確認を別に重ねない。既存の観測とその時点の版は保全する。ADR-0185の全体目的との整合という評価目的は維持し、関係する既存報告を共用する。先行評価の実施状況を確認せず「機会不足」と決めつけない。問いの妥当性の確認と担当分離の効果は区別し、分離した実施機会がなければ後者は未評価とする。実装前の初回レビュー等は設計・重複・負担を考える参考材料として利用するが、実装後の3件には数えず、新定義を実際に運用した評価と混同しない。

| 観点 | 判定 | 根拠 |
