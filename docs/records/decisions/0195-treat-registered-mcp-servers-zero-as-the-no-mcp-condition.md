# ADR-0195: 「MCP登録なし」は登録済みMCPサーバー0件で判定し、常設ゲートウェイは製品挙動として記録する

- **Status**: Proposed
- **Date**: 2026-09-15

## Context

仕様 `docs/current/specs/2026-09-09-isolated-verification/02-isolated-execution.md`「実行設定と起動前確認」は、VM作成前に「workspaceなし、no-share-skills、MCP登録なし、ホスト原本/home/control/Dockerへの接続なし」を確認することを求める。MCPはVM内のエージェントが外部サービスをツールとして呼ぶための接続方式で、ここでは子に余計な接続経路を与えないための条件である。

2026-09-14の実測（`.tmp/sbx-capability-20260914/32-inspect.json`、daemon.log）では、承認済みの固定引数（workspaceなし・共有skillsなし・deny-network '*'・固定digest）で作ったVMにも、製品が常設するMCPゲートウェイ（`mcp_gateway: true`）と、そのゲートウェイ用のsecret（名前 `mcpgateway`、出所 uploaded。プロキシが管理するセンチネルトークンで、利用者の資格情報ではないと理解している）が付いていた。ゲートウェイに登録されたMCPサーバーは0件（`mcp: built catalog snapshot ... servers: 0`）で、通信はdeny-allで拒否されている。

実装計画の初回確定前レビュー（2026-09-14、claude-opus-5、M3-1）は、計画がこの判定基準を持たず、厳格に読めば常にblocked、緩く読めば保護緩和の無記録受容になると指摘した。ユーザーは2026-09-15に、センチネルトークンとMCPゲートウェイが外部通信経路の一種であることの説明を受けたうえで、選択肢1を選んだ（ユーザーの個別承認）。

## Considered Alternatives

1. 「登録済みMCPサーバー0件」を条件とし、ゲートウェイの常設とセンチネルトークンは製品挙動として記録に残す。判定は `sbx mcp ls --json`（または同等の照会）で登録0件、activationRecordに `mcp_gateway` と `mcpgateway` secret の存在を明記する。利用者の資格情報の露出判定（credentialExposure）はこれとは別に行う。
2. 仕様どおり厳格に読み、ゲートウェイの常設が確認された時点でblockedにする。現状の製品では道具が常に起動できず、製品側で無効化する方法の調査（未確認）が先に必要になる。
3. 判断を保留し、ゲートウェイを外す設定や引数が製品にあるかを先に調べる（読み取りのみ）。

## Decision

案1を採用する。仕様02の「MCP登録なし」は「当該デーモンに登録済みのMCPサーバーが0件」として判定する。起動前確認（計画のタスク3の activationRecord.checks.mcpServers）で毎回照会し、1件でも登録があればblockedにする。ゲートウェイの常設とセンチネルトークンの存在は保護の緩和ではなく製品挙動として記録し、結果の表示から省略しない。

## Consequences

- 残余リスク: 将来、利用者が別の目的で同じデーモンにMCPサーバーを登録すると、この道具のVMからも見えうる。毎回の登録0件検査で、その状態では道具が起動しないことを保証する。
- センチネルトークンの差し替え動作そのものは未実測であり、本ADRは「VMに利用者の本物の資格情報が置かれていない」ことを断定しない。credentialExposure の判定は inspect の secrets 欄とVM内の環境変数を別に照合する（計画のタスク3）。
- ゲートウェイを外す製品設定が後日見つかった場合は、その適用を別承認とし、本ADRの判定基準は「登録0件」のまま維持する（外せればより強い状態になるだけで、条件は変わらない）。
- 本ADRは仕様02の条件の解釈であり、条件の文言を変更しない。ADR-0157/0158/0160〜0162/0192〜0194 を置換しない。Proposedで個別承認を保存し、サイクル全体整合検査を伴う次の確定チェックポイントで昇格する。
