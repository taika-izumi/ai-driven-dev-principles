# ADR-0202: worktreeは禁止も全面標準化もせず、作成の合意はsuperpowersに任せ、開始時に読む側で検出する

- **Status**: Proposed
- **Date**: 2026-09-18

## Context

本ガイドラインは当初、1つの作業フォルダで作業する前提で設計されており、worktreeへの言及は `skills/subagent-dispatch/SKILL.md` の並列書き込みの隔離手段1行のみである。ガイドライン改修を任せたモデル（GPT Astra）が利用者に諮らずworktreeを作成して作業し、以後このリポジトリでは案件ごとに `.worktrees/<名前>` とブランチ別handoffを使う運用が定着した（2026-09-18時点で統合済みのworktreeが証跡保全のため5つ残る）。

この運用で次の失敗が観測された。

- 2026-09-15: masterでstart-workし、masterのhandoffだけを根拠に「進行中タスクなし」と要約した。直近セッションは `.worktrees/isolated-verification` 側で行われ、実装計画の確定まで済んでいた（worklog `MakeAiInstructions-2026-09-15-03`、利用者の指摘で判明）。利用者は「メモリに残すのではなく、worktree使用を踏まえた作業フローを定義したほうがよい」と示唆した。
- 専用Issueを持たない隔離検証worktreeの再開経路として、Issue-0136を開いたまま使っていた（2026-09-18クローズ）。

worktreeはモデルの判断だけでなくツールの既定動作からも生じる（Codexアプリは `~/.codex/` 配下へ自動作成する。superpowersの `using-git-worktrees` は実装計画の実行前の使用を説明文に持つ。Claude Codeにもworktree機能がある）。

## Considered Alternatives

1. **原則禁止し、並列隔離など明示した例外だけ認める**: 作業フォルダが1つに保たれ既存の引き継ぎがそのまま機能する。ただし発生源がモデル判断とツール既定動作の双方にあり禁止文では止めきれず、破られた時に引き継ぎが壊れる構造が残る。特定モデルの逸脱を前提にした規範になり、`subagent-dispatch` の隔離指定とも衝突する。
2. **作成から片付けまでの全体フローを定義する**: worktreeの利点を最大限使える。ただし根拠は1プロジェクト・実害1回で、ライフサイクル全体の規範は読込・保守の費用が大きく、目的の正本（`docs/overview/project-purpose.md`）の「規範や工程の追加だけを改善としない」に照らして見合わない。
3. **作成の合意と開始時の検出の2点に絞る（採用）**: 作成の合意で無断の作業場所の分散を減らし、どの経路で作られたworktreeでも開始時に新しいhandoffを見落とさないようにする。作成の合意をガイドラインの規範として書く案は、`superpowers:using-git-worktrees` が作成前の同意確認を既に持つため二重になり不採用とした。
4. **worktree側の引き継ぎ処理でmaster側のhandoffも更新する**: masterのhandoffを読むだけで状況が分かる。ただし本体フォルダのmaster.mdを直接書くと、本体フォルダで並行する作業へ未コミット変更が混入する。ブランチ内の写しを書くと取り込み時に衝突する（2026-09-18時点で各worktreeに3,047〜37,428バイトの異なる `master.md` が残る）。worktreeの用途である並行作業ほど衝突が増えるため不採用とした。
5. **リスク受容（何もしない）、または既存工程の文言拡張で足りるか**: リスク受容では、worktreeを使う限り見落としが再発しうる（観測1回: 2026-09-15、利用者の指摘まで誤った要約のまま次の作業候補を提示した）。既存工程の文言拡張としては、read操作に検出の1段を加え、start-work Phase 0の分岐へ1句を足す形が最小であり、これを案3の実現方法とした（新しいスキル・工程は設けない）。一度作れば継続して維持するもので、維持の対象はread操作の数行とPhase 0の1句である。

## Decision

案3を採用する（利用者の個別承認、2026-09-18「1で」）。

1. worktree作成時の合意は、ガイドラインに新しい規範を足さず、`superpowers:using-git-worktrees` の同意確認（作成前に利用者の同意を求め、既に表明された方針があればそれに従う）に任せる（利用者の個別承認、2026-09-18）。同じ確認を二重に定めないため。
2. 作業の開始・再開時に、worktreeが複数あれば他のworktreeのhandoffを読む側で検出し、要約に明記して再開先を選択肢に含める。worktree側のセッションからmaster側のhandoffへは書き込まない（本体フォルダの未コミット変更の混入と、各ブランチが持つ `master.md` の写しの取り込み時の衝突を避けるため。利用者の個別承認、2026-09-18）。masterのセッション自身がworktreeを作成・取り込むときに、masterのhandoffへ1行記載することは任意の補助として妨げない。

3. 検出は `skills/session-handoff/references/op-read.md`（read操作）に置く。read操作はstart-workのPhase 0で必ず読まれるため、読む文書は増えない（利用者の個別承認、2026-09-18）。今のブランチのhandoffが無い場合も検出を行うため、検出はread操作の「ファイルが存在しなければ「ハンドオフなし」と返す」手順より前に置き、「ハンドオフなし」の返却にも検出結果を添える。これを受けて、start-work Phase 0に、ハンドオフの有無の両分岐に共通する1句を足す: 検出結果があれば再開先の選択肢として提示し、別のworktreeへ移ると決まったら開き直しを促して終え、Phase 1へ進まない（今のブランチに不要なhandoffを作らないため。確定前レビューの指摘による。start-workの本文への追記はこの1句に限る）。手順は次のとおり。
   - `git worktree list --porcelain` を1回実行する。worktreeが1つだけなら検出を終える。
   - 他のworktreeそれぞれで、そのブランチのhandoff 1ファイルの冒頭（`Last Updated` と `Status` の欄）だけを読む。本文は読まない。ファイル名は今のブランチと同じ規則で組み立てる（`refs/heads/` を除き、スラッシュを `_` に置換する）。
   - プロジェクト外のworktreeのhandoffを読めない場合（読み取りの拒否・エラー）は、`git show <ブランチ>:<handoffのパス>` でコミット済みの版を読む。未コミットの更新は見えないことを要約に添える。直接読める場合は、未コミットの最新状態を含むファイルを優先する（2026-09-18にClaude Code・Windowsでプロジェクト外のhandoffを承認要求なしで読めた。承認を要する環境での挙動は未確認）。
   - `Status` が `in_progress` または `paused` のものを候補とする。候補についてだけ、既定ブランチにある同名のhandoffの写しの冒頭を `git show <既定ブランチ>:<handoffのパス>` で読む。既定ブランチは、`origin/HEAD` が指すブランチの手元の名前（`origin/` を除いた名前。手元で取り込んで未pushの `completed` も見えるようにするため）とし、設定が無ければ `git worktree list` の先頭〈本体の作業フォルダ〉のブランチとして、その推定である旨を要約に添える（2026-09-18時点で本リポジトリには `origin/HEAD` の設定が無い）。写しの `Status` が `completed` で、かつ写しの `Last Updated` がworktree側と同じか新しければ、取り込み済みとして除外する（このリポジトリの慣行では、取り込み後の `completed` は既定ブランチ側の写しにだけ書かれ、worktree側は `in_progress` のまま残る。2026-09-18の実測で5件中5件が該当し、5件とも写しの更新日時がworktree側と同じか新しかった。新旧を併せて見るのは、取り込み後に同じブランチで作業を再開した場合の見落としを防ぐため）。取り込み判定に `git merge-base --is-ancestor` は使わない（コミットの無い新しいブランチも取り込み済みと判定するため）。
   - 残った候補を更新日時の新しい順に要約へ出し、再開先の選択肢に加える。今のブランチのhandoffとの新旧は絞り込みに使わない（masterを後から更新すると、中断中のworktreeが古く見えて漏れるため）。
   - handoffを特定できないworktree（ブランチを持たないdetached HEADのものや、handoffの無いもの）は、パスとブランチの有無を1行出す。無断で作られたworktreeを最も見落としやすい形のため。
   - 別のworktreeが再開先に選ばれたら、今のセッションでは続けず、そのworktreeのフォルダでセッションを開き直してstart-workを行うよう利用者に促す（今のセッションから別のworktreeへ書き込む混入を避けるため）。
   - 以上は1回のシェルコマンドにまとめてよい。

統合済みworktreeの片付けは規範化せず、一度きりの整理として別途扱う。

## Consequences

- どの主体・ツールが作成したworktreeでも、開始時の見落としを防げる。ClaudeCode用メモリ `check-worktree-handoffs-at-start` の応急処置をガイドラインの手順へ置き換え、Codexや配布先にも届く。
- 作成の合意はsuperpowersの手順を読んだモデルが守るとは限らない（利用者の使用感では、GPT Astraはsuperpowersを読んだうえで合意なしに作成する）。また同意確認は `superpowers:using-git-worktrees` を経る経路にしか無く、ツールの既定動作（Codexアプリの自動作成など）で作られるworktreeや、superpowersの無い環境には効かない。いずれの場合も決定2の検出で、作成後の最初の開始時に把握できる。
- 検出はworktree側のhandoffがファイルとして存在することを前提にする。handoffを更新しないまま中断したセッションは検出できない（handoff更新頻度の問題であり、本決定の範囲外）。
- worktreeの片付け基準は定めないため、統合済みworktreeは利用者判断で残り続けうる。取り込み済みのものは既定ブランチ側の `completed` で除外されるが、次の場合は毎回1行表示される: 取り込まれずに放棄された作業のhandoffが `in_progress` のまま残る場合、取り込まれたが誰も `completed` を書かなかった場合（forge上でPRを取り込んだ場合など）、handoffを持たないworktree（Codexアプリの自動作成など）が残る場合。いずれも状態更新か片付けの契機になるため受容する。また、本体の作業フォルダが既定ブランチ以外に切り替わっている状態で既定ブランチを推定した場合は、取り込み済みのworktreeが再び表示されうる（見落としではなく表示過多の側の誤りであり、推定である旨を添えるため受容する）。
- 費用: worktreeが1つだけの環境（配布先の大半と想定）ではコマンド1回。このリポジトリ（worktree 6つ、うち取り込み済み5つ）ではコマンド1回と、handoff冒頭5件および既定ブランチ側の写し5件の読み取り。対象をhandoff冒頭の2欄に絞るため、読む量は件数に比例して小さく保たれる。
- 期待検出量: 発火機会は、`git worktree list` が2件以上を返す環境での開始・再開ごと。対象期間は本ADRの実装から次回の棚卸しまでとする。検出の提示自体は記録しないため、発火機会は、その期間にhandoffを更新したコミットの数（`git log --all --since=<実装日> -- docs/working/handoff/`）で近似する。これはhandoffを更新したセッションの近似であり、既定ブランチ上のセッションも含む。開始しただけでhandoffを更新しないセッションは数えず、1セッションで複数回更新したコミットやworktreeを使わないfeatureブランチの更新は数える（向きの定まらない近似であり、worktreeが2件以上あった期間を併記して読む）。捕捉したい欠陥の残存は、同期間の見落としの再発記録（worklog・利用者指摘）の件数で数える。捕捉したい欠陥型は、別worktreeの進行中・中断中のhandoffと、handoffを特定できないworktreeの見落とし。
- 規範の廃止条件: 次のいずれかが観測されたら廃止側とする。(a) 利用する基盤（start-workの依存するプラグインやエージェント本体）が、開始時にworktree横断の作業状態を自ら提示するようになった。(b) 棚卸し時点で、本リポジトリと把握している配布先のいずれでも `git worktree list` が2件以上を返さず、かつ見落としの再発記録（worklog・利用者指摘）が無い。判断は利用者が行う。

## 過剰適合点検（ADR-0079）

| 観点 | 判定 | 根拠 |
|------|------|------|
| 出所の偏り | 問題なし | 根拠は1プロジェクト（本リポジトリ）・1件（worklog `MakeAiInstructions-2026-09-15-03`、claude-fable-5-1）。worktreeの作成主体はGPT Astra・Codexアプリ・superpowersと複数だが、見落としの観測は1回。無条件の規範にはせず、`git worktree list` が2件以上という観測可能な発動条件でゲートした。確定前レビュー（フル実施2回・差分再確認1回）後に追加した除外条件（既定ブランチ側の写しの `completed` と更新日時）・再開先選択後の案内・Phase 0の1句も、同じゲートの内側でのみ働く。`completed` が既定ブランチ側に書かれるのは本リポジトリの慣行の観測であり、書かれない経路は表示過多として受容した（2026-09-18に再点検） |
| システム種別依存性 | 問題なし | Gitを使うプロジェクトを前提とする。取り込み済みの判定は、session-handoffの既存のStatus定義（`completed` はマージ完了時に付ける）に依拠し、新しい状態値を足さない。read操作の既存手順1（`git branch --show-current`）が既にGitを前提にしており、前提は増えない。worktreeを使わないプロジェクトではコマンド1回で終わる。引き写し箇所: なし |
| AIモデル/ツール依存性 | 問題なし | 特定モデルの挙動を前提にしない（作成主体を問わず検出する）。プロジェクト外のパスを読めないツール・設定がありうるため、読めない場合の `git show` による代替経路を持たせた（承認を要する環境での挙動は未確認であり、観測したらこの経路の条件を見直す）。引き写し箇所: `superpowers:using-git-worktrees` の同意確認を決定1で参照するが、規範として引き写さず委ねる（同スキルの条件節〈既に表明された方針があれば従う〉を落としていない） |
| 規範の廃止条件 | 定義済み | 上記Consequencesの (a)(b)。向き: いずれかが観測されたら廃止側 |
