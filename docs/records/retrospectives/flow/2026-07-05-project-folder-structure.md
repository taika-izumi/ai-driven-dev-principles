## 開発フロー/ガイドライン課題

各課題は抽出と分類までにとどめる。**対策の設計・採否判断・ADR 化は行わない**（次サイクルでユーザーが対策要と判断した時点で着手。ADR-0021）。

- **課題 #1**: 質問ツールの表示特性が選択肢提示規範に織り込まれていない
  - **事象**: 選択肢＋推奨規範（ADR-0024）に従い AskUserQuestion を使ったが、同一ターンに書いた説明文がユーザーに表示されず、説明の欠落した状態で選択を求める形になった（GTD の説明を2回要求される再質問が発生）
  - **原因**: 規範が「構造化された質問ツールを使う」ことは定めているが、ツールの表示特性（先行テキストが見えない場合がある）への対処を定めていない
  - **影響**: 意思決定に必要な情報が届かない、質問のやり直しによる往復増
  - **なぜフロー課題か**: 特定システムではなく、ガイドラインの対話規範（ADR-0024）とツール利用手順の問題であるため
  - **関連**: ADR-0024、CLAUDE.md「ユーザーへの質問と意思決定要求」
- **課題 #2**: 選択UIの誤操作が即「方針確定」として扱われる
  - **事象**: AskUserQuestion の誤クリックで意図しない選択肢（既存パス維持）が確定し、ADR ドラフト作成→ユーザー申告→破棄の手戻りが発生した
  - **原因**: 重要度の高い意思決定でも確認ステップなしに選択が確定される。意思決定の継続検出ルール（ADR-0006）が「検出→即ドラフト」を求めるため、誤確定が即座にADR作業へ増幅される
  - **影響**: ADR 作成・インデックス更新・取り消しの往復コスト（今回は未コミットだったため軽微）
  - **なぜフロー課題か**: 意思決定の確定プロセスと ADR 起票タイミングというガイドライン運用の問題であるため
  - **関連**: ADR-0006、ADR-0024、decision-log スキル
- **課題 #3**: 横断的なパス変更で実装計画に網羅漏れが出た
  - **事象**: CLAUDE.md の原則参照パスと、extend-guidelines / session-handoff 内の旧パスが実装計画のタスクから漏れ、レビュー段階で発見・追加修正になった
  - **原因**: 計画時の変更対象リストが「仕様書で明示したファイル」に偏り、リポジトリ全体の旧参照の洗い出し（横断 grep）が計画作成時ではなくタスク末尾の検証に寄っていた
  - **影響**: レビュー往復の増加（最終的には回収できたが、計画の網羅性への信頼が下がる）
  - **なぜフロー課題か**: writing-plans 時の横断的変更の洗い出し手順というプロセスの問題であるため
  - **関連**: superpowers:writing-plans、feature-block-design
- **課題 #4**: retrospective の課題バックログと issue 管理の関係が未定義
  - **事象**: 課題の置き場が振り返り記録（`docs/records/retrospectives/system|flow/`）と `docs/working/issues/` の2系統になり、起票基準・分類表現・相互参照の方法が決まっていない。課題ファイルのフォーマットにはフロー/システムの分類フィールドもない
  - **原因**: 課題管理（ADR-0025）の導入時に、既存の retrospective 運用（ADR-0021）との統合を検討しなかった
  - **影響**: 課題の見落とし・二重管理のリスク。振り返り由来の課題に open/closed のライフサイクル管理が適用されない
  - **なぜフロー課題か**: ガイドラインの課題管理体系そのものの設計問題であるため。ただし本リポジトリでは成果物＝ガイドラインであり、今回作成した folder-structure.md §7 の設計漏れという「対象システム固有」の性格も併せ持つ境界事例（rubber-duck 指摘 #2）。対策の主対象がプロセス設計であることから flow に分類した
  - **関連**: ADR-0021、ADR-0025、retrospective スキル、decision-log スキル、docs/overview/folder-structure.md §7
