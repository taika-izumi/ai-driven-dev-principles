## 開発フロー/ガイドライン課題

各課題は抽出と分類までにとどめる。**対策の設計・採否判断・ADR 化は行わない**（次サイクルでユーザーが対策要と判断した時点で着手。ADR-0021）。

- **課題 #1**: ADR 起票時に粒度（1決定=1ADR）を確認する観点がない
  - **事象**: ADR-0041 の初版に「Rejected 経路の定義」「Superseded の置換特定と台帳監査」「本サイクルの実施項目」という複数の独立した決定・実行計画を束ねて起票し、ユーザーレビューで分割の指摘を受けて書き直した
  - **原因**: `decision-log` の作成手順に「1つの ADR に収める決定の単位」を確認する観点がなく、「1サイクル=1ADR」の暗黙の慣性で束ねた
  - **影響**: ADR の書き直しと再コミット1回（軽微）。レビューがなければ、将来「部分修正あり」注記が増えやすい大型 ADR が台帳に蓄積し、本サイクルで定義したステータス管理（部分置換の扱い）を自ら悪化させるところだった
  - **なぜフロー課題か**: ガイドライン（開発フロー）側の成果物である `decision-log` スキルの起票手順に対する課題であり、配布先の個別システム成果物の課題ではない
  - **関連**: `skills/decision-log/SKILL.md`（ADR作成手順）、ADR-0019（記述規律）、ADR-0041/0042（分割の実例）
