## 開発フロー/ガイドライン課題

各課題は抽出と分類までにとどめる。**対策の設計・採否判断・ADR 化は行わない**（次サイクルでユーザーが対策要と判断した時点で着手。ADR-0021）。

- **課題 #1**: スキルを改定したサイクルでは、その改定を同一セッション内で検証できない
  - **事象**: 本サイクルで `skills/worklog-extract/SKILL.md` と `skills/worklog-record/SKILL.md` を改定した後、同じセッションでそれらのスキルを起動したところ、**Skill ツールが返した本文は改定前のままだった**。ディスク上のファイルと `git show HEAD:<path>` の両方に編集が存在することを確認して初めて、返り値側が古いと判明した
  - **原因**: スキル本文はセッション開始時点の内容で提供される。ADR-0055 は「スキルが使えるか（availability）」の AI 側判定規範を定めているが、「**改定内容が反映されているか**」は扱っていない。両者は別の問いである
  - **影響**: セッション序盤に「スキルはリポジトリ直下から解決されており改定が反映済み。プラグイン更新は不要」とユーザーへ報告し、後で訂正する必要が生じた。より重いのは、**改定したスキルを同サイクル内で実地検証できない**ことである。本サイクルで改定した 2 スキルは動作未確認のまま次サイクルへ渡る
  - **なぜフロー課題か**: 対象システムに依存しない。スキルを改定するあらゆるサイクルで同じ制約が働き、配布先でも同様に起きる
  - **振り分け判定**: 構造観察型（改定の有無と Skill 返り値という 2 つの状態を突き合わせて初めて見える。delta としても `MakeAiInstructions-2026-08-05-04` に記録済みだが、フロー設計の欠落が本体）
  - **関連**: ADR-0055（availability の AI 側判定）/ Issue-0039（ガイドライン遵守が不可視機構に依存しうる）/ `start-work` Phase -1
  - **起票**: Issue-0044（`../../working/issues/flow/0044-skill-revision-unverifiable-in-same-session.md`）

- **課題 #2**: 既存 open 課題の対策方針が実行可能かを点検する工程がない
  - **事象**: Issue-0033 は「`subagent-driven-development` / `dispatching-parallel-agents` への定型チェックリスト追加が適する」、Issue-0034 は「`requesting-code-review` の射程拡大」「`writing-plans` の末尾へ工程追加」を対策方針として書いていた。しかし `worklog-skillify` を起動した段階で、**これらがすべて superpowers プラグインのスキルであり編集できない**と判明した
  - **原因**: 対策方針は起票時・`worklog-extract` の採用時に書かれるが、その**実行可能性**（拡張先が自リポジトリに実在するか、編集が永続するか）は着手時まで検証されない。起票と採用のどちらの工程にも確認ステップがない
  - **影響**: 本サイクルでは ADR-0069 で今後の規範を定めて解消したが、**既に起票済みの未着手課題に同種の見落としが潜在する**。対策に着手して初めて方針が成立しないと分かる状態が残っており、着手時の手戻りとして現れる
  - **なぜフロー課題か**: 課題管理の運用（対策方針をいつ・どこまで検証するか）の問題であり、対象システムに依存しない
  - **振り分け判定**: 構造観察型（複数の課題の対策方針を横断して見たときに初めて見える。単一作業時点の delta としては現れない）
  - **関連**: ADR-0069（拡張先の制約。本サイクルで決定）/ ADR-0032（規範の判定条件はエージェントが観測・実行できる事実で書く。近縁だが対象が異なる）/ `docs/overview/folder-structure.md` 7.2〜7.3
  - **起票**: Issue-0045（`../../working/issues/flow/0045-issue-countermeasure-feasibility-unchecked.md`）

- **課題 #3**: サイクル規模の再見積もりチェックポイントがない
  - **事象**: 計画は Task 1〜8 で確定したが、実行中に Task 7 のスコープ変更（ADR-0065）、ADR 粒度点検による 2 本の分割新設（ADR-0068 / 0069）、母数の訂正が追加された。結果として ADR は 1 サイクルで 9 本（ADR-0061〜0069）になった
  - **原因**: 節目で残作業の規模を再見積もりし、サイクル分割の要否を利用者に確認する工程がフローに存在しない
  - **影響**: 本サイクルは完走できたため実害は出ていない。ただし **ADR-0062 の Consequences に「規模膨張の歯止めが無い」と自ら記録したうえで着手し、予告どおりの膨張が起きた**。予測できていても止める手段が無いことが確認された形である
  - **なぜフロー課題か**: 計画・実行フローの構造の問題であり、対象システムに依存しない。`LoopForAlpha#Issue-0042` として配布先でも 2 サイクル連続で観測されている
  - **振り分け判定**: 構造観察型（サイクル全体を俯瞰して初めて見える。作業時点の躓きとしては現れない）
  - **関連**: `LoopForAlpha#Issue-0042`（配布先での同一課題。本リポジトリに受け皿が無かった）/ `superpowers:writing-plans` / `start-work` Phase 2 / ADR-0062
  - **起票**: Issue-0046（`../../working/issues/flow/0046-cycle-scale-re-estimation-checkpoint-missing.md`）
