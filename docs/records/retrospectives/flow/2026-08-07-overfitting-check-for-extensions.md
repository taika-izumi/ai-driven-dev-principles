## 開発フロー/ガイドライン課題

各課題は抽出と分類までにとどめる。**対策の設計・採否判断・ADR 化は行わない**（次サイクルでユーザーが対策要と判断した時点で着手。ADR-0021）。

- **課題 #1**: 確定前レビューの次手提示が成果物の性質を問わず中立で、安全網の無い成果物でも AI が非推奨側に倒す
  - **事象**: spec 承認直後の次手提示で、AI は「writing-plans へ進む（推奨）」を先頭に置き、確定前レビュー（`pre-finalization-review`）を非推奨の選択肢として並べた。ユーザーが実施を指示した結果、3 観点の独立レビューが Critical 3 件・Major 8 件を検出し、spec は全面改訂（コミット `b34e2ca`、98 insertions / 45 deletions）に至った。改訂内容は点検観点 3→4 点、是正パターン 3→4 型、記録先の固定、執行点の新設、配線範囲の拡大と、設計の骨格に及ぶ
  - **原因**: ADR-0072 は「writing-plans / feature-block-design の完了後に毎回提示する」ことだけを定め、**成果物の性質による推奨の強弱を定めていない**。AI 側は「上流で自己レビュー済み」「計画は spec の機械的写像」といった一般論から非推奨側を選んだが、この判断が見落としていたのは次の構造である:

    > **コードには「実装して最初に実行すれば数分で露見する」という安全網があるが、ルール・規範・文書型の成果物には無い。** 欠陥は数サイクル後にルールが誤発動・空振りするまで顕在化しない。加えて、実装時レビュー（`subagent-driven-development` の二段レビュー）は「実装が spec に忠実か」を見るため、**spec 自体の設計欠陥はむしろ忠実に実装される**。

  - **本サイクルで判明した「確定前レビューでしか捕まらない欠陥クラス」**（次サイクルで対処を設計するときの一次資料。単一サイクル由来である点は下記「留意」参照）:
    1. **選定漏れ型（spec に「載っていない」欠陥）**: 実装も検証も spec に存在するものしか見ないため、比較対象が下流のどの工程にも存在しない。本サイクルの実例 = 点検観点に「退役経路」が無い（契機 worklog の示唆 2 点のうち 1 点が脱落していた）/ スナップショット仕様書 `04-skill3-skillify.md` の同期タスクが spec に無く、計画にも実装にも現れなかった / 是正パターンに「見送り・撤回」が無く、点検を回すほど規範が増える一方になる棘輪構造だった
    2. **文書間相互作用型（編集対象外ファイルとの矛盾）**: タスク単位で委譲された実装者は自分の編集箇所しか読まないため、構造的に検出できない。実例 = 記録義務が「ADR に書け」と定めるのに、対象 3 シナリオでは ADR 作成が「重要な変更の場合」の任意であり記録先が存在しない経路が残っていた / `worklog-skillify` の CLAUDE.md 追記分岐（本 repo では template 配布物）が「汎用スコープのみ」の但し書きで点検対象から免除されていた / 記録先の規定が ADR-0019（決定のみ記載）と衝突していた
    3. **検出力欠陥型（検証が緑を返すが何も守っていない）**: レビュアーが実装後状態を scratchpad にシミュレーション構築して写経実行したことで初めて実証された。実例 = 検証 1 の grep が節見出しを特定せずチェックリスト行にもヒットするため、**横断節の新設を丸ごと忘れてもチェックリスト 7 行さえ入れば合格**する状態だった（Issue-0042 と同型）
    - **対照（後工程でも拾えた型）**: 期待値の数値ズレ（8 件 vs 実際 9 件）、PowerShell の構文誤り、renumber の連番ズレ、挿入アンカーの不一致。これらは実装・検証時に機械的に露見するため、確定前レビューで拾う必要性は低い
  - **影響**: 最もレビュー価値が高い場面で、AI が実施しない側へユーザーを誘導する。本サイクルはユーザーが明示的に指示したため回避されたが、指示が無ければ骨格に欠陥を残したまま実装を完了し、欠陥は次にこのルールが発動する数サイクル後まで発見されなかった
  - **なぜフロー課題か**: 特定の成果物の欠陥ではなく、`pre-finalization-review` の発動提示規範（ADR-0072）の設計に欠けている観点である。対象システムを問わず、非コード成果物を作るあらゆるサイクルで同じ判断の偏りが起きる
  - **振り分け判定**: delta 型（worklog `MakeAiInstructions-2026-08-07-04` に記録済み）。ただし**本サイクルで実害寸前（設計骨格の欠陥を抱えたまま実装へ進む寸前）まで至ったため、ユーザー判断により早期対処として起票**（ADR-0056）
  - **関連**: ADR-0072（発動はユーザー指示のみ・AI は毎回提示）/ `skills/pre-finalization-review/SKILL.md` / ADR-0079（本サイクルの成果物＝レビュー対象）/ worklog `MakeAiInstructions-2026-08-07-04`
  - **起票**: Issue-0062（`../../working/issues/flow/0062-review-recommendation-ignores-artifact-safety-net.md`）

- **課題 #2**: 実装中に確定した文言を正本（spec）へ同期する運用はあるが、作業文書（plan）への反映規約がない
  - **事象**: 品質レビュー由来の文言修正（手順のラベル形式化・語尾の統一）で spec は同期した（`408d1bb` / `6670ea6`）が、実装計画ファイルは旧文言のまま残った。ファイナルレビューが差異として検出した
  - **原因**: 「plan は時系列の作業記録だから実装中の変更を戻さない」のか「同期漏れ」なのかを区別する規約がない。spec にはスナップショット規約（書き換え更新）があるが、plan にはこれに対応する規約が明文化されていない
  - **影響**: 計画を再読したときに差異が漏れに見え、突合コストが生じる。本サイクルでの実害は小さい
  - **なぜフロー課題か**: 対象システムに依存せず、`writing-plans` と spec 運用規約の境界の未定義である
  - **振り分け判定**: 構造観察型（作業時点の躓きとしては現れず、成果物群を突き合わせて初めて見える）
  - **関連**: `superpowers:writing-plans` / ADR-0008（スナップショット規約）/ `CLAUDE.md` ドキュメント運用
  - **起票**: Issue-0063（`../../working/issues/flow/0063-plan-document-sync-policy-undefined.md`）
