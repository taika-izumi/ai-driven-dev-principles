## 開発フロー/ガイドライン課題

各課題は抽出と分類までにとどめる。**対策の設計・採否判断・ADR 化は行わない**（次サイクルでユーザーが対策要と判断した時点で着手）。

- **課題 #1**: 計画の検証ステップの期待値が、実装中に判明した事実で陳腐化し、計画自身のタスク内容と矛盾する
  - **事象**: 本サイクルで 4 件発生した。(a) 残存識別子の検証コマンドが、同じ計画の別タスクが**意図的に**導入する中立名プレースホルダを拾い、期待値 0 が原理的に達成不能だった。(b) 検証の検索語が仕様本文の実際の表現と一致していなかった。(c) 注記の日付を計画作成日で固定しており実施日とずれた。(d) 自己テストの期待ケース数が古いまま（17 に対し実際は 21）
  - **原因**: 実装計画の検証期待値と編集内容の整合を確認する規範は、**計画作成時の 1 回の突合**を想定している。実装中に判明した事実（追加された対象行、精緻化された仕様の表現、拡張されたテストケース）で期待値が陳腐化する経路を扱っていない。また (a) は、検証コマンドを「素朴な正規表現」で書いたために、規約が持つ許可リストを反映できなかったことにも起因する
  - **影響**: 検証が「必ず失敗する」か「形だけ通る」状態になる。本サイクルでは実装者が実態優先の報告をしたため露見したが、指示に黙って従っていれば検証を通過したことになり、欠陥が下流へ流れる
  - **なぜフロー課題か**: 対象システムの仕様ではなく、実装計画という成果物の書き方と、その検証手順の維持に関する問題であるため
  - **振り分け判定**: 構造観察型（個々の delta としても現れたが、規範に「実装中の期待値更新」の経路がないという欠落は、サイクル全体を俯瞰して初めて見える）
  - **関連**: ADR-0034（実装計画の検証ステップ期待値と編集内容の整合）、`CLAUDE.md`「検証」節、`superpowers:writing-plans`
  - **起票**: Issue-0073（`../../working/issues/flow/0073-plan-verification-expectation-goes-stale.md`）

- **課題 #2**: 決定を Accepted へ昇格させる前に、仕様が実装のスナップショットになっているかを検査する工程がない
  - **事象**: 計画 12 タスクを完走し、決定 4 件を Accepted 化して課題を close した**直後**のブランチ全体レビューで、仕様が実装に追いついていない箇所が 3 件見つかった。(a) 移行の過程で追加された 10 行の書き換え（規約適合だが除去後に文が壊れる行）が仕様のどこにも記載されていなかった。(b) レビューで新設し規約として稼働している 2 項目が、仕様にも決定にも書かれていなかった。(c) 完了基準の件数が正本・下位仕様・実装で三すくみになっていた
  - **原因**: 決定の昇格チェックポイントは粒度の点検を含むが、仕様との整合検査を含まない。またタスク単位のレビューは「そのタスクの成果物が正しいか」を見るため、タスクをまたいで増えた規範や、上流仕様との差の累積を原理的に検出できない。サイクル途中で仕様を何度も改訂したことが、この累積を見えにくくした
  - **影響**: 決定が確定した状態で仕様が古いまま残る。仕様書はスナップショットとして維持する規範に反し、次サイクルの読み手が現状を誤って理解する
  - **なぜフロー課題か**: 決定記録の運用（昇格の手順）と、レビューの射程という開発の進め方の問題であるため
  - **振り分け判定**: 構造観察型（タスク単位の作業では観測できず、サイクル全体のレビューで初めて見えた）
  - **関連**: ADR-0019（承認の遅延昇格）、`skills/decision-log/SKILL.md`「承認の昇格」、Issue-0065（タスク単位レビューの射程。同型の先行課題）、`CLAUDE.md`「ドキュメント運用」のスナップショット規範
  - **起票**: Issue-0074（`../../working/issues/flow/0074-spec-snapshot-check-missing-before-adr-promotion.md`）

- **課題 #3**: 規約・手順文書の「読者が実際に使えるか」を検査する観点が、確定前レビューにない
  - **事象**: 新設した規約節が、仕様との逐語突合 39 項目すべて一致で仕様準拠レビューを通過した。その後の品質レビューで「この節だけを読んで作業する人になったつもりで 4 つの作業を試す」検査を課したところ、**3 つで詰まった**。(a) 本リポジトリの慣用形が別の規約違反として弾かれ、しかもエラーに出る規約名が書き手の意図と食い違う。(b) 規約に完全適合していても配布物が壊れる書き方があり、その予防規則が書かれていない。(c) 目視確認を指示しながら対象の所在が文書全体で一度も書かれていない
  - **原因**: 確定前レビューの 3 観点（敵対的・実装整合性・仕様適合）は「書いてあることが正しいか」を検査するが、「書いていないことで詰まるか」を検査しない。規約を書いた側は既にその規約を理解しているため、初見の書き手が最初に選ぶ形が違反になることに気づけない
  - **影響**: 規約・手順文書が「正確だが使えない」状態で確定する。この型の成果物は実行による安全網がないため、欠陥は使われる時まで潜伏する
  - **なぜフロー課題か**: 特定の規約の内容ではなく、規範・手順文書に対するレビュー観点の欠落であるため
  - **振り分け判定**: 構造観察型（レビュー観点の欠落は、実際に観点を足して比較して初めて見える）
  - **関連**: ADR-0072 / ADR-0080（確定前レビューの発動と提示規則）、`skills/pre-finalization-review/SKILL.md` の 3 観点、Issue-0062（レビュー推奨が成果物の安全網の有無を考慮しない。同型の先行課題）
  - **起票**: Issue-0075（`../../working/issues/flow/0075-review-lacks-usability-check-for-normative-docs.md`）

- **課題 #4**: 破壊的な検証を委譲するとき、隔離の作り方を指定する制約項目がない
  - **事象**: 「破壊的検証はスクラッチパッドの複製で行う」と委譲プロンプトへ明記し、委譲先も複製で実施したと報告したにもかかわらず、**実リポジトリのファイルが 2 度壊れた**。(a) 決定記録インデックス 92 行が空ファイルになった（追跡ファイルだったため復旧できた）。(b) 配布物 1 ファイルに BOM が書き込まれた。原因は後者の委譲先が自己申告し、PowerShell の `Set-Location` が .NET の静的 API（`[System.IO.File]::WriteAllText` 等）に効かず、プロセスの作業ディレクトリが基準になるためと判明した
  - **原因**: 委譲制約の常時適用項目には「既存ファイル・ディレクトリの削除は事前承認を要する」があるが、**隔離環境の作り方**（複製の手段・絶対パスの使用・作業前後の状態比較）を指定する項目がない。「複製で検証する」という指示だけでは、言語とランタイムの組み合わせによって成立しない
  - **影響**: git 管理下のファイルなら復旧できるが、未追跡ファイルや生成物であれば復旧手段がない。委譲先の自己申告と実態が食い違うため、事後の切り分けもできない（1 度目は原因を特定できないまま終わった）
  - **なぜフロー課題か**: 特定の検証内容ではなく、サブエージェントへの委譲プロンプトに入れる制約項目の設計に関する問題であるため
  - **振り分け判定**: delta 型（早期対処のため起票）。同じ機構で 2 度発生しており、worklog にも記録済み（`MakeAiInstructions-2026-08-08-06` / `-09`）。再発の裏付けを横断走査に委ねる前に対処が要ると判断した
  - **関連**: ADR-0066（A 群 / B 群の分割）、ADR-0071（B 群の発火判定）、ADR-0073（根拠と退役経路）、`skills/subagent-dispatch/SKILL.md`
  - **起票**: Issue-0076（`../../working/issues/flow/0076-dispatch-lacks-isolation-method-constraint.md`）
