## 3. Struggled（苦労したこと・手戻り）

- 本サイクルでは実質的な手戻り・誤解は発生しなかった。強いて挙げると:
- **事象**: `git add --renormalize .` が untracked ファイル（`.gitattributes` 自身）をステージしないことに、実行後の `git status` で気づいた
  - **原因**: renormalize は追跡済みファイルの再正規化のみを対象とする仕様
  - **影響**: なし（個別 `git add` で対応し、コミット構成も意図通りに保てた）
  - **対処**: `git status` の読み合わせで検出し、コミット時に個別ステージした

## 4. Tech Notes（古びない技術知見）

- **タイトル**: `.gitattributes` の `* text=auto` は最小記述の改行正規化
  - **コンテキスト**: 改行正規化を貢献者のローカル設定（core.autocrlf）任せにせず、リポジトリ側で固定したい場合
  - **知見**: `* text=auto` 1行で「コミット時に LF 正規化、バイナリは自動判定で除外、チェックアウト時の改行は各自のローカル設定に委ねる」が実現できる。拡張子列挙の保守は不要。チェックアウト側も固定したければ `eol=lf` を足すが、ローカル設定より強い制約になる
  - **参照**: ADR-0037、.gitattributes (2904a88)
- **タイトル**: `git add --renormalize .` は追跡済みファイルのみが対象
  - **コンテキスト**: .gitattributes 導入時の一括再正規化
  - **知見**: renormalize は追跡済みファイルの再正規化のみを行い、untracked ファイル（新規追加した `.gitattributes` 自身など）はステージしない。別途 `git add` が必要
  - **参照**: 本サイクルのコミット作業 (2904a88)
- **タイトル**: `git ls-files --eol` で正規化の事前影響調査と事後検証ができる
  - **コンテキスト**: 改行正規化の導入前後で「何が変わるか / 変わったか」を確認したい場合
  - **知見**: index の改行・作業ツリーの改行・適用中の attr を一覧できる（例: `i/lf w/crlf attr/text=auto`）。導入前に流せば renormalize で差分が出るファイルを予見でき、導入後に流せば attr の適用漏れを検出できる
  - **参照**: ADR-0037（Context に調査結果を記録）、本ファイル §1 Done
- **タイトル**: 改行正規化の実機検証は使い捨てファイルで数秒でできる
  - **コンテキスト**: .gitattributes を「書いただけ」で終えず、実際の正規化動作を確認したい場合
  - **知見**: 使い捨て CRLF ファイルを作成 → `git add` → `git ls-files --eol` で `i/lf w/crlf` を確認 → `git rm --cached` と削除で後始末。リポジトリを汚さない
  - **参照**: 本ファイル §1 Done（完了宣言前に実施）
