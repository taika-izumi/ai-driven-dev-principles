## 4. Tech Notes（古びない技術知見）

> **スコープ（ADR-0021 / ADR-0012）**
> - **含める**: ツール挙動・環境の罠・回避策・推奨手順など、開発フローやプロジェクトに依存せず古びない汎用技術知見
> - **除外**: 開発対象システムの仕様・ドメイン知識（ビジネスルール・用語・業務制約など）。これらは当該システムの仕様書に記載すること

- **タイトル**: 環境・モデル特性に依存する対策指示は「条件付き適用＋撤去基準」の3点セットで書く
  - **コンテキスト**: LLM モデルやツール UI の特性（表示挙動など）に起因する問題への対策を、恒久的なガイドラインに書き込むとき
  - **知見**: ①事象確認済み環境の列挙、②未確認環境では従わない旨、③撤去の判断基準——を指示自体に含めると、環境が変わったときの陳腐化・不要な制約の残存を防げる
  - **回避策・代替**: 撤去基準は実行可能な主体（通常はユーザー）に紐づけて書く
  - **参照**: ADR-0029、CLAUDE.md「ユーザーへの質問と意思決定要求」
- **タイトル**: エージェントが観測できない事象を規範の判定条件にしない
  - **コンテキスト**: AI エージェント向けの規範・ルールに判定条件や発動条件を書くとき
  - **知見**: 「ユーザー画面でどう表示されたか」「セッション横断でどのモデルを使ってきたか」等はエージェントから観測不能。観測不能な条件に基づく判定は自動化せず、ユーザー判断に委ねる設計にする
  - **回避策・代替**: 規範ドラフト時に「この判定・動作をエージェントは実行できるか」を確認する（本サイクルの課題 #1 として起票）
  - **参照**: ADR-0029 Considered Alternatives / Decision 3
- **タイトル**: 改行コードのみの差分の見分け方と安全な戻し方
  - **コンテキスト**: スクリプトやツールがファイルを再生成し、`git status` で modified と出るが内容が変わっていないように見えるとき
  - **知見**: `git diff --stat` に行数変化が出ない（またはファイル自体が現れない）modified ファイルは改行コード等の空白のみの変更の可能性が高い。ただしこの見え方は `core.autocrlf` / `.gitattributes` の設定に依存する（設定によっては全行差分として現れる）ため、設定非依存の確認は `git diff --ignore-cr-at-eol` で行う（出力が空なら CR の有無のみの変更）。CRLF/LF 警告の有無も手がかりになる
  - **回避策・代替**: 内容変更がないことを確認のうえ `git restore <file>` で戻し、差分ノイズをコミットに含めない
  - **参照**: git の EOL 正規化挙動（`core.autocrlf` / `.gitattributes`）、Issue-0002（本プロジェクトでの発生例）
