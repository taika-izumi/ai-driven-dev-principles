## 4. Tech Notes（古びない技術知見）

- **タイトル**: Markdown テーブル内のパイプ文字はコードスパンでも区切りになる
  - **コンテキスト**: GFM のテーブルセル内に `system|flow` のようなパス表記を書こうとした
  - **知見**: GFM 系レンダラーでは、バッククォート（コードスパン）内でも `|` はセル区切りとして解釈され、テーブルが壊れる（レンダラーにより挙動差あり）
  - **回避策・代替**: エスケープ（\|）は可読性が下がるため、セル内では「配下の system/ または flow/」のような言い換えで回避するのが安全
  - **参照**: docs/overview/folder-structure.md §6 配置表
- **タイトル**: git mv は移動先ディレクトリを自動作成しない
  - **コンテキスト**: 課題ファイルを新設サブフォルダへ git mv しようとした
  - **知見**: 移動先フォルダが存在しないと `fatal: renaming ... failed: No such file or directory` になる
  - **回避策・代替**: 先にディレクトリを作成（mkdir / New-Item）してから git mv する
  - **参照**: コミット 6c88d26 の作業過程
- **タイトル**: 実行環境にインストールされたスキル/プラグインは repo の作業コピーとは別物
  - **コンテキスト**: プラグイン機構で配信されるスキル定義を、その配信元 repo 内で改修するサイクル
  - **知見**: repo 内の定義ファイルを編集・マージしても、実行環境はインストール/キャッシュ済みの版を使い続ける。配信機構の更新手順を経るまで変更は反映されない
  - **回避策・代替**: 改修後は配信機構の更新（例: Claude Code なら `/plugin marketplace update <name>`）を実行してから動作確認する
  - **参照**: 本サイクルの merge 後手順（rubber-duck 指摘 #3 を受け、コマンド固有の記述から一般化して書き直し）
