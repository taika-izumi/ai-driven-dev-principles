## 3. Struggled（苦労したこと・手戻り）

- **事象**: 当初設計（Issue-0017 を CLAUDE.md + CONTRIBUTING.md の両方へ配置）をいったん提示し ADR-0039 ドラフトまで作成した後、ユーザーの懸念提起（常時指示の規模拡大）を受けて CONTRIBUTING.md のみへ縮小する方針変更が発生した
  - **原因**: 設計時の選択肢評価が「課題を確実に塞ぐ配置はどれか」に偏り、「その配置が常時指示に与える累積コスト」と「課題の放置リスクの大きさ」の突合を初回提示前に行っていなかった
  - **影響**: 軽微（ADR ドラフト1本の書き直しと質問1往復。ADR-0030 の書き直し自由により手戻りコストは小さかった）。むしろ議論を通じて Issue-0018 という新課題の発見につながった
  - **対処**: 放置リスクを課題ごとに再評価し、リスクに比例した配置（0016 のみ常時指示へ）に再設計した

## 4. Tech Notes（古びない技術知見）

- **タイトル**: 常時ロード指示の負荷は「量」より「ゲートの有無」で決まる
  - **コンテキスト**: AI エージェントが毎セッション読み込む指示ファイル（CLAUDE.md 等）へ規範を追加するとき
  - **知見**: 発動条件付き（例: 「節目の直前は」「再発防止策を設計するときは」）の規範は、非該当タスクでは「該当しない」と判定されやすく、無条件の「常に〜せよ」型より注意配分への影響が小さい。常時指示に足すなら観測可能な発動条件でゲートすること（ADR-0032 の観測可能性要件とも整合）。ただしこれは LLM 内部挙動の実測に基づかない経験則・作業仮説であり、ゲートは1件あたりの負荷を下げるが累積自体を無害化するわけではない（累積の管理は監視・棚卸しの領分。Issue-0018）
  - **参照**: ADR-0038（発動条件2つに限定した設計）、本サイクルの設計議論
- **タイトル**: ガードレールの配置はリスク特性で使い分ける
  - **コンテキスト**: 失敗の再発防止をどの層（常時指示 / 手順書 / 自動機構）に置くか決めるとき
  - **知見**: 「静かに壊れ、発見が遅れ、修復コストが高い」失敗は常時指示・自動機構で塞ぐ価値がある。「人間レビューが必ず挟まる工程で顕在化する」失敗は、発生箇所の手順書・チェックリストで足りることが多い。常時指示は最も高価な置き場所として最後に選ぶ
  - **参照**: ADR-0038/0039 の配置判断（0016 → CLAUDE.md / 0017 → CONTRIBUTING.md）
- **タイトル**: 指示ファイルの重さは議論の前に実測する
  - **コンテキスト**: 「指示ファイルの肥大化が心配」という議論を始めるとき
  - **知見**: 感覚論になりやすいため、トークン実測（Claude Code なら /context コマンド等 — 2026-07 時点の例示。他ツールでも相当の計測手段）で「現在値と追加分」を数字にしてから判断すると、過剰反応も過小評価も避けられる。本サイクルでは CLAUDE.md 約3.8kトークンに対し追加約100トークンと確認して判断した
  - **参照**: 本サイクルの設計議論、Issue-0018
