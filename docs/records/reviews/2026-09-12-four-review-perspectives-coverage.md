# 4観点の網羅性と一般的なレビュー指摘の比較

2026-09-12。ユーザーは、要求・根拠・成立性・敵対的の4観点が十分か、既存4観点と一般的な指摘類型を比較した意見を求めた。本書は分析と推奨候補であり、構成採用・規範改定・4担当の実行を決めるものではない。

## 判断

**現状の短い定義だけでは十分と言えない。4つを役割の大枠として使う余地はあるが、必要な品質項目が誰の検査対象になるかを補う必要がある。** 何でも要求・根拠・成立性へ分類できることと、実際に探す問いが担当へ届くことは異なる。

前の案では性能・機密性・保守性等を「対象で要求される品質」に含めるとしたが、それだけでは要求自体に書かれていない必要な品質を見落とす。要求担当が要求の十分性も問い、関係する品質項目を明示的に確認する必要がある。また、成立性担当へすべてを集めると担当分離の利点を失うため、変更の性質に応じた分担が必要になる。

## 既存4観点との比較

| 現行 | 候補 | 実質的な差と限界 |
|---|---|---|
| 仕様適合（目的・要求との一致） | 要求 | 現行も既に全体目的と仕様自身の妥当性を含む。改名だけでは拡張にならない。候補では不足した品質要求や成功指標も担当範囲へ明記できる |
| 前提実在（根拠・必要性） | 根拠 | 現行は問題・保護対象・重複・欠落等の実在に重点。因果・測定方法・設計案選択の妥当性まで含めるなら実質的な拡張であり、別途定義が必要 |
| 実装整合性（実体・接続との一致） | 成立性 | 現行は実体や契約との整合。候補は実際の利用・検証・運用まで含める想定だが、「成立する」だけでは保守や復旧の責任が曖昧 |
| 敵対的（失敗経路の探索） | 独立した敵対的担当 | 観点自体は維持。変更点は他担当と文脈を分ける体制候補。独立化による品質向上は未比較 |

したがって「新しい4つなら足りる」という説明は支持できない。候補の利点を出すには、定義・分担・必要な証拠を変更する必要がある。

## 外部の比較材料

- [Googleのコードレビュー指針](https://google.github.io/eng-practices/review/reviewer/looking-for.html)は、設計・動作だけでなく複雑さ、テストの有効性、命名・コメント・文書を扱い、担当が判断できない専門領域は適切なレビュアーに確認を求める。コードレビューの実務指針であり、全成果物の分類表ではない。
- [Microsoft Azure Well-Architectedの5つの柱](https://learn.microsoft.com/en-us/azure/well-architected/pillars)は、信頼性・セキュリティ・費用・運用・性能を分けている。クラウド向けの設計評価であり、その構成をそのまま全プロジェクトへ義務化しない。
- [ISO/IEC 25010:2023の公開概要](https://www.iso.org/standard/78176.html)は、9つの品質特性によるモデルを説明し、要求の網羅性確認や評価への利用を挙げる。今回確認したのは公開概要で、規格本文の全条項との適合検査はしていない。

いずれも提供元の一次資料（2026-09-12閲覧）。これらは確認すべき品質を考える材料であり、4体・5体等のエージェント数や費用対効果の根拠ではない。

## 一般的な指摘の類型と担当候補

以下は上記資料とプロジェクトの実例から組み立てた分析上の分類。特定規格の分類の転載でも、完全な網羅の証明でもない。題材に関係するものを選ぶための一覧である。

| 指摘の種類 | 例 | 今の4観点での不足・担当候補 |
|---|---|---|
| 目的・要求・範囲 | 解決したい問題と機能が違う、必要な利用者が対象外、成功指標が目的を測っていない | 要求。書かれた要求への一致だけでなく、要求自体の十分性を確認 |
| 根拠・推論・測定 | 誤ったAPI知識、出典が主張を支持しない、相関から因果を断定、比較条件が不公平 | 根拠。「実在するか」に加え、結論を支持する証拠かを確認 |
| 設計品質・複雑さ | 動くが責務が混在、強い結合、過剰な汎用化、変更が多数箇所へ波及 | 現状は曖昧。根拠担当の設計案の妥当性と、成立性担当の変更影響に分担 |
| 正常動作・接続・データ整合 | API契約違反、単位や時刻の混同、欠損値処理、境界・順序の誤り | 成立性。実体の一致と、実際に期待した動作になることを区別 |
| 信頼性・復旧・移行 | 二重実行でデータ破損、途中停止から復旧不能、更新後に旧データが使えない | 成立性が復旧・移行を確認し、敵対的担当が故障条件から再検査 |
| セキュリティ・プライバシー・安全 | 権限の過大付与、情報露出、危険操作の経路 | 要求で保護対象、根拠で脅威前提、成立性で制御、敵対的で迂回を確認。専門検査を一般的な反例探索だけで代替しない |
| 性能・規模・資源・費用 | 小規模でしか動かない、負荷増大で急増する処理・メモリ・料金 | 要求で条件と許容値、根拠で見積り・測定の妥当性、成立性で達成を確認 |
| 利用可能性・アクセシビリティ・文書 | 初見で次に何をすべきか不明、誤操作しやすい、使えない例やリンク | 要求で利用者と作業、成立性で実際の手順・操作を確認。文書の正確さだけでは不足 |
| 運用・観測・保守 | 障害を検知できない、原因を調べられない、設定更新・依存更新が困難 | 成立性の範囲へ明記が必要。設計担当が運用・変更負担も比較 |
| 検証の有効性 | 壊しても通るテスト、実装と同じ誤りを持つ期待値、再現不能な評価 | 成立性が検証を、根拠が期待値と評価設計を確認。合格表示だけで証明済みにしない |
| 変更の完全性・追跡・適用条件 | 仕様と実装の同期漏れ、旧制約の無意識な削除、依存更新の取りこぼし | 要求と成立性。編集対象外の接続、変更前後の意味を照合 |
| 規約・外部制約 | 必須の書式や契約条件への不適合、対象に適用される制約の確認漏れ | 要求で適用性を確認。書式は既存機械検査を優先し、解釈に専門性が必要なものは専門確認を検討 |

敵対的担当は上記の独立した品質項目ではなく、各項目へ反例・失敗条件から切り込む役割である。品質項目と調べる姿勢の混在を認めた上で、独立した担当にする価値を検討できる。ただし「そのほか全部」を敵対的担当へ丸投げすると、運用・保守・専門領域の検査漏れが残る。

## 推奨する考え方（未採用）

4つは固定的な欠陥分類ではなく、以下の重点を持つ基本の分担候補とする。

1. **目的・要求の妥当性**: 書かれた要求だけでなく、利用者・目的に必要な品質条件の不足も確認する。
2. **根拠・設計判断の妥当性**: 前提・推論・必要性、代替案に比べた構造の適切さ、過剰設計や将来の変更負担を確認する。最終採否は既存の主担当の集約で行い、全員に同じ採否表を作らせない。
3. **動作・検証・運用の成立性**: 正常動作、契約、検証の有効性、実際の利用と運用・復旧まで、変更に関係する経路を確認する。
4. **独立した反例・失敗経路の探索**: 他担当の肯定的な結論を前提にせず、仕様・設計・根拠を崩せる条件を探す。反論数を成果指標にしない。

これに、対象に関係する品質項目と担当を既存の委譲文へ短く示す。別の常設台帳や全件必須チェックを直ちに設ける案ではない。目的は、要求にないというだけで安全・運用・保守が無担当になることを防ぐこと。

大きな設計変更なら設計・保守、セキュリティに関わる変更なら当該領域、評価アルゴリズムなら統計・測定など、専門性や担当量によって担当の追加・組替えを検討する。新しいエージェントに専門名を付けただけでは専門知識・証拠・検査能力が得られる保証はない。

**4体は基本体制として検討可能だが、4つの名前だけで十分とは判断しない。** 今の定義のまま固定するより、品質項目の明示と責任分担を先に具体化することを推奨する。4体の実効性と費用対効果はまだ比較していない。

## 追記: プロジェクト全体の目的・方針との整合を保持する

2026-09-12、ユーザーは、既存の仕様適合レビューが「その時指示された狭い範囲の目的」だけでなく「プロジェクトのそもそもの方針や目的」に沿うかを要求していたことを確認し、今回も忘れず保持するよう求めた。

ADR-0185 Decisionと現行review-criteria.mdの仕様適合定義に、この要求が実在することを確認した。新規観点の追加ではなく、既存の要求の保持として扱う。構成候補の選択とは切り離し、どの案でも次を保つ。

- 要求担当の中心の問いは「成果物と今回の範囲は、プロジェクト全体の目的・方針に沿い、今回の要求を適切に満たしているか」とする。直近の依頼・Issue・spec・作成者の要約だけを基準にしない。
- プロジェクト全体の目的・方針を定める原文と、今回の要求・範囲・限定理由を区別して渡す。根拠の所在・対象範囲を確認し、資料不足を整合済みにしない。
- 局所要求に合っていても、全体目的に必要な対象を落とす、方針と矛盾する、目的に見合わない負担を加える場合は指摘対象にする。
- 承認された段階的な限定は全体目的へのつながりと理由から評価する。全体目的との整合を、今回すべてを実装する義務や自動的なスコープ拡大へ変えない。
- 全体目的は要求担当の重点とするが、他担当から隠す情報ではない。根拠・成立性・敵対的の各担当も、その目的を共有し、担当範囲での矛盾を報告できるようにする。

後続の保持確認では、少なくとも「局所要求に一致するが全体方針に反する案」と「全体方針に沿う承認済みの限定案」を区別できるかを見る。今回の追記は既存ADRの再確認とユーザー指示の記録であり、追加モデル試験の承認ではない。
