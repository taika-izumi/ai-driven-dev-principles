## 指摘と採否

重複は1件へ集約した。採否の判断順は「前提と根拠 → 対応案 → 増設案の比較 → 採否と理由」。

### 採用1（Critical。担当2 C2 と担当3 Critical が独立に検出）

- **前提と根拠**: `credentialExposure` 検査は `inspect --json` の secrets に `mcpgateway` 以外が無いことを `verified` の要件にし、役割で分岐していない（`SbxRuntime.psm1` の当該行。委譲元が実体で再確認した）。いずれかの check が `failed` なら VM 作成は `blocked` で止まる（同関数の判定）。`activation-record.schema.json` は `credentialExposure` を全役割で必須としている。改訂前の ADR は決定3の対象を `policy` 検査だけとし、さらに決定4はこの検査を `credentialMethod` の証拠に使っていた。前提となる「グローバル保存したモデル資格情報が提案用VMの secrets に現れるか」は未確認だが、`mcpgateway`（製品が常設するグローバル管理の秘密）が現れる前例（ADR-0195）があるため、成立しうる経路として扱う。今回足した決定が生んだ問題であり、必要な修正にあたる。
- **対応案**: 決定3の対象へ `credentialExposure` を加え、提案用では「secrets に現れてよいのは `mcpgateway` とモデル資格情報のサービス名だけ」を要件にする。決定4の観測要件を同じ表現へ書き換える。
- **増設案の比較**: 新しい工程は足さない。既存の実行設定記録の検査を役割別にするだけで、不一致時に停止する動作は既存機構がそのまま担う。別経路の監視を新設する案は、同じ失敗を既存検査の修正で防げるため採らない。
- **採否**: 採用。改訂済み（決定3・決定4）。

### 採用2（Critical。担当2 C1 と担当1 指摘1 が同じ前提を指す）

- **前提と根拠**: 決定2の実現手段は「キット宣言の13ドメインが policy 層の allow 規則として現れ、作成時の拒否で絞れる」ことを前提にする。ブリーフ5.10 がこれを未確認と明記しているのに、改訂前の Context は「codex キットは既定で13ドメインを許可する」と確定事実として書いていた。shell キットの0件は実行ファイル内の試験コードが裏付けており、確度の異なる主張を同列に並べていた。
- **対応案**: Context を「確定した実測」と「宣言から読み取った事項（実行時の挙動は未確認）」に分け、当該記述を後者へ移す。決定6を新設し、実機の最初の提案用VMで実効許可・secrets・エージェント起動時点を確認し、想定と異なれば停止して利用者に諮る。
- **増設案の比較**: 決定6の確認は決定4の証拠取得と同じ操作（`policy ls` と `policy check` の対照、`inspect --json`）で取れるため、新しい観測工程は増えない。想定と異なるときに止める動作も既存の検査が担う。前提を確かめずに進めた場合の費用は、提案用VM 2台分の作成と証拠取得のやり直しであり、確認の費用（同じ出力を読む）を上回る。
- **採否**: 採用。改訂済み（Context の書き分け、決定6の新設）。

### 採用3（Important。担当1 指摘2）

- **前提と根拠**: グローバル保存の共有範囲は同一デーモン上の全サンドボックスであり（`secret --help` の原文）、改訂前の Consequences は「本サイクルで作るVM」という自プロジェクトの管理策だけを書いていた。利用者が別用途で openai を宣言するキットのサンドボックスを作った場合の露出が評価の外にあった。
- **対応案・増設案の比較**: 記述の修正のみ。新しい制御は足さない（APIキー方式へ戻せば範囲は絞れるが、それは利用者が選ばなかった案であり、ここで覆さない）。
- **採否**: 採用。改訂済み（Consequences 2項目め）。

### 採用4（Important。担当2 I1）

- **前提と根拠**: 拒否されたホストへの接続はTCP接続が成立したうえでデータが返らない形になる実測がある（`docs/reference/sbx-sandbox-runtime-facts.md`）。Issue-0148（無音の停滞を検知しない）と重なると、失敗が全体期限まで無反応として現れうる。担当2自身が「codex 側のタイムアウトは未確認のため必ず全体期限まで無反応になるとは断定できない」と留保を付けている。
- **対応案・増設案の比較**: 記述の追加のみ。停滞検知の新設は Issue-0148 として起票済みで、本サイクルでは実装しない判断が既にある。ここで例外を作らない。
- **採否**: 採用（記述として）。改訂済み（Consequences 3項目め）。

### 採用8（Important。担当3。初回の集約で対応表への記載が漏れていたもの）

- **前提と根拠**: 改訂前の決定5は診断手段を `policy log` の拒否記録に限定していた。`policy log` はネットワーク層の可否だけを記録するため（`docs/reference/sbx-sandbox-runtime-facts.md` の実測）、許可済みホストへの接続が成立したうえで認証・認可の層で失敗する種別（OAuthトークンの失効・権限不足など）は診断できない。OAuth方式は失効・再認可が起こりうる方式であり（`secret set --help`）、この障害は成立する。「拒否記録が無い＝許可は足りている」と誤診し、不要に許可を広げる方向へ誘導されるおそれがあった。
- **対応案・増設案の比較**: 決定5に限界と代替の切り分け手順を1文加える。新しい機構は足さない。
- **採否**: 採用。改訂済み（決定5の後段）。**この項目は初回の集約時に対応表へ書き漏れており、差分再確認（指摘#1）で「未追跡の追加」として検出された。** ADR 本文への反映は初回改訂時に済んでいたが、採否の根拠がここに無い状態だった。

### 判断が割れた点（記録）

担当1は「決定4と既存の `credentialExposure` 検査は整合的」と判定し、担当3・担当2は同じ箇所を Critical と判定した。差は「グローバル保存した秘密が `inspect --json` の secrets に現れるか」という未確認事実の扱いにあり、担当1はそれを暗黙に「現れない」と仮定していた。委譲元が実体（検査に役割分岐が無いこと、全役割で必須であること）を確認し、仮定を置かない側の判定を採った。
