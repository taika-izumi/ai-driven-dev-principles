# AI組織を用いた開発に利用する公式ツールの調査

- 確認日: 2026-09-08
- 目的: [開発ガイドライン整備のロードマップ](../current/development-roadmap.md)に先立ち、公式基盤を利用する範囲と独自に整備する範囲を判断する。
- 確認方法: OpenAI・Anthropicの公式文書を閲覧。製品の機能説明として信頼するが、この利用環境での動作実証・契約確認・課金実測は未実施。以下の推奨は調査からの判断である。

## 1. 結論

公式ツールを利用・組み込みできる。エージェントの起動、モデル呼び出し、担当への委譲を一から作る必要はない。ガイドライン側では、役割と判断の分担、終了基準、独立検査、記録の保存・読み戻しを定義し、公式機能で満たせない部分だけ接続コードを用意する案が適切である。

「組み込み」には、既存CLIやアプリに役割定義・スキルを読み込ませる方法と、SDK（プログラムから利用するためのライブラリ）で実行する方法がある。前者を先に試せる。プラグインを入れるだけで、既存ガイドラインの全工程・記録・権限が自動的に満たされるわけではない。

## 2. 公式機能と適合性

| 候補 | 公式資料で確認した機能 | 今回の位置づけ |
|---|---|---|
| Claude Codeのサブエージェント | 専門担当、個別の文脈、モデル・ツールの設定、プロジェクトやプラグインからの定義 | LoopForAlphaの既存環境に近い初回候補。取りまとめ・実装・検査の分業から試す。[公式資料](https://code.claude.com/docs/en/sub-agents) |
| Claude Code Agent teams | リーダーと担当者、共有タスク、担当者間の通信 | 相互通信が必要な場合の候補。実験機能で、担当者の再開、タスク状態、終了に制限がある。初回の必須条件にしない。[公式資料](https://code.claude.com/docs/en/agent-teams) |
| Claude Agent SDK | Claude Codeの実行をPython／TypeScriptから利用。サブエージェント、権限、フック、セッション等 | 結果回収・制御をプログラムへ組み込む必要が確認された場合の候補。[概要](https://code.claude.com/docs/en/agent-sdk/overview)、[サブエージェント](https://code.claude.com/docs/en/agent-sdk/subagents) |
| Codexのサブエージェント | 専門担当への分担と結果集約、カスタム担当のモデル・指示・設定 | 同じ役割と報告要件を別の基盤で試す候補。現行リリースは委譲要求または適用される指示に従って分担する。[公式資料](https://learn.chatgpt.com/docs/agent-configuration/subagents) |
| Codex SDK／App Server | SDKはローカルのスレッドの開始・継続・再開。App Serverは認証・承認・イベント等を扱うクライアント向けインターフェース | 自動実行はSDK、より細かなクライアント制御が必要ならApp Serverを比較する。[SDK](https://learn.chatgpt.com/docs/codex-sdk)、[App Server](https://learn.chatgpt.com/docs/app-server) |
| OpenAI Agents SDK | エージェント間の委譲や、エージェントをツールとして呼ぶ構成 | 独自の取りまとめ処理を必要とする段階の候補。Codexを実行するSDKとは役割が異なり、併用を最初から必須にしない。[公式資料](https://developers.openai.com/api/docs/guides/agents/orchestration) |
| Claude Managed Agents | 管理された実行基盤、永続セッション、複数エージェントの協調。ベータ提供 | ローカルの運用負担や長時間実行が障害になった場合に比較。データ・ツール・認証の移行費用があるため初回から移さない。[概要](https://platform.claude.com/docs/en/managed-agents/overview)、[協調実行](https://platform.claude.com/docs/en/managed-agents/multiagent-orchestration) |

前の会話で紹介した「Agents SDK＋Codex MCP server」の[公式サンプル](https://learn.chatgpt.com/docs/mcp-server)は、役割分担の参考にはなる。ただし現在のCodex SDK文書では `codex mcp-server` は非推奨である。新規の接続方式としてそのまま採用しない。

## 3. 公式機能とガイドラインの責任分担

| 必要なこと | 利用する基盤の役割 | ガイドライン・実証側で用意するもの |
|---|---|---|
| 分業 | エージェント起動・モデル選択・通信 | 担当範囲、入力資料、報告内容、兼務してよい範囲 |
| 検査の独立性 | 個別の文脈、アクセス制御の機能 | 承認済み要件からの検査、実装者の自己評価を初回に渡さない手順、検査対象の版の固定 |
| 完了と停止 | 実行イベント、停止機能、製品ごとの上限 | 成果物の合否とプロセス終了の区別、上限到達時の帰結、子処理を含む停止の確認 |
| 書き込みの保護 | サンドボックスや権限設定 | 保護対象の指定、実際の拒否の確認、作業コピーと実行権限の区別 |
| 記録 | 会話・イベント・利用量などの取得機能 | 仕様・ADR・課題・引き継ぎへの整理、証拠への参照、再開時の読み戻し |
| 失敗からの改善 | 失敗やツール結果の出力 | 手戻り・人の訂正の記録、原因の仮説と事実の区別、改善の採否 |

worktreeは作業コピーを分ける仕組みであり、それだけでツールやホームディレクトリへの書き込みを禁止できるとは扱わない。特にIssue-0136の対処は実行環境で確かめる。権限の要求を子へ渡すことと、その権限が実際に制限されることを分けて検証する。

## 4. 利用・配布に関する具体的な制限

Claude Codeではプロジェクトの `.claude/agents/` やプラグインの `agents/` に担当を定義できる。ただし公式資料では、プラグイン由来の担当定義の `hooks`・`mcpServers`・`permissionMode` は無視されるとされる。権限までプラグインだけで配布できるとは見積もらず、プロジェクト側設定との分担を確認する。[定義の配置と制限](https://code.claude.com/docs/en/sub-agents)

Codexの担当定義は `.codex/agents/` のTOML形式で例示されている。Claude用定義と同一ファイルをそのまま配布する構成にはしない。共通なのは役割の意味と報告要件であり、製品固有の設定形式は分ける。[Codexのカスタム担当](https://learn.chatgpt.com/docs/agent-configuration/subagents)

現行の `scripts/build-dist.ps1` は `skills/` を配布物へ変換する構成である。担当定義やSDK接続を自動配布できることは未確認なので、試行時は実証プロジェクトに置き、汎用化時に必要な配布変更を設計する。利用者には、初回の認証・必要な設定・利用枠確認と、更新後の動作確認を依頼する可能性がある。

Agent teamsの担当者はリーダーの権限設定を引き継ぐ。製品内の計画承認は、本ガイドラインで人に留保した設計判断の承認と同義ではない。SDKも含め、設定の読み込み元・プラグインの可視範囲・個別権限を実行ごとに確認する。[Agent teamsの権限](https://code.claude.com/docs/en/agent-teams)

SDK・管理基盤の認証や利用料金を、既存CLIの契約枠と同じと仮定しない。今回の調査では利用者の契約・鍵・残枠を調べていない。実行候補を絞った後に、その経路に必要な条件だけ確認する。[Claude Agent SDKの開始条件](https://code.claude.com/docs/en/agent-sdk/overview)

## 5. OpenAIとAnthropicを混在させる場合

同じ提供元の中で実装者と検査者のモデルを変えることと、ClaudeとCodexをまたいで分業することは異なる。後者について、今回確認した資料から、両製品のチームが設定だけで共通のタスク・権限・再開状態を共有するとは確認できない。

必要になった場合の構成案は、取りまとめ処理が両方の公式SDK等を呼び、対象版・役割・渡した資料・結果・証拠・実行状態を共通の報告へ変換する方法である。接続には認証、タイムアウト、キャンセル、費用集計、再実行の重複防止が必要となる。モデルの実行ループを作り直す必要はないが、この接続作業はゼロではない。

最初は同一提供元内の分業で成立を確認し、別提供元の利用は同等の作業を別実行で比較する。混在による独立検査の改善が追加負担を上回る見込みを得てから、同時運用を検討する。現行の確定前レビューが求める作成側と異なるモデルの利用は維持し、提供元まで異なることを一律の必須条件にはしない。

## 6. 実証開始時に確認する項目

バージョンと実際に読み込まれた設定、担当起動・結果回収、検査資料への到達、保護対象への書き込み拒否、中断時の子処理停止、保存記録からの再開を、小さな隔離対象で確認する。失敗・未確認は項目ごとに残し、機能の存在だけで合格にしない。

CLIと設定だけで満たせるならそこで止める。手動回収が繰り返し必要、停止・再開を外から制御できない等の不足が確認されたら、公式SDKや管理基盤を比較し、必要な接続だけ追加する。試行中に基盤を変更した場合は別の実行条件として記録する。

本調査は将来も更新する参照知識である。採用や接続実装の直前に該当する公式ページと利用版を再確認し、対応しない機能や変更された制限を更新する。
