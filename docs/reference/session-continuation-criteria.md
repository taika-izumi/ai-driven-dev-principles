# セッション継続/切替の判断基準（メモ）

- **Date**: 2026-07-11
- **出所**: 別プロジェクト（LoopForAlpha）で、ユーザーの「同じセッションで作業を続けていいのか毎回悩む」という問いにエージェント（Claude Fable 5）が回答した内容の記録
- **性質**: 開発フロー一般の知見。将来的にはガイドラインリポジトリ（ai-driven-dev-principles）への展開候補（organize-inbox での分類時に判断）

## 基本原則

長いセッションの主リスクは「古い中間状態の誤参照」（修正前のコード・旧設計・却下案がコンテキストに堆積し、新しい作業で混入する）と「コンテキスト要約による記憶の劣化」。一方、新セッションの立ち上げコストは、ハンドオフ・issue が整備されているフローでは小さい（文書を読み直す数万トークン程度）。**したがって迷ったら切る側に倒すのがデフォルト**。ただし切る前に「今の暗黙知が文書化済みか」を必ず確認する。

## 判断基準（上から順に評価）

1. **マイルストーン基準（最優先・定性的だが明確）**: サブプロジェクトのマージ・handoff finalize・retrospective 完了などの節目を跨ぐ「新しい種類の作業」は新セッション。同一タスクの継続・直前成果物の修正は同セッション
2. **文書化基準**: 新作業に必要な文脈が文書（handoff / issue / spec / ADR / 振り返り）に外部化済みなら新セッション向き。対話の暗黙文脈（直前の議論のニュアンス）に依存するなら、**先にその文脈を issue や inbox に書き出してから**切る
3. **要約発生基準（定量的シグナル）**: セッション中にコンテキストの要約・圧縮が挟まった後は、原文の正確な把握が必要な精密作業（既存ファイルの編集・レビュー）は新セッションが安全。要約後の記憶は原文より劣化している
4. **中間状態の堆積基準**: そのセッションで「今はもう正しくない状態」（大きな設計変更前の版、複数回の修正を経たファイル）を何度も扱ったか。新作業がそれらと紛らわしい領域なら切る
5. **コスト基準（定量的）**: 継続する場合、以降の全ターンが蓄積コンテキストの再読み込みコストを払い続ける。「引き継ぎ文書を書くコスト < 継続の累積コスト + 誤参照リスク」なら切る。ハンドオフ常備のフローでは左辺が恒常的に小さい

## 運用の型

- 節目（マージ・retrospective 後）に「次の作業は新しい種類か?」を自問 → Yes なら handoff の「次セッション開始時のアクション」を埋めて終了、新セッションで start-work
- 切替前チェック: (a) handoff の次アクションが具体的か (b) 進行中の論点が issue / inbox に外部化されているか (c) 未コミットの成果物がないか
