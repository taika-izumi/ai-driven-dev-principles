# 作業ログのエントリフォーマット設計意図（worklog パイプライン紹介用）

- **対象読者**: worklog スキル群（worklog-record / worklog-extract / worklog-skillify）をこれから使う人・導入を検討する人
- **目的**: 「何を記録するのか」「なぜこのフォーマットなのか」「なぜこの項目が必要で、なぜ候補に挙がった他の項目・方式は不採用になったのか」を、設計議論を追わなくても理解できるように説明する
- **正典**: フォーマット仕様そのものは `skills/worklog-record/references/store-format.md` が正。本書は設計理由の解説
- **設計記録**: ADR-0044（アーキテクチャ）/ ADR-0045（スキーマ・ライフサイクル）

---

## 1. この仕組みが解きたい問題

AI エージェントに作業をさせると、「AI が自力ではできなかったこと」「人間が毎回口頭で注入している指示」が日々発生する。これらは本来スキルやルールに昇華すれば再利用できるノウハウだが、セッションが終わると消えてしまい、複数プロジェクトに散らばると誰も全体像を把握できない。

そこで、**作業の節目ごとに小さな構造化ログを 1 件書き溜めておき（worklog-record）、あとから横断的に走査してスキル化候補を抽出する（worklog-extract）** という 2 段構えにした。エントリフォーマットは「あとから機械走査で価値判定できる最小限の記録」として設計されている。

## 2. 核心原理: 記録すべきは「delta」である

### なぜ「作業内容を全部記録する」ではないのか

最初の素朴な発想は「AI にやらせた作業内容・判断・手順を記録する」だった。しかしこれでは記録が肥大するうえ、大半は記録する価値がない。**AI が自律判断で毎回同じように再現できる作業は、記録してもスキル化する意味がない**（すでに AI ができるのだから）。

スキル化する価値があるのは、**「AI がデフォルトでやること」と「実際に必要だったこと」の差分**だけである。この差分を **delta** と呼び、記録の核心に据えた。

### delta の 2 つの発生源

| 型 | フィールド | 中身 | スキル化したときの姿 |
|---|---|---|---|
| **躓き型** | `friction` | エラー・手戻り・非自明な試行錯誤 | 落とし穴の回避手順（「この操作はこの順でやらないと失敗する」） |
| **注入型** | `corrections` | 人間が与えた指示・修正・好み | 規約・作法のルール化（「毎回口頭で言っていることを書面化して再注入を不要にする」） |

**この 2 つの少なくとも一方が存在することを記録の必須条件（記録ゲート）にした**。両方が空＝AI が自律で完遂できた作業＝記録不要、として構造的に弾く。「スキル化する価値があるか」という曖昧な判断を、「delta が存在するか」という機械的に検証できる条件に落とし込んだのがこの設計の要点である。

### 見落とされがちな注入型の価値

躓き型（エラーや手戻り）は目立つので気づきやすい。しかし実は注入型のほうが取りこぼしやすく、価値が高いことが多い。「分類は flow と system で分けて」「README には 1 行インデックスだけ足して」のような人間の修正発言は、その人の頭の中にしかない規約の注入であり、**AI が自力では推測できない**。この発言をそのまま記録しておけば、それがほぼそのままスキルやルールの原文になる。`corrections` を「発言に近い形で 1〜2 行」と規定しているのはこのためである。

## 3. 最終フォーマット

形式は JSONL（1 行 1 エントリ、追記専用）。

### 必須フィールド（いずれか空なら記録を弾く）

| フィールド | 型 | なぜ必須か |
|---|---|---|
| `id` | string | `<プロジェクト名>-<日付>-<連番>`。処理済み台帳（processed.jsonl）との突合キー。これがないと「この記録はもうスキル化検討済みか」を機械判定できず、抽出のたびに全件を再分析・再提案してしまう |
| `date` | string | 抽出時の時系列・頻度分析の基礎。「最近も再発しているか」の判定に使う |
| `project` | string | 出所プロジェクト名。複数プロジェクトのログを連結して 1 パス走査する設計のため、**行単体で出所が分かる**必要がある（ファイルパスに頼ると連結した瞬間に出所が消える） |
| `scope` | enum | `project-specific` / `general-candidate`。記録時点の暫定タグ。抽出側が「複数プロジェクトで再発→汎用に格上げ」の最終判定をするための出発点 |
| `title` | string | 動詞句 15 文字程度。候補リストの一覧表示・人間の重複目視用。自由長の `context` とは役割が別（一覧性のために書式を縛っている） |
| `context` | string | 何をしていて、なぜこの作業が発生したか。delta だけあっても状況が分からないと、抽出側が「これは汎用パターンか、この場限りか」を判定できない |
| `procedure` | string[] | 実際に踏んだ手順。**スキル本体の種**になる（スキル化するとき、手順がそのまま下書きになる）。文字列配列にしたのは、JSONL 1 行のまま手順の構造を保持して可読性を確保するため |

### delta ペア（少なくとも一方が必須）

| フィールド | 型 | 役割 |
|---|---|---|
| `friction` | string | 躓き型 delta（前述） |
| `corrections` | string[] | 注入型 delta（前述）。複数の指示を個別に保持するため配列 |

### 任意フィールド（空でよい。あれば抽出精度が上がる）

| フィールド | 型 | なぜ任意で十分か |
|---|---|---|
| `skillification_hint` | string | 「なぜスキル化価値があるか」の記録者の仮説。抽出側は friction / corrections から価値を再導出できるため必須ではない。あれば判断の補助になる |
| `outcome` | enum | `success` / `partial` / `failed`（作業の結果）。failed の手順をそのままスキル化すると事故るため、抽出側のフィルタに使う。failed はアンチパターン集の種として別の価値を持つ |
| `tools` | string[] | 使ったツール・コマンド。「このツール操作が頻出している」という機械的クラスタリングの補助 |
| `applied_rules` | string[] | 適用した明示ルール（ADR・CLAUDE.md 等）。逸脱注記（例: `"ADR-0033 (逸脱)"`）も書ける。将来「既存ルールの改訂候補発見」に使うためのデータを安いコストで貯めておく保険 |
| `refs` | string[] | 関連 ADR・コミット・ファイルパス。追跡可能性の確保 |

### 具体例

```jsonl
{"id":"MakeAiInstructions-2026-07-16-01","date":"2026-07-16","project":"MakeAiInstructions","scope":"general-candidate","title":"未追跡ファイルのパス指定コミット回避","context":"handoff更新をコミットしようとしたが対象が未追跡でgit commit -Fにパス指定して失敗","procedure":["git add <file> で先にステージ","git commit -F <msgfile> でメッセージ渡し"],"friction":"未追跡ファイルへ直接パス指定コミットが不可でエラー。原因特定に試行錯誤","outcome":"success","tools":["git"]}
{"id":"MakeAiInstructions-2026-07-16-02","date":"2026-07-16","project":"MakeAiInstructions","scope":"general-candidate","title":"走り書きメモを規約付きで分類整理","context":"複数の走り書きファイルを人間の分類方針に従って整理させたかった。躓きは無い","procedure":["ファイル群を内容で分類","指定された分類軸でフォルダへ振り分け"],"corrections":["分類はflowとsystemで分けて","READMEには1行インデックスだけ足して"],"outcome":"success","skillification_hint":"AIが自力では推測できない分類規約を毎回注入している。規約化すれば再注入不要"}
```

1 件目は躓き型のみ、2 件目は **friction が空でも corrections があるので記録が成立**する例。注入型を取りこぼさないことがフォーマットの意図に組み込まれている。

## 4. 検討して不採用にしたもの（と、その理由）

設計の納得感には「なぜ採用したか」と同じくらい「なぜ採用しなかったか」が効く。主要な不採用判断を挙げる。

### 4.1 純粋判断型エントリ（friction も corrections も無く hint だけ）→ 弾く

「これはスキル化できそう」という直感（hint）だけのエントリも許す案があった。不採用。delta の裏付けがない候補は**最も弱い候補**であり、抽出時のノイズになる。hint は任意フィールドに降格し、delta の存在を必須ゲートにした。

### 4.2 「頻発するものだけ記録する」ゲート → 撤回

初期案には「頻発する作業か」を記録時の条件にする発想があった。これは前提誤りとして撤回。**記録時点では頻発かどうか分からない**（頻度は複数プロジェクト・複数時点を横断して初めて分かる）。頻度判定は抽出側（worklog-extract）の責務とし、記録側は「delta があるか」だけを見る。頻度は抽出時もハード閾値にせず、人間が採否判断するときのソフトな材料にとどめている。

### 4.3 タスクごとの継続的インラインログ → 節目 1 回のコンパクト追記

作業中に細かくログを取り続ける案は不採用。記録コストが作業を圧迫し、ノイズだらけの大量ログは後段の分析コストも爆発させる。**作業の節目（スキル完了・計画タスク完了・重要な分岐通過）で 1 回、各フィールド原則 1〜2 行のコンパクトなエントリを追記**する方式にした。記録は full context を持つメインエージェント本人が書く（後から別プロセスが復元するより正確で安い）。

### 4.4 人間可読な整形 JSON → JSONL

読みやすさのために整形 JSON（複数行・インデント付き）にする案は不採用。この仕組みの根幹は「**複数プロジェクトのログファイルを単純連結して 1 パスで機械走査できる**」ことにあり、1 行 1 エントリの JSONL が最適。人間可読性は書き込み形式ではなく表示側の問題（jq 等で整形して見る）として切り離した。

### 4.5 scope をフォルダで物理分離 → エントリ内のタグ

「汎用候補は共通フォルダ、プロジェクト固有はプロジェクトフォルダ」と物理的に分ける案（保存レイアウトの対抗案）は不採用。記録時の scope 判断は**暫定**であり、物理配置で固定すると誤分類の修正がファイル移動になり高くつく。タグ方式なら誤分類はタグの読み替えで済み、横断分析も project フィールドで group-by するだけでよい。フォルダ分割は「出所プロジェクト」という安定した属性にのみ使う。

### 4.6 ライフサイクル対策なし（記録しっぱなし）→ 処理済み台帳の導入

エントリフォーマット自体には現れないが、運用面で重要な不採用判断。記録しっぱなしだと (1) ログが積み上がるほど抽出の分析が重くなる、(2) すでにスキル化済みの記録から同じ候補を再提案してしまう。対策として**追記専用の処理済み台帳（processed.jsonl）**を導入し、エントリに台帳との突合キー（`id`）を必須化した。抽出済み・却下済み・保留の別を台帳に記録し、抽出側は未処理エントリだけを分析する（分析コストが未処理件数でスケールする）。

- 保留（deferred）を却下と同じ完全除外にする案も不採用: 保留が事実上忘れられてしまう。保留時点の根拠件数を記録し、**新しい該当エントリが増えたときだけ再浮上**させる方式にした
- 採用済みだが未スキル化の状態（adopted）を台帳に残さない案も不採用: 採用からスキル化完了までの間に中断が挟まると、次回抽出で採用済み候補が再提案される穴があるため、採用時に即台帳記録する

### 4.7 アーカイブ機構・git 管理・強いプロジェクト識別子 → v1 では作らない

物理ファイル肥大時のアーカイブ退避、ログの git 管理、git remote URL による強いプロジェクト識別はいずれも「必要になってから作る」（YAGNI）として初版から除外。プロジェクト識別はフォルダ名＋パス存在チェックの自己修復方式で開始している。

## 5. まとめ: フォーマットが体現している設計判断

1. **記録の価値基準を「delta の存在」という検証可能な条件に落とした**。曖昧な「価値があるか」判断を記録者に委ねない
2. **記録は安く、分析は後で**。記録時はコンパクトな 1 エントリ、頻度・重複・汎用性の重い判定は抽出時に遅延する
3. **機械走査可能性を最優先**（JSONL・行内に出所・突合キー）。可読性・分類の柔軟性はそれぞれ表示側・タグに逃がす
4. **人間の発言を原文に近い形で残す**。注入型 delta はスキル・ルールの原文素材だから
5. **判断の暫定性を認める設計**。scope は暫定タグ・hint は仮説扱いで、最終判定は横断視点を持つ抽出側と人間に委ねる
