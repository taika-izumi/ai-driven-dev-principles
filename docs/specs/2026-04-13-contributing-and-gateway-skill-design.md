# CONTRIBUTING.md & extend-guidelines Skill 設計仕様

**日付:** 2026-04-13
**ステータス:** 承認済み

## 課題

新しいセッションのAIエージェントは、会話履歴がないため、このリポジトリの設計思想・拡張ルールを把握できない。README.mdの「成長サイクル」の記述だけでは抽象的すぎて、適切な拡張判断ができない。

## 提案するアプローチ

**シナリオ駆動型CONTRIBUTING.md + ゲートウェイSkill** の2層構成で解決する。

- **CONTRIBUTING.md** — 設計思想と拡張ルールの単一ソース（Single Source of Truth）
- **extend-guidelines Skill** — ゲートウェイとして CONTRIBUTING.md を読み込み、brainstorming skill へ自動接続

## 成果物

### 1. CONTRIBUTING.md

**配置:** リポジトリルート
**言語:** 日本語
**主な読者:** AIエージェント（指示調で記述）
**構成:** シナリオ駆動型（やりたいことベースで逆引き）

#### セクション構成

**セクション1: 設計思想（15-20行）**

冒頭に配置。エージェントが最初に全体像を掴むための要約。

- リポジトリの目的：AIエージェント開発のメタ・ガイドラインを管理
- 3層アーキテクチャの概要と各層の役割
  - Layer 1: `docs/principles.md` — ツール非依存の普遍的原則
  - Layer 2: `.github/copilot-instructions.md` — Copilot固有の行動指示
  - Layer 3: `skills/` — 自動化されたワークフロー
- 核心的な設計原則：
  - **各層は独立して拡張可能** — 原則を追加しても即座に全層反映は不要
  - **リスクスケーリング** — 原則1-3は常時適用、4-5はリスクに応じてスケール
  - **具体性の勾配** — Layer 1は抽象的・汎用的、Layer 3は具体的・自動化
- 「拡張したい場合は以下のシナリオから該当するものを読め」と誘導

**セクション2: 原則を追加・変更するとき**

判定基準:
- 複数プロジェクトで繰り返し同じ失敗/成功パターンが観察されたとき
- 既存の5原則でカバーできない新しい関心事があるとき
- 「ルール」ではなく「なぜそうすべきか」を説明できる抽象度があること

手順:
1. ADRを作成して追加理由を記録（decision-log skill使用）
2. `docs/principles.md` に原則を追加
3. 前文のリスクスケーリング注記を更新する必要があるか確認
4. 必要に応じてLayer 2・3への反映を検討（即座の全層対応は不要）

チェックリスト:
- 既存原則と重複・矛盾していないか
- ツール非依存の表現になっているか（Layer 1の要件）
- リスクスケーリングの分類（常時適用 or リスク比例）を決めたか

**セクション3: copilot-instructions.md を更新するとき**

レイヤー対応規則:
- Layer 2はLayer 1の原則をCopilot固有の行動指示に変換したもの
- 各原則 → copilot-instructions.md の対応セクションへ1:1マッピング
- 新原則追加時は対応セクションの追加を検討

判定基準（何をここに書くか）:
- セッション横断で常に適用したい行動規範
- Copilot特有の設定（言語、応答スタイル等）
- Skill化するほど複雑ではないが毎回伝えたい指示

注意事項:
- **他プロジェクトへの流用前提**で書く — プロジェクト固有の参照（ファイルパス等）を含めない
- カテゴリ構成（システム設定 / メタ・ガイドライン）を維持
- 記述言語は日本語で統一（plugin注入部分は除く）

**セクション4: Skillを新規作成するとき**

Skill化の判定表:

| 観点 | copilot-instructions.md に書く | Skill にする |
|---|---|---|
| 複雑さ | 数行で表現できる | 手順・分岐・テンプレートがある |
| 発動条件 | 常時適用 | 特定の状況でのみ必要 |
| 自律性 | 判断基準の提示 | ワークフローの自動化 |
| 例 | 「変更前にログを残せ」 | ADR作成の完全な手順とテンプレート |

手順:
1. 判定表でSkill化が適切か確認
2. `skills/<skill-name>/SKILL.md` を作成（YAMLフロントマター + markdown本文）
3. 対応する原則との紐付けをSkill内に記載
4. ADRで作成理由を記録

チェックリスト:
- copilot-instructions.md の記述で十分ではないか（YAGNI確認）
- Skill名が動作を端的に表しているか
- YAML frontmatter（name, description）が正しいか
- 対応する原則への参照があるか

**セクション5: ADRを記録するとき**

判定基準:
- 原則の追加・変更・削除
- アーキテクチャ（層構成）に影響する変更
- 既存方針を覆す判断をしたとき
- 複数選択肢を検討し、選択理由を残す価値があるとき

手順: decision-log skill に従う（Skillへの参照のみ、手順の重複を避ける）

### 2. skills/extend-guidelines/SKILL.md

**ゲートウェイSkill** — ガイドラインの拡張作業を自動的にガイドする。

YAML frontmatter:
- name: extend-guidelines
- description: ガイドラインの拡張（原則追加・Skill作成・copilot-instructions更新）を行う際のゲートウェイ

フロー:
1. `CONTRIBUTING.md` を読み込み、設計思想と拡張ルールを把握する
2. ユーザーに「何を拡張したいか」をヒアリング（選択肢提示）
   - 原則を追加・変更したい
   - copilot-instructions.md を更新したい
   - 新しいSkillを作成したい
   - その他
3. 該当シナリオのガイダンスをCONTRIBUTING.mdの内容から確認
4. brainstorming skill を呼び出し、具体的な追加内容の設計→実装フローへ接続

Skill本文に含める指示:
- CONTRIBUTING.md を最初に読むこと（ファイルパス明記）
- シナリオ選択のための質問テンプレート
- brainstorming skill への遷移指示
- 「CONTRIBUTING.md が見つからない場合はユーザーに報告する」フォールバック

### 3. README.md 更新

- CONTRIBUTING.md へのリンクを追加（既存の構成に自然に組み込む）
- 「AIエージェントに読ませてください」の記述は不要（ゲートウェイSkillが解決）

## 設計判断

- **シナリオ駆動型を採用** — AIエージェントが「何をしたいか」から逆引きしやすい（リファレンス型、判定ツリー型と比較検討）
- **1つの汎用ゲートウェイSkill** — エントリポイントを1つにすることで発見性を最大化（シナリオ別複数Skillと比較検討）
- **CONTRIBUTING.md参照方式** — DRY原則に従い、情報の二重管理を回避（Skill内埋め込み方式と比較検討）
- **copilot-instructions.md には参照を追加しない** — 他プロジェクトへの流用性を維持
