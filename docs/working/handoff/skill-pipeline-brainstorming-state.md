## 1. この作業の位置づけ

- 起点: `start-work` → セッション継続チェック（前回 handoff は `ready-for-next-cycle`）→ ユーザーが「対話モードのガイドライン拡張（スキル新規作成）」を希望
- 事前確認済み: **対話モードのガイドライン拡張は ADR-0043 と矛盾しない**。ADR-0043 の「無変更維持／何も追加しない」は *ループ対応の改修* に限定された凍結であり、対話モードの改善（既存バックログ含む）はむしろ「現行体系を対話モード専用として現役継続」と整合する。守る境界: ①ループ対応の改修はしない ②2プロファイル構成の設計・実装は始めない ③Layer 1（5原則）を触るときは注意（Layer 2/3 の対話向け拡張が安全）
- フロー: `extend-guidelines`（CONTRIBUTING.md 読了・「Skillを新規作成するとき」シナリオに合致）→ `brainstorming` に入り、現在ここ

## 2. 作りたいもの（ユーザーの要望）

相互に連なる3スキルのパイプライン:

1. **スキル1（記録）**: AI に作業させた後、その作業内容・判断・手順を構造化した「作業ログ」として蓄積する
2. **スキル2（候補抽出）**: 蓄積された作業ログを走査し、スキル化・ルール化する価値のある作業手順やルールの候補をリストアップする
3. **スキル3（スキル化）**: スキル2で選んだ候補から、新規スキル作成または既存スキル拡張を行う

## 3. 確定した決定（ユーザー承認済み）

### D1. スキル3の委譲エンジン選定 ✅ 承認済み
- 比較対象は Anthropic **公式** の Skill Creator（`anthropics/skills`。ローカルにも `claude-plugins-official` プラグインとして導入済み）と superpowers の `writing-skills`
- **既定エンジン = `writing-skills`**（superpowers エコシステム内・TDD/規律思想が本repoのADR/検証文化と一致・軽量・日本語doc運用に馴染む・description規約が既存スキル群と同じ）
- **Skill Creator の「description 自動最適化」「定量 eval ループ」は writing-skills に無い固有の強み → オプション部品として借用**（トリガー精度が重要なスキルを作るとき）
- **スキル3自体は薄いオーケストレーション層**（候補コンテキストを集め、職人技は下位エンジンへ委譲し、本repo規約=CONTRIBUTING.md「Skill新規作成」チェックリスト・ADR記録・READMEスキル一覧更新・sync-template.ps1 の充足を保証する）。既存 `extend-guidelines` への橋渡しで済む可能性も要検討（YAGNI 論点）

### D2. スキル1は新規作成する ✅ 確定
- 既存 retrospective は「課題抽出・改善ポイント特定」には有用だが、「頻発する/重要な作業手順・ルールの抽出・活用」には上手く使えていない、というユーザー実感。別レンズの別スキルが要る

### D3. スキル1の記録方式 ✅ ユーザーが選択（案1）
- **既存 handoff マイルストーンと同じ節目**（スキル完了・plan 1タスク完了・重要分岐通過など）で、**コンパクトな構造化エントリを1回追記**
- **メインエージェント本人が書く**（full context を持つので正確）
- タスクごとの継続的インラインログはしない（トークン増・メイン作業の精度低下の懸念に対応）
- **横断的な重い分析（複数作業を跨いだパターン発見・頻度判定）はスキル1では一切やらず、スキル2へ全面遅延**

### D4. 記録ゲートの考え方 ✅ ユーザーが前提を訂正・合意
- **「頻発／重要」の判定はスキル2の仕事**。スキル1は複数プロジェクトの様々な場所でログを書くため、記録時点では1プロジェクト/1セッションしか見えず横断頻度は判断不能。頻度はスキル2が**集約後のコーパス全体**で判定する
- 記録時のゲートは「頻発か」ではなく「**スキル化する価値があるか**」。次の両方を満たすとき記録する:
  - (a) 既存スキルで既に実施している作業では**ない**
  - (b) AIが自律判断でも毎回同じやり方で確実に再現できる作業では**ない**（＝標準化・知識固定の価値がある。手戻り・明示ルール適用・非自明な試行錯誤を伴ったもの）
- ※ ブレスト中に一度「頻度で記録を絞る」案（旧・質問3の案1）を出したが、前提誤りとして**撤回済み**

## 4. 新たに判明した重要な制約

- **複数プロジェクト横断で使う**。「様々な場所からログを収集する予定」（ユーザー発言）
- パイプラインの**出口（想定・未確認）**: スキル化されたものは、このメタ・ガイドラインrepo（`ai-driven-dev-principles`）の**プラグイン配信スキル**として作られ、全プロジェクトへ配布し戻される循環。ただし writing-skills の指針どおり **プロジェクト固有の規約はスキル化せず、そのプロジェクトの CLAUDE.md へ振り分ける**。← この出口像は**ユーザー未確認**（再開時に確認する）

## ■ 再開ポイント（次に AI が発すべき質問）

前提（第3〜4章）が合っているかを一言確認したうえで、以下の未回答質問を再提示する:

**質問（集約アーキテクチャ）: 各プロジェクトのログはどこに書き、スキル2はどこから集めるか？**

- **案1（推奨）**: 各プロジェクトのローカルに書き（例: `docs/records/work-log/`）、スキル2実行時にユーザー指定の複数プロジェクトのログ置き場を横断して収集・分析。「様々な場所から収集」に最も合致し、中央パス結合を避けられ、各プロジェクトが自己完結
- **案2**: 中央共有ストア（固定パス）に全プロジェクトが追記し、スキル2はそこ1箇所を読む。集約は単純だが共有書き込みパスの前提とパス結合が必要
- **案3**: 各プロジェクトでスキル2を回して部分結果を出し後でマージ。分散的だが手間増

**あわせて確認**: 第4章の「出口像」（候補→本repoのプラグイン配信スキル／プロジェクト固有→そのCLAUDEmd）で合っているか。
