## 1. この作業の位置づけ

- 起点: `start-work` → セッション継続チェック → ユーザーが「対話モードのガイドライン拡張（スキル新規作成）」を希望
- 事前確認済み: **対話モードのガイドライン拡張は ADR-0043 と矛盾しない**。ADR-0043 の凍結は *ループ対応の改修* に限定。守る境界: ①ループ対応の改修はしない ②2プロファイル構成の設計・実装は始めない ③Layer 1（5原則）を触るときは注意
- フロー: `extend-guidelines`（CONTRIBUTING.md 読了）→ `brainstorming` に入り、現在ここ

## 2. 作りたいもの（ユーザーの要望）

相互に連なる3スキルのパイプライン:

1. **スキル1（記録）**: AI に作業させた後、その作業内容・判断・手順を構造化した「作業ログ」として蓄積する
2. **スキル2（候補抽出）**: 蓄積された作業ログを走査し、スキル化・ルール化する価値のある候補をリストアップする
3. **スキル3（スキル化）**: スキル2で選んだ候補から、新規スキル作成または既存スキル拡張を行う

## 3. 確定した決定（ユーザー承認済み）

### D1. スキル3の委譲エンジン選定 ✅
- **既定エンジン = `writing-skills`**（superpowers エコシステム内・TDD/規律思想が本repoのADR/検証文化と一致・軽量・日本語doc運用に馴染む）
- Skill Creator の「description 自動最適化」「定量 eval ループ」は writing-skills に無い固有の強み → **オプション部品として借用**
- スキル3自体は**薄いオーケストレーション層**（候補コンテキスト収集＋本repo規約充足の保証。既存 `extend-guidelines` への橋渡しで済む可能性も要検討＝論点5）

### D2. スキル1は新規作成する ✅
- 既存 retrospective は「課題抽出」には有用だが「頻発/重要な作業手順・ルールの抽出」には使えていない、というユーザー実感。別レンズの別スキルが要る

### D3. スキル1の記録方式 ✅
- **既存 handoff マイルストーンと同じ節目**で、**コンパクトな構造化エントリを1回追記**
- **メインエージェント本人が書く**（full context を持つ）
- タスクごとの継続的インラインログはしない
- 横断的な重い分析（複数作業跨ぎのパターン発見・頻度判定）はスキル1では**やらず、スキル2へ遅延**（※ D6 で境界を精緻化）

### D4. 記録ゲート ✅
- 記録時のゲートは「スキル化する価値があるか」＝ (a) 既存スキルで既に実施している作業では**ない** かつ (b) AIが自律判断でも毎回同じに確実に再現できる作業では**ない**
- 「頻発か」で絞る案は前提誤りとして撤回済み

### D5. 出口像＝スコープによる振り分け（3分岐） ✅ 【新規・本セッション＝暗黙合意】
- ※ ユーザーの明示承認発話はなし。ユーザーは「出口像を修正したい」＋トリガー誤爆の懸念を提起し、AI の本3分岐がその回答。ユーザーは反対せず後続（D6/D7）が全面的に前提化した＝暗黙合意。撤回されていない
- スキル2が候補を分類、スキル3が振り分け先を決める:
  - **汎用**（複数プロジェクトで再現・ドメイン非依存）→ **本 repo のプラグイン配信スキル**（全プロジェクトへ配布）
  - **プロジェクト固有だがスキル化の価値あり** → **そのプロジェクトのローカルスキル**（`.claude/skills/`）
  - **固有ルールでスキル化不要** → そのプロジェクトの **CLAUDE.md**
- 根拠: スキルのトリガー（description）は**インストールされたスコープ内でのみ評価される**。固有スキルをプロジェクトローカルに留めれば、他プロジェクトのトリガー誤爆が構造的に起きない。「誤爆回避」の負担をインストール先スコープが肩代わりする

### D6. スコープ分類は「記録時」に行う（スキル1/2 の境界を精緻化） ✅ 【新規・本セッション確定】
- **スキル1（記録時）**: 各エントリに **scope タグ**（`project-specific` / `general-candidate`）を付ける。記録時点のメインエージェントはドメイン固有か汎用型かを判断できる
- **スキル2（横断分析）**: 依然として (a) 複数プロジェクト横断の**再発頻度**検出、(b) 既存スキルとの**重複排除**、(c) 優先順位付け、(d) 候補リスト提示 を担う。record 時タグは**暫定ヒント**で、スキル2が横断視点で `project-specific`↔`general` を最終確定（格上げ/格下げ）できる
- D3 の「重い横断分析はスキル2」は保たれる（頻度・重複判定は依然スキル2）

### D7. 保存先＝中央・安定・プロジェクト分割・scope はタグ（案X） ✅ 【新規・本セッション確定】
- **中央のユーザーレベル固定ルート**に集約（各プロジェクト repo の外。folder-structure.md の5分類の管轄外＝後で明示が要る）
- **プロジェクト単位でフォルダ分割**（出所属性）。scope は**フォルダで物理分離せず、エントリ内のタグ（フィールド）**で持つ（案X）
- 案Y（汎用=共通フォルダ / 固有=プロジェクトフォルダの物理分離）は不採用。理由: 暫定分類が物理配置を固定し、誤分類時の移動コスト・横断再発検出の全走査が残る。タグ方式なら誤分類はタグ書き換えで安く直せ、横断再発は project で group-by するだけ
- スキル2の収集: 固定ルート1ツリーを走査（ルート一覧の維持不要）

### D8. プロジェクト識別子スキーム ✅ 【新規・本セッション確定】
- **フォルダ名 = 各プロジェクトのルートフォルダ名**（実パスは長すぎるので使わない）
- 集約ルートに**リスト（`projects.<ext>`）**を置き、`フォルダ名 → 現在の絶対パス`（＋任意で最終更新日）を記録
- **ルール1（upsert 自己修復）**: リストは毎回の記録時に「フォルダ名をキーに実パスを最新へ更新」。フォルダ名が同じなら、プロジェクトを丸ごと移動しても次回記録時にパスが自動修正される
- **ルール2（衝突判定）**: フォルダ名がリストにあり実パスが違う場合、**旧パスがまだ存在→別プロジェクト同名**（サフィックス付き別フォルダ＋リスト追加）、**旧パスが消失→同一プロジェクト移動**（パス更新）
- リスト中身は最小限（フォルダ名→実パス）で開始。git remote URL 等の強い識別子は将来拡張（リモート未プッシュのプロジェクトもあるためパス存在チェックを基本機構にする。YAGNI）

### D9. スキル1のエントリ・スキーマ ✅ 【新規・本セッション確定】
- **核心原理**: スキル2が見たい信号は **delta**＝「AIがデフォルトでやること」と「実際に必要だったこと」の差分。発生源は2種類＝**躓き型（friction）** と **注入型（corrections＝人間が注入した指示・修正）**。少なくとも一方の存在が「スキル化価値（D4(b)）」の構造的実装
- **必須**（空だと弾く）: `date` / `project`（連結後も出所が残る行内属性）/ `scope` / `title`（動詞句15字程度）/ `context` / `procedure`（string[]）、**かつ `friction`（string）または `corrections`（string[]）の少なくとも一方**
- **任意**: `skillification_hint`（主張・スキル2が再導出可）/ `outcome`（success/partial/failed。failedはアンチパターン種）/ `tools`（string[]）/ `applied_rules`（string[]。逸脱注記可）/ `refs`（string[]）
- **形式**: JSONL（連結1パス走査が根幹。可読性は表示側 jq の問題として分離）
- **純粋判断型**（friction・corrections 無しで hint のみ）は弾く（最弱候補・ノイズ防止）
- 詳細・具体例・根拠: `docs/working/skill1-entry-schema-strawman.md`（確定版）

### D10. retrospective との overlap 対応＝Issue 起票先行・統合バックログで重複排除 ✅ 【新規・本セッション確定】
- 役割線引き: **retrospective**＝サイクル終端・本 repo 自身のフロー改善・人間5観点。**skill-pipeline**＝継続的・全プロジェクト横断・再利用ノウハウのスキル化
- **skill2 の本 repo 向け汎用候補も、スキルを直接作らず Issue 草案として `docs/working/issues/` に起票**。retrospective も既に全課題を同所へ起票（ADR-0028）。**重複排除は Issue 起票時にバックログ1箇所で**（唯一の合流点＝dedup ゲート）
- 訂正メモ: 他プロジェクトの失敗は「各プロジェクトで起票→本 repo へ手動移行」の経路が定義済みだが、面倒で未使用。skill1 の中央集約はこの手動移行を低摩擦で自動化し得る位置にいる（将来 v2）

### D11. skill3（汎用パス）は既存フローへの橋渡し ✅ 【新規・本セッション確定】
- 汎用候補向けの skill3 は独立の重いスキルにせず、既存「**Issue → extend-guidelines → スキル作成**」フローへの橋渡しで足りる（D1 の薄いオーケストレーション層がさらに薄く。YAGNI）。skill2 の出力＝**Issue 草案**という具体形も定まった（論点5 が前進）

### D12. 逸脱注記はデータのみ・skill2 出力3 は v2 延期 ✅ 【新規・本セッション確定】
- `applied_rules` の逸脱注記（例 `"ADR-0033 (逸脱)"`）は**データとして捕捉**する（安い保険）
- skill2 の**出力3（既存ルール・スキルの改訂候補発見）は v1 で作らない・v2 の明示拡張**。理由は「retrospective と重複だから」ではなく「コア目的＝スキル化とは別関心で v1 スコープを絞る」。データは貯まるので v2 でいつでも作れる

### D13. 中央ストアの保存レイアウト ✅ 【新規・本セッション確定】
- ルート: **`<ホーム>/.ai-dev-worklog/`**（ツール中立名。`~/.claude/` は Claude Code 固有なので避ける。実装側で `$HOME`/`%USERPROFILE%` 解決）
- リスト: **`projects.json`**（JSON オブジェクト `{ "<folderName>": { "path": ..., "lastSeen": ... } }`。upsert が全体読み書きで容易）
- ログ: **各プロジェクト `<folderName>/log.jsonl` に追記専用1本**（節目1回追記に素直。時系列は `date` フィールドで持つ）
- スキル2は `cat */log.jsonl` 相当で1パス走査
- **folder-structure.md には追記しない**。skill1 doc に「repo 外・中央に置く理由（管轄外）」を明記して records 誤解を予防（将来混乱が起きたら一文足す）
- git 管理はオプション（v1 は素のファイル。YAGNI）

### D14. スキル2の抽出フロー（基本形） ✅ 【新規・本セッション確定＝基本形は承認】
1. **入力**: 中央ストア（`projects.json` ＋ 全 `log.jsonl`）。**ユーザーがオンデマンド実行**（自動起動しない）
2. **走査はサブエージェントで**（全コーパスをメインコンテキストに載せない。rubber-duck と同様の委譲）。全エントリを読み**類似エントリをクラスタリング**（同型手順の横断再発をまとめる）
3. **各クラスタを評価**: 横断再発回数・出所プロジェクト数・friction/corrections の重みを集計 / **scope 再判定**（≥2プロジェクト再発→general 格上げ、単一・ドメイン依存→project-specific）/ **既存スキル重複排除**（superpowers＋ai-driven-dev-principles＋プロジェクトローカルの description と突合）
4. **出力＝ランク付き候補リスト**（再発数・scope・重複有無・根拠エントリ参照つき）を人間に提示
5. **人間が採否を選択**（原則4／ADR-0021 と一貫）→ 選ばれたものを Issue 草案化（general→本 repo backlog、project-specific→当該プロジェクト）
6. **頻度はソフトな判断材料**（ハード閾値なし。件数を見せて人間が判断。D4 の思想と一貫）
- ※ ユーザーは基本形を「良いと思う」と承認しつつ、**下記「未確定論点」のライフサイクル懸念を提起**（積み上がるログで分析が重くなる／スキル化済みログから既存スキルと同内容を再提案してしまう）

### D15. ログ・ライフサイクル対策＝id・processed.jsonl・deferred 再浮上 ✅ 【新規・本セッション確定＝最終論点】
- **提案(1)〜(6)を確定**（前セッションの未承認提案をユーザーが承認）:
  - エントリに **`id` 必須追加**（人間可読・安定な `<project>-<date>-<NN>`。NN＝そのプロジェクトのその日の連番。skill1 が既存 log 末尾を見て採番）
  - 集約ルートに **`processed.jsonl`（追記専用の処理済み台帳）** 新設。skill2 は開始時に台帳を読み処理済み id を分析対象から**除外**（分析コストは未処理エントリ数でスケール＝heaviness 解決）。人間の採否後に結果を追記
  - 再提案防止は**二層**: ①台帳（厳密＝処理済みは丸ごと除外）②既存スキル重複排除（あいまい＝未処理でも既存 description 一致で除外）
  - archive 退避は **v1 では作らず v2**（YAGNI）
- **保留候補の扱い（ユーザーの指摘で追加確定）**: skill2 が提案したが人間が採否を**保留**した候補は、`processed.jsonl` に **`outcome:"deferred"`** として、**その時点のクラスタ根拠数（エントリ件数）**とともに記録する。skill2 は次回実行時、deferred クラスタに**新しい該当エントリが増えた場合のみ**再提示する（増えていなければ除外）。効果: 保留分も分析対象から一旦外れる（heaviness）＋毎回のしつこい再提示を防ぐ＋他プロジェクトでの再発時に強い証拠つきで再浮上（D14 クラスタリングと整合）
- **`processed.jsonl` の outcome は4種**: `skillified` / `rejected` / `merged` / `deferred`（`rejected` も除外扱い。台帳に残るので監査・手動再検討は可能）
- ※ エントリ側の `outcome`（success/partial/failed＝作業結果）と、台帳側の `outcome`（採否結果）は別フィールド。混同しないこと

### D16. スキル3の実行環境ガード ✅ 【新規・本セッション確定】
- **汎用 → プラグイン配信スキル**パス（D5）は本 repo（ai-driven-dev-principles）実行が前提（配信元がこの repo）。他 repo での汎用パス実行は配信先が無い
- 残り2パス（固有→プロジェクトローカル `.claude/skills/` ／ 固有ルール→CLAUDE.md）はどの repo でも正しく動く
- **ガード**: スキル3冒頭で実行環境が本 repo かを安定マーカーで判定（git remote URL に `ai-driven-dev-principles`、またはプラグイン manifest 等の固有ファイル存在。実装時に確定）。**汎用パス かつ 本 repo でない**→警告＋ユーザー確認（①この場のローカルスキルとして作成 ②配信元 repo へ移動して実行 ③中止）。固有パスはガード不要
- 根拠: 原則4（人間の関与）・誤配置の予防

### D17. Skill Creator 借用は「設計時抽出」で実現（実行時依存なし） ✅ 【新規・本セッション確定】
- D1 の「Skill Creator の一部借用」を**実行時依存にしない**。skill3 は実行時に Skill Creator をロードしない（まるごと読み込むと未使用部分まで文脈に載るムダ＋内部構成への結合が生じる、というユーザー懸念への回答）
- 実現方式＝**設計時抽出**: 実装段階で Skill Creator の実体を一度読み、2技術（description 自動最適化・定量 eval ループ）の**手法だけを抽出**し、skill3 自身の `references/` に自前の言葉で蒸留内包する
- 実行時エンジンは **writing-skills のみ**ロード。ムダな読み込みゼロ・Skill Creator の内部構成／インストール前提への結合なし（高凝集・疎結合）
- トレードオフ: Skill Creator の将来改良に自動追従しない（手法は安定で実害小＝YAGNI）

### 提案内容（未承認・要ユーザー確認）

**目的**: 運用でログが積み上がると (1) スキル2の分析が重くなる、(2) スキル化済みログから既存スキルと同内容を再提案してしまう —— この2つを1つの仕組みで解く。

**提案した仕組み（すべて追記専用でファイル in-place 書き換えを避ける）**:
1. **エントリに `id` を必須追加**（D9 の修正案）。方式は人間可読で安定な `<project>-<date>-<NN>`（NN＝そのプロジェクトのその日の連番。skill1 が既存 log 末尾を見て採番）
2. **集約ルートに `processed.jsonl`（追記専用の処理済み台帳）を新設**（D13 の修正案）:
   ```jsonl
   {"id":"MakeAiInstructions-2026-07-16-01","outcome":"skillified","ref":"skills/xxx","date":"2026-07-20"}
   {"id":"LoopForAlpha-2026-07-18-03","outcome":"rejected","date":"2026-07-20"}
   ```
   `outcome` は `skillified` / `rejected` / `merged`（既存スキルへ統合）
3. **スキル2フローの追補**: 開始時に台帳を読み **処理済み id を分析対象から除外**（→ 分析コストは未処理エントリ数でスケール＝heaviness 解決）。人間の採否後に結果を `processed.jsonl` へ追記
4. **再提案防止は二層**: ①台帳（厳密＝処理済みは丸ごと除外）②既存スキル重複排除（あいまい＝未処理でも既存 description と一致で除外）

6. 物理ファイル肥大時の **archive 退避は v1 では作らず v2**（YAGNI）

**未確定の分岐（ユーザーに問うべきこと）**:
- (A) この追補（id＋processed.jsonl）で確定してよいか
- (B) archive 退避を v1 に入れるか（提案では v2）
