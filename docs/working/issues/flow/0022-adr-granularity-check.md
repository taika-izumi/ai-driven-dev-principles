# Issue-0022: ADR 起票時に粒度（1決定=1ADR）を確認する観点がない

- **Status**: closed
- **Opened**: 2026-07-07
- **Closed**: 2026-08-04
- **起票元**: `docs/records/retrospectives/flow/2026-07-07-adr-rejected-status-path.md` 課題#1
- **関連**: `skills/decision-log/SKILL.md`（ADR作成手順）、ADR-0019（記述規律）、ADR-0041/0042（レビュー指摘により1決定=1ADRへ分割した実例）

## 課題内容

ADR-0041 の初版に複数の独立した決定（Rejected 経路の定義 / Superseded の置換特定と台帳監査）と実行計画を束ねて起票し、ユーザーレビューで分割となった。`decision-log` の作成手順には「1つの ADR に収める決定の単位」を確認する観点がなく、「1サイクル=1ADR」の慣性で束ねやすい。束ねた大型 ADR は将来の部分修正（一部だけ置換される状態）を増やし、台帳のステータス管理を悪化させる。

詳細（事象/原因/影響）は起票元の振り返りファイルが正。

## 検討状況

- 2026-08-03: retrospective（Post ラッパー消化可視化サイクル）でユーザーが再提起。LoopForAlpha で再発実例あり — 1つの Proposed ADR に議論の往復で決定が9件まで肥大し、「後から探しに来るときの問い」を単位に4本へ再分割した（中央ストア `LoopForAlpha-2026-07-19-02` に利用者指示の原文と対策案 skillification_hint あり。worklog-extract の横断走査でも同クラスタとして検出される見込み）。粒度の確認観点に加え、**Proposed のまま決定を追記し続けると主題がずれる**という肥大経路と、**文章量の上限目安**も論点に含めること

## 結論

ADR-0059（粒度の基準）と ADR-0060（点検の契機）で決着した。

- 粒度の単位は「後から探しに来るときの問い」1つ。決定の件数は数えない
- **文章量は基準にしない**。実測により、分割は総文章量を増やし（5,545文字 → 4本合計 13,918文字）、肥大 ADR より大きい正常な ADR が存在するため、閾値は見逃しと誤検出を同時に生む
- 点検は起票時・追記時・昇格前の3箇所。規範は `decision-log` に一本化し、`start-work` は参照のみ
