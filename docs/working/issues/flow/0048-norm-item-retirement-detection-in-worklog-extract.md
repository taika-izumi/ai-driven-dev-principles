# Issue-0048: 規範項目の退役候補を worklog-extract の走査で機械検出できない

- **Status**: open
- **Opened**: 2026-08-05
- **起票元**: ADR-0073（退役経路の設計時、機械化を今サイクルの規模超過として分離）
- **関連**: ADR-0073（根拠・世代の記録と退役規範）、ADR-0070（強める方向の測定）、ADR-0040（CLAUDE.md 棚卸し。同じ「減らす側」の既存フロー）、Issue-0047（フック注入。同じ ADR-0070 系の繰り延べ）、`worklog-extract`

## 課題内容

ADR-0073 は、委譲制約の各規範項目に根拠エントリ id とモデル世代を添え、「同型 delta が長期にわたり現れない項目は退役候補としてユーザーへ提案する」という退役規範を置いた。しかし現状、この検出は手動（棚卸し時・ユーザー指示時）に依存する。

`worklog-extract` は中央ストアを走査してクラスタを検出する能力を既に持っており、逆方向の問い —「スキルに記載済みの規範項目のうち、対応する同型 delta が最近 N サイクル観測されていないものはどれか」— にも原理的には答えられる。これが実装されれば、規範の増加（新クラスタ検出）と減少（退役候補検出）が同じ走査で対になり、測定ループが双方向に閉じる。

## 未解決の論点

- **同型判定の手段**: 規範項目と delta エントリの対応付けをどう取るか。項目に添えた根拠 id からの逆引きか、クラスタリングの再利用か
- **「長期」の定義**: 何サイクル / 何ヶ月観測されなければ退役候補とするか。モデル世代の切り替わりを判定材料に含めるか（項目に世代が記録されるため参照可能）
- **対象範囲**: 委譲制約（`subagent-dispatch`）に限るか、スキル内規範一般へ広げるか。広げる場合、規範側の記載形式（根拠 id の書式）を揃える必要がある
- **提示の場所**: `worklog-extract` の候補リストに「退役候補」セクションを足すか、別レポートにするか

## 着手判断の材料

退役候補が実際に発生する（＝どれかの項目の delta が観測されなくなる）には数サイクルの蓄積が要る。`subagent-dispatch` の運用開始から数サイクル分の worklog が貯まった時点で着手するのが、検証データが揃っていて安い。

2026-08-16 追記（Issue-0092 監査の実測）: 未解決論点「『長期』の定義」が実害を生むことが確認された。全数監査の分類規則 1-B は、退役条項を持ち検出 0 の 21 行について「『長期にわたり』が未定義のため条項の成立を判定できない」となり、条項が分類の根拠として機能しなかった（ADR-0101・report.md 規則 1）。監査は退役条項の初回行使（ADR-0073 の「検出は手動〈棚卸し時〉」）にあたるが、条件の未数値化により行使が空転した形。対策設計時は「長期」を発火機会数ベース（例: 発火機会 30 回で delta 0）で数値化することが、本監査の露出閾値の設計（rule of three）を先例にできる。保留 44 行の再判定（Issue-0097）を機械化する場合も本課題の管轄。
