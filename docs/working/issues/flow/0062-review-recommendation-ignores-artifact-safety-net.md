# Issue-0062: 確定前レビューの次手提示が成果物の性質を問わず中立で、安全網の無い成果物でも非推奨側に倒れる

- **Status**: closed
- **Opened**: 2026-08-07
- **Closed**: 2026-08-07
- **起票元**: `retrospectives/flow/2026-08-07-overfitting-check-for-extensions.md` 課題#1
- **関連**: ADR-0072（確定前レビューの発動はユーザー指示のみ・AI は毎回提示）、`skills/pre-finalization-review/SKILL.md`、worklog `MakeAiInstructions-2026-08-07-04`、Issue-0034（確定前の独立レビュー工程の導入元）

## 課題内容

ADR-0072 は「`writing-plans` / `feature-block-design` の完了後に確定前レビューの実施を毎回提示する」ことだけを定め、**成果物の性質による推奨の強弱を定めていない**。そのため AI は「上流で自己レビュー済み」「計画は spec の機械的写像」といった一般論から非推奨側へ倒しうる。

2026-08-07 の ADR-0079 サイクルで実際にそれが起きた。AI は spec 承認直後に「writing-plans へ進む（推奨）」を先頭に置いたが、ユーザーの指示で実施した 3 観点の独立レビューが Critical 3 件・Major 8 件を検出し、spec は設計骨格に及ぶ全面改訂（コミット `b34e2ca`）になった。

見落とされていた構造は次のとおり: **コードには「実装して最初に実行すれば数分で露見する」安全網があるが、ルール・規範・文書型の成果物には無い。** さらに実装時レビュー（`subagent-driven-development` の二段レビュー）は「実装が spec に忠実か」を見るため、spec 自体の設計欠陥はむしろ忠実に実装される。欠陥が顕在化するのは、そのルールが誤発動・空振りする数サイクル後になる。

## 留意（対処を設計するときに参照すること）

- **一次資料は起票元の振り返りファイル**にある。本サイクルで実証された「確定前レビューでしか捕まらない欠陥クラス」3 種（①選定漏れ型＝spec に載っていない欠陥 ②文書間相互作用型＝編集対象外ファイルとの矛盾 ③検出力欠陥型＝緑を返すが何も守っていない検証）と、それぞれの実例・対照（後工程でも拾えた型）が記載されている。対処を設計する前に必ず読むこと
- **この知見は単一サイクル・単一成果物種別（ルール文書）由来である**。したがって対処の設計時は、本サイクルで導入した ADR-0079 の過剰適合点検を自分自身に適用すること（とくに観点 1「出所の偏り」）。列挙した 3 クラスが網羅である保証はなく、クラスの列挙をそのまま拘束的規範へ昇格させると別種の成果物で不適合を起こしうる
- 推奨の強弱を分ける判定条件は、エージェントが観測できる事実で書くこと（ADR-0032）。「安全網の有無」は抽象的すぎるため、観測可能な代理指標（成果物の種別・拡張規範を含むか・実行可能な検証手段があるか等）への翻訳が要る
- ADR-0072 の骨格（発動はユーザー指示のみ・AI は提示にとどまる）は維持したまま、提示の仕方だけを変える対処が最小である可能性がある

- 2026-08-07: 対策サイクルで ADR-0080 を策定。設計段階で「spec レビュー済みの写像 plan に軽量レビュー（仕様適合単観点）を推奨する」枝も設計したが、本 ADR 自身への確定前レビューで根拠の崩壊が実証され撤回した（Issue-0006 は spec に明示されない横断参照側の漏れであり、母数を spec 要件数に取る突合では原理的に拾えない）。再導入条件は ADR-0080 の Considered Alternatives 6 に記載

## 結論

ADR-0080（確定前レビューは spec/plan 確定点で提示し、未レビューの規範・手順文書の変更を含む成果物では推奨側に倒す）で対処。`start-work` に判定規則の正本を置き、`pre-finalization-review` / `feature-block-design` / `session-handoff` を整合させた。
