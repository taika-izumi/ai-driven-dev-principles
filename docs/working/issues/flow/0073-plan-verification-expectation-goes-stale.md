# Issue-0073: 計画の検証ステップの期待値が、実装中に判明した事実で陳腐化する

- **Status**: open
- **Opened**: 2026-08-08
- **起票元**: `retrospectives/flow/2026-08-08-distributed-artifact-generation.md` 課題#1
- **関連**: ADR-0034（実装計画の検証ステップ期待値と編集内容の整合）、`CLAUDE.md`「検証」節、`superpowers:writing-plans`

## 課題内容

実装計画の検証期待値と編集内容の整合を確認する規範は、**計画作成時の 1 回の突合**を想定している。実装中に判明した事実で期待値が陳腐化する経路を扱っていない。

2026-08-08 のサイクルで 4 件発生した（詳細は起票元参照）。

| 型 | 例 |
|---|---|
| 別タスクの意図的な成果物を検証が拾う | 残存識別子の検証が、同じ計画の別タスクが導入する中立名プレースホルダを拾い、期待値 0 が原理的に達成不能だった |
| 検証の検索語が正本の表現と不一致 | 計画の grep 語が仕様本文の実際の表現と食い違い、期待値 1 に対し実測 0 |
| 実施日に依存する固定値 | 注記の日付を計画作成日で固定しており、実施日とずれた |
| 上流の変更に追随しない | 自己テストの期待ケース数が 17 のまま（実際は 21 へ拡張済み） |

いずれも実装者が実態優先の報告をしたため露見した。指示に黙って従えば検証を通過したことになり、欠陥が下流へ流れる。

## 影響

- 検証が「必ず失敗する」か「形だけ通る」状態になる
- 前者は実装者をスコープ外の修正へ誘導する（実際、規約の適用対象外であるはずのコード修正へ誘導しかけた）
- 後者は検証の意味を失わせる

## 対策の方向（採否は未定）

- 検証期待値の更新を、計画のタスク完了時の手順に組み込む（現行は計画作成時のみ）
- 検証コマンドを書くとき、判定ロジックが既に実装にある場合はそれを呼ぶ（素朴な正規表現で書き直すと、許可リストなどの例外を落とす）
- 実施日など可変の値はプレースホルダにし、検索語は日付に依存しない形にする
