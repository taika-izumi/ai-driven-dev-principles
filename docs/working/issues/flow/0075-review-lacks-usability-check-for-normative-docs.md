# Issue-0075: 規約・手順文書の「読者が実際に使えるか」を検査する観点が確定前レビューにない

- **Status**: open
- **Opened**: 2026-08-08
- **起票元**: `retrospectives/flow/2026-08-08-distributed-artifact-generation.md` 課題#3
- **関連**: ADR-0072 / ADR-0080（確定前レビューの発動と提示規則）、`skills/pre-finalization-review/SKILL.md` の 3 観点、Issue-0062（レビュー推奨が成果物の安全網の有無を考慮しない。同型の先行課題）

## 課題内容

確定前レビューの 3 観点（敵対的・実装整合性・仕様適合）は「**書いてあることが正しいか**」を検査するが、「**書いていないことで詰まるか**」を検査しない。

2026-08-08 のサイクルで、新設した規約節が仕様との逐語突合 39 項目すべて一致で仕様準拠レビューを通過した。その後の品質レビューで「この節だけを読んで作業する人になったつもりで 4 つの作業を実際に試す」検査を課したところ、**3 つで詰まった**。

| 詰まった作業 | 原因 |
|---|---|
| 決定記録の一覧節を書く | 本リポジトリの慣用形が別の規約違反として弾かれ、エラーに出る規約名も書き手の意図と食い違う |
| 本文に参照を入れる | 規約に完全適合していても配布物が壊れる書き方があり、その予防規則が書かれていない |
| 変更後に何をするか判断する | 目視確認を指示しながら、対象の所在が文書全体で一度も書かれていない |

規約を書いた側は既にその規約を理解しているため、初見の書き手が最初に選ぶ形が違反になることに気づけない。あわせて、手順書に書いた理由づけ 2 件が事実と異なっていたことも同じ検査で判明した（陳腐化検査が両側を見る／コミットを止めるフックがある、のいずれも偽）。

## 影響

- 規約・手順文書が「正確だが使えない」状態で確定する
- この型の成果物は実行による安全網がないため、欠陥は使われる時まで潜伏する
- 手順書では指示より理由づけの方が長生きするため、偽の理由は指示そのものより害が大きい

## 対策の方向（採否は未定）

- 確定前レビューへ第 4 の観点として「実効性」を足す。レビュアーへ、その文書だけを読んで実際に数種類の作業をさせ、詰まった箇所を指摘として出させる
- あわせて文書内の理由づけ（なぜそうするか）を実測で検証させる
- 観点を増やすとレビューの費用が上がるため、適用条件（規範・手順文書の新設・改定に限る等）の設計が要る
