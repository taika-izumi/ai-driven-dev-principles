# Issue-0078: cycle-reset の発火点が長期サイクル運用と噛み合わず、サイクル内の蓄積を制御する機構がない

- **Status**: open
- **Opened**: 2026-08-13
- **起票元**: feature/handoff-bloat-analysis サイクルのアドホック調査（LoopForAlpha のハンドオフ肥大化）
- **関連**: ADR-0075（finalize の基準付き圧縮と cycle-reset）、Issue-0049（closed。肥大化の元課題＝ADR-0074/0075 の起点。本課題はその対策の射程外を扱う）、`skills/session-handoff/SKILL.md`、Issue-0079 / Issue-0080 / Issue-0081（同調査で起票した兄弟課題）

## 課題内容

cycle-reset の発火点は「サブプロジェクトの master マージ後（retrospective の仕上げ）」だけであり、**サイクルが長期化する運用では、サイクル内に蓄積する保護対象（`review=` を含む消化記録行・現役の申し送り）を制御する機構が何もない**。

LoopForAlpha（`D:\Dev\001_Trade\LoopForAlpha`）での実測（2026-08-13）:

- 同 repo は master 直接開発で、1 つの「段階」（サブプロジェクト相当）が数週間続く
- cycle-reset は実行されている（2026-08-06 `1880d6f` で 211KB→23KB。それ以前にも 2026-07-24 `fa7cba9` で手動刈り込み 154KB→6.9KB）
- finalize の基準付き圧縮も毎セッション実行されている（約 10% 縮小を git 履歴で実測）
- それでも**増加が約 10KB/日**で圧縮を上回り、cycle-reset 後 7 日で 23KB→97KB へ戻った

つまり「策が未展開」でも「策が実行されない」でもなく、**リセット間隔（数週間）と増加速度（10KB/日）の積が防止策の射程外**にある。

## 影響

- ハンドオフが 100KB 規模になると、セッション開始時の read でコンテキストを大量消費し、引き継ぎの精度・効率がともに落ちる
- 圧縮の頻度を上げる規範がないため、運用側では「手動刈り込み」（2026-07-24 実測）という規範外の対処が発生している

## 対策の方向（採否は未定）

- サイクル内の中間リセット点を定義する（例: フェーズ完了時の「phase-reset」。cycle-reset より軽い基準で、完了フェーズの消化記録・申し送りを正本へ移して落とす）
- サイズ閾値トリガーを設ける（例: read または finalize 時にサイズを実測し、閾値超過で剪定を提案・実施する）
- cycle-reset の発火点定義を「マージ後」から「作業単位の完了」へ広げ、master 直接開発でも段階完了時に発火するようにする
