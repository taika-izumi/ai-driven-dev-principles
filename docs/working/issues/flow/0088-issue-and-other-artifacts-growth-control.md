# Issue-0088: Issue など handoff 以外の成果物に、肥大化を抑制する機構がない

- **Status**: open
- **Opened**: 2026-08-15
- **起票元**: ユーザー報告（配布先での実測。旧版ガイドライン（2026-06〜07 頃の版）を業務のシステム開発マネジメントに利用した経験。データは業務 PC 上にあり本リポジトリからは参照不可＝報告者の記憶ベース）
- **関連**: Issue-0049（handoff の同型課題。closed）、ADR-0074/0075/0077（handoff 側の対策: 受け皿は git 履歴のみ・二段階剪定・安定識別子参照）、ADR-0086/0087/0088（正本移設の標準・サイズ実測トリガー・節別記載規範）、Issue-0018（CLAUDE.md 肥大監視。closed）、Issue-0087（条件発火表の行数増加）、Issue-0050（長期化で 1 回の retrospective の材料が過大になる）、Issue-0021（Tech Notes の集約機構）、Issue-0045（open 課題の棚卸し）

## 課題内容

ハンドオフの肥大化には対策（二段階剪定・正本移設・サイズ実測トリガー・節別記載規範）が入ったが、**それ以外の成果物には肥大化を抑制する機構がない**。配布先の業務利用で、Issue で同型の肥大化が実際に発生した。

配布先での観測（システム開発業務のマネジメント用途、旧版ガイドライン）:

- プロジェクト推進に開発チーム外とのコミュニケーションや解決手段の調査が必要で、Issue ごとに関連情報の収集・整理 → 対策決定 → ADR 作成という流れになった
- そのため Issue を単一ファイル管理からフォルダ管理（Issue ごとにフォルダを作り、関連情報・検討内容のファイルを格納。即決する Issue は従来どおり単一ファイル）へ切り替えた
- **それでもフォルダ内の Issue ファイル本体に検討経緯・状況が次々と追記されて肥大化し、内容を把握しづらくなった**
- **フォルダ内のファイルも場当たり的に（体系化・分類されずに）増え、どのファイルに何が書いてあるか分からなくなった**

一般化すると、本ガイドラインの成果物には「時系列追記で成長する単一ファイル」「件数が増え続ける一覧・台帳」が複数あり（Issue ファイル・Issue インデックス・ADR インデックス・worklog 台帳・retrospective など）、handoff 以外は成長を制御する規約を持たない。

## 論点（対処を設計する前に判断すること）

- **本リポジトリで対処すべき問題か**。マネジメント用途に使わない場合、現行運用で Issue 肥大は顕在化していない（本リポジトリの Issue は概ね単一ファイルで収まっている）。配布先の利用シナリオ（マネジメント用途）をガイドラインのスコープに含めるかどうかが先行論点
- 観測データが手元に残っていないため、事象の詳細（何行・何ファイルまで膨らんだか、何が最も困ったか）は報告者の記憶に依存する

## 対策の方向（採否は未定）

- まず肥大化しうる成果物の棚卸し（成長様式で分類: 時系列追記型 / 件数増加型 / フォルダ内無秩序増加型）を行い、対処要否を成果物ごとに判断する
- 対処する場合、handoff 対策（正本の分離・移設・基準付き剪定・サイズ実測トリガー）の一般化が候補。Issue フォルダ運用にはファイル配置の体系（命名・索引）の規約化が候補
