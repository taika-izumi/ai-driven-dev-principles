- 2026-08-25: 【事例 7・外部で実証された欠陥を塞ぐ増設を、受容で済ませなかった判断】
  - 局面: plan 確定点フル巡 1 巡目の指摘 15 件を反映するときの応じ方の選択。前置 1 の計数上はこれが「増設 1 回目」にあたる。
  - 状況の具体（何を増設するか / 受容案は何か）:
    - 指摘の中身: 敵対的レビュアーが、正本 `.claude-plugin/marketplace.json` の `plugins[].source` をオブジェクト形式（`{"source":"github","repo":"o/r"}`）にした場合、生成器の `ConvertTo-JsonStringValue` が `param([string]$Value)` で受けるため PowerShell の暗黙変換が働き、`"path": "@{source=github; repo=o/r}"` という**壊れた値を持つ構文的に妥当な JSON** が出力されると実証した（計画のコードを逐語転記した probe を写経実行。ケース D）。構文が妥当なので `-Check` も自己一致して `exit=0` を返し、Codex 側でのみ解決不能になる。同じ probe で `plugins` が空配列なら空マーケットプレイスを無警告出力（ケース A）、`plugins[0].name` 欠損なら `"name": ""` を無警告出力（ケース E）することも確認された。
    - 動機の実在性: 本計画自身が README（Task 6 Step 3）で GitHub 経由配布 `codex plugin marketplace add taika-izumi/ai-driven-dev-principles` を正式手順に掲げている。つまり正本の `source` を object 形式へ変える動機が**体系の内側に存在する**。仮定の入力ではない。
    - 受容案（増設しない選択肢）: spec と plan に「`source` は文字列形式のみ対応。object 形式へ変える場合は生成器の改修が必要」と 1 行書くだけにし、コードは足さない。
    - 増設案の中身: `New-CodexMarketplaceContent` に中断分岐 3 本（`plugins` 0 件 / `name` 空 / `source` が非文字列）＋診断 3 行、および Task 2 Step 13 の検証手順（異常入力 3 通りの実行）。
  - 規範推奨: 前置 1 は「増設 2 回連続」で発火するため、1 回目のこの局面では設計縮小は推奨側に載らない。ただし「修正の既定」（骨格安定時は削る/受容を既定とし増設を既定にしない）は、骨格安定でないため非適用。**規範はこの局面で増設の当否を何も言わない**。
  - 実選択: 増設。ただし「増設で応じた」旨を反復提示へ明示し、前置 1 の計数 1 回目であることも添えた。
  - 判断要因: 失敗様式が「静かに壊れて外形上検出されない」型で、`-Check` が緑を返し続ける。受容案が塞げるのは「正本 JSON を触る人がその文書を読んでいれば」という条件つきだが、生成器を触る人と正本を触る人は別のタイミングで動くため条件が成立しない。維持コストは分岐 3 本・診断 3 行で、削っても文書の複雑性は実質減らない。ADR-0054（検査は silent tolerance をせず、検出したら報告して停止する）と同型の判断。事例 2 の候補 (i)（version 一致検査）と同じ「欠陥駆動の最小機構」型。
  - 結果: 第 2〜4 巡を通じて**型ガードそのものへの指摘はゼロ**（関連指摘は「上流 spec の中断条件が version 不一致 1 本のままなので書き足せ」という記述の追随 Minor 1 件のみ）。第 5 巡の注入テストで 3 通りとも計画記載どおりの診断つき `exit=1` を確認。維持コストの増加は観測されなかった。
