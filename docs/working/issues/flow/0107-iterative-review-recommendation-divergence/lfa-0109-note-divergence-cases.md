# 検討ノート: 反復レビューの推奨判定は、どの状況材料を入力すべきか — 乖離事例の蓄積

> **問い**: 確定前レビューの反復規範（`start-work`「指摘反映後の反復」の前置1・前置2・2段型・骨格安定）の推奨判定に、形式条件（増設回数・改訂の型・巡数）に加えて**どの状況材料**を入力すれば、実態と割れない推奨が出せるか。
>
> 本ノートは「規範ベースの推奨」と「実際に妥当だった選択」が乖離した事例を、**判断の具体的材料つきで**蓄積する。将来の規範改善（ガイドライン repo への申し送り）の一次入力。
>
> **追記様式**: 事例ごとに「規範の挙動 / 実態（具体的材料） / 内容判断の結論と採択 / この事例から抽象化できる判定材料」の4点を書く。要約だけにせず、**縮小・巡追加などの各候補について「なぜ採らなかったか」の対応物（実測・実欠陥・実在物）を必ず残す**。

## 事例1（2026-08-22）: 前置1（設計縮小）が「縮小すべきでない状況」で縮小を推奨した

**局面**: 第6段階フェーズ5 詳細化の確定前レビュー反復・2巡目の指摘反映後（対象 = 計画フェーズ5 節 + ADR-0154）。

**規範の挙動**: 1巡目・2巡目の反映がともに「機構の増設」を含み、前置1 の計数条件（2回連続）が成立 → 「設計縮小」を推奨先頭に置いた5択を提示。

**実態 — 増設の内訳と、縮小した場合に起きること**（すべて独立レビューが写経実行で実証した欠陥と1:1対応）:

| 増設された機構 | 塞いだ実測欠陥（すべて写経・実行で実証） | 縮小した場合に起きること | レイヤ |
|---|---|---|---|
| 指紋関数の書式・型検査（区切り文字・平坦リスト・非文字列の throw） | `['a,b']` と `['a','b']`、平坦リストと1銘柄組の集合、整数と文字列がそれぞれ**同一指紋になる衝突**（レビュアーがハッシュ一致を実測） | フェーズ6 の事後突合（本番ファイルを直接パースする単独呼び出し）で衝突が防げない。代替の担い手は「必ず Read-EvalSets 経由で読む」という**利用規約**になるが、本プロジェクトは「記述による規律は再発を防がない。実効的なのは機械検査」を実測から学んでいる（参照知識 §6） | 検証（実行時挙動に非分岐） |
| 索引の「設定」列（`config_sha256` の16hex） | `-Config` は閾値ごと差し替える最強の逃げ道なのに記録が summary のみ = **ADR-0092 が明示的に退けた「痕跡が気づく場所から1階層離れる」形の再演**（独立レビュー2巡がともに指摘） | 台帳と索引が食い違ったとき、乖離に気づく場所（索引）で理由が読めない — ADR-0092 Context がフェーズ4 以前に実測した問題の復活 | 記録（実行時挙動に非分岐） |
| param 名と `$script:` 定数の交差検査（Pester・AST） | `run.ps1` に**現に衝突3件が実在**（AST 全数走査で検出）し、本フェーズ新設の関数がその定数を読む**初めての消費者**になる。上書きは写経で再現済み（値が無言で定数に化ける = ADR-0107 の実バグと同型） | 将来 param・変数を足した人が同じ穴を踏んでも検出されない。唯一の再発防止網が消える | 検証（テスト内 AST 数行） |
| デビット前の指紋/ハッシュ非空表明 | `Mandatory [string]` は空文字でバインダ throw し、索引追記は**デビット後** — そこで落ちると**最終テスト枠を焼いて verdict を捨てる**（束縛失敗を実測） | 到達可能になった時点で不可逆の実害（テスト枠の空費）。「デビット前へ前倒しする」という確立済み設計規律（D19）との食い違いが残る | 実行時（ただし分岐でなく fail-closed の前倒し） |

**内容判断の結論**（利用者採択）: 縮小は見送り、フル巡（3巡目）へ。参考: このとき唯一「筋が良い」と評価した縮小候補（指紋関数の防御を Read-EvalSets 経由の強制に一本化する案）ですら、上表1行目の理由で見送りが妥当と結論された。**最良の縮小候補でも実測欠陥の再開放と引き換え**だった、というのがこの局面の特徴。

**この事例から抽象化できる判定材料**:

1. **増設が本番の実行時挙動に条件・分岐を足していない** — 前置1 が警戒する「どの条件で安全装置が働くか追えなくなる複雑化」（ADR-0153 が実際に踏んだ形）は、実行時分岐の増殖で起きる。テスト・静的検査・記録列は読解コストを増やすが挙動の場合分けを増やさない
2. **各増設に写経実証された欠陥が1:1で対応している** — 「念のため」の防御が積もったのではなく、全部に「これを外すと再現手順つきの穴が開く」という対応物がある。縮小の利得（数行〜数十行の削減）と損失（実測済みの穴の再開放）が釣り合わない
3. **設計中核（決定構造）は2巡を通じて不変だった** — 前置1 の本来の検出対象「決定そのものが巡ごとに書き換わり続ける発散」は起きていない。動いていたのは周縁の検出力だけ
4. **単一の正は保たれていた** — 検問点（書式検査の適用箇所）は複数化したが、正の定義（`$script:EvalSetSymbolPattern` / `_SYMBOL_PATTERN`）は1箇所のまま。「単一の正」の原則との摩擦は見かけ上のもの

## 事例2（2026-08-22）: 2段型 + 骨格安定の既定が「収束が明白な局面」でフル巡を推奨した

**局面**: 同反復・3巡目の指摘反映後。

**規範の挙動**: 改訂が新規の配線（検査定義・順序固定 pytest）を含むため2段型はフル巡側。骨格安定は「2巡目の指摘（検証機構への指摘）を『迷ったら骨格側』の既定で骨格扱いした」ため2巡連続ゼロが未成立 → 4巡目のフル巡を推奨。

**実態 — 収束を示していた具体的材料**:

- **収量曲線**: 1巡目 Critical 2（計画どおり実装すると動かないレベル）→ 2巡目 Critical 0 → 3巡目 **設計骨格への新規指摘 0**（3観点とも）。指摘の重心が「設計の欠陥」→「検査の精密化」→「計画文書の会計（件数・アンカー・行番号）」へ移動
- **攻撃の不成立率**: 3巡通算で攻撃シナリオ89本中54本不成立。設計中核（実行時判定なし・指紋記録・フロー D のみ・単一導出）への有効な攻撃はゼロのまま
- **残リスク種別と安全網の対応**: 残る欠陥候補は「3巡目の反映が書き込んだ数値の相互整合」型 — これは①機械検証（grep・再計算）が直接照合でき、②実装時にも各 Task の TDD + 2観点レビュー + 変異実測、計画に埋め込んだ「母数は着手時に数え直す」指示、Task 5.10 の仕様突合が受け止める種別
- **コスト対効果**: 4巡目フル（3体・写経つき）の予測収量は Minor 中心。一方、確定前レビューの本来の役目「実装しても露見しない構造的な誤りを潰す」は3巡で果たされていた

**内容判断の結論**（利用者採択）: 4巡目フルは見送り、**機械検証で締めて確定**。機械検証は齟齬ゼロ（黄金値5種の再計算・It/変異対応・掃討母数の実測・完了条件表の双方向）を返し、実質収束で確定。事後に問題は出ていない（→ 出た場合はここへ追記して反例として記録する）。

**この事例から抽象化できる判定材料**:

1. **収量曲線の傾き** — 直近巡の Critical 数・骨格新規指摘数の推移が 0 に収束しているか（規範は「骨格安定」の目安に使うが、『迷ったら骨格側』の既定 × 2巡連続条件の組み合わせが、実際に収束していても締めモードに入ることを妨げた）
2. **残リスク種別と検証手段の適合** — 残る欠陥候補が「機械照合できる型」に純化しているなら、フル巡でなく機械検証が適切な検証手段
3. **下流の安全網の存在** — 確定後の工程（実装時レビュー・TDD・締めの突合）が受け止められる種別の残リスクは、確定前に潰し切る必要がない

## 事例3（2026-08-23〜24）: 前置1 が「増設 = 実証済みの穴の封鎖」局面で再び縮小を推奨した — ただし増設側にも新しい教訓がある

**局面**: 第7段階第1部（執行基盤の刷新）仕様の確定前レビュー反復・2巡目の指摘反映後（対象 = 仕様6ファイル + ADR-0158〜0161）。

**規範の挙動**: 第1巡反映（免除条項・成否信号 `completed`/`failure`・専用タイムアウト・記録スキーマ等）と第2巡反映（空きスロット上限・シム起動時の予約名検査・`session.symbols` キー等）がともに増設を含み、前置1 が発火 → 縮小を推奨先頭に置いた5択を提示。

**実態 — 増設の内訳と、縮小した場合に起きること**（計数対象になった主な増設。実証はいずれもレビュアーの scratch 実験）:

| 増設された機構 | 塞いだ実測欠陥 | 縮小した場合に起きること | レイヤ |
|---|---|---|---|
| 空きスロット上限（規則1。第2巡） | 手仕舞いのバー欠落 × 新規建てで保有が K+5・グロスレバレッジ約1.9倍まで成長（`exp1_k_breach.py`・毎日1銘柄ずつ売買停止する系列で実測） | K 制約が会計側で破れたまま第2部の校正へ進み、「K 銘柄ポートフォリオ」という帰無分布の前提自体が偽になる。契約検査（宣言サイズ ≤ K）は保有超過を検出できないことが実測済みで、代替の担い手が無い | 会計の fail-safe（実行時分岐だが例外時のみ） |
| シム起動時の予約名検査（02 §3.1b。第2巡） | read-only プロパティはサブクラスのクラス属性と `--params` の無名サブクラス機構で**静かに覆せる**（`prop_shadow.py`: 99 が返る実測）。「契約違反とする」と書くだけでは担い手が無い | 戦略が `PARAMS = ("max_positions",)` と宣言して K を自己改変できる。発覚は契約検査の「K 超過」だが診断が原因（予約名の乗っ取り）を指さない。規約のみの防御は本プロジェクトが「再発を防がない」と実測済みの型 | 検証（起動時1回） |
| `session.symbols` キー（08 §3.7。第2巡） | 断面型の核心（候補全体の中での順位づけ）に対し、`bars` は当日バーのある銘柄しか含まず**選別母集合が戦略から構造的に見えない** | 戦略は母集合を履歴から推測するしかなく、契約検査「評価対象外の銘柄」の判定基準が戦略に開示されない片務契約になる | 契約（情報の開示。第2部への申し送りつき） |
| フロー P の免除条項 + 成否信号 `completed`/`failure`（第1巡） | 起動境界規範（ADR-0087/0088「全経路がセットで設計」）に対しフロー P の適用可否が未定義 = 監査主題「全経路が…通っている」が充足不能な文言だった / 正常完走と契約違反中断が**いずれも exit 0 + 記録あり**で区別不能だった | 免除を書かないと監査が評価不能のまま・成否信号を削ると完了基準4「end-to-end 完走」が機械検証不能に戻る | 規範の明文化・記録 |
| 専用タイムアウト `portfolio.total_timeout_sec`（第1巡） | 既定900秒は銘柄1本ぶんの予算で、ラン全体1セッションの断面ではフィクスチャ相当 123〜203 秒の実測に対し余裕5倍未満 | 現実的な戦略で正当な実行がタイムアウトへ倒れ、フロー P のデモ・突合が成立しない | 設定（値の分離） |

**縮小候補の個別検討**: (a) `symbols` キー削除 — 上表3行目の片務契約が残る。開示の重さが懸念なら第2部論点化（採用済み）が正しい受け皿で、削除は解決にならない。(b) 予約名検査を規約へ格下げ — 上表2行目の実測（プロパティで塞げない）に反する。(c) 免除条項の削除 — 監査主題の充足不能が復活する。**どの候補も「実測（再現スクリプト）つきの穴の再開放」と引き換え**であり、数行の削減と釣り合わない。

**内容判断の結論**（利用者採択）: 縮小見送り・フル巡（第3巡）へ。

**この事例で新しく分かったこと（事例1 への追補）**:

1. **「増設は正しいが、増設した機構そのものに欠陥が入る」型が連続した** — 第3巡は第2巡の増設（空きスロット上限×方向転換・強制決済の順序）の未定義を、第4巡は第3巡の修正（「母数外」の1句）が作った K 破れを検出した。つまりこの局面で縮小が誤りなのと同じ強さで、**増設が続いている間は改訂部の再フル検証が要る**（前置1 の「縮小」も 2段型の「機械検証で締める」も誤りで、正解は「増設を維持したままフル巡続行」だった）。前置1 は「増設 = 発散の兆候」と読むが、実測では「増設 = 検証がまだ完了していない兆候」だった
2. 増設の中身の区別（事例1 の判定材料1）はこの局面でも有効: 増設はすべて fail-closed 検査・診断記録・契約検査で、本番の実行時挙動の分岐は増えていない

## 事例4（2026-08-24）: 前置1（縮小）と 2段型（フル巡）の両既定が外れ、差分確認巡が妥当だった — 事後結果つき

**局面**: 同反復・4巡目の指摘反映後。

**規範の挙動**: 前置1 が再発火（第3巡・第4巡と増設2回連続）→ 縮小推奨（既定）。2段型でも「改訂が設計骨格に触れる（規則1 再定義・null 化トリガー置換）」→ フル巡側。骨格安定は未成立（第3・4巡とも骨格レイヤの指摘あり）。

**縮小を採らなかった具体的状況**（第4巡の計数対象と、削った場合に起きること）: `--out-dir` 着地検査 = フロー P は起動境界を免除済みで、打ち間違い1つで凍結フィクスチャの成績記録が AI 可読側へ落ちる経路の**唯一の担い手**（レビュアーが「担保する層がどこにも無い」ことを免除条項・既定パス不在・人間直起動の3点から実証）/ 診断キー2件（`negative_equity_days`・`nulled_windows`） = 07 側の規範が既に要求する記録の受け皿で、削ると「診断節はスキーマどおり出力」という完了基準の検収対象が仕様に存在しなくなる / タイムアウト交差検証 = 既存 `session` ペアに実在する同型ガード（`config.py:556`）の混成ペアへの適用で、無いと `total=1`/`bar=10` が両方の検証を通って即締切超過に倒れることを実装実測。**なお同じ第4巡で「縮小が正しい増設」も1件あり、それは実際に縮小した**: 1% 資産閾値は、根拠（0近傍の資産で発散）がレビュアーの100万試行で反証されたため廃止・置換。つまりこの局面の実態は「増設回数」でなく**増設ごとの根拠の生死**で縮小可否が割れており、一律の縮小推奨はどちらの向きにも合わなかった。

**実態 — 差分確認巡で足りることを示していた材料**:

- **指摘の対象年代**: 第2巡以降の全指摘が「直前巡の改訂部分」に集中し、**それ以前から安定している部分への新規指摘は第3巡以降ゼロ**（第3巡レビュアー3体・第4巡2体がそれぞれ全数走査のうえ報告）。検証を要する面が改訂差分に縮んでいた
- **骨格修正の性質**: 第4巡の骨格修正（規則1 の再定義）は、レビュアー自身が900走行のランダムストレスで「違反0」を実測済みの読みへの**置換**であり、新しい設計の賭けではなかった
- **検証済みの土台**: K=1 両方向突合の完全一致（37シナリオ）・deny 算術・写像整合など「破れなかった前提」が2巡分の実走実証つきで積み上がっていた

**内容判断の結論**（利用者採択）: 縮小もフル巡も見送り、**差分確認巡（対応表方式・1体）**へ。

**事後結果（この選択の妥当性の実測）**: 第5巡（差分確認巡）は対応表17行を全数判定し、**新規の設計欠陥ゼロ**。検出した所見8件はすべて「長い1行の部分置換で旧記述が同じ行に残った」型 + 伝播漏れ — **フル巡が3巡かけて見逃し続けた型（委譲側の反映ミス）を、対応表方式が1体で効率よく拾った**。方式と欠陥型の適合が確認された形。

**この事例から抽象化できる判定材料**:

1. **指摘の対象年代**（各巡の指摘が、どの巡の改訂に対するものか）— 全指摘が直前巡の改訂に閉じ、旧安定部分への指摘がゼロなら、検証対象は改訂差分に縮んでおり差分確認巡が適合する。骨格安定ヒューリスティック（骨格新規指摘ゼロ×2巡連続）は「骨格指摘は毎巡出るが全て直前改訂由来」というこの収束形を捉えられない — 実際、本反復で骨格安定は最後まで成立しなかったが、収束は起きていた
2. **改訂が「レビュアー実証済みの読みへの置換」か「新しい設計の賭け」か** — 前者なら残る検証は「正しく書き写せたか」で、対応表方式の守備範囲
3. **方式と欠陥型の適合** — フル巡（全数走査）は選定漏れ・相互作用に強いが、「委譲側の反映ミス（部分置換の残存・伝播漏れ）」は対応表方式（期待される改訂と実文の突合）が構造的に強い。巡を重ねた反復の後半では後者の型が支配的になる

## 事例5（2026-08-24）: 差分確認巡の所見反映後、「迷えばフル巡」の既定に対し「このまま確定」が妥当だった

**内容判断の結論**（利用者採択）: このまま確定（終了状態 = 提示後確定〈実質収束せず〉）。

**この事例から抽象化できる判定材料**:

1. **修正の出所** — 改訂が「レビュアー指定文の逐語適用」なら、その正しさの検証者は当のレビュアー指摘そのものであり、独立再検証の限界効用は小さい（2段型は改訂の「型」だけを見て「誰が書いた文か」を見ない）
2. **停止判定の語彙の狭さ** — 実質収束の第1経路は「機械検証可能な型のみ」を要求するが、「レビュアー指定文の適用のみ」という同等に低リスクな残指摘型を収束と数えられない。終了状態も `提示後確定（実質収束せず）` となり、記録上「収束せず確定した」ように読めるが、実態は5巡で単調に収束していた（第1巡 Critical 6 級 → 第5巡 新規設計欠陥ゼロ）
