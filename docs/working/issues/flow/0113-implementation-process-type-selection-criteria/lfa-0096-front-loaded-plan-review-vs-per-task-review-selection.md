## 仮説: 使い分けの判定基準

**フェーズ3型（確定前レビューへ前倒し）を選ぶ3条件**（すべて揃うとき）:

1. 設計が確定している（依存ブロックを「完成品として呼ぶだけ」にできる）
2. 成果物を計画に実コードで全文載せられる規模（ここが崩れると「レビューした計画」と「出荷する実装」が別物になり保証が静かに消える）
3. 実行による安全網が無い（欠陥が静かに潜伏する型の成果物。だから写経実行つきの重いレビューが工数に見合う）

**フェーズ2型（タスク別独立レビュー往復）を選ぶ条件**（いずれかに当たるとき）:

1. 既存コードとの衝突が主リスク（計画段階の写経では再現しきれない）
2. 計画にコードを固定しきれない（書いてみないと形が決まらない）
3. 本番判定経路そのもので残余リスク許容度が低い

**どちらの型でも不変の規律**:

- 実装者ミューテーション + 実測（フェーズ3 実装で唯一の新規の穴を拾ったのはこれ。ただし当てる変異の一覧自体がレビュー成果物であり、フェーズ3型の「自己検証」はレビューが事前に用意した検査手順に依存して成立している）
- フェーズ3型の安全弁: **実装が計画コードから「機械的な適応」を超えて逸脱したら、そのタスクはタスク別独立レビューへ格下げする**（フェーズ3 は逸脱がコメント修正1件と検査の穴埋め1件で済んだから保証が保たれた）

## 未決の論点（意思決定はまだ下さない）

- サンプルは各型1フェーズずつで、**対象の性質差（統合点の少なさ・テスト増分の差）と工程の違いが分離できていない**。いま規範化すると交絡ごと固定する
- フェーズ3型の総工数は「消えた」のではなく上流（詳細化 + 3観点レビュー）へ移動している。第44回まで含めた総量での比較評価が未実施
- タスク別レビューを全て見送ったことの残余リスク（「書いた本人は自分のテストの穴を見つけにくい」はフェーズ1・2 で繰り返し実測された）が、フェーズ3 の成果物で将来顕在化しないかは未観測
