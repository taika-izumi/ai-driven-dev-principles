## 2. 機構の概要（何を・いつ・どこへ注入するか）

- **常時注入型の規範**: `SessionStart`・`UserPromptSubmit`・`SubagentStart` の 3 フックで、`skills/ponytail/SKILL.md` の本文（強度に応じて行フィルタ）を毎ターン・サブエージェント起動時にもコンテキストへ注入する。つまり「コード生成の**前段**で毎回問う判断梯子」が中核であり、事後検査は補助
- **強度 3 段**: lite（作るが、より怠惰な代替を1行で名指し）/ full（梯子を強制。既定）/ ultra（YAGNI 極端派。追加より削除・要件自体に挑戦）
- **事後検査**: `/ponytail-review`（差分単位）と `/ponytail-audit`（リポジトリ全体）。いずれも**過剰設計・複雑性のみ**を対象とし、正しさ・セキュリティ・性能は明示的に対象外（通常レビューへ回す）。修正は適用せず一覧のみ
- **意図的簡略化の台帳**: 天井（限界）と昇格経路を `ponytail:` コメントで残し、`/ponytail-debt` が集約する（「後で = 永遠に来ない」を防ぐ）

## 3. 観点の体系（一次ソースからの写し）

### 3-1. 生成前の判断梯子（7段。最初に成立した段で止まる）

| 段 | 問い | 本質 |
|---|---|---|
| 1 | そもそも作る必要があるか（YAGNI） | 存在の要否 |
| 2 | このコードベースに既にあるか（ヘルパー・ユーティリティ・型・パターン） | 再利用（「数ファイル先にあるものの再実装が最も多いスロップ」と明記） |
| 3 | 標準ライブラリが持っているか | 標準への委譲 |
| 4 | 実行環境（プラットフォーム）のネイティブ機能が賄うか（DB 制約 > アプリ側コード 等） | 環境への委譲 |
| 5 | 導入済み依存が解決するか（新規依存は「数行で済むもの」には追加しない） | 既存依存への委譲 |
| 6 | 1行にできるか | 圧縮 |
| 7 | ここで初めて「動く最小のコード」を書く | 最小実装 |

前提条件（重要）: **梯子は問題を理解した後に走らせる**。「変更が触るコードを読み、実フローを端から端まで追ってから段を選ぶ」。理解を省いた小さな差分は「効率を装った怠慢」と位置づける。バグ修正は症状でなく根因（触る関数の全呼び出し元を grep し、共有関数側で1回直す）。

### 3-2. 規則（生成時の禁止・優先）

- 要求されていない抽象を作らない（実装1つのインターフェース・製品1つのファクトリ・変わらない値の設定項目）
- 「後のため」のボイラープレート・足場を作らない
- 削除 > 追加。退屈 > 巧妙。ファイル数は最少
- 最短の動く差分が勝つ——ただし問題を理解してから
- 複雑な要求には「怠惰版を出荷し、同じ応答で要否を問う」（回答待ちで止まらない）
- 同サイズの標準ライブラリ案が2つなら**エッジケースで正しい方**を取る（怠惰 = 少ないコードであって脆弱なアルゴリズムではない）
- 実際に角を削った簡略化（グローバルロック・O(n²)・素朴なヒューリスティック等）には `ponytail:` コメントで**天井と昇格経路**を明記

### 3-3. 事後検査のタグ（review / audit 共通・5種）

| タグ | 検出対象 | 置換 |
|---|---|---|
| `delete:` | 死んだコード・未使用の柔軟性・投機的機能 | なし |
| `stdlib:` | 標準ライブラリが持つものの手製 | 関数名を名指し |
| `native:` | プラットフォームが既に持つことをする依存・コード | 機能名を名指し |
| `yagni:` | 実装1つの抽象・誰も設定しない設定・呼び出し元1つの層 | インライン化 |
| `shrink:` | 同じロジックでより少ない行数 | 短い形を提示 |

`/ponytail-audit` の探索対象（Hunt）: 標準/プラットフォームが既に持つ依存・単一実装のインターフェース・製品1つのファクトリ・委譲しかしないラッパー・1つしかエクスポートしないファイル・死んだフラグと設定・手製の標準ライブラリ。出力は「1行1件・削減幅の大きい順」、末尾に `net: -N lines, -M deps possible.`、切るものが無ければ `Lean already. Ship.`。

### 3-4. 削らないもの（明示の例外）

- 問題の理解（読む・追う）
- 信頼境界での入力検証
- データ損失を防ぐエラー処理
- セキュリティ・アクセシビリティ
- 実ハードウェアの校正つまみ（現実は仕様の理想値ではない）
- 利用者が明示的に要求したもの
- **非自明なロジックには「壊れたら落ちる最小の検査を1つ」残す**（assert ベースの自己検査か小さなテストファイル1つ。フレームワーク・フィクスチャ・関数ごとのスイートは要求がなければ作らない。自明な1行には不要 = **YAGNI はテストにも適用**）

### 3-5. 出力の規範

コード優先。その後に最大3行（省いたもの・追加すべき時期）。「説明がコードより長ければ説明を削る——簡略化を弁護する段落は散文に偽装した複雑性」。ただし利用者が明示的に求めた説明（報告・ウォークスルー）は負債ではない。

## 4. 起票時の抜粋5パターンとの対応

課題ファイル「調査の観点候補」1〜5 は、いずれも一次ソースに対応物がある（抜粋は正確だが**体系の一部**である）:

| 抜粋 | 一次ソースでの位置 |
|---|---|
| 1. 標準ライブラリで足りる処理に新依存 | 梯子 3・5、タグ `stdlib:`、規則「新規依存は避ける」 |
| 2. 実行環境の機能をアプリ側で再実装 | 梯子 4、タグ `native:` |
| 3. 実装1つのインターフェース・ファクトリ | 規則「要求されていない抽象」、タグ `yagni:`、audit の Hunt |
| 4. 計測前のキャッシュ・リトライ・抽象化 | 強度の例示（「プロファイラが言うまでキャッシュ無し」）、review 例「冪等なローカル呼び出しへのリトライラッパー」 |
| 5. 未使用の設定項目 | 規則「変わらない値の設定項目」、タグ `yagni:`、Hunt「死んだフラグと設定」 |

抜粋に**含まれていなかった**要素で、本課題の軸2 に効きうるもの:

- (i) **梯子 2 = コードベース内の再利用**（最も多いスロップと明記。本プロジェクトの Issue-0116・ADR-0166/0140 と主題が重なる）
- (ii) **梯子の前提 = 理解を省かない**（「小さくすること」と「読まないこと」を明確に分離）
- (iii) **意図的簡略化の台帳**（天井と昇格経路を残す。「後で」の腐敗防止）
- (iv) **検査の最小主義**（非自明ロジックに検査1つ。YAGNI をテストにも適用）——本課題の**軸1（検査工程の過剰）と軸2 を同じ物差しで結ぶ**要素
- (v) **削らないものの明示リスト**（信頼境界・データ損失・セキュリティ）——本プロジェクトの情報衛生（ADR-0020/0090/0091）・fail-closed 設計（ADR-0153）は、この規範でも「削減対象外」に該当する

## 5. 本システムへの写像候補（未合意・当てはめの設計は次の一手）

ponytail の観点はライブラリ・Web アプリ向けの粒度（関数・依存）で書かれている。本プロジェクト（PowerShell 起動スクリプト + Python バックテスト基盤 + ループ運用文書）へ当てるには、観点ごとに「本プロジェクトで何がそれに相当するか」を定める必要がある。候補:

| ponytail の観点 | 本システムでの相当物（候補） | 機械列挙の可否 |
|---|---|---|
| `yagni:` 実装1つの抽象 | `src/` の Protocol / ABC / 基底クラスで実装が1つのもの。スロット機構（ADR-0159）のスロットで実装が1つのもの | 可（grep + import 追跡） |
| `yagni:` 誰も設定しない設定 | `loop/eval-config.json`・仕様が定める設定項目のうち、既定値以外で一度も使われていないもの | 可（設定キー × 参照箇所） |
| `yagni:` 呼び出し元1つの層 | 委譲しかしないラッパー関数・モジュール | 可（呼び出し元計数） |
| `delete:` 投機的機能 | 仕様 00〜10 の条項のうち、完了基準に紐づかない実装（逆引き: 実装 → どの完了基準・仕様条項が要求したか） | 半自動（逆引きは人手） |
| `stdlib:` / `native:` | pandas/numpy/stdlib で足りる処理の手製。PowerShell 組み込みで足りる処理の手製 | 部分的（レビュアー判断） |
| 計測前の最適化 | キャッシュ・`history` の性能対策等で「計測が先にあったか」 | 人手（完了記録の突合） |
| 検査の最小主義 | 検出器（テスト）1件あたり守る実挙動の数。軸1 集計の「検出器 72%」と接続 | 軸1 資料の再利用 |
| 意図的簡略化の台帳 | 本プロジェクトでは ADR の申し送り・Issue が同じ役割（`ponytail:` コメント相当は無い） | 対応関係の確認のみ |

観点の粒度が合わないもの（アクセシビリティ・ハードウェア校正）は対象外。ただし「校正つまみを残す」は本プロジェクトの `_calibrated`（Issue-0093）と同型であり、削減対象にしない側の根拠になる。

## 6. 本資料の限界

- ツールの**効果**（-54% 等）は検証していない。本課題が必要とするのは観点の体系であり、効果測定は対象外
- 観点は「生成前の問い」として設計されており、**既存資産の事後監査に転用したときの精度は ponytail 自身も主張していない**（`/ponytail-audit` は一覧を出すのみで、適用判断は人間）
- 本システムへの写像（§5）は候補であり、当てはめ方の確定は利用者判断（課題ファイル「次の一手」の後半）
