# Issue-0130: 完了認識と次セッションの公開状態確認が食い違う

- **Status**: open
- **Opened**: 2026-09-07
- **起票元**: 2026-09-07のstart-work実行後、ユーザーが完了認識の齟齬と「公開状態の確認」自体の必要性を調査し、必要に応じて改修する課題の起票を依頼。
- **関連**: Issue-0102、Issue-0128・0129、ADR-0131・0132

## 課題内容

前セッションで一通りの作業を完了したとユーザーが認識していたにもかかわらず、本セッションのエージェントはmasterの引き継ぎを読み、「公開状態の確認」を残作業として提示した。完了したはずの作業について利用者が再度説明する必要が生じ、手順上の完了と利用者の認識が一致していない可能性があるため起票する。

起票時点で確認できた事象は以下のとおり。

- `docs/working/handoff/master.md`（Last Updated: 2026-09-07 09:18）は、Statusが`ready-for-next-cycle`でありながら、進行中タスクに「公開状態の確認」、次アクションにfetch後のorigin/masterとの比較を記載していた。実装・ローカルマージ・振り返りは完了と記録されていた。
- 本セッションではこの記載に基づき確認作業を案内した。ユーザーは「すでにpushして最新バージョンのスキルがこのセッションで適用されている」と説明した。
- 指定されたキャッシュ0.1.20は存在せず、導入済みの0.1.22にあるstart-workとsession-handoffを実際に読み込んだ。ただし、最新版キャッシュの存在だけでは、リモートに反映されたブランチやコミットの範囲までは証明しない。
- エージェントはユーザーの説明を受けて「追加のpushやスキル更新は不要、引き継ぎの修正だけ」と回答した。この時点でfetchやリモートとの照合は実施しておらず、前セッションの指示・実行結果・引き継ぎ更新順序も未調査だった。

原因はTBD。スキル・ガイドラインの不備を前提にしない。前セッションのユーザー指示の範囲や終了タイミングによって確認が残っただけで、スキルやガイドライン自体には問題がない可能性もある。既存手順の実行漏れ、引き継ぎの更新時点、今セッションのエージェントの解釈・説明の問題も区別して調べる。

## 調査・検討事項

1. 前セッションの会話・承認・push結果・コミット履歴・引き継ぎ更新順序を照合し、利用者が求めた完了範囲と実際の到達状態を整理する。参照できない証拠は未確認として残す。
2. 「公開状態の確認」が必要な作業なのかを検討する。必要なら目的・実施条件・実施時点・完了根拠を整理し、毎回の次セッションでの再確認が必要か、既存のpush結果や記録で十分かを評価する。確認工程の追加や恒久化を前提にしない。
3. start-workの完了工程・終了処理、session-handoffのfinalize・cycle-reset・read、CONTRIBUTING.mdの公開境界を照合する。手順の定義不足、既存手順の未実行、ユーザー指示の解釈、状態記録の不整合を切り分ける。
4. 原因に応じて、スキル・ガイドラインの改修、記録や実行の是正、変更不要のいずれかを根拠付きで判断する。利用者に毎回追加の指示や確認を求める負担も評価する。

Issue-0102はマージ後のcycle-resetの適用先、Issue-0128は完了工程へ入る接続を扱う。本課題は公開確認の必要性とセッションをまたぐ完了認識の一致を対象とする。調査で同じ原因と判明した場合は既存課題との統合を判断する。
