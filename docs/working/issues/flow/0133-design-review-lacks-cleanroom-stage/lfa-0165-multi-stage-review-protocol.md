# 多段レビューの型（実測 → クリーンルーム → 突合 → 反証）— 手順・委譲プロンプト雛形・失敗の型

- **種別**: 参照知識（レビュー・検証の運用ノウハウ）。`ai-review-and-verification-practices.md` が確定前レビュー（計画・仕様の確定点）の実践集であるのに対し、本書は**抜本的な見直し（設計・ロードマップ・開発の進め方そのもの）を対象にした多段レビューの型**を扱う
- **出所**: 2026-09-04 第124回「開発の進め方の見直し」（報告書 `docs/records/reviews/2026-09-04-dev-process-review/report.md`。本書の委譲プロンプト雛形と検査項目はこのセッションの一次情報）。同じ型の先行例 = 設計・ロードマップの全体レビュー第 3 巡追試（`docs/records/reviews/2026-09-04-round3-retest-cleanroom.md`。記録からの再構成で、当時の委譲プロンプトは残っていない）
- **スキル化の候補**: 本書の §2〜§4 はガイドライン側のスキル（確定前レビューへの「クリーンルーム段」「反証段」の追加、または独立の「構造レビュー」スキル）の材料。申し送り先 = Issue-0165（→ 配信元）。スキル化の判断は配信元
- **読むとき**: 抜本的なレビューを計画するとき（ブリーフを書く前）。確定前レビューの通常の反復には使わない（そちらは `pre-finalization-review` が正本）

## 1. 型の全体

| 段 | 担当 | 入力 | 出力 | 目的 |
|---|---|---|---|---|
| 0. ブリーフ | 主レビュアー + 利用者 | 問い・目的関数・データの所在 | 実施計画（観点・体制・費用上限・記録先） | 「何を最適化するか」と「いくら掛けるか」を先に決める |
| 1. 実測 | 主レビュアー + 副（集計・分類・深読み） | 一次データ（会話履歴・記録類・規範文書） | 表・集計・分類・深読み → **要約 1 本**（設計層 / 面 / 点 / 既知の問題 / 深読み / 測定の限界） | 判断の根拠を「読んだ印象」でなく数値と典拠にする |
| 2. クリーンルーム | 副 1 体（上位モデル・新規起動・**リポジトリ読み取り禁止**） | 要約 1 本のみ（目的関数・原則・現行の要約・実測の要約・測定の限界） | 診断・代替案 3 案以上・差分表・推奨・**未確認事項**・**入力の内部矛盾** | 既存決定に係留されていない第一原理の視点を得る |
| 3. 突合 | 副 1 体（読み取り専用・リポジトリ全読） | クリーンルームの出力 + 主レビュアーの抜き取り検査記録 + 照合先の一覧 | 提案の 6 分類（採用済み / 既存決定と衝突 / 既知 / 既知 + 追加 / 新規 / 要約の誤りに起因）・未確認事項への典拠つき回答・効果量の実測置換 | 提案を既存の決定・課題・実測に係留し直す |
| 4. 統合草稿 | 主レビュアー | 1〜3 の出力 | 判定・所見・代替案評価・提案の採否候補・**命題一覧** | 利用者が採否を判断できる形にする |
| 5. 反証 | 副 1 体（読み取り専用） | 草稿 + 典拠の所在 | 命題ごとの判定（一致 / 一部不一致 / 不一致 / 判定不能）+ 追加命題 | 主レビュアーの誤りを、結論を確定する前に捕まえる |
| 6. 報告書・採否 | 主レビュアー + 利用者 | 反証を反映した草稿 | 報告書・起票・申し送り | — |

**主レビュアーは各段の出力を次段へ渡す前に抜き取り検査する**（§4）。主レビュアー自身の工程（要約・草稿）が単一障害点になるため、反証段は省略しない。

## 2. 各段の手順

### 2-1. ブリーフ（段 0）

- **目的関数を利用者との対話で確定する**（単一スカラーにしない。例: 品質は制約〈事後欠陥の検出数〉・費用を最小化〈人間の関与・トークン・壁時計・期待将来費用〉）
- **データを 3 層で置く**: 面（流れ。会話履歴のプロセストレース・計画の完了記録・逸脱記録）/ 点（症状。作業記録のクラスタ）/ 設計（あるべき流れ。規範文書）+ 既知の問題（課題・ADR）
- **費用上限を先に決める**（先行レビューの実測の 1.5 倍など）。超える見込みなら段を別セッションに分ける
- **情報衛生**: 会話本文は読まない（数値・順序のみ）。深読みする異常値は事前に本数を決める
- ブリーフは `docs/working/plans/` に置き、実施後に closed にして要点を報告書へ移す

### 2-2. 実測（段 1）

- 抽出・集計は**ファイルに書いたスクリプト**で行い、再走可能にする（heredoc に長い日本語を埋めない = 作業記録 `LoopForAlpha-2026-09-04-11`）
- 副エージェントへ委譲するのは「全数走査 + 分類」（作業記録のクラスタリング・記録類の分類・ゲートの棚卸し・深読み）。委譲プロンプトには全数走査・母数明示・実証なし不採用・絶対パスを入れる
- 要約 1 本（クリーンルーム段への入力）は**主レビュアーが書く**。必須の内容:
  1. 「AI に返る情報」と「記録側の情報」の区別（無いものと、あるが読まれないものを分ける）
  2. 各ゲート・各値の**意味論**（誰が・いつ・何を決めるか。記録の各欄が何の結果か。例: `worklog=` は AI の記録ゲート判定結果であって人間の採否ではない）
  3. 既に存在する規則（停止判定・上限・例外）は「存在する」と明記する（書かないと「無い」と読まれる）
  4. 測定の限界（欠測・代理指標・誤検知率）
  5. 合計を省いた部分列挙には「主な内訳」と書く（内部矛盾として指摘される）

### 2-3. クリーンルーム（段 2）

- 新規起動 1 体・上位モデル。**読んでよいファイルを 1 本に限定**し、リポジトリ・記録・スキル定義・検索・git を禁止する（開いた時点で段が無効）
- 課題は 7 点で固定する: 診断（典拠つき）/ 代替案 3 案以上（骨格・原則との整合・効果の見積もり・導入費用と可逆性・撤退条件）/ 利用者の構想を同じ土俵で評価 / 差分表（行 = 現行の全項目・母数明示）/ 推奨と最小変更 / 未確認事項（判明するとどの判断が変わるか）/ 入力の内部矛盾
- 「仮説」と「実測」を印で分けさせる。一般知見（外部の論文等）は出典を明示させ、実測と区別させる
- 出力の分量目安を書く（15〜30KB）。超過は A 群 1（実態優先）で許容される

### 2-4. 突合（段 3）

- 別の 1 体・読み取り専用。照合先を**絶対パスと母数つきで列挙**し、全数走査させる
- 6 分類は 1 件 1 分類（複数該当は主判定 + 備考）。分類の対象を明示する（診断の主張 / 案の構成要素 / 差分表のセル / 最小変更）
- 未確認事項は、数値で答えられるものはスクリプトで再計算させ、スクリプトを保存させる
- 効果量は「仮説」を実測で置き換えさせ、置き換えられないものは「測定不能（理由）」と書かせる
- 導入費用は「変更が必要なファイルの絶対パスと行数」で示させる

### 2-5. 統合草稿と反証（段 4〜5）

- 草稿には**命題一覧**（20〜25 件。各命題に「支える所見・提案」を添える）を必ず置く。反証段の対象を主レビュアーが選ぶことになるため、結論を支える命題を漏らさない（反証段に「追加命題」を最大 3 件挙げる余地を与える）
- 反証段は「典拠が実体に在るか」「推論の前提が現設計で成立するか」の 2 軸。判定値 4 種を全数で残す
- **集計値を命題の根拠に引くときは、集計を構成する個々の事例の型を深読み原文まで戻って確認する**（作業記録 `-13`。今回の結論を変えた指摘はこれ）
- **「既存決定なし」と書く前に、当該機構の初出 ADR の Decision を読む**（今回の 2 件目の指摘）

## 3. 委譲プロンプト雛形（今回使ったものの一般化）

共通の骨格: 役割宣言 → `B群判定` 行 → A 群 4 件（根拠つき）→ 検査委譲の制約 → 段固有の規律 → 入力の絶対パス → 課題（番号つき）→ 出力（絶対パス・構成・分量・冒頭の宣言）→ チャット報告の行数。A 群・B 群の正本は `subagent-dispatch` スキル。以下は段固有の部分だけを示す。

### 3-1. クリーンルーム段

```
あなたは <レビュー名> の**クリーンルーム段**を担当する独立レビュアーである。
（B群判定 / A 群 4 件 / 検査委譲の制約 = 全数走査・母数明示・実証なし指摘は「仮説」と明示・絶対パス）

## クリーンルームの規律（最重要）
このレビューは「現行の <対象> を知らない上位モデルが、目的関数と実測だけから第一原理で代替案を出したら何が出るか」を測る設計である。
あなたの価値は、現行の手続き・記録・既存の議論に係留されていないことにある。したがって:
- 読んでよいファイルは次の 1 本だけである: <絶対パス>
- リポジトリ <絶対パス>・設定・ログ・作業記録ストア・スキル定義は一切読まないこと。git・Grep・Glob・Web 検索も使わないこと
  （入力文書内に他ファイルへの参照が出てくるが開いてはならない。開いた時点でクリーンルームが破れ、この段の測定が無効になる）
- 入力文書の記述に不足・曖昧さがあれば、推測で埋めずに「未確認事項」として列挙すること（後続の突合段が実体で答える）
- あなた自身が汎用的に知っている慣行・研究知見は自由に使ってよい。ただし出典を明示し、入力文書の実測と区別すること

## 入力文書の構成
<§ 構成の要約>

## 課題
1. 現行の診断（第一原理から。典拠 = 入力文書の節番号・数値。実測から言えないことは仮説と明示）
2. 代替案を 3 案以上（漸進 〜 構造変更の幅）: (a) 骨格〈誰が・いつ・何を判断し、情報がどう次の行動へ戻るか〉 (b) 原則との整合 (c) 目的関数の各項への効果を実測値との差分で (d) 導入費用と不可逆性 (e) 壊れる条件
3. <利用者の構想> を同じ土俵で (a)〜(e) の形で評価し、上位互換性を判定
4. 差分表（行 = 現行の全項目・母数明示 / 列 = 各案での扱い）
5. 推奨 1 つと理由。前提のうち実測で確認済み / 未確認を分ける。<制約下> で今すぐ変える価値のある最小の変更 1〜3 件
6. 未確認事項（番号つき。判明するとどの判断が変わるか）
7. 入力文書の内部矛盾・不足

## 出力
<絶対パス> へ Markdown 1 本。冒頭に「読んだファイル」「読まなかったこと（未接触の宣言）」「走査した節と根拠にした母数」。分量 15〜30KB。数値に節番号。略号を新造しない。
最後にチャットで出力パスと要点を 10 行以内で報告。
```

### 3-2. 突合段

```
あなたは <レビュー名> の**突合段**を担当する独立レビュアーである。読み取り専用で作業する（出力はスクラッチパッドへのみ）。
（B群判定 / A 群 4 件 / 検査委譲の制約 = 照合先は全数走査し母数を報告・分類には典拠〈絶対パス + 行番号 / ADR 番号 / Issue 番号〉・示せなければ「典拠なし（仮説）」・絶対パス・会話本文は読まない）

## 背景
4 段構成（実測 → クリーンルーム → 突合 → 反証）。クリーンルーム段は <対象> を知らない 1 体が要約だけから代替案を出した。あなたはその出力をリポジトリの実体と照合する役である。

## 読む入力（絶対パス）
1. クリーンルーム段への入力 2. クリーンルーム段の出力（照合対象） 3. 主レビュアーの抜き取り検査（未検証の項目番号を明示し、あなたに確認を委ねる）

## 照合先（絶対パス。全数走査の対象）
<ADR フォルダ（件数）/ 課題索引（行数）/ 規範文書（配布版と正本の差の扱い）/ 実測の正本と CSV（列定義の所在）/ 読み方の注意>

## 課題
1. 提案の 6 分類（採用済み / 既存決定と衝突〈ADR 番号〉/ 既知〈Issue 番号〉/ 既知 + 追加〈何が追加か〉/ 新規 / 要約の誤りに起因〈実体を示す〉）。対象 = 診断の主張・案の構成要素・利用者の構想の評価点・差分表のセル・最小変更。件数を明示し全件を表に。末尾に集計表
2. 未確認事項 N 問への典拠つき回答。数値で答えられるものはスクリプトで計算し保存（判定規則と限界を明記）。答えられない問いは「答えられない（理由）」
3. 費用・効果の見積もり: 「仮説」を実測で置換、置換できないものは「測定不能（理由）」。導入費用は変更対象ファイルの絶対パスと行数
4. 要約の残検査: <主レビュアーが未検証とした項目>

## 出力
<絶対パス> へ。冒頭に「走査した照合先と母数」。分量 30〜50KB。
最後にチャットで 6 分類の集計・「新規」と「衝突」の要点・数値で答えた問いの数を 12 行以内で報告。
```

### 3-3. 反証段

```
あなたは <レビュー名> の**反証段**を担当する独立レビュアーである。読み取り専用。
（B群判定 / A 群 4 件 / 検査委譲の制約 = 命題は全数判定し判定不能も表に残す〈母数明示〉・判定には典拠・絶対パス・会話本文は読まない）

## 費用の制約
残り目安 ≈ <N> 万トークン。命題の典拠として名指しされたファイル・行だけを読む。全件の再走査は不要（突合段が済ませている）。出力は 15KB 以内。

## 役割
草稿 §<命題一覧> の命題 <N> 件を実体で判定する。2 軸: (1) 典拠が実体に在るか（名指しされたファイル・行・数値が実在し文言どおりか） (2) 推論の前提が現設計で成立するか（命題が支える所見・提案がその典拠から本当に導けるか）。
判定値: 一致 / 一部不一致（訂正文つき）/ 不一致（根拠つき）/ 判定不能（理由）。不一致は「草稿のどの所見・提案にどう影響するか（結論が変わるか・数値が変わるだけか）」を 1 行で。
命題に挙がっていないが草稿の結論を支える暗黙の前提に気づいたら「追加命題」として最大 3 件まで判定してよい。

## 読む入力（絶対パス）
草稿 / 典拠の所在（実測・CSV・再計算スクリプト〈再走可〉・ADR・課題・配布版スキル・対象プロジェクトの規範文書）

## 出力
<絶対パス> へ: (1) 読んだファイル一覧と再走したスクリプト (2) 判定表（# / 命題の要約 / 判定 / 典拠 / 影響）+ 追加命題 (3) 集計 (4) 結論が変わる指摘の要旨（無ければ「無し」と明記）。
最後にチャットで出力パス・集計・結論を変える指摘の有無を 6 行以内で報告。
```

## 4. 主レビュアーの検査項目（各段の受け取り時）

| 受け取る段 | 検査 | 今回捕まえたもの |
|---|---|---|
| 実測の要約（自分で書く） | 合計の整合 / 意味論の記載 / 「あるが読まれない」と「無い」の区別 | 捕まえられず（クリーンルーム段が内部矛盾 11 点を指摘。実質の誤り 1 点） |
| クリーンルーム段 | 内部矛盾の指摘を正本で全数検査 / 提案が要約の誤りの上に立っていないか | 要約の部分列挙 5 点・帰属の誤り 1 点を確認し検査記録へ |
| 突合段 | 衝突判定の典拠（ADR の Decision 節）を実体で読む / 機械計算を再走 / 母数の一致 / **推論の前提を書き出す**（例: 集計の代理指標の限界） | 典拠は全一致・行番号ずれ 1 点。前提 4 点を書き出し反証段の対象に含めた（うち 1 点が結論を変えた） |
| 反証段 | 不一致・一部不一致の典拠を実体で読む | 全件一致 |

検査記録は各段の出力と同じフォルダに残す（`cleanroom/02`・`04`）。「主レビュアーが疑った前提は自分で原文へ戻る」を追加すべきだった（今回は反証段へ委ねた結果、1 体分の費用で済んだが、次回は主レビュアーが先に戻る）。

## 5. 費用の実測配分（次回の予算設計の基線）

| 段 | 体数 | トークン | 結論への寄与 |
|---|---|---|---|
| 実測（集計・分類・棚卸し・深読み 2） | 5 | ≈ 140 万（61%） | 判断の根拠すべて。深読みが最も高価で、修正語辞書の誤検知（85〜90%）を暴いた |
| クリーンルーム | 1 | 8.6 万（4%） | 新規の視点 1 件（停止点の費用）+ 要約の誤り検出 |
| 突合 | 1 | 61.5 万（27%） | 衝突 5 系統の特定・効果量の実測置換。判断を変える指摘は無し |
| 反証 | 1 | 18.2 万（8%） | **結論を変える指摘 2 件** |
| 計 | 8 | ≈ 228 万（上限目安 246 万 = 先行レビュー 164 万の 1.5 倍） | — |

読み方: 反証 > クリーンルーム > 突合 の順に費用対効果が高い。突合は分類の網羅性に価値があるが、照合先を絞れば半減できる（今回は ADR 122 件の索引全行 + 本文 26 本・課題 121 件 + 本文 23 本・配布版スキル 36 ファイル全文）。

## 6. 失敗の型（再演を防ぐために読む）

1. **要約の意味論の欠落**（2 回目）: 「停止規則が無い」「`worklog=` は人間の採否」がクリーンルーム段の提案に混入。第 3 巡追試でも同型（`LoopForAlpha-2026-09-04-06`）。対策 = §2-2 の必須項目 2・3
2. **集計値の型の誤帰属**: 突合段が「番号回答型」として算入した放置 1,063 分は、深読み原文ではレビュー指摘採否 + ADR 承認だった。主レビュアーも草稿の提案の根拠に引いた。対策 = §2-5 の原文回帰（`-13`）
3. **「既存決定なし」の見落とし**: 継続確認は ADR-0005 が明文で定めていた。対策 = 機構の初出 ADR の Decision を読む
4. **主レビュアーの単一障害点**: 要約・草稿・検査を 1 体が担い、誤りは独立レビュアーが捕まえた。対策 = 反証段を省かない。要約の意味論の検査だけは別の 1 体に委ねる案（未試行）
5. **測定の代理指標の限界**: 人間待ちは読了時間と離席を区別できず、番号回答は 15 字以下で代理した。効果量の全体値は異常値標本からの外挿で選択バイアスがある。対策 = 報告書に「未確認」として残し、利用者運用で 1 サイクル計測してから機構化する（Issue-0170）
6. **文脈の消失**: 設計・ロードマップの全体レビュー（第120〜121回）の委譲プロンプトと判断の経緯は記録に残さず、本書は記録からの再構成しかできない。対策 = レビューを閉じる前に本書のような手順書を書く（本書自体がその実践）

## 7. 適用条件と撤退条件

- **使うとき**: 対象が「体系」（設計群・ロードマップ・進め方）で、既存の決定に係留されたレビューでは視点が出ないと疑うとき。実測データ（会話履歴・記録類）があり、費用上限を先に置けるとき
- **使わないとき**: 計画・仕様の確定点の通常レビュー（`pre-finalization-review` で足りる）。実測が無い対象（クリーンルーム段の入力が「意見」になる）
- **撤退**: 実測段で費用上限の 6 割を超えたら、クリーンルーム + 反証だけに縮める（突合は主レビュアーの抜き取りで代替）。反証段は縮めない
