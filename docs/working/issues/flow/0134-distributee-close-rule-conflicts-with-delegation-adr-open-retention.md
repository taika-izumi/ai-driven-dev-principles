## 課題内容

課題管理定義 §4 は、配布先の `flow/` 課題を「ガイドライン repo へ申し送り済み」で close し、その契機を「受け皿の実在を確認した時点」と定める。一方 ADR-0118 は、委譲した 4 課題（LoopForAlpha#Issue-0043 / 0096 / 0109 / 0117）について「委譲済み・以後の正本はガイドライン repo」を追記して **open 維持**（配布先側の新観測の追記先として残す。close は対策実装後に効果を確認できた時点）と定めた。受け皿 4 件と ADR-0118 の実在は配布先で 2026-08-31 に確認済みなので、§4 に従えば 4 課題は close 条件を満たしており、両者は同時には満たせない。

**射程は狭い**（配布先の 2026-09-03 実測）: ADR-0118 の「open 維持」は同 ADR が名指しした 4 課題への個別の状態遷移指示であり一般規範ではない。以後の申し送り（LoopForAlpha#Issue-0130 → Issue-0119、LoopForAlpha#Issue-0140 → Issue-0121）は §4 のとおり close して何とも衝突しなかった。したがって矛盾は 4 課題に限局する。

**一般形として残るもの**: 「委譲した後も配布先に新観測の追記先を残したい」という要求はどの配布先でも起こりうる。課題管理定義には委譲後の新観測の追記先が定義されていない（§4 の再発・進展の一次記録は「既存 open 課題」を前提にしており、close 済み課題への追記も、受け皿への直接追記も規定がない）。配布先が §4 の例外条項を固有ルールとして書くと配信物をローカルで分岐させるため、配布先は課題化で受けた（LoopForAlpha#ADR-0181）。

**本リポジトリで決めるべき問い**:

- (a) ADR-0118 が保留した 4 課題の扱い: §4 どおり配布先で close させるか、open 維持を続けるか（ADR-0118 の Consequences の保留の解消。決めたら配布先へ伝える）
- (b) 課題管理定義 §4 に、委譲後の新観測の追記先を一般規則として置くか。候補: 配布先は close し新観測は受け皿（本リポジトリ）へ `<repo>#Issue-NNNN` 修飾つきで直接追記する / 配布先の close 済み課題への追記を許す / 現状どおり個別 ADR で指示する

# Issue-0126: 配信物の課題管理定義が定める「申し送り済みで close」と、委譲元 ADR が定める「対策実装まで open 維持」が矛盾する

- **Status**: open
- **Opened**: 2026-08-31
- **起票元**: 2026-08-30 のガイドライン repo 委譲作業（LoopForAlpha 側 4 課題への追記）をコミットする前の整合確認で検出
- **関連**: ADR-0181 / MakeAiInstructions#ADR-0118 / Issue-0043 / Issue-0096 / Issue-0109 / Issue-0117

## 課題内容

課題管理定義（`docs/overview/issue-management.md` §4 ライフサイクル）は、配布先プロジェクトの `flow/` 課題について次の 2 点を定めている:

- 配布先の `flow/` 課題は「ガイドライン repo へ申し送り済み（または対応済み）」で close する。close の条件は「解決済み」ではなく「申し送り済み」である
- close トリガーは、ガイドライン repo 側に受け皿が**実在することを確認した時点**である

一方、委譲を決めた `MakeAiInstructions#ADR-0118`（Status: Accepted）は「LoopForAlpha 側の状態遷移」として次を定めている:

- 4 課題へ「委譲済み・以後の正本はガイドライン repo」を追記し **open 維持**（LoopForAlpha 側の新観測の追記先として残す。close は対策実装後に効果を確認できた時点）

受け皿（`MakeAiInstructions#Issue-0112` / `#0113` / `#0107` / `#0114`）と `MakeAiInstructions#ADR-0118` の実在は 2026-08-31 に実体確認済みであるため、課題管理定義に従えば Issue-0043 / 0096 / 0109 / 0117 は既に close 条件を満たしている。両者は同時には満たせない。

`MakeAiInstructions#ADR-0118` の Consequences 自身が「LoopForAlpha 側の更新方法・クローズ判断はユーザーと確認する」と保留を明記しており、この判断は未了のまま残っている。

**一般形である点**: 本件は LoopForAlpha 固有の事情ではなく、「配信先の課題を配信元へ委譲したが、対策実装まで配信先に新観測の追記先を残したい」という、どの配信先でも起こりうる型である。したがって解消の正本は配信元側の課題管理定義にある。

**配信物である点（実測）**: `docs/overview/issue-management.md` は配信元の `template/docs/overview/issue-management.md` と**バイト単位で同一**（ともに 15,830 バイト・`diff` の差分 0 行。2026-08-31 実測）。LoopForAlpha は本文書を一度もカスタマイズしていない。したがってこのファイルへ直接例外条項を書くと、配信物をローカルで分岐させることになる。

**放置した場合の影響**: 次サイクルで課題管理定義を読んだセッションが「受け皿実在＝close」と判定し、4 課題を新観測の追記先として残す意図が失われうる。各課題の追記行に「open を維持」と明記されているため気づける可能性はあるが、規約と課題本文が食い違ったままになる。
