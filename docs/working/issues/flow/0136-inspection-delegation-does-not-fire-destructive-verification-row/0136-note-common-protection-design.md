## 改定案

中心は `skills/subagent-dispatch/SKILL.md`。既存の常時適用4件と条件判定の仕組みを利用し、次を組み込む。

1. **委譲本文と判定行を照合する。** 「検査」等の名称だけで判断せず、変更実験を指示する場合は破壊的検証も適用する。変異検査の適用例は対象のテスト文化に合わせるという既存条件を維持する。
2. **指示外の変更実験を無保護で始めさせない。** 委譲元は下記の起動前確認で、検査対象の原本・共有ツール・既存記録を変更できない実行経路を準備する。追加の変更実験が必要なら、実行前に委譲元へ報告して範囲と経路を決める。文書の静的確認だけの担当へ、VM起動や全ファイルのハッシュ比較を一律に課さない。
3. **許可先を具体的に渡す。** 検証用コピー・新規出力先・保護対象を区別する。パスは信頼できる基点から絶対パスへ解決して照合し、実行文脈によって別ファイルを指す変数を基点にしない。制限外への書き込みが必要なら、その処理を停止し、解除して自動再試行しない。
4. **後片付けを名指しにする。** 今回作ったパスを記録し、その範囲だけを対象とする。共有の一時領域を時刻・ワイルドカードだけで選ばない。既存物の削除承認と、作成物の削除可否を混同しない。
5. **委譲元が結果を確認する。** 破壊的検証を明示した委譲に加え、実行を伴う検査委譲でも、起動時の実行経路・対象版・保護範囲と実際の実行・結果を照合する。明示的な変異がないことを確認省略の根拠にしない。既存の前後比較は対象を絞って維持し、ツールチェーン全域の常設ハッシュ監視は初期案に含めない。範囲外の破損を事後比較だけで防げるとは扱わない。

環境別の起動条件・確認項目は、新設候補 `skills/subagent-dispatch/references/inspection-isolation.md` にまとめ、実行を伴う検査委譲時に読む。コマンドの固定複写は避け、利用版のヘルプと実効設定を確認する。実行を取りまとめる新しい汎用基盤や、全員分のVMは今回の初期案に含めない。

## 起動前確認の担当と順序

`subagent-dispatch` は、委譲条件の組み立てに加え、委譲元が行う起動前・受け取り時の確認を定める。実際の起動・権限設定は委譲元が既存ツールで行う。参照文書を渡すだけでこの準備を完了したとは扱わない。

1. 委譲元が、対象版、検証用コピー、新規出力先、原本・共有ツール・既存記録の保護範囲を特定する。現在の未コミット・未追跡の検証対象も含むという既存条件を維持する。
2. 実行を伴う検査では、既存の起動機能で担当全体を狭い権限に置くか、書き込み可能な操作を保護された経路だけへ限定する。親の広い権限を継承したまま、狭いコマンドの使用を指示するだけでは不可。使用可能なシェル、内蔵編集、MCP等に直接の変更経路が残らないことを実効設定・ツールの利用可否・無害な確認結果で確かめる。
3. 準備した実経路と保護範囲を確認してから起動する。能力・設定を確認できない場合、書き込み可能な操作を持たない静的確認へ限定できるなら、その未検証範囲を明示して委譲する。限定もできない場合は実行を伴う委譲を止め、必要な環境・依存と利用者の作業を相談する。プロンプトで「書き込み禁止」と伝えるだけでは限定成立としない。
4. 担当から実行内容と結果を受け取ったら、「改定案」5に従って委譲元が照合する。制限外の操作が必要になっても、担当が制限を解除して自動再試行しない。

上記を満たす具体的なCodex・Claude Codeの起動方法は、既存機能の実証後に参照文書へ記載する。今の環境で未実証の起動方法を、対応済みの経路として配布しない。既存機能だけで条件を満たせない場合は、規範だけを完成扱いにせず、承認記録の相談事項へ戻る。

## ツール別の完了条件

| 経路 | 現在の証拠 | 改定完了までに必要なこと |
|---|---|---|
| Codex・Windows | 試験専用ファイルの親子拒否・内蔵編集拒否・副担当への制限継承、配布検査成功。Pester変異は同じCodex隔離を使う固定接続で確認 | 実際の検査担当の起動から受け取りまで同じ制限を保持し、狭いコマンドを迂回する直接操作ができないこと。Pesterの変更実験と既存記録保全を無害な例で確認 |
| Claude Code | Readと固定MCP1件だけのClaude起動で、既存Codexを介したPester正常・変異・復元、親子拒否、既存記録保全・結果回収を確認 | 実際のClaude Code起点の経路で同じ保護条件と結果回収を確認。担当全体の制限または直接操作経路の無効化を含める。Windowsネイティブから既存の隔離実行を呼ぶ案と、WSL2で完結する案を対象の互換性・負担で比較する |

Claude Code対応の条件を満たさないまま本作業を完了扱いにしない。ただし1経路の成功を全OS対応とは呼ばず、確認したOS・ツール版・必要な依存を明示する。Claude Codeのみの環境へCodex導入を必須にすること、WSL移行、別ランタイムの新設が必要と分かった場合は、利用者の追加作業と維持負担を示して設計を見直す。

## 検証で区別するケース

- 静的な確認では変更実験の保護手順が過剰に適用されない。
- 実行経路を制限できない例では、書き込み可能な操作を持たない静的確認への限定、または実行委譲の停止へ進む。禁止文だけの委譲や、シェル以外の直接変更経路が残る例は成立と判定しない。
- 検査の中で明示した変異は関連する判定が適用される。指示外の変更実験は報告へ戻り、原本を変更できない。
- 正常な検証用書き込みは成功し、原本・共有ツールの代わりに用意した保護ファイルは親・子の両方から変更できない。単に処理全体が失敗した結果を保護成功に数えない。
- 隔離内でも既存記録を混在させた例で、今回作ったものだけが後片付け対象になる。検証では対象選択と内容保全を確かめ、実記録を削除しない。
- 同じ検証が通常環境と隔離環境で成立し、見送り・未実行・環境不一致を成功に含めない。重い検証は16GB環境でまず1件ずつ確認する。

## 判断の分担の提案

設計承認後は、文言・参照配置・無害な試験ケース・既存機能内の引数調整をAIに任せる案。後続の計画・実装・記録にも適用する。対応ツールの削減、保護条件の緩和、新しい必須依存、利用者の環境移行、実験による既存データの変更は相談事項とする。設計確定前レビューの実施・方式は既存規範に従って提示する。
