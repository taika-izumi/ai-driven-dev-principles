## Docker Sandboxesが今回に近い理由

[Codex対応の公式案内](https://docs.docker.com/ai/sandboxes/agents/codex/)には、ホスト上のOAuthまたはAPIキー設定、ホスト側での認証保持がある。したがって、認証キャッシュをコンテナへコピーする独自処理を先に作る必要はない可能性がある。契約・アカウント・導入版での実認証は未確認で、API課金への移行を決めたわけではない。

[隔離の公式説明](https://docs.docker.com/ai/sandboxes/security/isolation/)は、個別Linuxカーネルを持つmicroVM、ホストとは別のDocker Engine、ホスト側のネットワーク制御を説明する。子の内蔵ツールをすべて列挙して削除する方式への依存を減らせる、というのが今回の推論。ただしVM内ではsudoを利用できるので、VM内の権限設定を子に対する強制境界と読み替えない。

[構成の説明](https://docs.docker.com/ai/sandboxes/architecture/)では、ホスト作業フォルダの直接共有、読み取り専用の原本からのclone、ホスト作業フォルダを共有しない方式が区別される。直接共有なら編集はホストへ即時反映される。原本worktreeをそのまま起動対象にせず、既存RequestCopyが準備したコピーを搬入する案で比較する。cloneだけで未コミット内容・HEAD・全参照が今回と同じになるとは認定しない。

## そのまま導入しても満たせない条件

1. **共有領域:** [既定設定](https://docs.docker.com/ai/sandboxes/security/defaults/)では、対応エージェント用の共有スキル領域が読み書き可能。`--no-share-skills`を明示する必要がある。暗黙の現在ディレクトリ共有も避ける。
2. **ホストへの追加経路:** 隔離説明にはホストのクリップボードへの書き込み経路がある。MCP gatewayに登録したローカルSTDIOサーバーはホストで動く。これらを使わない設定・接続を確認し、ファイルを共有しないことだけで全ホスト操作不可と主張しない。
3. **通信:** [ネットワークポリシー](https://docs.docker.com/ai/sandboxes/governance/access-controls/network/)は許可先を制御できるが、Codexとテストを同じVMに置けばテストからも許可先へ到達する可能性がある。モデル通信を許すこととテストの外部通信なしは別。子が管理できるVM内Dockerへnetwork=noneを設定しても、子による変更を阻止する保証にはならない。
4. **Gitの保全:** VM内コピーの.gitを読み取り専用にするだけでは、sudoを持つ子に対する保護と認定できない。原本の保全と、子が触るコピー内Gitの変更禁止は別の要求。ホスト側強制の読取専用共有等が利用可能か検証するか、変更禁止を維持する別配置を設計する必要がある。
5. **証拠:** ファイル・出力を回収できることと、子が実行証拠を偽造できないことは別。VM内の自己申告ログをそのままCommandRecordにしない。信頼する外側の実行・再実行と対応させる方式を確認する。stop後の状態照会と、別実行が継続する対照も必要。

上記を仕様から削除して採用を容易にする判断はしていない。この比較からは「ホスト隔離と認証の自作を減らせそう」と言えるが、「全要求を既製品だけで満たせる」とは言えない。

## 最小実証の提案範囲

これは承認前の試験案であり、そのまま実行する確定済み実装計画ではない。

1. **導入前確認:** Windows/WHPとsbx配布版を確認。利用者へ必要なインストール・ログイン・OS変更の有無を示す。旧DockerやLoopForAlphaは変更しない。
2. **AIなしの固定試験:** 新規の合成Gitリポジトリだけを使用。共有スキルなし、ホスト原本・control・ホームを共有しない配置で、固定コマンドによるファイル搬入・出力回収・停止を検査する。`sbx create`のworkspace省略と`sbx cp`は公式機能として存在するが、採用版のargvと動作を再確認する。
3. **保護の対照:** 作業コピーへ書けること、原本・Git・control・機密代用品を守ること、許可外通信を拒否すること、別実行を止めないことを確認。MCP gateway・共有スキル・クリップボード等の追加経路も検査対象にする。保持できない要求があれば実モデルへ進まず差分を報告する。
4. **認証の固定試験:** 利用者の選んだ方式で認証し、秘密値を子へ公開せずモデル要求が通るかを、小さな固定入力と別承認で検査する。モデルへ実プロジェクト本文を送らない。
5. **成立後の往復:** 正式な構成・保護条件を確定し、小さなPython欠陥の検査→回収→修正→同じテストの再検証を両主担当から実施する。共通CLI・証拠照合の自作範囲をそこで確定する。

初期負担は製品導入とログイン、後続負担はテンプレート版・ポリシー・保存領域の維持。Modalではこれにクラウド課金と搬入出処理、独自Docker案では認証・通信基盤の実装保守が加わる、という概算比較である。実測の工数や成功率ではない。

## 現時点の結論

Docker Sandboxesを先に実証する案が、Codexを維持しローカルの既存コピー資産を活かす条件に最も近い。採用を確定するには、上記の未充足条件とWindows導入条件を解消する必要がある。クラウド利用・保護緩和・新規導入を比較着手の承認へ含めない。
