# Linux・Python試作で隔離と担当間の往復を成立させる構成案

問い: リポジトリとGit履歴を子が自由に探索し、追加テストを作成・実行できる状態を保ちながら、ホスト上の原本・機密・サービスを操作できない構成を小さく試せるか。

状態: 2026-09-09、設計案。Linux試作の設計を先行する選択はADR-0151に記録。以下のMCP接続・コンテナ構成の採用はまだ確定していない。実エージェントや試験コンテナは起動していない。

## 確認できた前提

- 通常ユーザー権限でDockerサービスの版とローカルイメージ一覧を読み取り確認。Docker Desktop 4.81.0、Engine 29.6.1、Linux/amd64、WSL2。`loopforalpha-sandbox:latest`（短縮ID `b6f82765069d`、一覧表示1.11GB）とhello-worldが存在する。コンテナの起動・停止・イメージ取得は行っていない。
- サンドボックスユーザーからのDocker API接続は拒否された。起動側には通常ユーザーのDocker利用権限が必要。モデルへDockerソケットやその権限を渡すこととは区別する。
- 既存DockerfileはPython 3.12 slimを基に、uvとプロジェクト依存を含む。既存pyprojectにはpytestがある。稼働イメージ内の実バイナリ・Gitの有無・版は未確認。DockerfileだけでGit利用可能とは扱わない。
- Codex CLI 0.153.4の`features list`で`--disable shell_tool`による`false`を確認。一方、`unified_exec`・`code_mode_host`は`true`のまま。設定値の確認だけで全実行経路が閉じたとは扱わない。
- `--ignore-user-config`はこの版のexec側オプションで、トップレベルのfeatures照会では受理されない。検査と実起動の引数位置を混同しない。

公開仕様の根拠（2026-09-09閲覧、提供元の一次資料）:

- [OpenAI設定リファレンス](https://learn.chatgpt.com/docs/config-file/config-reference): `features.shell_tool`は既定シェルの有効化、`mcp_servers.<id>.enabled_tools`はMCPツールの許可リスト。これだけで全内蔵ツールを制限できるとは書かれていない。
- [OpenAIのMCP接続](https://learn.chatgpt.com/docs/extend/mcp?surface=cli): STDIOによる子プロセス接続を設定できる。
- [Dockerのnoneネットワーク](https://docs.docker.com/engine/network/drivers/none/): `--network none`ではコンテナ内にループバックだけが作られる。今回の実機でホストのローカルサービスへ到達できないことは別途実証する。

## 比較した構成

| 案 | 利点 | 負担・未確認 |
|---|---|---|
| ホストの通常シェルからDockerラッパーを呼ばせる | 既存コードに近い | 通常シェルが残るとラッパーを迂回できる。現在の通信制限の不足を解消したことにならない |
| ホストAIには限定したMCP接続を渡し、コマンドはDocker内だけで実行する | 既存認証・コピー・Git履歴を活かせる。子は汎用コマンドで資料を探索できる | 小さな接続処理の追加と、通常シェル等の無効化の実効確認が必要 |
| AI本体も別環境へ移し、モデル通信だけを許可する | ホストからさらに分離できる | AI認証・通信の許可先・環境の保守が増える。初回の準備が大きい |

第2案を推奨候補とする。MCPはAIが外部の操作を呼ぶための接続方式であり、常駐のサービスや組織全体のメッセージ基盤を設ける案ではない。検証1回に紐づくSTDIO接続を起動側が用意する。

## 推奨候補の処理の流れ

1. 主担当が短い依頼（目的・合格条件・対象）を作る。既存のRequestCopyでリポジトリのファイルと履歴を独立コピーへ準備する。本文のコピーと履歴移送はスクリプトが行う。
2. 信頼する起動処理が、当該実行専用のLinuxコンテナとMCP接続を作る。コンテナIDを保存し、以後の操作先をこのIDに固定する。
3. ホスト上のCodex検証担当には、コンテナ内でコマンドを実行する入口を渡す。通常のホストシェル、別のコード実行、外部アプリ等の迂回経路は公開しない。実際に閉じられなければこの方式を対応済みとしない。
4. 子はコンテナ内でファイル一覧・検索・本文・git log/show/blameを必要に応じて読み、追加テストを作成して実行する。親が関連資料を事前選択し続ける運用にしない。
5. 信頼する起動側が、要求したコマンド、実際のDocker呼び出し、開始・終了状態、標準出力・標準エラーを保存し、成果物のパスとハッシュを照合する。
6. 主担当が指摘と再現テストを受け取る。修正版と同じ再現テストを新しい実行番号へ渡し、再検証する。通常の受け渡しに人の手動転記を含めない。

## 3ブロックの責務

既存の依頼準備・実行・回収の分割を維持する。3つ以上の構成要素にまたがるため、方針承認後はfeature-block-designの修正モードで現行仕様00〜03を更新する。

| ブロック | 活かす部分 | 具体化する差分 |
|---|---|---|
| 依頼・コピー準備 | RequestCopy、Git履歴・headRef、原本状態のmanifest | Linuxで使うパス、実行イメージの固定、必要な依存の確認 |
| 制限付き実行 | 主担当2種から共通入口へ依頼する構成、出力保存 | 実行ごとのSTDIO MCP接続、Codexの操作制限、Dockerコンテナ作成・コマンド実行・停止 |
| 結果回収 | 原本状態・生成物・応答の照合 | MCP操作と起動側の実行記録の対応付け、再現テストの次回への受け渡し |

`Result.psm1`は現在Codexの`command_execution`イベントに依存している。MCP経由の結果をそのイベントに偽装せず、実際のMCP呼び出しと起動側の記録を対応付ける。Dockerクライアントの終了をコンテナ内の停止確認の代わりにしない。

## 操作の境界

- コマンド入口の実行先・イメージ・マウント・通信設定は起動側が固定する。子からDockerオプション、コンテナID、ホストのパスを受け取って自由に差し替える機能は設けない。
- 子のコマンド文字列はコンテナ内のシェルだけで解釈する。ホストでは実行ファイルと引数配列でDockerを呼び、子の文字列をPowerShell等で評価しない。
- 作業コピーを`/work`へ渡し、Git管理領域は読み取り専用にする。制御用記録・原本・ホーム・AI認証・Dockerソケットをコンテナへ渡さない。作業領域の外で生成したファイルは原本に戻さない。
- コンテナは通信なし、ホストの名前空間や特権を共有しない。CPU・メモリ・プロセス数・実行時間を制限し、権限追加を避ける。値は小さな題材の正常動作と併せて具体化する。
- 起動側がログを保存し、子による既存ログの上書きを許可しない。大きい出力は部分表示と明示し、全文を保存する。子からの追加閲覧の方法も詳細仕様で定める。
- 時間超過・中断では保存済みの当該コンテナIDだけを停止し、停止状態を照会する。既存LoopForAlphaの接頭辞による一括停止は流用しない。
- 子のコードはホスト上でimport・実行しない。追加テストを採用した後も、そのコードを実行する場所と承認は通常の検証手順で判断する。

## 最初に確かめる条件

1. **迂回経路の閉鎖**: Codexの機能設定・実際のツール構成を照合し、ホストシェル・コード実行・外部ツール・再委譲が利用できないことを確認する。内蔵編集等を残す場合も保護領域への操作が拒否される必要がある。設定受理だけで合格にしない。確認できる起動方法が得られなければ、実モデルを無制限で起動せず方式判断へ戻る。
2. **AIなしの実行境界**: 合成データでコピー内の書き込みは成功し、原本代用品・Git管理領域の変更とホストサービスへの接続は失敗する。通常側の成功を対照に取る。リンク・子プロセス・時間超過・別実行の継続も確認する。
3. **担当間の往復**: 小さなPython題材の欠陥を追加テストで検出し、指摘・証拠・テストを回収する。修正版の新しい実行で同じテストが成功する。子が途中で必要になった仕様やGit履歴を自分で参照できることを含む。
4. **結果の真正性**: 起動不能・通信拒否・時間超過・応答不正・原本更新を合格にしない。自己申告ではなく起動側の記録と照合する。テスト内容の十分性まで機械的に証明したとは扱わない。

## 準備と利用者の負担

Dockerは既に動作しているため、現時点で新規インストールを依頼する必要はない。実行時は起動側にDockerへの接続権限が必要。既存イメージ内に必要なGitやテスト依存がなければ、専用の派生イメージを作る案になる。既存イメージの上書きやLoopForAlpha本体の改修を前提にしない。

初回にはイメージと依存の準備、Codex認証・起動設定、保護条件の確認が必要。実際に利用者のログインや操作が必要と判明したものだけを依頼する。コマンドごとのコンテナ作り直しを避け、検証1回の間は同じコンテナを使う案とし、資源と時間は終了時に回収する。削除を伴うコンテナ廃棄は、試作実行の対象と終了処理をまとめて承認する段階で扱う。

既存CLIの直接流用はできず、MCP接続とDocker管理・結果照合の差分を保守する負担は残る。初回から汎用プラグイン・常設DB・並列ジョブ管理を作る案ではない。

## 判断の分担案

この構成案の承認後、Linux試作の詳細仕様作成までを対象に、既存3ブロック内の補助関数・データ項目・検査ケースの具体化はAIが進める。原本保護・資料とGit履歴の探索・主担当2種と検証担当Codex・手動転記不要という要求を維持する。

新たな必須依存、検証担当の変更、保護条件の緩和、既存LoopForAlphaの変更は相談する。仕様確定前レビューの要否、実装計画、イメージ取得・ビルド、コンテナの起動・終了、実エージェント起動・外部送信、導入・公開はこの設計案の承認へ含めず、内容を具体化してから既存の承認条件へ接続する。
