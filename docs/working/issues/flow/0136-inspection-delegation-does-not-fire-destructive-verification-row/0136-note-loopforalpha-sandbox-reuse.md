# LoopForAlphaの既存隔離基盤を今回の検証担当に再利用できるか

問い: 別の隔離環境を新設する前に、LoopForAlphaで構築済みのDocker実行基盤を利用し、今回の不足分だけを追加できるか。

## 経緯と現在地

2026-09-09、ユーザーが「Docker利用ならLoopForAlphaの戦略構築AI用隔離環境と同じことになりそう」と指摘した。主担当は既存仕様・Dockerfile・実行引数生成コード・方式選定ADRを読み、重なる部分が大きいと回答した。次の候補として再利用差分の確認を提案した段階で、ユーザーがセッション中断を指示した。

Docker採用、LoopForAlphaの変更、共通基盤の切り出し、現行実装の撤去は決定していない。元の問題と部品の到達点は`0136-note-network-risk-assessment.md`と本プロジェクトの実装計画が正本。

## 読み取った既存構成

- エージェント本体（Claude）はホスト上で動き、ツール権限を制限する。
- AI製コードの実行を`--network none`のDockerコンテナに限定する。エージェント本体を丸ごと隔離している構成とは区別する。
- ホストのリポジトリ全体をマウントせず、モード別の許可リストで必要なパスだけを読み取り専用で渡す。
- pytest・practice・strategy-sessionの実行モードがあり、資源上限、引数検証、終了コード中継などが既に実装されている。
- 既存イメージは`python:3.12-slim`とuvを使うLinux・Python環境。今回のWindows固有の検証をそのまま移せるとは扱わない。

これらは今回読み取った構成の説明であり、このセッションでDockerを起動して再実証した結果ではない。

## 次に確認する差分

1. 今回の検証対象のうちLinuxで実行できるものとWindows固有のものを分ける。Windowsジョブ等の既存試作をそのままコンテナへ移す前提にしない。
2. 検証担当が追加テストを作る作業領域、原本からのコピー、生成物・ログの安全な回収を、既存の読み取り専用マウント構成にどう接続するか確認する。
3. ホスト側エージェントの読み取り・編集・コマンド・外部ツールの権限が、隔離されたコード実行を迂回しないか確認する。Dockerの採用だけでこの条件が満たされるとは扱わない。
4. 既存ラッパーの直接利用、必要部分の共通化、今回専用の薄い接続のどれが小さい変更で済むか比較する。共通化そのものを先に目的にしない。

今回のコピー準備・結果照合は再利用候補。Windows固有のプロセス管理はDockerの実行管理へ置換する可能性があるが、廃止は未決定。

## 再開後の差分確認（2026-09-09）

本節は方式選択前の調査結果であり、承認済み仕様の改訂ではない。LoopForAlphaのHEADは`544ec7f659eecbca178f26a73e8f402198d4b595`。参照対象は作業ツリーの実ファイルであり、HEADと実ファイルの同一性までは主張しない。

### 調べた方法と限界

前記ファイルに加え、`loop/HarnessLib.ps1`の時間超過処理、`loop/run.ps1`、`loop/settings/loop-settings-0005.json`を読んだ。既存の純関数`Build-SandboxDockerArgs`を、仮の原本パス`D:/synthetic/review-copy`・コンテナ名`lfa-sandbox-inspection-probe`・ゴール`0005`で3モード分呼び、引数列を確認した。ファイルコピー・Docker起動・AI呼び出しは行っていない。

- 3モードとも`run --rm --network none`と資源上限を生成した。
- 読み取り専用マウントはpytestが5件、practiceが5件、strategy-sessionが3件。いずれも書き込み用マウントは無い。
- コマンドは`uv run --no-sync`の後にpytestまたはLoopForAlphaのPythonモジュールを指定する。任意の検証環境を選ぶ入口ではない。
- 標準入力を継続接続する`-i`はstrategy-sessionだけに付く。これは戦略用プロトコルであり、開発担当同士の質問経路ではない。

この確認が証明するのは引数生成の内容だけである。通信拒否・読み取り制限・停止・成果物往復の実効性は未実証。

### 再利用できるものと接続に必要な差分

| 対象 | 実体から確認したこと | 今回への含意 |
|---|---|---|

| ホスト側AIの操作 | 設定0005は編集先とBash入口を限定。`run.ps1`は設定を指定してClaudeを起動する | Codexへ設定をそのまま転用できない。汎用シェル・編集・外部ツールによる迂回を各実経路で確認する必要がある |

### 役割間で成果物を往復させる場合

現仕様の依頼・コピー・回収を使うと、取りまとめ担当から固定した成果物を検証担当へ渡し、指摘・追加テスト・証拠を返す経路を構成できる。ただし、共通CLIが未完成なので往復の動作確認はまだない。

確認すべき一連の例は、欠陥を含む小さな対象を渡す→検証担当が追加テストで欠陥を示す→取りまとめ側が結果と対象版を照合する→実装担当が修正する→新しい実行番号で同じ再現テストと修正版を渡す→再検証する、である。前回の再現テストの明示的な再受け渡しは、現CLIが自動化していない部分である。人の手動転記を通常手順に含めないという現仕様の条件は維持する。

途中の質問は現仕様に専用経路が無い。資料不足は未確認として返して追加資料と再依頼で進める形が候補となる。これはリアルタイムの担当間対話と同等ではなく、必要性と往復費用は小構成で評価する。

並行する実装で原本が変わった場合、現処理は`source_changed`として返すため、旧版の検査結果を最新版の合格にはできない。複数担当の連携では、原本を固定する期間または版ごとの提出物を取りまとめ側で管理する必要がある。全担当が同じ作業領域を編集することは、この連携の必要条件ではない。

### 次に必要な判断

Linux・Python対象で連携と保護の成立を試すことを先行させるか、初回仕様のWindows対応を維持して代替環境の比較を続けるか。前者を選んでもWindows対応の完了には数えない。既存探索用コンテナ・権限設定・ラッパーの変更はどちらにも含めない。

Linux試作にはDockerの利用可能性、対象依存を含むイメージ、AIの認証と権限設定の準備が必要となる。利用者の新規設定・ログイン等が必要かは未確認。試作中の人の判断は準備不足と範囲変更時に残り、日常の依頼・結果の手動転記は導入しない。常設DBやメッセージ基盤の新設は現調査の結論に含めない。

方式選択後の設計では、ホスト機密・ローカルサービスへの到達、制御領域への書き込み、別実行への干渉、対象版の不一致を、許可側の成功と拒否側の確認を組にして検証可能な形にする。現段階で新しい方式の安全性を承認済みとは扱わない。
