# sbx実証後の保護条件と構成案

2026-09-09。AIなし試験成功後の設計検討資料。2案提示後、ユーザーは詳細説明と比較表を受けて「なるほど。案１で行きましょうか。」と回答。案1の基本方針は承認済み（ADR-0157）。以下の案比較は判断時の記録。詳細仕様・実モデル起動は未確定。変更理由は、既製sbxの権限構成が旧Linux仕様の強制境界と一致しないため。実機記録は`docs/records/experiments/2026-09-09-sbx-smoke.md`20:21節。

## 確認できた土台

通常ターミナルで起動したsbxを主担当のCLIから利用し、共有なしのVMへ合成ファイル・Git履歴を搬入、追加出力と終了コードを回収し、VMを停止できた。コピーの所有者調整が必要だった。実モデル・実プロジェクト・追加ホスト経路の保護・強制停止は未実証。通常起動は今回の環境で有効だった手順で、権限原因の確定ではない。

## 旧仕様との差

| 旧仕様が要求すること | sbx単体に置き換えた場合 |
|---|---|
| 原本・ホストホーム・制御記録を子から隔離 | 共有なしとホスト側制御を基本にできる。ただしクリップボード等の追加経路を別途検証する |
| コピー内.gitも子が変更できない | コピーはVM内の書き込み可能データ。sudoを持つ子に対し所有者・chmodだけでは強制できない |
| 検証コマンドの外向き通信なし | Codexのモデル通信を許すと同VMの他プロセスにも許可先が開く可能性がある |
| 子の各操作に信頼側の実行記録が対応する | VM内ログは子が変更できる。外からのexec記録だけで子の全内部操作を網羅したとは言えない |

根拠は提供元の一次資料：[既定の権限](https://docs.docker.com/ai/sandboxes/security/defaults/)、[隔離境界](https://docs.docker.com/ai/sandboxes/security/isolation/)。VM内sudo・全面的なファイル操作・VM単位の通信制御という記載からの設計上の推論であり、今回すべての迂回経路を実証したわけではない。

## 案1: 提案作成と採否用の再実行を分ける（推奨候補）

1. ホストの信頼する準備処理が原本・Git履歴の基準版を保存する。元のプロジェクトは共有しない。
2. Codexはモデル通信に必要な接続だけを許した専用VMで、独立コピーを探索し、テストや修正を提案する。ここでのGitコピーと自己申告ログは信頼しない。
3. ホストの回収処理が提案ファイルをデータとして回収する。パス逸脱・リンク・容量上限を検査し、ホスト上では実行しない。子の.gitや実行ログを基準版へ取り込まない。
4. 信頼する起動処理が、基準版と検査済みの提案から、別の通信なし実行環境を作る。Codexの認証・モデル接続・VM管理権限は渡さない。ホスト原本・制御領域は共有しない。
5. 外側が指定コマンドの出力・終了・時間制限・停止を記録する。修正前に再現し、修正後に解消することを同条件で確認し、その結果を採否に使う。子の自己申告で成功を確定しない。

これは旧仕様の完全維持ではない。「すべての試行コマンドが通信なし・記録対象」から「採否に使う再実行が通信なし・外側記録」へ、「コピー内Gitの変更不能」から「基準Gitは外側で保全し、子のコピーは信頼しない」へ変更する。ユーザー承認なしに置き換えない。

負担は、2つの実行環境と搬入出・再実行処理の実装・維持、および実行時間・ディスク消費の増加。利用者の日常の本文転記は増やさず、共通CLIで自動化する。現PCではデーモンの通常起動が事前作業になる。第2環境の基盤・資源量はまだ確定しない。単にVMを2台作れば成立するとは扱わない。

## 案2: 旧仕様の強制条件をすべて維持する

コピー内Gitの変更不能、子のすべての操作の外側記録、テスト実行時の通信禁止を維持する。既製sbx単体での代替は成立とせず、子が変更できない実行仲介・権限制限を追加検討する。ホスト上の子の全ツール制限が未確認だった旧タスク0を、別配置へ移しただけで解決済みと扱わない。

要求は維持できるが、制御境界の実装・実証が増え、実行可能な構成が見つかる保証はない。費用と所要時間の見積もりは現段階では定性的な比較に留める。

## 採用判断前後の境界

案1の推奨理由は、原本と採否用の検証を保護し、子の自由な試行そのものを全面監視する自作基盤を減らせる可能性があるため。ただし上記の保証変更への判断が必要。どちらも現段階で未採用。

合意後に詳細を設計する。モデル認証や実起動より先に、クリップボード書込・MCP gateway・SSH等のホスト側経路、回収物検査、基準版保全、通信なし再実行、停止の保護試験を具体化する。現行版で追加ホスト経路を閉じられない場合は実モデルへ進まず、差分を報告する。認証方式・モデル利用費・送信対象は別に固定し、実プロジェクトの送信を設計継続の指示から推定しない。

## 基本方針承認後の機能分割案

feature-block-designの適用しきい値（3コンポーネント以上）を満たす。4ブロックで、共通CLIから順に呼び出す。分割案は詳細仕様作成前の提示段階。

| ブロック | 責務と受け渡し | 既存実体との関係 |
|---|---|---|
| 依頼・基準版準備 | 依頼を検査し、ファイル・履歴の基準版と識別情報を保全。子へ渡すコピーを別に作る | RequestCopy.psm1のNew-VerificationRunとmanifest生成を参照。ただし現状workを基準版と兼用しないよう分離が必要 |
| Codexの提案作成・回収 | sbxで子を動かし、終了後に提案ファイルを隔離した受取領域へ回収・検査。自己申告は参考情報として返す | 新規責務。Execution.psm1のInvoke-VerificationProcessはCLIプロセス管理の候補であり、VM停止を代替しない |
| 通信なし再実行 | 検査済み提案と基準版から別環境を準備し、固定した同じテストを修正前後で実行。出力・終了・停止を外側で記録 | 新規責務。子のコマンド文字列をホストで実行しない。基盤・イメージの具体選択は詳細設計で確認 |
| 結果照合・返却 | 原本の変化、対象版、テスト同一性、実行・停止証拠を照合して主担当へ返す | Result.psm1の原本・成果物検査を参照。既存command_executionイベントの照合を新構成の証拠に偽装しない |

流れは準備→提案→再実行→照合。基準版は準備から再実行へ直接渡し、提案側が上書きしない。回収時に検査を通らないものは再実行へ送らない。成功報告より前に各環境の停止を確認し、停止未確認・出力欠落・原本更新・時間超過を成功にしない。

詳細設計では、まず小さなLinux・Pythonの欠陥を対象にする。認証・実モデル・実プロジェクト送信の前に、AIなしで回収の拒否条件、同一テストの修正前失敗/修正後成功、時間超過時の停止を検査する。提案そのものの内容審査と、実行結果の機械照合を区別する。

判断の分担案: 上記4責務と基本方針を維持する補助的なデータ形式・内部構造・検証手順の詳細はAIが作成し、仕様をまとめて提示する。保護の追加緩和、新たな必須基盤・利用者作業、モデル認証・利用費・送信範囲、既存物の削除、公開は個別相談する。この分担自体も承認前の提案で、既存の許可を拡張済みとは扱わない。

### 分割・分担の承認と詳細化

上記を提示した選択肢1へユーザーが「１で」と回答。4責務と補助設計の委任を承認した根拠はADR-0158にも保持する。現行の詳細仕様は`docs/current/specs/2026-09-09-isolated-verification/00-overview.md`と01〜04（schemaVersion=3草案）。旧v2仕様の差分追記ではなく、全体のスナップショットを書き換えた。

仕様の自己確認では、証拠とプロファイルの相互参照によるハッシュ循環、再検証時に別の修正候補を混ぜる経路、未起動時の失敗結果生成を補正した。旧pids上限の保護は無断で外さず、sbxで強制できるかを起動前の未確認項目へ残した。実モデルの実行はまだできない。新たな基盤を勝手に導入する方法でこの未確認を解消しない。

確定前レビューは未実施。旧Linux仕様のレビューを新構成のレビューとして流用しない。新規1担当で4観点を通すフルレビューを推奨する。対象は5仕様と必要な既存実装・ADR、特に回収境界・信頼側記録・実行設定の成立条件。新しい保護手順を含むため成果物の型は規範改定型。保護の動的実証は後続で必須であり、静的レビューだけでは利用可能にならない。
