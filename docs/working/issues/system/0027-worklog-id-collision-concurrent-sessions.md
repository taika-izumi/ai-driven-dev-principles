# Issue-0027: 並行セッションで worklog の id 採番が衝突しうる

- **Status**: closed

- **関連**: `skills/worklog-record/references/store-format.md`（id 採番アルゴリズム）、ADR-0045

## 課題内容

id 採番は「`<folderName>/log.jsonl` を読み、同一 date のエントリ数 + 1 を NN とする」方式。同一プロジェクトで複数セッションを並行稼働させた場合（git worktree 運用・複数ウィンドウ・サブエージェント併用などで現実に起こりうる）、両セッションが同じ件数を読んで同じ NN を採番する競合（read-count-append の非原子性）がある。

影響: id は処理済み台帳（processed.jsonl）との突合キーであり、重複 id は「片方のエントリだけ処理済みなのに両方が除外される／されない」という処理済み判定の誤りに直結する。

対処候補: (a) 追記直前の再カウント（競合窓を縮めるが排除はしない）、(b) id への時刻やセッション識別子の混入（一意性を強くするが人間可読性・スキーマとのトレードオフ）、(c) 発生確率が低いと見て運用回避（同一プロジェクトの並行記録を避ける規範）。採否は発生確率と対処コストの見合いで判断する。

## 検討状況

- 2026-07-17（worklog v1.1 改訂サイクル）: 対処候補 (a)〜(c) を比較し、(a) の強化版＝**追記直前の再カウント＋追記後の読み直し検証（重複時は自行のみ再採番して書き直す。追記専用原則の唯一の例外）**を採用。(b) 識別子混入は可読性・台帳突合キーへの波及が発生確率に対し過剰、(c) 運用回避のみは検出手段がないため退けた。並行記録が常態化して実害が出た場合は id 一意化を再検討する

## 結論

ADR-0050 で決定（store-format.md の採番アルゴリズム・spec 01 へ反映済み）。closed
