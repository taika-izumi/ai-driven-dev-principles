# Issue-0031: worklog の model フィールドが「記録時のモデル」定義で、セッションがモデルをまたぐと delta を誤帰属する

- **Status**: closed
- **Opened**: 2026-07-18
- **Closed**: 2026-07-18
- **起票元**: worklog v1.1 完了後の worklog-record 実行（2026-07-18）で実際に顕在化した delta
- **関連**: ADR-0048（model 必須フィールド。文言「記録時の AI モデル ID」）、Issue-0025（model フィールドの動機）、`skills/worklog-record/references/store-format.md`、`skills/worklog-record/SKILL.md`

## 課題内容

ADR-0048 は `model` を「**記録時**の AI モデル ID」と定義している。しかしこのフィールドの分析目的（Issue-0025）は「この friction は特定モデル固有か、全モデル共通か」を判定することであり、本来欲しいのは「**delta 発生元**のモデル」である。両者は、1 セッションの途中でモデルが切り替わると食い違う。

**具体的に発生した事例（2026-07-18）**: worklog v1.1 改訂サイクルは実装・スモークテスト・brainstorming を Claude Fable 5 で行い、merge 以降の作業終了処理を Claude Opus 4.8 で行った。セッション末に worklog-record を実行して 3 件記録した際、各 delta の発生元は Fable 5（-01/-02）と Opus 4.8（-03）で異なった。ADR-0048 の文言どおり「記録時」で機械的に埋めると 3 件すべて Opus 4.8 になり、Fable 5 由来の 2 件を誤帰属する。実際には目的を優先して発生元モデルで帰属させた（文言からの逸脱）。

**恒常性（ユーザー確認済み）**: ユーザーは「今後もメインの作業は高コストな AI に実施させ、作業終了後の処理はコストを抑えたモデルに実施させる可能性がある」と明言。すなわち「主作業＝高性能モデル / 事後処理＝安価モデル」の使い分けは**意図された恒常運用パターン**であり、セッションのモデルまたぎは例外でなく常態になりうる。この運用ではモデル別 friction 分析の価値が高まる一方、「記録時のモデル」定義では事後処理モデルに全 delta が寄ってしまい、分析が成り立たなくなる。

## 対処候補

- ADR-0048 の文言を「記録時の AI モデル ID」→「**delta 発生元のモデル ID**（記録時と異なる場合は発生元を優先）」へ修正し、`store-format.md` / `worklog-record` SKILL.md の該当記述も揃える（最小コスト。ADR-0032 の観測可能性は満たす＝記録者は各 delta がどのモデルの作業中に生じたか判別可能）
- 発生元が複数モデルにまたがる 1 エントリのケースは、記録単位規範（ADR-0053: 1 エントリ = 同一 context の delta 束）により通常は単一モデルに収まる想定。またぐ場合はテーマ分割で対応する旨を注記
- 次サイクルの「worklog 実運用堅牢化」（Issue-0030 / Issue-0024）と同じ領域のため一括対処が効率的

## 検討状況

- 2026-07-18: 起票。今回の記録では暫定的に発生元モデルで帰属させた（ADR-0048 文言からの逸脱を承知の上）。文言修正は次サイクルで実施予定

## 結論

ADR-0048 を in-place 改定して対処。model 定義を「記録時の AI モデル ID」→「delta 発生元の AI モデル ID（記録時と異なる場合は発生元を優先）」へ訂正し、store-format.md / worklog-record SKILL.md / spec 01・02 の文言も揃えた。複数モデルまたぎの 1 エントリは ADR-0053 の記録単位でテーマ分割する。
