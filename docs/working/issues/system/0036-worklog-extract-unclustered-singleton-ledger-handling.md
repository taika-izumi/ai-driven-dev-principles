# Issue-0036: worklog-extract でクラスタ化されなかった単発エントリの台帳上の扱いが未定義

- **Status**: open
- **Opened**: 2026-07-31
- **起票元**: `worklog-extract` 初回実行（2026-07-31）中に検出した仕様の欠落（採用候補 4 件とは別。実行者が手順を適用しようとして判断根拠がないことに気づいた）
- **関連**: `skills/worklog-extract/SKILL.md`（手順7〜8）、`skills/worklog-record/references/store-format.md`（台帳レコード）、ADR-0045（台帳による処理済み除外・deferred 再浮上）、Issue-0032（同スキルの健全性検証手段が未定義。同じく実行時に判明した欠落）

## 課題内容

`worklog-extract` の手順は、**クラスタ化された候補**について「採用 / rejected / deferred」を人間が判断し `processed.jsonl` へ反映する、と定めている。しかし走査の結果**どのクラスタにも属さなかった単発エントリ**の扱いが定義されていない。

初回実行（2026-07-31）では 94 エントリ中 5 件が単発として残った。取りうる扱いは 2 通りで、どちらもトレードオフがある:

- **A: 台帳へ記録しない（今回採用した暫定措置）** — 次回走査で再び分析対象になる。新しいエントリと結び付いてクラスタ化される可能性を残せる一方、恒久的に束ならない単発が溜まると走査コストが単調増加する（SKILL.md は「分析コストは未処理エントリ数でスケール」と明記している）
- **B: `deferred`（`evidence_count: 1`）として記録する** — 走査コストは抑えられるが、`deferred` の再浮上判定は「台帳の代表 id を含む現在のクラスタ」を再同定する仕組みであり、そもそもクラスタを形成していない単発に対して再同定が成立するかが SKILL.md の記述からは読み取れない

また、単発エントリのうち scope が `project-specific` に確定したもの（今回 3 件）は、汎用スキル化の対象になり得ないため、`general-candidate` 据え置きの単発とは別の扱いが妥当な可能性がある。

## 検討状況

- 2026-07-31: 初回実行では **A（台帳へ記録しない）** を暫定適用し、5 件を未処理のまま残した。該当 id: `LoopForAlpha-2026-07-22-06`（general-candidate 据え置き）、`LoopForAlpha-2026-07-23-07`（同）、`LoopForAlpha-2026-07-23-08`（project-specific 確定）、`LoopForAlpha-2026-07-29-09`（project-specific 確定）、`MakeAiInstructions-2026-07-17-02`（project-specific 確定）
- 現時点のストアは 94 エントリと小さく、A で実害は出ていない。判断が必要になるのは走査コストが体感できる規模に育ってからで、それまでに規約を決めておきたい
