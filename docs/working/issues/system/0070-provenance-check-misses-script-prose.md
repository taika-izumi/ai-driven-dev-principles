# Issue-0070: 出所識別子の機械判定がスクリプト内の散文（docstring・利用者向けメッセージ）に届かない

- **Status**: open
- **Opened**: 2026-08-08
- **起票元**: Task 7（配布物生成）の仕様準拠レビューが、生成物 `dist/skills/worklog-extract/scripts/check-store-health.py` に出所識別子 3 件の残存を検出
- **関連**: ADR-0083（記法規約と生成器による検査）、`docs/current/specs/2026-08-07-distributed-artifact-generation/01-provenance-notation-convention.md`「適用範囲」、同 `00-overview.md`「スコープ外」、`scripts/lib/strip-provenance.ps1`

## 課題内容

配布対象ソースの記法規約は、スクリプトファイル（`.py` / `.ps1`）の機械判定を `#` で始まるコメント行に限定している。テストフィクスチャの架空データを規約で縛らないための限定である。

しかしこの限定は、**フィクスチャではない散文まで判定の外へ落とす**。実際に配布物へ次の 3 件が残った（2026-08-08 実測）。

| 箇所 | 内容 |
|---|---|
| モジュールの説明文字列 | `中央ストアのバイト健全性を検査する（ADR-0054 の契約: …）` |
| 関数の説明文字列 | `混入しうる（Issue-0032）。頭だけを見る実装ではそれを取り逃がす。` |
| 実行時に出力するメッセージ | `違反 N 件。走査を中止する（ADR-0054: silent tolerance はしない）` |

3 件目は配布先で**実行するたび画面に表示される**。いずれも配布先の読み手・利用者が読むテキストであり、規約が防ごうとしている「配布先で解決できない参照」そのものである。

規約の適用対象は Task 7 で見直し、docstring と利用者向けメッセージをスコープ内へ改めた（spec 01「適用範囲」の対応表）。実データ 3 件も同時に是正済み。**残る課題は機械判定が届かないこと**であり、現状は書き手が守る規律に依存している。

## 同型（機械判定の届かない箇所）

スクリプト以外にも、判定が構造的に届かない位置がある。

**コードフェンスの開始行（情報文字列）**: 共有ライブラリ `scripts/lib/strip-provenance.ps1` の判定・変換・残存検査の 3 関数はいずれも `` ```  `` で始まる行を素通しする。したがって `` ```ADR-0011 `` のように開始行へ識別子を書くと、規約違反として報告されず、変換もされず、`-Check` の残存検査も書き出し後の自己検査も通り、**exit 0 のまま配布物へ出荷される**（2026-08-08 実証）。両生成器で同一の挙動であり、ライブラリ側の穴である。

現時点の実害は 0 件（`dist/` と `template/` の全数走査で該当なし）。修正は開始行そのものを判定へ渡す形になるが、フェンス行を「フェンス内」と扱うと R4 判定になり既存の規約解釈と食い違うため、扱いの設計が要る。

## 影響

- 逆戻り（新しい docstring や `print` に識別子を書く）を生成器が検出できない。規約適合していても配布物が壊れる型として潜伏する
- 本サイクルが確立した「規約違反は生成の失敗として顕在化させ、別途の lint を設けない」という執行モデルの外に、書き手の注意力に依存する領域が残る

## 対策の方向（採否は未定）

- Python は `ast` で docstring と文字列リテラルを抽出し、フィクスチャ（テスト用の架空データ）と利用者向け文字列を判別する
- 判別を機械化できない場合、対象を「モジュール/関数の docstring」と「`print` / ログ出力の実引数」に限定する案もある
- PowerShell 側（`.ps1`）は `Write-Host` の文字列が同型の対象になる

判別の設計コストが実害に見合うかを含めて次サイクル以降で判断する。
