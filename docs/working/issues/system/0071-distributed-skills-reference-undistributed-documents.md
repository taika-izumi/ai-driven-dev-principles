# Issue-0071: 配布されるスキルが、配布されない文書を必須参照にしている

- **Status**: open
- **Opened**: 2026-08-08
- **起票元**: Task 7（配布物生成）の品質レビューが、生成物 `dist/skills/` を配布先の読み手として通読して検出
- **関連**: ADR-0081（除くのは「配布先で解決できない参照」であり決定記録番号に限らない）、ADR-0083（記法規約と生成器による検査）、Issue-0067、Issue-0070（同型。機械判定の届かない領域）

## 課題内容

出所識別子の除去体制は、識別子 5 種（決定記録番号・課題番号・`<repo>#` 修飾参照・作業ログ id・出所注記）を機械的に判定・除去する。しかし ADR-0081 が立てた判定基準は「**配布先の読み手が解決できるか**」であり、5 種はその十分条件ではない。

配布物の通読で、5 種のいずれにも当たらないが配布先で解決できない参照が 3 系統見つかった（2026-08-08 実測）。

| 参照先 | 出現箇所 | 影響 |
|---|---|---|
| `CONTRIBUTING.md` | `extend-guidelines/SKILL.md`（必須参照・複数箇所）、`decision-log/SKILL.md`、`worklog-skillify/SKILL.md` | **`extend-guidelines` は配布先で必ず中断する**。同スキルは冒頭で `CONTRIBUTING.md` の読み込みを求め、無い場合は「作業を開始できません」と停止する設計 |
| `template.manifest` / `scripts/sync-template.ps1` | `extend-guidelines/SKILL.md` | 配布先に存在しない運用手順を案内する |
| `docs/current/specs/2026-05-01-retrospective-design.md` | `retrospective/SKILL.md` | 参照先が配布されない |

いずれも配布対象は `template.manifest` 記載の 4 ファイルと `skills/` 配下に限られるため、配布先には届かない。

同型はテンプレート配布物側にもある（2026-08-08 実測）。

| 参照先 | 出現箇所 | 影響 |
|---|---|---|
| `skills/retrospective/SKILL.md` / `template.md` / `flow-template.md` | `template/docs/records/retrospectives/README.md:17,30,31` | 配布先プロジェクトに `skills/` は存在しない（スキルはプラグインキャッシュの不透明なパスから供給される）。読み手はパスを辿れない |

**初期状態のひな形に履歴的な自己参照が残る問題**もある。`template/docs/records/retrospectives/README.md:17-18` は「2026-07-31 以降の形式」「それ以前の記録は当時の形式のまま改変しない」と書くが、配布先の初期状態では記録が 0 件であり、「それ以前の記録」は原理的に存在しない。裸の日付は種別 4 の正規表現（プロジェクト名の後にハイフンを要求する形）に当たらないため生成器は素通しする。

この 2 件は**ソース側を書き換えて解決できない**点が前掲の 3 系統と異なる。ソース側の記述は本リポジトリの実態として正しく、配布物としてのみ不適切であるため、配布物固有の書き換え（変換規則の追加、あるいは配布物専用の差し替え）が要る。

## 影響

- 配布先の利用者が `extend-guidelines` を起動すると、前提文書が無いため作業に入れない。スキルとして機能しない状態で出荷されている
- 識別子 5 種を 0 件にしても「配布先で解決できない参照」は残る。ADR-0081 の原理と ADR-0083 の実装の間に構造的な隙がある
- 機械判定の対象を広げにくい（文書名・パスは無限に多様で、正規表現で列挙できない）

## 論点

1. **`extend-guidelines` を配布対象に含め続けるか**。このスキルはガイドライン自体を拡張する作業のためのもので、配布先で使う場面があるかを含めて判断が要る。除外するなら生成器に除外リストが要る
2. **`CONTRIBUTING.md` を配布対象に加えるか**。加えると配布先が本リポジトリの寄稿手順を受け取ることになり、内容の適合性を別途検討する必要がある
3. **参照の解決可能性をどう検査するか**。文書パスの実在確認（配布物内で解決できるリンクか）は機械化できる余地がある。一方 `CONTRIBUTING.md` のような裸の文書名は文脈依存で難しい
4. **ソース側の書き換えで解決できない記述をどう扱うか**。本リポジトリの実態として正しく、配布物としてのみ不適切な記述（履歴的な自己参照など）は、変換規則の追加か配布物専用の差し替えが要る。前者は「ソースを正本とし生成物を派生させる」現行体制を保てるが、変換規則が文脈依存で複雑になる
