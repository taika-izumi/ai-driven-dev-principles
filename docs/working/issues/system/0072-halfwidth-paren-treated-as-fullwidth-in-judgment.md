# Issue-0072: 括弧内判定が半角括弧を全角括弧と同一視し、除去後に空の括弧が残る

- **Status**: open
- **Opened**: 2026-08-08
- **起票元**: Task 9（規約の文書化）の品質レビューが、規約節だけを読んで作業を試す過程で検出
- **関連**: ADR-0083（記法規約と生成器による検査）、`scripts/lib/strip-provenance.ps1` の `Test-InsideParen`、Issue-0070（同型。機械判定の穴）

## 課題内容

R1 は出所識別子を**全角括弧 `（）` の内側**に置くことを求める。しかし括弧内判定に使っている `String.LastIndexOf(char)` は既定で現在のカルチャに従う比較を行い、**半角 `(` と全角 `（` を同一視する**。

```
'型(あ'.LastIndexOf('（')                             = 1    ← 半角にマッチしてしまう
'型(あ'.LastIndexOf('（', [StringComparison]::Ordinal) = -1   ← 正しい
```

結果、半角括弧で書いた行は「括弧の内側にある」と判定されて違反にならない。一方、除去後の掃除規則は全角括弧のリテラルを対象にしているため半角の対は消えず、空の括弧が残る（2026-08-08 実測）。

```
入力:   出力ファイルは時系列追記型(ADR-0011)に従い追記する
判定:   ok（違反として報告されない）
変換後: 出力ファイルは時系列追記型()に従い追記する
```

日本語入力では半角括弧の混入が起こりやすく、書き手が気づかないまま配布物へ残骸が出る。

## 影響

- 規約に適合しているつもりの行が、違反として報告されないまま配布物を壊す。生成器も `-Check` も通るため静かに失敗する
- 暫定の対処として `CONTRIBUTING.md` の規約表へ R1-b（括弧は全角を使う。半角は判定を通過するが残骸が出る）を明記したが、これは書き手の注意力に依存する

## 対策の方向（採否は未定）

- `Test-InsideParen` の `LastIndexOf` に `[StringComparison]::Ordinal` を指定する。1 行の修正で、半角括弧は「括弧の外」と判定されるようになり R2 違反として報告される
- **現時点の実害は 0 件**（2026-08-08 実測。配布対象ソース全件を走査し、半角括弧の内側に識別子を置いた行は 0）。したがって `Ordinal` 指定を入れても既存ソースの判定結果は変わらず、安全に適用できる
- 掃除規則側でも半角の空括弧を除去するかは別途判断する（規約が全角を求める以上、半角は違反として弾くのが筋であり、掃除で救う必要はない可能性が高い）
