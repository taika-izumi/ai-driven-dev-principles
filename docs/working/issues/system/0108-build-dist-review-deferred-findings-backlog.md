- **Opened**: 2026-08-25
- **起票元**: Codex 対応サイクル Task 2 のコード品質レビュー（独立サブエージェント・claude-opus-5）
- **関連**: ADR-0113（採否の判断）、ADR-0112（生成器の導出生成設計）、ADR-0054（異常を検出したら黙認せず止める規律）、Issue-0072（括弧内判定が半角括弧を全角と同一視する。生成器まわりの同種の穴）

## 課題内容

`scripts/build-dist.ps1` の Task 2 実装（コミット `015e79e`）に対するコード品質レビューが Important 1 件・Minor 6 件を報告した。このうち Important（型・欠損ガードの非対称）と Minor 1 件（規約違反レポートが marketplace 不正に隠される）は同サイクルで対処したが、残る 3 群と、追加決定の再レビューで出た 1 群は**採用を見送り、実装時レビューまたは次サイクルへ委ねる**とした（ADR-0113）。本 Issue はその受け皿である。

見送った 4 群は次のとおり（群 4 は追加決定の実装への再レビューで後から加わった）。いずれもレビュアーが隔離コピーで実証済みで、推測ではない。

### 群 1: `ConvertTo-JsonStringValue` が C0 制御文字を素通りする

`scripts/build-dist.ps1` の `ConvertTo-JsonStringValue` は `\` `"` `\r` `\n` `\t` の 5 種のみをエスケープし、他の C0 制御文字（`U+0008` バックスペース、`U+000C` 改ページ、`U+001B` エスケープ、`U+0000` NUL）は素通りする。

問題は**このリポジトリ内では検出できない**ことにある。PowerShell の `ConvertFrom-Json` は寛容でこれらを受理するため、`-Check` も書き込み後の自己検査も通る。RFC 8259 準拠の厳格パーサ（`System.Text.Json`）は `'0x08' is invalid within a JSON string` として拒否する。したがって壊れた JSON が無検知で出荷され、Codex CLI 側（serde_json 想定）で初めて落ちる。

到達には正本 JSON に当該文字を書き込む必要があり、現在の正本には存在しないため実害は出ていない。

**この項目は ADR-0113 の採用基準 (i)（検出機構が構造的に効かない型）に文言どおり該当する。**不採用としたのは基準の適用漏れではなく、到達可能性が実質ゼロという別軸の判断による繰り延べである（この区別は再レビューでレビュアーが明示的に指摘した）。基準 (i) の定義が緩められたわけではない。修正は 1 行（`ConvertTo-JsonStringValue` の `return` 直前へ、U+0000〜U+001F の範囲を `\uXXXX` 形式へ置換する `[regex]::Replace` を 1 本足す。\r / \n / \t は先に処理済みのため残りだけを拾う）で済むため、次に同ファイルへ触れる機会に同梱するのが現実的である。

### 群 2: `.agents/` 配下の余分なファイル（stale）を生成器が一切検出しない

ルート直下の生成物は「既知パスのホワイトリストに対するファイル単位の生成・存在・内容比較」とし、「余分なファイルの不在」条件を適用しない設計である（ADR-0112。リポジトリルートを走査すると生成物以外の全ファイルが陳腐化判定になり、wipe に含めれば不可逆事故になるため）。この判断自体は正当である。

ただしレビュアーの実測では `.agents/` 配下の追跡ファイルは `.agents/plugins/marketplace.json` の 1 件のみで、**ディレクトリ全体が生成物専用**である。したがって「リポジトリルート走査」ではなく「`.agents/` 配下限定の走査」にすれば、ルート走査の危険を持ち込まずに stale 検出を追加できる（wipe は入れず `-Check` の報告のみに留めればリスクはゼロ）。計画 Task 2 Step 11 の但し書きも、`.agents/` 配下へスクラッチファイルが紛れ込むと以降のどの検証でも捕捉されないことを警告している。

### 群 3: 保守性の指摘 4 件

- `New-CodexMarketplaceContent` 内の `$plugins.Count -eq 0` ガードが到達不能な死にコードになっている（ADR-0113 の差分 2 で version 検査の前に同一判定の外側ガードを置いたため）。関数の自己完結のため残置しているが、診断メッセージ文字列が 2 箇所へ逐語重複しており、片方だけ直すと乖離する
- BOM 判定の 3 バイト比較が 2 箇所へ逐語重複している（`dist/` 側と ルート側）
- 生成物の書き出しループが 2 箇所へ逐語重複している（`dist/` 側と ルート側）
- **（群 3 のなかで優先度が高い）**関数内 `exit 1` の経路（`ConvertFrom-JsonText` / `New-CodexMarketplaceContent`）が `Aborted. Generated artifacts were not modified.` 行を出さないため、失敗時に「途中まで書かれたのか」が出力から読めない。実体は不変であることが実測済みなので、欠けているのは出力の情報だけである。**この項目は ADR-0113 の追加決定の実装で相対的に悪化した**——新設した `Get-RequiredJsonString` は `Aborted.` 行を出すのに対し、据え置いた `plugins[].source` / `plugins[].name` のガードは出さないため、同一関数まわりに 2 つの流儀が並んだ（再レビューでレビュアーが指摘）
- 診断の `plugins[]` 添字に `$entries.Count` を流用しており、将来ループに `continue` が入ると添字が黙ってずれる

なおこのファイルは既に `Get-RepoRelativePath`（「同じ算出式が複数箇所に重複していたのを1本化」）とライブラリ関数の利用（「従来はライブラリのロジックを build-dist.ps1 側へ逐語コピーしており、片方だけ直すと乖離する問題があった」）で同種の重複を 2 度潰しており、今回の追加分にその方針が適用されていない。

### 群 4: 追加決定の実装に対する再レビューで新たに出た 2 件

ADR-0113 の追加決定で新設した `Get-RequiredJsonString` に対し、コード品質の再レビューが Minor 2 件を報告した（判定は ✅ 承認でブロッカーではない）。いずれも採用基準 (i)(ii) のどちらにも当たらないため本 Issue へ回した。

- **1 要素配列がガードの契約を素通りする**。`Get-JsonProperty` の `return` が PowerShell の配列アンロールを起こすため、`"name": ["solo"]` は関数を出た時点でスカラー文字列 `"solo"` になり `-isnot [string]` を通過する。2 要素以上なら `Object[]` として正しく落ちるため、**要素数によって判定が変わる**。出力される値自体は正しく JSON も健全なので実害は小さいが、ガードの契約（「string であること」）と実挙動が乖離している。修正案は、判定を `Get-JsonProperty` の戻り値ではなく `$Object.PSObject.Properties[$Name].Value`（アンロールが起きない）で行うこと
- **marketplace のトップレベル `name` のラベルが `plugins[].name` と紛らわしい**。同一ファイルについて「name が空」を訴えるメッセージが 2 系統（`name must be a non-empty string: .claude-plugin/marketplace.json (missing)` と `plugin name is missing or empty in .claude-plugin/marketplace.json plugins[0]`）出るが、前者にはどの `name` かの位置情報が無い。修正は呼び出し側のラベルを `'marketplace name'` / `'plugin name'` 等に変えるだけで、関数側も Step 13 の期待出力も触れずに済む

## 対策の方向（採否は未定）

- 群 1・群 3・群 4 は `scripts/build-dist.ps1` を次に編集するサイクルでまとめて処理するのが自然である。単独で 1 サイクルを立てる価値は現時点では見込めない
- 群 2 は追加が小さく副作用も無いため、群 1・3・4 と同時に入れられる
- いずれも本サイクル（Codex 対応）の Task 11 の検証範囲外である。Task 11 では捕捉されないことを前提に扱うこと
