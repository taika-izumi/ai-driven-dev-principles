## 課題内容

**2026-09-17訂正**: 下記の当初説明は、静的なキット宣言を実効規則と同一視した誤りを含む。実VMのallowは明示的な`:443`/`:80`で、2接続先の8443番は拒否された。専用キットが必要という説明を撤回し、実効規則とコードの期待値の不一致、およびpolicy checkの正常拒否（終了1）を失敗にする不備への対応を再開する。実測・未確認範囲・未承認の修正案は`docs/records/experiments/2026-09-17-v3-task9-proposal-probe-first-attempt.md`を正とする。以下は当初の検討経緯として残す。

ADR-0199は、提案用VMの通信を `auth.openai.com:443` と `chatgpt.com:443` の2件に限り、codexキットが宣言する残る11ドメインを作成時に拒否する構成を確定した。しかし、キットの2接続先はポート番号なしで宣言されている。ポート番号なしのホスト規則はそのホストの全ポートに一致するため、他のドメインを拒否しても、承認した2ホストの443番以外の許可が残る。

実装途中では、拒否側の宣言にも機械的に `:443` を付けていた。これも元のポート番号なし許可を全面的に打ち消さない。さらに、既知の接続先と対照1件の `policy check` が合っているだけでは、規則一覧に別の追加allowがあるケースを排除できない。

「2ホスト・443番限定」という要求を変更するか、要求を保った実現方法へ設計を修正する必要がある。認証方式のOAuth採用そのものとは別の問題である。現時点のコードは未確定の作業差分で、proposalの作成や実機probeへ使わない。

## 根拠と確認範囲

- 現行 `C:/Users/d12an/AppData/Local/DockerSandboxes/bin/sbx.exe` の埋め込みcodexキット宣言で、`auth.openai.com`・`chatgpt.com` がポート番号なしであることを確認した。実機の通信成功・拒否を測った結果ではない。
- [Docker公式 Policy concepts / Network rules](https://docs.docker.com/ai/sandboxes/governance/concepts/) は、exact hostnameを全ポート、hostname with portを指定ポートだけに一致すると定義する（2026-09-16参照）。
- [Docker公式 Kit v2仕様 5.2・7](https://github.com/docker/sbx-kits-contrib/blob/main/spec/SPEC-v2.md) も同じポート意味を定義し、allow/deny一覧は合成時に追加されるとする。ポート範囲はこの仕様版では施行されず、単に443以外を範囲指定で拒否する案の成立根拠にできない（同日参照）。
- ローカル `sbx create --help` は `--deny-network` の反復指定を明示している。ここではヘルプを読んだだけで、createは実行していない。
- 通信・認証の設定、VM作成・停止、モデル呼出しは本調査では行っていない。

## 対策候補（未採用）

1. **443番限定を維持する**: 作成前から許可を2件へ限定した専用キットを用意する案を詳細化する。既定codexキットを単純にextendsしても許可は減らないため、利用版のキットを基にした固定定義と、認証・起動設定の追随範囲を定める必要がある。新しい実行基盤の導入は前提にしないが、キット定義の保守・版固定・検証が増える。ローカル版での具体的な作成経路は未検証。
2. **2ホストの全ポートを許可する**: 要求を緩和し、残る11ドメインを宣言全体に対して拒否する。保護範囲を変更するため利用者の明示判断が必要。追加allowの拒否と実効規則の照合はこの案でも必要。
3. **本件を保留する**: 作業差分を維持し、実機試験へ進まない。

VM作成後に規則を差し替える方法は、キット由来規則の変更可否と、作成直後からエージェント起動までの通信範囲が未確認であり、現時点の採用候補には確定していない。
