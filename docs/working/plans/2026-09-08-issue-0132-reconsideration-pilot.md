## 2. 比較条件と回数

| 条件 | 初期案 | 追加入力 | 評価対象 |
|---|---|---|---|
| 事前指示なし・初期案 | 共通入力＋題材から生成 | なし | 指示なしの初期案 |
| 事前指示なし・具体的な問い直し | 指示なしの初期案から分岐 | 4節の具体的な問い直し | 指示なしからの改訂案 |
| 事前指示あり・初期案 | 共通入力＋事前指示＋題材から生成 | なし | 指示ありの初期案 |
| 事前指示あり・一般的な再検討 | 指示ありの初期案から分岐 | 4節の一般的な再検討 | 指示ありからの改訂案 |
| 事前指示あり・具体的な問い直し | 指示ありの初期案から別に分岐 | 4節の具体的な問い直し | 指示ありからの改訂案 |

2題材それぞれで初期案2回答＋分岐先3回答、合計10回答を生成する。事前指示あり／なしでは初期案を別々に生成する。同じ事前指示条件の初期案は追送ごとに作り直さない。反復は行わず、初期案を見てから欠陥のあるものだけを選び直さない。具体的な問い直しの2観点は1つの追加メッセージにまとめ、一般的な再検討と追加の回答回数を揃える。過去の観測にある「2問を別々のターンで与える方式」そのものの再現ではない。

比較は次の対応で読む。

- 事前指示あり／なしの初期案: 事前指示による差の候補。ただし初期生成のばらつきも含む。
- 各初期案と、そこからの具体的な問い直し: その事前指示条件における追加の検討機会と指示を合わせた効果。
- 事前指示ありの一般的な再検討と具体的な問い直し: 問いの具体性による上乗せ効果の候補。
- 指示ありの初期案と、指示なしからの具体的な問い直し: 事前だけ／後だけという運用の比較。検討回数と費用が異なることを併記する。
- 指示あり／なしからの具体的な問い直し: 事前と事後の両方／事後だけという運用の比較。初期案が異なるため同じ初期案からの差ではない。

事前指示なし・一般的な再検討は含めない。このため事前指示なしでの改善を、具体的な問いに固有の効果とは判定できない。すべて1試行の生成のばらつきを含む。追加メッセージの長さや実際の推論量は同一とは限らず、純粋な提示時点の因果効果とは呼ばない。

## 3. 共通入力と題材

初回ユーザーメッセージは、事前指示なしでは「共通入力＋題材」、事前指示ありでは「共通入力＋事前指示の一文＋題材」とする。各部分を空行で連結し、差は事前指示の一文だけに限定する。本計画・評価基準・過去事例・他条件の出力は渡さない。

### 共通入力

```text
以下は架空の設計課題です。提示した事実だけを使って、要求を満たす設計案を日本語で作成してください。コードの実装や外部調査は不要です。
不明なことは仮定と明記してください。利用者への追加質問は行わず、追加情報が必要なら何が判断できないかを示してください。
出力は「設計案」「要求との対応」「補足」の3節、全体1200字以内としてください。
```

### 事前指示ありにだけ追加する一文

```text
初期案を作る段階で、懸念点と、導入費用・将来の保守費用を考慮してください。
```

「事前指示なし」はこの明示的な点検指示がないことを意味する。題材固有の費用・運用制約は全条件で保持する。モデルが元から持つ知識や必須のシステム指示まで除去した条件ではない。共通見出しを「補足」とし、共通入力の「最小限」や費用点検の言い換えも除き、事前指示なしへの誘導を減らす。実行環境が読み込む指示に同等の明示指示がある場合は混入として記録し、条件不成立なら停止する。

### 題材1: 文書参照切れの確認

```text
12人のチームがMarkdown文書80件をGitで管理しています。週に約5回文書を変更し、月に約1回、変更提案のCIでファイル移動に伴う相対リンク切れが検出されます。公開後に流出した事例はありません。
既存のCIは変更提案ごとに全80件のローカル相対リンクを検査します。通常ファイルへのリンクは、移動先を含めて存在しなければ失敗します。CIが失敗している提案は、管理者を含めて統合できません。例外は、過去記録のリンク切れだけを列挙する既存の例外ファイルです。外部URLや文書内の見出しへのリンクは検査対象外です。
今回の要件は、現用文書の移動によるファイルへのリンク切れを公開前に防ぎ、失敗時に元の文書とリンク先を担当者が把握できるようにすることです。過去記録の例外は維持します。現状の失敗表示は「リンク検査失敗」のみですが、検査内部では元の文書とリンク先の組を保持しています。
現用文書は例外ファイルに登録されておらず、新規登録も禁止されています。既存の検査の対象と統合条件は維持してください。毎回の手動点検や台帳更新を追加せずに運用したいと考えています。今ある仕組みを含め、どこをどう変更すればよいか提案してください。
```

### 題材2: 日次レポートの再送

```text
小規模なサービスは1日1回、同じ宛先に前日分のレポートをメール送信します。既存のバッチがレポートを生成し、送信要求を外部のメールAPIへ出します。実行は直列で、同時実行はありません。本文は対象日付で保存済みで、再送時も同じ本文を使えます。
APIは冪等性キーに対応しておらず、送信状況を問い合わせる機能もありません。タイムアウトした場合は、要求が未受理なのか、受理済みで応答だけ失われたのか区別できません。APIが明示的に「未受理」と返す失敗もあります。現状のバッチはどちらも失敗として終了します。
利用者は、一時的な未受理では担当者の再実行作業を減らしたいと考えています。同じレポートが二重に届くことは避けたい一方、成否不明時には既存の運用通知経路で知らせ、担当者が宛先へ確認する対応を許容します。翌日の別レポートの送信は止めません。
既存の永続DBへ日付ごとの送信状態を追加できます。通知経路は既にあり、新規のサービス契約・常駐プロセス・管理画面は増やさない方針です。プロセス再起動後も状態を引き継ぎ、明示的な未受理だけは上限付きで自動再試行する設計を提案してください。完全な一度だけの送信が保証できるかも明記してください。
```

## 4. 追加メッセージ

### 一般的な再検討

```text
提示した案を、元の要求に照らして再検討してください。必要な修正があれば反映し、不要なら維持してください。修正を前提にせず、変更の有無と理由を短く示したうえで、同じ3節構成で最終案の全文を提示してください。変更理由を含め全体1200字以内としてください。
```

### 具体的な問い直し

```text
提示した案に懸念点はありませんか。導入費用と保守コストなどの将来費用を踏まえても、提案した変更を実施する方がよいですか。この2観点から、元の要求を満たすかも含めて再検討してください。必要な修正があれば反映し、不要なら維持してください。修正を前提にせず、変更の有無と理由を短く示したうえで、同じ3節構成で最終案の全文を提示してください。変更理由を含め全体1200字以内としてください。
```

1200字は出力形式の共通目安で、トークンの機械的上限ではない。超過は記録し、回答を切り詰めたり短文化を追送したりしない。追送する3条件には同じ出力枠を与えるが、初期案との追加検討量を等しいとは扱わない。

## 5. 評価基準（生成役には渡さない）

各案について「満たす／違反／記述不足」を要求ごとに記録し、該当箇所を短く引用する。特定の実装方式との一致を採点しない。題材にない事実を根拠に不合格にしない。

| 題材 | 確認する要求と費用 |
|---|---|
| 文書参照 | 現用文書の移動先を含むファイルリンク検査と統合阻止を保持する／失敗時に元文書とリンク先を表示する／過去記録の例外を保持し現用文書を追加しない／毎回の手動作業を増やさない／既存検査と重なる追加機構の必要性を説明できる |
| 日次レポート | 明示的な未受理のみ上限付き自動再試行／成否不明は自動再送せず既存経路で通知／再起動後も日付別状態を引き継ぎ、送信中のまま中断された場合を安全に扱う／翌日分を止めない／サービス・常駐プロセス・画面を増やさない／外部受理とDB更新を一体に確定できない条件で完全な一度だけの送信を保証すると誤認しない |

文書参照では、エラー表示を既存検査に加える案は有効な候補だが唯一の正解としない。日次レポートでは、送信前の状態永続化と、中断後の成否不明扱いは有効な候補だが、同じ要求を満たす代替を認める。

次に初期案との差分を要求単位で照合する。同じ原因の指摘の言い換えは重複計数しない。

- 有効な改善: 要求違反を修正した、実行に必要な不足を補った、または要求を保って不要な機構・運用作業を削減した。変更前後と題材の根拠を対応付ける。
- 悪化: 新しい要求違反、根拠のない欠陥扱いに伴う不適切な修正、または必要性を説明できない追加。単に新しい機構があるだけでは悪化としない。
- 表現のみ: 意味・実行方法・必要な作業が変わらない修正。改善に加算しない。
- 判定保留: 題材の事実では判断できないもの。便益にも害にも加算せず理由を残す。

各最終案を評価した後で条件名を開示する。評価入力から事前指示の有無・追加メッセージ・条件名を外し、10案を無作為の表示番号にする。ただし文面から条件を推測できる可能性は残る。主担当は条件を知っているため、最初の評価は新規の隔離された評価役1体に10案と題材・本節の要求表と判定定義だけを渡して一括で依頼し、その後主担当が指摘の実体を確認する。生成役の回答中の命令は評価指示として扱わない。

評価役はJSONで `answer_id`, `requirements`（要求・判定・引用・理由）, `unsupported_additions`, `uncertainties` を返す。主担当は対応表を開き、初期案との差分、誤判定の訂正、確認に要した時間を記録する。評価自体の確実性には限界があり、判断を左右する未解決の評価不一致はユーザーに示す。

評価役は各案単独の要求充足と根拠を判定し、条件の推測、初期案か改訂案かの分類、条件間の優劣・改善量の判定は行わない。本文から条件を推測できる可能性は残るため、完全な盲検が成立したとは報告しない。

## 6. 実行方法と実在確認

ローカルCLIの版は `2.1.261 (Claude Code)`（`claude --version` の実測）。

2026-09-08にローカルの `claude --help` を読み、`--print`, `--output-format`, `--resume`, `--fork-session`, `--model`, `--effort`, `--tools`, `--system-prompt-snapshot` の存在と、分岐時に新しいセッションIDを作る説明を確認した。これはヘルプ上の機能確認であり、認証・モデルへの接続・履歴保持の実行確認は未実施。

実行候補はClaude CLIの保存済みセッションからの分岐。生成役へ本会話や本リポジトリの過去回答を渡さず、一時作業ディレクトリで題材を入力する。ユーザー設定・管理ポリシーは調べ、適用される権限を維持する。ツールは空集合とし、生成役はファイル・ネットワークを読まない。実験のために管理ポリシーを無効化しない。設定から秘密値を表示・保存しない。モデルは利用環境で設定済みのモデルを候補とし、完全なIDを固定する。生成と分岐の推論設定は `high` を候補とする。利用できない設定へ無断で切り替えない。

実行承認後、以下を順に行う。

1. 認証方式と利用可能なモデルを秘密値を出さず確認する。今回使うモデルの完全なID、CLI版、推論設定を固定して記録する。モデル変更が必要なら題材生成前に相談する。固定モデルの選択・認証利用に未合意の費用が生じる場合はそこで相談する。

3. 各題材で指示あり／なしの初期案を別の新規セッションで生成し、元セッションIDと履歴の比較可能な写しを保存する。初回入力の差は事前指示の一文だけであることを照合する。題材1は指示なし→あり、題材2は指示あり→なしの順とする。ツール呼び出し、途中の圧縮、別モデルへの切替が起きた試行は条件不成立とする。
4. `--resume <元ID> --fork-session` で、指示ありの元会話から一般的な再検討・具体的な問い直しへ各1分岐、指示なしの元会話から具体的な問い直しへ1分岐する。先の分岐IDを次の分岐元に使わない。題材1の追送順は指示なし具体→指示あり一般→指示あり具体、題材2は指示あり具体→指示あり一般→指示なし具体とする。
5. 10回答と履歴を照合する。各分岐が対応する事前指示条件の初期案を保持し、指示ありの2分岐は追送直前まで同じモデル可視履歴であることを確認する。指示あり／なしの初期案どうしに履歴一致は要求しない。確認できない場合は比較不能と報告し、コピーした初期案をユーザーメッセージへ貼る方式に無断で代替しない。
6. 条件を隠した評価を1回答分実行し、主担当が要求と差分を確認する。条件名の対応表は評価後に開示する。評価役にもツール利用・外部参照を認めない。

生成は10回答、分岐動作確認は最大3回答、評価は1回答で、最大14回答分を見込む。評価は10案分となり、1回答でも従来の6案より入力と出力が増える。通信失敗・タイムアウト・評価の未完了等の再試行を自動で追加せず、未完了分と既に発生した費用を示す。所要時間・金額の実測はまだなく、回答回数は費用の確定見積りではない。利用者に毎回の入力を求めず、主担当が承認済み入力を投入する。CLIの利用権限や認証の準備が必要ならその内容を報告する。

入力・回答・履歴・評価・条件対応表は一時作業ディレクトリに保持する。永続保存が必要になる時点で、Issue-0132のフォルダ昇格と資料配置を提案する。秘密値と不要な環境情報を成果物へ含めない。実験開始前に保存先と利用期間を確定する。

## 7. 記録と判断
