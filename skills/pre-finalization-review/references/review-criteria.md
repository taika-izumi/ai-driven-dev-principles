# 独立レビューの確認領域と入力

会話の経緯を知らない担当が、何を比べ、何を根拠に判断するかを定める。設計・計画・実装を対象とし、目的・要求、根拠・設計判断、動作・検証・運用の3領域と、反例・失敗経路の探索を扱う。フル実施ではこれらの問いをすべて覆う。差分再確認などの確認範囲は呼び出し側の方式に従い、その範囲でプロジェクト全体の目的・方針との整合を確認する。観点の参照だけで実施権限を変えない（ADR-0185/0186/0189）。

## 委譲元が渡すもの

既存資料の所在・版・関連箇所を渡す。対象の版・差分範囲を明示し、複数版を混同させない。担当がアクセスできない資料は必要な原文と出所を渡し、原文と作成側の要約を区別する。

- **対象と分担**: 成果物、対象版と変更範囲、確認する品質項目、担当する領域と兼務先、今回の方式で確認する範囲。人数を減らしても必要な問いを無担当にしない。
- **全体目的と今回の要求**: プロジェクト全体の目的・方針、今回の要求・制約・成功条件、承認済みの限定理由。正本のパスと節、文書化されていない指示は発言内容と出所を示す。直近の依頼・Issue・spec・作成者の要約だけで全体目的を代替しない。
  正本は案内文書からたどり、文書の対象範囲を確認して特定する。既に特定済みで有効な正本は再利用する。特定できない・矛盾する場合は、探した場所と未確認の点を示す。
- **実体と設計理由**: 関係するコード・設定・データ・文書・実行記録の所在、対処する問題、既存の対策が分かる資料。
- **実行条件と報告先**: 許可される操作、保護・停止条件、閲覧できる資料、既知の未確認、結果の形式。実行を伴う検査の保護は`subagent-dispatch`の`references/inspection-isolation.md`に従う。

全体目的は要求担当だけの入力ではなく全担当へ共有する。担当は許可された範囲で追加の根拠を自分で検索・閲覧する。閲覧可能な範囲と毎回読む範囲は別であり、全資料の一律読破や専用の目的一覧・台帳は作らない。全数走査は指定された検査対象を指し、根拠資料は判断に必要な箇所を読む。根拠の不足・矛盾・対象版の不明は、確認できる範囲と確認できない判断に分けて報告し、作成者の推測で埋めない。資料の閲覧可能性と外部送信の許可を混同しない。

## 確認領域と独立した反証

名称だけで指示せず、担当する問い・境界・品質項目が分かるように渡す。

| 領域・役割 | 中心の問い | 主な比較対象と根拠 |
|---|---|---|
| **目的・要求の妥当性** | 成果物と今回の範囲は、プロジェクト全体の目的・方針に沿い、今回の要求を適切に満たしているか | 目的・利用者・要求・成功指標と成果物を比較する。要求自体の不足、未記載の必要事項、根拠のない範囲縮小・拡大、目的を超える負担も確認する |
| **根拠・設計判断の妥当性** | 前提と推論は結論を支持し、選んだ仕組み・構造は要求に対して適切か | 原文・方針・実体・測定・既存対策と設計理由を比較する。引用条件と主張の向き、必要性、重複・保護の欠落、過剰設計・一般化、代替案と変更負担を確認する |
| **動作・検証・運用の成立性** | 関係する実体と契約の下で動き、検証でき、利用・運用できるか | 接続・入出力・単位・順序・状態・数値、検証の有効性、初見利用、運用・観測、移行・復旧と記述を比較する。複数機構の組合せも確認する |
| **独立した反例・失敗経路の探索** | 他の確認とは独立に、目的・要求・根拠・設計・運用を破る条件や見落としはないか | 未記載の前提、境界・並行・中断・再開・迂回・部分失敗等から、状態→操作→望ましくない結果を具体化する。必要な条件と害の根拠を示し、反論数を成果にしない |

独立した反証を実施するときは、他担当の初回所見を見せずに初回判断を回収する。同一担当が兼務した反例探索を、独立した反証とは称さない。人数を変えることと、確認する問いを減らすことは別である。人数・方式の選択はSKILL.md「方式・人数の判断」に従う。

### 担当境界と重複の扱い

| 重なる確認 | 担当する問いの違い |
|---|---|
| 要求不足と保護の欠落 | 要求担当は何を満たす必要があるか、根拠担当はその必要をどの対策が覆い何が不足するかを見る |
| 前提の誤りと実装不一致 | 根拠担当は対策理由・結論への影響、成立性担当は契約・経路・動作への影響を見る |
| 設計品質と動作・保守 | 根拠担当は構造の選択と代替案、成立性担当はその構造で変更・利用・運用できる実際の経路を見る |
| 期待値と検出力 | 根拠担当は期待値・評価設計が妥当か、成立性担当は正常例と想定した欠陥を検証が区別できるかを見る |
| 通常の確認と反証 | 同じ対象を異なる文脈と姿勢から見る意図的な重なり。同一の欠陥は集約時に1件へまとめ、独立に検出した経路と根拠は保持する |

各担当は共通の原文を自分の重点から確認する。担当同士の初回前の協議を要求せず、結果の照合と最終採否は主担当が`review-procedure.md`手順5「集約」で行う。分類先を唯一一致させるために指摘を落とさず、反証担当へ残りすべてを丸投げしない。

## 対象に応じた品質項目

次は割当ての手がかりであり、全項目を全案件へ課す固定チェックリストではない。関係する項目と担当を委譲文へ示す。要求に書かれていないだけで必要な品質を除外せず、確認できなかった項目を「問題なし」へ含めない。反証は表の各行を横断して失敗条件を見る。

| 品質項目 | 主な確認責任 |
|---|---|
| 目的・要求・範囲、利用者、成功条件、適用される外部制約 | 要求担当。要求自体の十分性も確認 |
| 前提・推論・引用・測定、設計構造、過剰設計・一般化、必要性・費用 | 根拠担当。機会不足・記録不足を不要としない |
| 正常動作、API・データ・単位・時刻、互換性、仕様と実体の同期 | 成立性担当。契約変更の要求面は要求担当と分担 |
| 信頼性・移行・復旧、運用・観測、設定・依存の更新 | 成立性担当。構造の維持負担は根拠担当と分担 |
| 利用可能性・アクセシビリティ・文書 | 要求担当が利用者と必要条件、成立性担当が具体的な操作・読解経路 |
| 検証の有効性・期待値・再現可能性 | 根拠担当が評価の妥当性、成立性担当が検出力と実行可能性 |
| 性能・規模・資源・費用 | 要求担当が条件と許容値、根拠担当が見積り・測定、成立性担当が達成と限界 |
| セキュリティ・プライバシー・安全 | 要求担当が保護対象、根拠担当が脅威の前提、成立性担当が制御 |

大きな設計変更や専門性の高い検査では、担当量・必要な知識・使える検査手段に応じて担当の追加・組替えを検討する。専門名を付けただけで専門検査済みとはしない。既存の機械検査が扱える書式等はその結果を使い、全担当へ同じ検査を重ねない。

## 必要性・実在と判断の境界

新設・変更する仕組みには、条件・分岐・ゲート・記録・接続・データ経路・禁止事項も含む。各仕組みが守るもの・得るものを1行で示し、方針の原文と実体を確認する。手がかりは`examples-and-evidence.md`「適用例: 根拠・必要性で特に疑う型」の6類型を参照し、その列挙だけに検査対象を限定しない。

| 判定 | 意味 |
|---|---|
| 必要 | 対処すべき問題・保護対象が実在し、その仕組みが必要な理由を確認できる。特定案が最善という意味ではない |
| 不要 | 想定した問題・保護対象・到達経路が成立せず、提示された対策理由を支持しない |
| 重複 | 同じ条件・対象を既存の仕組みが覆う。別の役割や不足がないかも確認する |
| 欠落 | 必要な対処・保護が実在するのに、対象成果物にも既存の仕組みにも満たす経路がない |
| 前提誤り | 仕組みは必要だが、必要性の説明に使った事実が誤っている |

証拠不足は5判定へ無理に入れず「未確認」とする。必要性を示さずに「前提誤りだが必要」としない。不在の判断には、読んだ対象・探索範囲・到達経路または到達しない根拠を示す。記載が無いことから、実施していない・実在しないと断定しない。観測がないだけで不要としない。

統計設計・測定・因果や設計案選択の妥当性は、事実の実在だけでは判定できない。5判定の範囲外の問いには必要な専門的確認を用い、実在確認の合格で代替しない。

全体目的に沿う承認済みの段階的な限定は、理由とつながりから評価する。全目的を今回同時に実装することや、無断の範囲拡大を要求しない。仮定を置く依頼では、その条件内の結論と実環境での条件成立を分ける。与件を再び未確認にして結論を保留せず、与件にない担当・実施状況等を補わない。

将来作成することが計画に明記された部品は、現在ないだけで欠陥としない。既存部品として誤って扱っていないか、作成・接続・検証の担当と順序が資料上揃うかを確認し、不明な部分は不明として示す。

規範・手順の利用可能性が確認対象なら、担当が文書に従って代表作業を試し、詰まる箇所を確認する。机上の経路確認と許可された実行を区別し、実行できない部分は未確認とする。定義を全箇所へ複写して初見の理解を補う方法は採らない。

必要な要求を確認したうえで対策案を比べる。必要性の検査と、導入・運用・保守・副作用を含む対策の最終採否は分け、後者は既存の集約で行う。全担当へ同じ費用審査を課さず、費用が高そうという印象だけで必要な保護を不要としない。

## 報告の契約

確認した対象・版・領域・範囲と、未確認の範囲を既存報告へ示す。各指摘は**対象箇所／問題／根拠／目的・動作への影響**を含み、事実・仮定・改善提案を区別する。対策案は欠陥の成立と分け、既存の重大度・採否形式を使う。新しい台帳は作らない。

文書の不一致は原文の対比を示す。動作や失敗経路を根拠にする指摘は成立条件と具体的な状態・操作・結果を示し、「順序次第で失敗する」だけで済ませない。条件が資料に無い場合はその不明を示す。許可された実行が必要な検証では実測し、原文対比や未実行の経路を動作成功の証拠にしない。未実行ならその旨と実行を妨げた制約を示し、必須の実行検証の代わりにしない。

「問題なし」は確認範囲内の結果で、未確認部分の安全・整合を意味しない。目的・方針との整合を見た原文の箇所を示す。書かれていない必要事項、編集対象外との相互作用、検証自体の検出力も、今回の対象に関係する範囲で確認する。
