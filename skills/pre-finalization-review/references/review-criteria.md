# 独立レビューの観点と入力

会話の経緯を知らないレビュー担当が、何と何を比べ、何を根拠に報告するかを定める。設計・計画・実装を対象とする。確定前レビューは4観点を使う。他の独立レビューでは呼び出し側の担当範囲に従い、その範囲に全体目的・方針との整合確認を含める。観点の参照だけでレビューの起動・人数・方式・権限は変わらない（ADR-0185 / ADR-0186）。

## 委譲元が渡すもの

次の情報を既存資料の所在と関連箇所で渡す。担当がアクセスできない資料は必要な原文と出所を渡し、原文と委譲元の要約を区別する。対象の版・差分範囲を明示し、複数版を混同させない。

- **対象と担当範囲**: レビューする成果物、変更範囲、担当観点、今回確認する内容。
- **目的・要求の根拠**: プロジェクト全体の目的・方針、今回の要求・制約・成功条件、承認済みの限定理由。正本のパスと節、文書化されていない指示はその発言内容と出所を渡す。直近の設計や作成者の要約だけで全体目的を代替しない。
  正本の所在は、プロジェクトの案内文書（README・エージェント指示・文書索引など）からたどり、その文書の対象範囲を確認して特定する。既に特定済みで有効な正本は再利用する。特定できない・資料間に矛盾がある場合は、探した場所と未確認の点を示す。
- **実体と設計理由の根拠**: 関係するコード・設定・データ・既存文書・実行記録の所在。新設・変更する仕組みが対処する問題と、既存の対策が分かる資料。
- **実行条件と報告先**: 許可される操作、保護・停止条件、既知の未確認、結果の形式。実行を伴う確認の保護は`subagent-dispatch`スキルの`references/inspection-isolation.md`に従う。

各欄の専用文書や全資料の一律読破は要求しない。全数走査は指定された検査範囲を対象とし、参照資料は判断に関係する箇所を読む。必要な原文へ到達できる情報を選ぶ。根拠の不足・矛盾・対象版の不明は、確認できる範囲と確認できない判断に分けて報告し、作成者の推測で埋めない。

## 4観点の問いと根拠

観点名だけで指示せず、担当する行の問いと境界を渡すか、この文書の該当箇所を読むよう指示する。

| 観点 | 中心となる問い | 主な比較対象と指摘の根拠 |
|---|---|---|
| **仕様適合（目的・要求との一致）** | 作るものと今回の範囲は、全体目的・方針と個別要求を満たすか | 要求の原文と成果物を比較する。満たしていない要求、目的との矛盾、根拠のない範囲縮小・拡大を箇所付きで示す |
| **前提実在（根拠・必要性）** | その仕組みを必要とする問題・条件・保護対象は実在し、対策の根拠になるか | 設計理由を事実・方針・既存対策と比較する。存在しない保護対象、到達不能な危険、既存対策との重複、実在する必要を取りこぼした箇所を証拠で示す |
| **実装整合性（実体・接続との一致）** | 記述した仕組みは、実際の構成・契約・順序・状態と整合するか | 設計・計画・実装を、実際のコード・設定・データ配置・呼び出し元・関係文書と比較する。参照先、入出力、前後条件、期待値と実測が食い違う箇所を示す |
| **敵対的（失敗経路の探索）** | 想定どおりでない入力・順序・状態で、どう失敗し、どんな害が生じるか | 境界値・並行操作・中断・再開・部分失敗など、対象に関係する条件から具体的な経路を作る。成立条件→操作や状態遷移→望ましくない結果を示し、その結果が問題になる根拠も添える |

### 仕様適合と前提実在の境界

仕様適合は**達成すべきこととの比較**、前提実在は**対策理由として使った事実・必要性の検査**である。仕様そのものもレビュー対象なら、仕様に書いてあることだけで目的への適合や対策の必要性を証明したことにはならない。

- 各種開発向けの要求を、説明なく検証準備だけへ限定した: 仕様適合で要求と対象範囲を照合する。
- 「未公開情報を守る」仕組みだが、その情報は既に公開されている: 前提実在で保護理由を問い直す。
- 段階的な導入として、初回対象を限定する承認と全体目的へのつながりがある: 限定だけを欠陥としない。全目的を今回同時に実装することを求めない。

前提実在では、新設・変更する各仕組みが守るもの・得るものを1行で示し、方針の正本と実体を読む。根拠が得られた場合の判定は次の5つを維持する。

| 判定 | 意味 |
|---|---|
| 必要 | 対処すべき問題・保護対象が実在し、その仕組みが必要な理由を確認できる。特定の実装案が最善であることまでは意味しない |
| 不要 | 想定した問題・保護対象・到達経路が成立せず、提示された対策理由を支持しない |
| 重複 | 同じ条件・対象を既存の仕組みが覆っている。別の役割・不足がないかも確認する |
| 欠落 | 必要な対処・保護が実在するのに、対象成果物にも既存の仕組みにも満たす経路がない |
| 前提誤り | 仕組みは必要だが、必要性の説明に使った事実が誤っている |

証拠不足は上記5判定へ無理に入れず「未確認」とし、足りない資料・条件を示す。「不在」の判断には、読んだ対象・探索範囲・到達経路または到達しない根拠を添える。観測したことがないだけで不要としない。統計設計の妥当性など事実の実在だけで決まらない問いを、この5判定だけで結論づけない。

仮定を置いて検討する依頼では、その条件内の結論と実環境で条件が成立するかの確認を分ける。明示された仮定まで資料不足と扱って結論を保留しない。実環境の安全性を仮定だけで認定するものではない。

### 実装整合性と前提実在の境界

「参照している関数が実際のAPIにない」は主に実装整合性、「秘密だと仮定した情報が公開済み」は主に前提実在。同じ不一致が接続と設計理由の両方を崩す場合は、両方の関係を示してよい。

将来作成することが計画に明記された部品は、現在ないだけで不整合・前提誤りにしない。既存部品として誤って扱っていないか、作成・接続・検証の担当と順序が揃うかを確認する。

### 重なりと費用の扱い

4観点は排他的な分類ではない。敵対的は失敗を見つける方法でもあり、他の観点と組み合わせる。同じ欠陥は1件にまとめ、必要なら関係する観点を併記する。分類の迷いだけで指摘を落とさない。

明示された費用・時間・運用制約に違反するなら仕様適合で指摘する。存在しない問題への対策や既存対策の重複は前提実在で扱う。必要な機構の代替案・導入・運用・保守・副作用を比べる最終採否は、`review-procedure.md`手順5「集約」で行う。費用が高そうという印象だけで、必要な保護や要求を不要と判定しない。

## 報告の契約

既存のレビュー報告に、確認した対象・版・観点・範囲と、未確認の範囲を示す。各指摘には、**対象箇所／問題／根拠／目的・動作への影響**を含める。事実、仮定、改善提案を区別し、対策案は欠陥の成立と分ける。既存の重大度・採否形式があれば従い、新たな台帳は作らない。

「問題なし」は確認範囲内の結果であり、未確認部分の安全・整合を意味しない。目的・方針との整合を見た根拠箇所を示す。記述の照合だけで確認できる指摘は原文の対比を、動作が根拠の指摘は許可された条件での実測・再現経路を示す。原文の対比は文書上の不一致を示す実証になるが、動作の実行成功を示す証拠ではない。再現経路が未実行ならその旨と実行を妨げた制約があればそれを記載し、必須の実行検証の代わりにしない。

例: 「仕様適合。対象の適用条件は検証準備だけだが、要求原文は設計・実装を含む。限定理由が資料に無いため、必要な対象を取りこぼす可能性がある。限定の意図は未確認」。これは直ちに対象拡大を実行する許可ではない。
