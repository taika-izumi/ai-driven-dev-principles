# 確定前レビューの実施手順

`pre-finalization-review` の実施操作（4 観点の独立レビューを実証つきで実行する手順）の正本。同スキルの SKILL.md から、ユーザーがレビューの実施を指示したときに読まれる。発動主体の規範と観点・方式・人数の判断は SKILL.md 側が正本である。

## 手順

実施・採否・確定の権限は `start-work` の `references/decision-delegation.md` を適用する。以下のユーザー回答による確定は、有効な委任に基づく判断結果でも行える。確認の根拠は既存の対応表・計画・課題へ残す。4観点の確認範囲には変更と委任範囲の一致を含め、別のレビュー工程を追加しない（ADR-0133）。

1. **対象と観点の確定**: 対象成果物（plan / spec / 設計文書）を特定し、4 観点を立てる:
   - **敵対的**: この計画・仕様が失敗するとしたらどこか。前提を崩す入力・順序・状態を探す
   - **実装整合性**: 既存コード・既存文書との矛盾はないか。参照先の実在、期待値と実測の整合
   - **仕様適合**: 上流の要求（spec / Issue / ADR）を漏れなく満たしているか。載っていない要求はないか
   - **前提実在**: 成果物が新設・変更する各機構（条件・分岐・ゲート・記録・接続の記述・データ経路・禁止事項）は本当に要るか。機構が守るもの・得るものを 1 件ずつ 1 行で特定し、それが方針の正本と実体（コード・設定・データ配置・起動順序）を読んだとき本当に存在するかを検査する。判定は 必要 / 不要 / 重複 / 欠落 / 前提誤り（機構は要るが根拠文が偽）の 5 値とし、「実在しない」と判定するときは到達経路・不在の根拠（何を読んで確認したか）を具体的に示す（実証要件は他観点と同じ）。統計設計の妥当性など「実在するか」では測れない検査は本観点の範囲外（必要なら他観点・別手段が担う）。特に疑う型は `examples-and-evidence.md`「適用例: 前提実在観点で特に疑う型」を参照
   観点は4つを維持する。初回・反復共通の人数判断と概算費用・1体兼務時の記録は SKILL.md「観点と初回フル実施の体数」が正本である。方式ごとの確認範囲と担当条件は `iteration-norms.md`「反復の実施」に従う。
2. **委譲プロンプトの組み立て**: SKILL.md「方式・人数の判断」で決めた人数に4観点を割り当て、独立サブエージェントへ委譲する。差分再確認1体・レビュアーを立てない機械検証は `iteration-norms.md`「反復の実施」に従う。委譲プロンプトは `subagent-dispatch` スキルで組む（条件発火の「検査・監査・走査」が発火し、全数走査・対象の総数明示・実証なし指摘の不採用が制約に入る）。**レビュアーのモデルは前工程（成果物を作った側）と変える**（根拠エントリ由来の運用ヒント。Issue-0034）。前提実在観点の委譲プロンプトには、方針の正本と実体の所在（ファイルパス）を明記して渡す（コンテキストを持たないレビュアーに、読むべき正本を知らせずに正本との照合を課さないため）
3. **実証を課す**: 成果物中のコード（テストコード・コマンド・スクリプト）は、レビュアーに**スクラッチで写経して実際に実行させる**。「読んだ限り妥当」は成果物として受け取らない（実測: 計画中のテストコード 10 件すべてが `CommandNotFoundException` で 1 件も動かないことを、写経実行だけが検出した。`LoopForAlpha-2026-07-28-11` / `LoopForAlpha#Issue-0054`）
4. **隔離**: レビュアーが写経実行等でファイルを書き換える場合の隔離・絶対パス・前後状態比較は、`subagent-dispatch` 条件発火の該当条件（破壊的検証・並列書き換え）の展開項目に従う
5. **集約**: 指摘を集約する。**実証の伴わない指摘は採用しない**。採否は指摘 1 件ずつ「前提（守るもの・得るもの）」と「実体での確認箇所」を書いてから決め、採否の判断とともに反復提示・報告へ添える——実証は事実を担保するが、その事実が問題になる前提は担保しない。実証つき指摘 26 件を前提検査なしに一括採用し、実在しない資産を守る機構を仕様へ足した実測がある（出所: LoopForAlpha#Issue-0125 / LoopForAlpha-2026-08-29-01）。採用する指摘ごとに、対象文書のどの箇所をどう直すかを決める。確定前レビューの反復（指摘反映後の再レビュー）の局面では、採否の確定は反復提示への回答による（本手順の採否決定は推奨案の作成として読む。`iteration-norms.md`「指摘反映後の反復」参照）
   仕組みの新設・増設を採用する案には、防ぐ失敗の発生実測または再現可能な到達経路、既存手順の文言修正・簡素化・リスク受容で足りるか、導入・運用・保守・副作用を比較して添える。今回限りか継続して維持するものかを示し、後者は将来の更新・実行・整合維持の負担も考慮する。満たすべき要求を確認し、その要求を満たす案の費用を比較する。実証された初回の失敗を過去に未発生というだけで排除せず、単に想像できるだけの失敗や架空の費用値を根拠にしない。比較は既存の指摘対応表・報告へ添え、採否は既存のユーザー判断に残す（ADR-0125）。

   今回の方式・人数の判断、上流確認、費用比較の導入後評価は、既存の計画・課題ログ・対応表・ADRから復元できる事例に限る。評価専用の必須保存行は設けない。復元できた範囲と記録不足を開示し、不明を「適用なし」「便益なし」へ換算せず、廃止判断に必要な情報が不足する場合は保留する（ADR-0124 / ADR-0125）。

6. **修正と報告**: すべての指摘反映の改訂に着手する前に、草稿の複製を退避する（`iteration-norms.md`「反復の実施」節の改訂前退避の規定に従う。無条件）。対象文書を修正し、指摘の採否と根拠をユーザーへ報告する。確定（コミット・次工程への引き渡し）はユーザー確認後に行う。改訂後の再レビュー（反復）の提示は `iteration-norms.md`「指摘反映後の反復」に従う。改訂対象が Accepted 済み ADR 本文である場合は decision-log の `references/status-updates.md`「ステータス変更」の改訂記録規定を適用する（ADR-0108）。
