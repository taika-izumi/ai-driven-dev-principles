# retrospective

開発サイクル末尾の振り返りを行い、ガイドライン・フローへの改善提案ドラフトと古びない技術ノウハウを構造化記録するスキル。

## いつ使うか

サブプロジェクトの feature ブランチを master へ `--no-ff` マージし、対応 handoff を completed 状態へ遷移させる**直前**。`start-work` Phase 2 マッピング表の「サブプロジェクトクローズ直後」行から推奨される。

実行は **手動トリガー**のみ。merge 検知などの自動起動は導入していない（ADR-0010 で代替案として却下）。

## 重要な前提

- ADR-0006（意思決定の継続検出ルール）は本スキル中も常時適用される。Phase 4 で行う「採用判断」は ADR起票対象である
- 出力ファイルは ADR-0011（時系列追記型）に従い、一度書いたら原則上書き禁止（typo 修正のみ例外）
- スキル内ではコミットしない。コミットはユーザーまたは通常フローに委ねる

## 手順

### Phase 0: 前提収集（メイン実行）

1. 対象サブプロジェクト名・feature ブランチ名・対応 plan/spec パスをユーザーから受け取る。直近 merge コミットから推定する場合は必ずユーザー確認を取る
2. 以下を読み込む:
   - 対応 plan ファイル（`docs/plans/...`）
   - 対応 spec ディレクトリ or ファイル（`docs/specs/...`）
   - 該当ブランチの merge コミット範囲の `git log --oneline`
   - `docs/handoff/master.md` 現行版
   - 該当期間に追加・変更された ADR
3. 既存 `docs/retrospectives/` を確認し、同一トピックの既存ファイルが無いことを確認する。あれば中止し、上書きの是非をユーザーに確認する（通常は別ファイル名にする）

### Phase 1: 5観点ヒアリング（メイン実行、1問ずつ）

ユーザーへ以下を順に1メッセージ1質問で確認する:

1. **Done**: 計画通り完了したこと（plan のタスク達成度・主要マイルストーン）
2. **Went Well**: うまくいったプラクティス（プロセス／ツール／設計判断／コミュニケーション）
3. **Struggled**: 苦労した点・手戻り・誤解（事象 / 原因 / 影響 をセットで聞く）
4. **Learned (Tech Notes)**: 古びない技術知見（ツール挙動、罠、回避策、推奨手順など）
5. **Improvement Drafts**: ガイドライン・フロー・スキルへの改善提案。各提案ごとに「採用 / 保留 / 却下」と理由を確定する

各回答はメインがその場でテンプレに埋める。ユーザーが言及していない観点があれば、Phase 0 で収集した plan / git log / spec 変更履歴を参照して具体ネタを問いかけて補完する（例:「Plan の Task 11 で revert があったようですが経緯は？」）。

### Phase 2: ドラフト保存（メイン実行）

`docs/retrospectives/YYYY-MM-DD-<topic>.md` に書き出す（テンプレ準拠、ファイル名は実施日 + サブプロジェクト識別子）。テンプレートは `skills/retrospective/template.md` を参照。

書き出し後、ユーザーへ提示し軽く確認する。

### Phase 3: 独立視点レビュー（サブエージェント `rubber-duck` 1回）

`task` ツールで `rubber-duck` を1回呼び出す。プロンプトに渡すもの:

- ドラフト全文
- 対応 plan の内容
- 対応 ADR 一覧
- レビュー観点として以下を明示:
  - 抽出漏れ（git log にあるが言及されていない事象はないか）
  - 改善提案の採用判断の妥当性（過剰採用 / 過小採用がないか）
  - Tech Notes 項目の「古びなさ」検証（特定バージョン・特定環境依存ではないか）

レビュー結果はメインが受け取り、ユーザーと相談の上で必要箇所をドラフトに反映する。やり取りはセクション「Independent Review Notes」に記録する。

### Phase 4: 採用判断の即時 ADR 化（メイン実行）

「Improvement Drafts」のうち**採用**と判定したものは、ADR-0006 に従い即時 ADR ドラフトを作成する。

- Status: **Proposed** のまま（実装は別セッションで `start-work` から再開）
- 起票内容: Context（採用根拠）/ Decision（何をどう変えるか）/ Alternatives Considered / Consequences
- ファイル名: `docs/decisions/NNNN-<slug>.md`（NNNN は次の連番）
- ADR README の表に行追加する

「保留」「却下」と判定したものは ADR を起票せず、ドラフト内に判断と理由を記録するのみ。

### Phase 5: ハンドオフ更新（メイン実行）

`session-handoff update` 操作を呼ぶ。

- 「次セッション開始時のアクション」に「Phase 4 で起票した ADR-NNNN を実装する（対応スキル/原則/ガイドライン更新）」を追記する
- handoff Status を `completed` → `ready-for-next-cycle` へ遷移
- 採用提案が複数ある場合は、次サブプロジェクトの起点候補として優先順位を明記する

## 出力ファイル

- 本体: `docs/retrospectives/YYYY-MM-DD-<topic>.md`
- インデックス更新: `docs/retrospectives/README.md` に行追加（過去行の編集は禁止、ADR-0011）
- テンプレ参照: `skills/retrospective/template.md`

## サブエージェント呼び出し詳細

Phase 3 の `rubber-duck` 呼び出し時は、以下を必ずプロンプトに含める:

- 「振り返りドラフトの独立視点レビューであり、再生成や書き換えではない」旨
- 「採用 / 保留 / 却下 の判定が適切か、抽出漏れがないか、Tech Notes が古びないか」を観点として明示
- 出力フォーマット指定（短い指摘のリスト形式、優先度タグ付き）

これによりレビューが拡散せず、メインが反映判断しやすい形で結果が返る。

## 対応する原則

- **原則1（追跡可能性）**: 振り返り出力ファイルにより各サイクルの判断・反省・採用提案が永続化
- **原則2（関心の分離）**: retrospective を独立スキルとして責務分離 / 振り返り = 抽出と判断、実装 = 次サイクル
- **原則3（コンテキスト管理）**: 振り返り出力が次サイクル開始時のコンテキスト源になる
- **原則4（人間の関与）**: 5観点ヒアリングが対話形式 / 採用判断はユーザー承認必須 / 自動トリガー禁止
- **原則5（漸進的検証）**: サイクル単位の振り返りでメタ・ガイドライン自体の検証ループを回す
