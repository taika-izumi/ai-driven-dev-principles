# プロジェクトの目的・方針の取得と受け渡し

主担当の開始・再開、目的の根拠を参照できなくなったとき、handoffの単独read、委譲時の目的入力に使う。同じ作業中の有効な取得結果は再利用し、毎応答の全文再読・目的の唱和・読了証明の専用ログは求めない。

## 正本を特定する

1. 対象プロジェクトのルートを明示された指示・作業対象から特定する。指定がなければ対象のGitリポジトリルート、非Gitなら明示されたプロジェクト作業ディレクトリを使う。コマンドの現在ディレクトリだけで推測しない。
2. 適用されるプロジェクト固有のAGENTS.mdに目的・方針の正本指定があれば優先する。相対パスの既定はプロジェクトルート基準。既存指定が別の基準を明示していればそれに従う。下位の局所作業指示だけで全体目的を置き換えず、別プロジェクトの目的指定は適用範囲を確認する。
3. 未指定なら `docs/overview/project-purpose.md` を標準入口として読む。参照だけの入口なら指定先の必要な節まで読む。明示先が不存在・読取不能なら報告し、別資料を黙って正本へ昇格しない。
4. 未定義ならREADME・overview・ロードマップなどの案内と、そこから参照された既存合意を調べる。現在の目的と判断に必要な根拠が確認できた時点で終え、全ADR・全履歴の一律読破はしない。判断に影響する不明・矛盾だけを確認する。

既存の適切な文書・節は再利用し、標準入口と両方へ本文を複写しない。目的本文は利用者・実現したい成果、良い成果の条件、判断の優先順位、重要な制約・方針を必要範囲で示す。数式や全欄記入を要求せず、進捗・作業順序・決定理由はそれぞれの既存文書へ置く。製品の目的と、開発方法の品質・費用の共通基準を区別して併用する。

## 参照結果を判断・引き継ぎに使う

既存の入力・関連資料欄へ、次を含める。別の帳票や台帳は作らない。

- **所在と適用範囲**: プロジェクトルート、正本のパスと必要な節。
- **参照内容の根拠**: 既存コミットとパス・節、または内容を保持した記録・必要な原文。未コミットならその旨を添え、コミット済み版と異なる作業ツリーの本文を同じ版としない。全ファイルのハッシュ採取は要求しない。
- **確定状況・未反映**: 確定した目的、草案、不明を区別する。正本未整備でも既存合意が確定している場合は、その根拠を使える。目的変更が未反映なら新しい確定内容・合意根拠・反映先を示す。

開始・再開では現在の正本、handoffの前回参照内容と未反映事項、今回の明示指示・承認範囲を照合する。古いhandoffの要約を正本として固定せず、今回の依頼が全体目的のどの部分へ寄与するかを見る。全体目的の全項目を一つのタスクへ要求しない。不明が影響する判断だけを相談し、影響のない読取りや承認済みの独立作業は続ける。

## 初期整備・変更・保存できない場合

正本・案内の作成や更新は、今回の作業範囲と実効権限が許す場合だけ行う。read-onlyのレビュー等では確認済みの既存根拠を使い、未整備状態・候補の所在を報告する。永続化のためだけに全体を止めたり、権限外の書込みを試みたりしない。新しい目的・優先順位・重要な解釈が必要なら根拠つき草案を示して判断を求め、草案を確定目的として流さない。

目的の明示変更・既知の正本差分がある場合、または根拠を参照できなくなった場合は再取得する。変更が確定したら権限内で正本と既存の決定記録を整合させ、実体を読み直してから依存判断・handoff・子へ渡す。保存が途中で止まる場合は未反映の新しい目的と合意根拠を既存handoff等へ残し、更新完了と報告しない。書込み自体ができなければ同じ内容を報告して永続化できる担当へ渡すが、保存完了の代わりにはしない。

未反映と分かっている旧正本を「最新」と扱わない。別主体による未知の変更の常時検知は保証しない。目的変更は作業範囲・操作許可を拡張しない。目的変更の記録はdecision-log、承認基準と許可は `decision-delegation.md` に従う。
